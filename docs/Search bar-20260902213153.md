## 1\. What a Search Bar Actually Is
A search bar is an input that takes a free-text query and returns matching results from a corpus. That's the whole job. But the word "search bar" gets slapped on four genuinely different components, and mixing them up is the #1 tell of an amateur build:
*   **Search bar (plain):** a text input plus a submit affordance. You type, you press Enter (or click the magnifying glass), you land on a results page. No dropdown. Google's homepage box _before_ suggestions existed. This is a `<form role="search">` with `<input type="search">`.
*   **Search bar as combobox:** the same input, but as you type it shows a **suggestions dropdown** (autocomplete, typeahead, recent searches). The moment a popup of options attaches to the input, it stops being "just an input" and becomes an **ARIA combobox** with a whole extra contract: `role="combobox"`, `aria-expanded`, `aria-controls`, `aria-activedescendant`, a `role="listbox"` popup, and arrow-key navigation.
*   **Combobox (select-style):** a form control where the user must ultimately pick _one value from a known list_ (country picker, assignee field). It looks like a search bar with a dropdown, but its purpose is **selection**, not querying a corpus. The value ends up in a form field.
*   **Command palette (Cmd-K):** a search bar that searches _actions and navigation_, not content. VS Code's `Ctrl+Shift+P`, Linear's and Notion's `Cmd-K`. Same combobox machinery, but the "results" are commands you execute, and it lives in a modal dialog summoned by a keyboard shortcut.

The distinction that trips people: **`role="search"`** **is a landmark;** **`role="combobox"`** **is a widget.** A plain search bar is a search landmark. Add live suggestions and the _input itself_ additionally becomes a combobox. They coexist — the search landmark wraps the combobox. Getting this wrong means either a screen reader user can't jump to search, or the suggestions list is announced as decorative noise.

One more that people fake: a `<div>` with a magnifying-glass icon and a click handler that "acts like search." It's not focusable, not typeable, not announced. If it takes a query, it's an `<input>`. Never fake it.

## 2\. Why It Matters
Search is where intent is highest and patience is lowest. A user who searches is _telling you exactly what they want_, and they'll punish you fast if you fumble it.
*   **Search is the highest-intent surface you own.** On e-commerce, users who search convert at 2–3x the rate of users who only browse. The search bar isn't a utility, it's a revenue funnel. A slow, dumb, or empty-handed search bar leaks money on your best-qualified traffic.
*   **It's a discovery and retention engine.** Good suggestions, recent searches, and scoped search turn a single query into a session. Bad search ("0 results" with no recovery) is a dead end that sends users to a competitor's tab.
*   **It's an accessibility and trust signal.** The search landmark is one of the first things a screen-reader user navigates to. A search bar with no visible label, an unlabeled clear button, or a suggestions list that doesn't announce itself reads as broken to assistive tech, and as sloppy to everyone.
*   **It's a performance stress test.** Search-as-you-type fires a request on nearly every keystroke. Do it naively and you DDoS your own backend, race responses so stale results overwrite fresh ones, and burn the user's battery. The search bar is where junior front-end code visibly falls apart.
* * *

## 3\. Anatomy of a Search Bar
Every well-built search bar is composed of predictable parts:
*   **The landmark wrapper:** a `<form role="search">` (or `<search>` element) so assistive tech can jump straight to it.
*   **The input:** `<input type="search">`. Type `search` gets you a UA-drawn clear button in some browsers, `enterkeyhint="search"` on mobile, and the correct role.
*   **Leading icon:** the magnifying glass. Decorative (`aria-hidden`) if there's a real label; it's a visual cue, not the accessible name.
*   **The label:** visible or visually-hidden, but _always present_. Placeholder text is not a label.
*   **The clear button (the little ✕):** appears when the field is non-empty, wipes the query, returns focus to the input. Needs an accessible name ("Clear search").
*   **Submit affordance:** an actual `type="submit"` button (often the magnifying glass), so Enter and click both work and the form degrades without JS.
*   **The suggestions popup (when it's a combobox):** a `role="listbox"` of `role="option"` rows — autocomplete matches, recent searches, scoped shortcuts.
*   **Scope selector (optional):** "All / Products / Docs / People" — a segmented control or dropdown that narrows the corpus.
*   **Status region:** an `aria-live` node that announces "12 results" / "Searching…" / "No results" to screen readers.
*   **The keyboard trigger:** the `/` or `Cmd-K` shortcut that focuses (or opens) the bar from anywhere.

## 4\. Sizes & Density
Search bars scale with prominence. A hero search on a homepage is not a table filter. Real values:

| Context | Height | Padding (H) | Font | Notes |
| ---| ---| ---| ---| --- |
| Inline / table filter | 32px | 8px | 13px | Dense admin UI, lives in a toolbar |
| Default app search | 40px | 12px | 14px | Header search, most common |
| Prominent / page search | 48px | 16px | 16px | Docs search, sidebar search |
| Hero search | 56–64px | 20–24px | 18px | Landing page, marketplace homepage |
| Command palette | 52px | 16px | 16px | Inside a centered modal, full-width of it |

Rules that matter:
*   **≥44px tap target regardless of visual height.** A 32px inline search still needs a 44px hit area (expand with padding), or thumbs miss it.
*   **The icon is inside the padding, not eating the text.** Reserve `padding-inline-start` room for the leading icon so the caret never sits under the magnifying glass.
*   **Width communicates ambition.** A hero search is wide (500–700px) because it invites a real query. A filter is narrow because it expects one word.
*   **Font-size ≥16px on mobile inputs** or iOS Safari zooms the viewport on focus. This is the single most common "why did my page jump" mobile bug.

## 5\. States (the part juniors forget)
A production search bar has far more states than a button, because it spans an async lifecycle _and_ a popup. Missing states is what makes search feel broken.
1. **Empty / rest** — placeholder visible, no clear button, maybe recent searches ready to show on focus.
2. **Focus** — visible ring; on a combobox this may open the popup with recent searches before a single key is pressed.
3. **Typing** — query present, clear button now visible, debounce timer running.
4. **Loading / in-flight** — a request is out. Show a subtle spinner _in the field_ (not a full-page block), keep the input responsive, set `aria-busy`.
5. **Suggestions open** — popup visible, `aria-expanded="true"`, options navigable by arrow keys.
6. **Option active (highlighted)** — one option is virtually focused via `aria-activedescendant`; DOM focus stays in the input.
7. **Results returned** — live region announces the count.
8. **Empty results / no matches** — "No results for 'x'" with a recovery path (spelling, broader scope, popular items). This is a designed state, not an accident.
9. **Error** — request failed. "Search is unavailable, try again" — never a silent dead input.
10. **Disabled** — rare, but e.g. search disabled until an index finishes building.
11. **Cleared** — the ✕ was pressed; input empty, focus returned, popup closed.

Bonus states specific to search: **stale/racing** (a slow response arrives after a newer one — you must _drop_ it), **min-length not met** ("keep typing…" when the query is under, say, 2 chars), and **scoped** (a chip shows the active scope: "in Products").
* * *

## 6\. Types & Variants
By behavior, not just looks:
*   **Submit-on-enter (plain):** no dropdown, query runs on Enter/click, navigates to a results page. Cheapest, most robust, best for full-corpus search where a results page does the heavy lifting (e-commerce, Google).
*   **Instant / live search (search-as-you-type):** results update in place as you type, no submit. Great for filtering a known, bounded set (a table, a settings list, a file tree). Expensive against a big backend — needs debounce + cancellation.
*   **Autocomplete / typeahead combobox:** suggestions dropdown predicts the _query_ (Google's suggestions) or jumps straight to a _result_ (a product, a doc). The workhorse of modern search.
*   **Scoped search:** a scope selector ("All / Docs / People") narrows the corpus before or during the query. Chips or a leading dropdown.
*   **Federated search:** one bar, results grouped by source ("Files", "People", "Messages"). Slack, Notion. Combobox with grouped `role="group"` options.
*   **Command palette (Cmd-K):** searches actions + navigation, opens in a modal, keyboard-first. Its own beast (see §9 and §11).
*   **Faceted search:** the bar plus filter facets (price, category, rating) that refine a results page. The bar is one input in a larger search UI.

Pick by corpus size and result destination. **Bounded + on-screen data → instant filter. Large backend + dedicated results page → submit-on-enter with an autocomplete assist. Actions/navigation → command palette.**

## 7\. When to Use One (and When Not To)
Use a search bar when the corpus is **too large to browse** or the user **already knows what they want**. Don't reach for it when:
*   The set is small (< ~15 items). A visible list, filter chips, or a `<select>` beats making someone type.
*   The user doesn't know your vocabulary. Search assumes they can name the thing. Pair it with browse/categories for discovery.
*   You're really building a form field with a fixed list of valid values — that's a **combobox/select**, not a search bar. The tell: the output must be one of N known options and lands in a form.
*   Navigation between a handful of known views — that's tabs or a nav, not search.

Placement heuristics:
*   **Top-center or top-right** for global search; users expect it there. A magnifying glass alone (icon that expands) is fine on mobile, but expose the full field on desktop where space allows.
*   **Persistent, not buried.** If search is core to the product (docs, e-commerce, admin), keep the bar visible, don't hide it behind a click.
*   **Command palette is summoned, not placed** — it lives behind `Cmd-K` and appears centered. Advertise the shortcut (a subtle "⌘K" hint in a secondary search field).
*   **Scope near the input**, so users see and change what they're searching before they commit a query.

## 8\. Search Bars Across Design Systems
Same component, different contracts. Knowing these makes you fluent anywhere.
*   **Material Design (Google):** distinguishes the **search bar** (the resting field) from the **search view** (the full-screen expanded state with suggestions), a formal two-state pattern. Rounded, elevation on the view, leading search icon + trailing avatar/clear.
*   **Apple HIG (iOS/macOS):** `UISearchBar` / `.searchable()` in SwiftUI. Search sits in navigation, often revealed by pulling down. Scope bar for scoped search is a first-class, documented control. Cancel button appears on focus.
*   **Fluent (Microsoft):** `SearchBox`. Explicit clear button, subtle depth, tight integration with command bars. Suggestions via the combobox pattern.
*   **Ant Design / enterprise:** `Input.Search` with an attached submit button, plus `AutoComplete` for the combobox flavor. Built for dense admin search with scope dropdowns baked in.
*   **Tailwind / utility-first:** no prescribed search component — you compose it. Freedom plus the risk of shipping an inaccessible div. Usually wrapped into a project `SearchBar` component.
*   **shadcn/Radix (2024+ web standard):** the **`Command`** component (built on `cmdk`) is the de-facto command-palette/combobox for search. Accessibility and keyboard nav baked in; you style it.
*   **Bootstrap:** no dedicated search widget. `<form role="search">` + `.form-control` + an input group with a submit button. Honest gap: the autocomplete dropdown is on you (or a plugin).

## 8b. Visual Styles (the same search bar, eleven skins)
Design systems are _whose_ rules; visual styles are _which look_. The same semantic search bar wears any of these. See them all in the [Design Styles gallery](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200551).
*   **Flat:** solid fill, crisp edge, one-pixel border, no shadow. Reads instantly.
*   **Material:** filled field, elevation shadow when the suggestions view opens, ripple-free but motion-aware.
*   **Glassmorphism:** translucent field with `backdrop-filter: blur()` over a vivid hero image. Watch contrast on the placeholder and the caret.
*   **Liquid Glass (the 2026 trend):** Apple's iOS 26 / macOS Tahoe material — the pill-shaped search field _refracts_ what's behind it with a specular rim and a moving sheen, not a static blur. The suggestions popup floats as its own glass layer. See the 2026 note.
*   **Neumorphism:** the field pressed _into_ the surface (inset dual shadows) — actually the one place neumorphism reads well, since an input _should_ look recessed. Still contrast-poor for text; use for accent only.
*   **Skeuomorphism:** the inset "search well" with an inner shadow and a bevel, like an old OS X search box. Tactile, nostalgic.
*   **Neo-Brutalism:** thick black border, hard offset shadow, zero radius, a magnifying glass that means it. High personality, great for a bold brand.
*   **Claymorphism:** big radius, soft inner top-light, puffy pill. Friendly, consumer.
*   **Aurora / Gradient:** animated gradient ring around the field on a dark hero. Premium; honor `prefers-reduced-motion` on the animation.
*   **Minimal / Swiss:** a single underline and a glyph. Typography does the work. Elegant, but make sure the hit target survives.
*   **UJG Brand:** Goldenrod magnifying glass and focus ring on a deep Eminence/Night field, confident radius, warm glow on focus. The suggestions popup is a Night surface with Goldenrod active-row highlight.

**Rule that never changes:** the style is skin. The `role="search"` landmark, the combobox semantics, `aria-activedescendant`, the clear button's name, the 44px target, and the focus ring stay identical across all eleven.

### What's trending in 2026
The dominant force is **Liquid Glass**: Apple shipped it across iOS 26 and macOS Tahoe in late 2025, and search fields — always pill-shaped in Apple's world — are its showcase surface. The web approximates with layered `backdrop-filter`, highlight rims, and the emerging refraction proposals.

Around it:
*   **AI-native search:** the bar is becoming a _prompt_. Natural-language queries ("show me last quarter's overdue invoices"), inline AI answers above the blue links, and streaming/generative result states replacing the old spinner. The command palette is merging with the chat box.
*   **Cmd-K everywhere:** the command palette graduated from developer tools to mainstream SaaS. Users now _expect_ `Cmd-K` to search anything.
*   **Semantic / vector search:** typo-tolerant, meaning-based matching (embeddings) so "cheap flights" finds "affordable airfare." Changes ranking basics (see §9).
*   **Scoped, agentic search:** "search then act" — results you can operate on inline (archive, assign, open) without leaving the palette.
*   **Motion-forward but restrained:** the field morphing into the results view, respected `prefers-reduced-motion` by default.

**For UJG:** a Liquid-Glass search pill over deep Eminence makes the refraction sing; keep Flat/Swiss for dense data-table filters; reserve the animated Aurora ring for the marketing homepage hero. Contrast and reduced-motion are non-negotiable no matter how on-trend the skin.

## 9\. The Code
### 9.1 HTML (the foundation everyone should master first)
The plain search bar is a form. Get this right and everything else is enhancement.

```plain
<!-- Plain, submit-on-enter search. Works with zero JavaScript. -->
<form role="search" action="/search" method="get">
  <label for="site-search" class="visually-hidden">Search the site</label>
  <span class="search__icon" aria-hidden="true">🔎</span>
  <input
    type="search"
    id="site-search"
    name="q"
    placeholder="Search…"
    autocomplete="off"
    enterkeyhint="search"
    spellcheck="false"
  />
  <button type="submit" class="search__submit">Search</button>
</form>
```

Key HTML rules:
*   **`type="search"`** gets you the right role, an `enterkeyhint="search"` keyboard on mobile, and (in some browsers) a native clear ✕. It is _not_ cosmetic.
*   **`role="search"`** on the form makes it a landmark — screen-reader users jump to it with a single shortcut. The newer HTML **`<search>`** element gives the landmark natively; wrap the form in `<search>` where you can.
*   **`name="q"`** + `method="get"` means the query lands in the URL (`/search?q=…`), which is shareable, bookmarkable, and back-button-friendly. This is a feature, not an accident.
*   **A real label is mandatory.** `visually-hidden` is fine, placeholder-as-label is not (it vanishes on type and fails contrast).
*   **`autocomplete="off"`** on a search field stops the browser's form-autofill from fighting your suggestions dropdown.

When suggestions attach, the input upgrades to the combobox contract:

```plain
<div class="combobox">
  <input
    type="search"
    role="combobox"
    aria-expanded="false"
    aria-controls="search-listbox"
    aria-autocomplete="list"
    aria-activedescendant=""
  />
  <ul id="search-listbox" role="listbox" hidden>
    <li id="opt-0" role="option" aria-selected="false">react hooks</li>
    <li id="opt-1" role="option" aria-selected="false">react router</li>
  </ul>
</div>
```

### 9.3 Vanilla JavaScript (debounce, cancel, and the race you must not lose)
This is the heart of the component. The single biggest search bug is a **race condition**: you fire a request per keystroke, a slow one for "re" resolves _after_ the fast one for "react", and the user sees results for "re". You fix it with **debounce + AbortController**.

```javascript
const input = document.querySelector("#site-search");
const listbox = document.querySelector("#search-listbox");
const field = input.closest(".search");

let controller = null;   // aborts the previous in-flight request
let timer = null;        // debounce timer

function debounce(fn, ms = 250) {
  return (...args) => { clearTimeout(timer); timer = setTimeout(() => fn(...args), ms); };
}

const runSearch = debounce(async (query) => {
  // Don't search on trivial input
  if (query.trim().length < 2) { closeList(); return; }

  // Cancel the previous request so its (stale) result can never win the race
  controller?.abort();
  controller = new AbortController();

  field.dataset.loading = "true";
  try {
    const res = await fetch(`/api/search?q=${encodeURIComponent(query)}`, {
      signal: controller.signal,
      headers: { "Accept": "application/json" },
    });
    if (!res.ok) throw new Error(res.statusText);
    const { results } = await res.json();
    renderOptions(results);           // only the latest request reaches here
  } catch (err) {
    if (err.name === "AbortError") return;   // superseded — ignore, not an error
    renderError();
  } finally {
    field.dataset.loading = "false";
  }
}, 250);

input.addEventListener("input", (e) => {
  const val = e.target.value;
  field.dataset.filled = String(val.length > 0);
  runSearch(val);
});
```

Why each piece is load-bearing:
*   **Debounce (250ms)** waits for a pause in typing so you send ~1 request per word, not per letter. Too short and you spam the server; too long and it feels laggy. 150–300ms is the sweet spot for remote search.
*   **`AbortController`** cancels the prior fetch. This is the _correct_ fix for stale results — cheaper and more reliable than tagging responses with sequence numbers and discarding late ones.
*   **`AbortError`** **is not an error.** When you cancel, the promise rejects with `AbortError`; swallow it silently or you'll flash a fake error on every fast typist.
*   **`encodeURIComponent`** on the query — non-negotiable, both for correctness (spaces, `&`, `#`) and as the first layer of injection hygiene (see §15).

**Debounce vs throttle** — know the difference cold. **Debounce** fires _after_ activity stops (perfect for search-as-you-type: you only care about the final query). **Throttle** fires at most once per interval _during_ activity (right for things like a scroll-driven "load more" or a live result counter you want to update continuously). For a search input, debounce is almost always the answer; throttle is for the streaming/continuous cousins.

### 9.4 The clear button (the little ✕), done accessibly
The ✕ looks trivial and is quietly a source of three separate a11y bugs: no name, wrong element, and stolen focus.

```plain
<button type="button" class="search__clear" aria-label="Clear search">
  <svg aria-hidden="true" viewBox="0 0 20 20"><path d="M5 5l10 10M15 5L5 15"/></svg>
</button>
```

```javascript
clearBtn.addEventListener("click", () => {
  input.value = "";
  field.dataset.filled = "false";
  closeList();
  input.focus();          // return focus to the input, don't strand the user
  input.dispatchEvent(new Event("input", { bubbles: true })); // re-run empty state
});

// Escape clears (or closes the popup first, then clears) — expected search behavior
input.addEventListener("keydown", (e) => {
  if (e.key === "Escape") {
    if (!listbox.hidden) { closeList(); }
    else if (input.value) { clearBtn.click(); }
  }
});
```

The rules the ✕ must obey:
*   **A real** **`<button type="button">`**, never a clickable `<span>`. It's keyboard-focusable and Enter/Space-activatable for free.
*   **`aria-label="Clear search"`** — icon-only, so it needs a name. Without it a screen reader announces "button," useless.
*   **`type="button"`** so it never accidentally submits the form.
*   **Return focus to the input** after clearing. Nothing worse than clearing search and having focus vanish to `<body>`.
*   **Only show it when there's text.** An always-visible ✕ on an empty field is a confusing dead control.
*   **Escape is the keyboard equivalent** — first press closes suggestions, second clears. Match the platform expectation.

### 9.5 React + TypeScript (a proper reusable combobox)
The longest block, because a real autocomplete search bar owns debounce, cancellation, keyboard nav, and the full ARIA combobox contract.

```typescript
import { useId, useRef, useState, useEffect, useCallback } from "react";

interface Result { id: string; label: string; }

interface SearchBarProps {
  onSearch: (q: string, signal: AbortSignal) => Promise<Result[]>;
  onSelect?: (r: Result) => void;
  placeholder?: string;
  label?: string;
  debounceMs?: number;
  minChars?: number;
}

export function SearchBar({
  onSearch,
  onSelect,
  placeholder = "Search…",
  label = "Search",
  debounceMs = 250,
  minChars = 2,
}: SearchBarProps) {
  const listId = useId();
  const [query, setQuery] = useState("");
  const [results, setResults] = useState<Result[]>([]);
  const [open, setOpen] = useState(false);
  const [active, setActive] = useState(-1);   // index of highlighted option
  const [loading, setLoading] = useState(false);
  const controllerRef = useRef<AbortController | null>(null);
  const timerRef = useRef<ReturnType<typeof setTimeout>>();

  const search = useCallback((q: string) => {
    clearTimeout(timerRef.current);
    if (q.trim().length < minChars) { setResults([]); setOpen(false); return; }
    timerRef.current = setTimeout(async () => {
      controllerRef.current?.abort();                 // cancel prior request
      const controller = new AbortController();
      controllerRef.current = controller;
      setLoading(true);
      try {
        const r = await onSearch(q, controller.signal);
        setResults(r);
        setOpen(true);
        setActive(-1);
      } catch (e) {
        if ((e as Error).name !== "AbortError") setResults([]);
      } finally {
        setLoading(false);
      }
    }, debounceMs);
  }, [onSearch, debounceMs, minChars]);

  useEffect(() => () => { clearTimeout(timerRef.current); controllerRef.current?.abort(); }, []); // clear pending debounce timer + cancel fetch on unmount

  function onKeyDown(e: React.KeyboardEvent) {
    if (!open && (e.key === "ArrowDown")) { setOpen(true); return; }
    switch (e.key) {
      case "ArrowDown": e.preventDefault(); setActive(i => Math.min(i + 1, results.length - 1)); break;
      case "ArrowUp":   e.preventDefault(); setActive(i => Math.max(i - 1, 0)); break;
      case "Enter":
        if (active >= 0 && results[active]) { e.preventDefault(); choose(results[active]); }
        break;
      case "Escape":    setOpen(false); setActive(-1); break;
    }
  }

  function choose(r: Result) {
    setQuery(r.label); setOpen(false); setActive(-1); onSelect?.(r);
  }

  return (
    <div className="search" role="search" data-loading={loading}>
      <label htmlFor="search-input" className="visually-hidden">{label}</label>
      <span className="search__icon" aria-hidden="true">🔎</span>
      <input
        id="search-input"
        type="search"
        role="combobox"
        aria-expanded={open}
        aria-controls={listId}
        aria-autocomplete="list"
        aria-activedescendant={active >= 0 ? `${listId}-opt-${active}` : undefined}
        autoComplete="off"
        placeholder={placeholder}
        value={query}
        onChange={(e) => { setQuery(e.target.value); search(e.target.value); }}
        onKeyDown={onKeyDown}
      />
      {query && (
        <button type="button" aria-label="Clear search"
          onClick={() => { setQuery(""); setResults([]); setOpen(false); }}>
          ✕
        </button>
      )}
      <ul id={listId} role="listbox" hidden={!open} className="search__listbox">
        {results.map((r, i) => (
          <li
            key={r.id}
            id={`${listId}-opt-${i}`}
            role="option"
            aria-selected={i === active}
            className="search__option"
            onMouseDown={(e) => { e.preventDefault(); choose(r); }}  // preempt blur
          >
            {r.label}
          </li>
        ))}
      </ul>
    </div>
  );
}
```

Why this is the senior version, not the junior one:
*   **DOM focus never leaves the input.** Arrow keys move a _virtual_ cursor via `aria-activedescendant`; the option rows are never tab stops. This is the ARIA combobox contract and the thing juniors get wrong (they put `tabindex` on every option and break the model).
*   **`onMouseDown`** **+** **`preventDefault`** **on options**, not `onClick`. A plain click first fires `blur` on the input, which can close the list before the click lands. Preempting `mousedown` selects reliably.
*   **AbortController per request, cancelled on unmount.** No state updates on an unmounted component, no stale results.
*   **`minChars`** **guard** avoids hammering the backend on one-letter queries that match everything.
*   **The** **`onSearch`** **prop takes the** **`signal`** so the _parent_ owns the fetch and passes cancellation through — the component doesn't hardcode an endpoint.

### 9.6 Vue 3 (Composition API combobox)
Same contract as React — debounce, cancellation, the ARIA combobox — expressed with `<script setup>` and reactive refs.

```plain
<!-- SearchBar.vue — Vue 3 <script setup>: debounce + AbortController + combobox -->
<script setup lang="ts">
import { ref, onBeforeUnmount } from "vue";

interface Result { id: string; label: string }
const props = withDefaults(defineProps<{ minChars?: number; debounceMs?: number }>(), {
  minChars: 2, debounceMs: 250,
});
const emit = defineEmits<{ (e: "select", r: Result): void }>();

const query = ref("");
const results = ref<Result[]>([]);
const open = ref(false);
const active = ref(-1);
let controller: AbortController | null = null;
let timer: ReturnType<typeof setTimeout> | undefined;

function onInput() {
  clearTimeout(timer);
  if (query.value.trim().length < props.minChars) { results.value = []; open.value = false; return; }
  timer = setTimeout(async () => {
    controller?.abort();                       // drop the stale in-flight request
    controller = new AbortController();
    try {
      const res = await fetch(`/api/search?q=${encodeURIComponent(query.value)}`,
        { signal: controller.signal });
      results.value = (await res.json()).results;
      open.value = true; active.value = -1;
    } catch (e) {
      if ((e as Error).name !== "AbortError") results.value = [];
    }
  }, props.debounceMs);
}

function onKeydown(e: KeyboardEvent) {
  if (e.key === "ArrowDown") { e.preventDefault(); active.value = Math.min(active.value + 1, results.value.length - 1); }
  else if (e.key === "ArrowUp") { e.preventDefault(); active.value = Math.max(active.value - 1, 0); }
  else if (e.key === "Enter" && results.value[active.value]) { emit("select", results.value[active.value]); open.value = false; }
  else if (e.key === "Escape") { open.value = false; active.value = -1; }
}

onBeforeUnmount(() => { clearTimeout(timer); controller?.abort(); }); // no pending timer or fetch resolving into a dead component
</script>

<template>
  <div class="search" role="search">
    <label for="q" class="visually-hidden">Search</label>
    <input id="q" type="search" role="combobox" autocomplete="off"
           :aria-expanded="open" aria-controls="search-listbox" aria-autocomplete="list"
           :aria-activedescendant="active >= 0 ? `opt-${active}` : undefined"
           v-model="query" @input="onInput" @keydown="onKeydown" />
    <ul id="search-listbox" role="listbox" v-show="open" class="search__listbox">
      <li v-for="(r, i) in results" :key="r.id" :id="`opt-${i}`" role="option"
          :aria-selected="i === active" class="search__option"
          @mousedown.prevent="emit('select', r)">{{ r.label }}</li>
    </ul>
  </div>
</template>
```

`@mousedown.prevent` is the Vue spelling of the same "preempt blur before it closes the list" trick from the React version.

### 9.8 Angular (RxJS `switchMap` for cancellation)
Angular does the debounce-and-cancel dance declaratively: `debounceTime` waits for the pause, `switchMap` cancels the previous HTTP request the instant a newer query arrives — the RxJS-native answer to the race condition.

```typescript
// search-bar.component.ts — standalone component, RxJS debounce + switchMap
import { Component, EventEmitter, Output } from "@angular/core";
import { CommonModule } from "@angular/common";
import { HttpClient } from "@angular/common/http";
import { Subject, of } from "rxjs";
import { debounceTime, distinctUntilChanged, filter, switchMap, catchError } from "rxjs/operators";

interface Result { id: string; label: string; }

@Component({
  selector: "app-search-bar",
  standalone: true,
  imports: [CommonModule],
  template: `
    <div class="search" role="search">
      <label for="q" class="visually-hidden">Search</label>
      <input id="q" type="search" role="combobox" autocomplete="off"
             [attr.aria-expanded]="open"
             aria-controls="search-listbox" aria-autocomplete="list"
             (input)="query$.next($any($event.target).value)" />
      <ul id="search-listbox" role="listbox" *ngIf="open" class="search__listbox">
        <li *ngFor="let r of results" role="option" class="search__option"
            (mousedown)="$event.preventDefault(); select.emit(r)">{{ r.label }}</li>
      </ul>
    </div>
  `,
})
export class SearchBarComponent {
  @Output() select = new EventEmitter<Result>();
  query$ = new Subject<string>();
  results: Result[] = [];
  open = false;

  constructor(private http: HttpClient) {
    this.query$.pipe(
      debounceTime(250),                         // wait for a pause in typing
      distinctUntilChanged(),
      filter((q) => q.trim().length >= 2),       // minChars guard
      switchMap((q) =>                            // cancels the prior request automatically
        this.http.get<{ results: Result[] }>("/api/search", { params: { q } }).pipe(
          catchError(() => of({ results: [] })),
        )),
    ).subscribe(({ results }) => { this.results = results; this.open = true; });
  }
}
```

`switchMap` is doing exactly what `AbortController` does in the vanilla version — unsubscribing from (and cancelling) the in-flight request when a new one supersedes it. That's why it's the idiomatic Angular fix for stale results.

### 9.9 Web Component (framework-free custom element)
When you can't assume a framework — an embeddable widget, a design-system primitive shared across stacks — a custom element ships the same behavior with zero dependencies.

```javascript
// <search-bar> — custom element with Shadow DOM, debounce + AbortController
class SearchBar extends HTMLElement {
  #controller = null;
  #timer = null;

  connectedCallback() {
    this.attachShadow({ mode: "open" }).innerHTML = `
      <div class="search" role="search">
        <input type="search" role="combobox" part="input" autocomplete="off"
               aria-expanded="false" aria-controls="list" aria-autocomplete="list"
               aria-label="Search" placeholder="Search…" />
        <ul id="list" role="listbox" hidden></ul>
      </div>`;
    this.input = this.shadowRoot.querySelector("input");
    this.list = this.shadowRoot.querySelector("ul");
    this.input.addEventListener("input", () => this.#onInput());
  }

  #onInput() {
    clearTimeout(this.#timer);
    const q = this.input.value.trim();
    if (q.length < 2) { this.#close(); return; }
    this.#timer = setTimeout(async () => {
      this.#controller?.abort();                 // drop the superseded request
      this.#controller = new AbortController();
      try {
        const res = await fetch(`/api/search?q=${encodeURIComponent(q)}`,
          { signal: this.#controller.signal });
        this.#render((await res.json()).results);
      } catch (e) { if (e.name !== "AbortError") this.#close(); }
    }, 250);
  }

  #render(results) {
    // textContent per row — never innerHTML user/result strings (see §15)
    this.list.replaceChildren(...results.map((r) => {
      const li = document.createElement("li");
      li.setAttribute("role", "option");
      li.dataset.id = r.id;
      li.textContent = r.label;
      li.addEventListener("mousedown", (e) => {
        e.preventDefault();
        this.dispatchEvent(new CustomEvent("select", { detail: r }));
      });
      return li;
    }));
    this.list.hidden = results.length === 0;
    this.input.setAttribute("aria-expanded", String(results.length > 0));
  }

  #close() { this.list.hidden = true; this.input.setAttribute("aria-expanded", "false"); }
  disconnectedCallback() { clearTimeout(this.#timer); this.#controller?.abort(); }
}
customElements.define("search-bar", SearchBar);
```

Building rows with `textContent` (not `innerHTML`) is deliberate: result labels are data, and interpolating them into markup is exactly the reflected-XSS hole §15 warns about.

### 9.12 Next.js (App Router: URL-as-state, server-filtered)
The senior Next pattern: **the query lives in the URL**, the results render on the **server**, and the input is a thin client component that debounces updates to the search param. Shareable, back-button-correct, and no client-side data fetching for the results.

```typescript
// app/search/SearchInput.tsx  — client: it has input + debounce
"use client";
import { useRouter, useSearchParams, usePathname } from "next/navigation";
import { useCallback, useEffect, useRef } from "react";

export function SearchInput() {
  const router = useRouter();
  const pathname = usePathname();
  const params = useSearchParams();
  const timer = useRef<ReturnType<typeof setTimeout>>();

  const onChange = useCallback((value: string) => {
    clearTimeout(timer.current);
    timer.current = setTimeout(() => {
      const next = new URLSearchParams(params);
      value ? next.set("q", value) : next.delete("q");
      router.replace(`${pathname}?${next}`);   // updates URL, re-renders server page
    }, 250);
  }, [params, pathname, router]);

  // Clear the pending debounce on unmount so a stale timer can't call router.replace on a dead component
  useEffect(() => () => clearTimeout(timer.current), []);

  return (
    <form role="search">
      <label htmlFor="q" className="sr-only">Search</label>
      <input id="q" type="search" name="q" defaultValue={params.get("q") ?? ""}
             placeholder="Search…" onChange={(e) => onChange(e.target.value)} />
    </form>
  );
}
```

### 9.13 Node.js (the search endpoint behind the bar)
The endpoint is where "search" actually happens. Debounced fetches land here, so it must be fast, cancellation-friendly, ranked, and hardened. Express-style, shape is universal.

```typescript
import express from "express";
import { z } from "zod";

const router = express.Router();

const Query = z.object({
  q: z.string().trim().min(1).max(200),           // bound the length — no 10KB queries
  scope: z.enum(["all", "products", "docs", "people"]).default("all"),
  limit: z.coerce.number().int().min(1).max(50).default(20),
});

router.get("/api/search", rateLimit({ windowMs: 60_000, max: 60 }), async (req, res) => {
  const parsed = Query.safeParse(req.query);
  if (!parsed.success) return res.status(422).json({ error: parsed.error.issues });
  const { q, scope, limit } = parsed.data;

  // PARAMETERIZED query — never string-concatenate user input into SQL
  const rows = await db.query(
    `SELECT id, title,
            ts_rank(search_vector, plainto_tsquery('english', $1)) AS rank
       FROM documents
      WHERE search_vector @@ plainto_tsquery('english', $1)
        AND ($2 = 'all' OR category = $2)
      ORDER BY rank DESC, updated_at DESC
      LIMIT $3`,
    [q, scope, limit]
  );

  // Short cache: identical popular queries shouldn't re-hit the DB every keystroke
  res.set("Cache-Control", "private, max-age=10");
  res.json({ query: q, results: rows });
});

export default router;
```

**Ranking basics** — what "good results" actually means:
*   **Text relevance:** how well the row matches (Postgres `ts_rank`, or BM25 in Elasticsearch/OpenSearch/Meilisearch/Typesense). Term frequency up, common-word weight down.
*   **Recency & popularity:** tie-break by freshness and click-through. A recent, frequently-opened doc outranks a stale exact match.
*   **Field boosting:** a match in the _title_ outweighs a match in the body. Weight fields.
*   **Typo tolerance & prefix matching:** for typeahead you want prefix ("reac" → "react") and fuzzy ("recat" → "react") matching. This is why dedicated engines (Meilisearch, Typesense, Algolia) beat naive `LIKE '%q%'`, which can't rank, can't tolerate typos, and can't use an index for a leading wildcard.
*   **Semantic layer (2026):** vector/embedding search for meaning-based matches, often blended with keyword ("hybrid search").

**Cancellation on the server:** because the client uses `AbortController`, a superseded request's socket closes. Wire that up so you don't waste DB work on an abandoned query:

```typescript
req.on("close", () => { if (!res.writableEnded) queryHandle?.cancel(); });
```

Search endpoints are an attack surface in their own right — injection, per-row authorization, rate limiting, ReDoS, and autocomplete data leakage. That whole contract now lives in its own section; see §15 Security.

### 9.14 Python (backend + a rendered search bar)
**Backend** (FastAPI) — same contract as Node: validate, bound, parameterize, rank, rate-limit.

```python
from fastapi import FastAPI, Query, HTTPException, Depends
from pydantic import constr

app = FastAPI()

@app.get("/api/search")
def search(
    q: constr(strip_whitespace=True, min_length=1, max_length=200),
    scope: str = Query("all", pattern="^(all|products|docs|people)$"),
    limit: int = Query(20, ge=1, le=50),
    user=Depends(require_auth),
):
    # Parameterized — the driver escapes q; no f-string SQL, ever.
    rows = db.execute(
        """
        SELECT id, title, ts_rank(search_vector, plainto_tsquery('english', %(q)s)) AS rank

         WHERE search_vector @@ plainto_tsquery('english', %(q)s)
           AND (%(scope)s = 'all' OR category = %(scope)s)
           AND (owner_id = %(uid)s OR is_public)     -- ACL in the query
         ORDER BY rank DESC, updated_at DESC
         LIMIT %(limit)s
        """,
        {"q": q, "scope": scope, "uid": user.id, "limit": limit},

  await page.goto("/search");
  await page.getByRole("searchbox", { name: "Search" }).fill("invoices");
  await expect(page).toHaveURL(/q=invoices/);
  await expect(page.getByText(/results for/i)).toBeVisible();
});
```

**Accessibility (jest-axe / Playwright axe):** run `axe` on the open-suggestions state, not just the closed one — the listbox is where combobox a11y bugs hide.

What to assert (and skip):
*   **Do test:** found by role, debounce collapses a burst into one call, arrow+Enter selects, clear resets and restores focus, stale responses are dropped, the live region announces counts.
*   **Don't test:** exact class names, hex colors, the debounce timer's internals.

## 10\. Accessibility (non-negotiable)
Search is a landmark _and_, when it has suggestions, a combobox. Both contracts must hold.

*   **Landmark:** wrap in `<form role="search">` (or the native `<search>` element) so screen-reader users jump to it directly. Exactly one primary search landmark per page, ideally.
*   **Real label always.** `<label>` (visually-hidden is fine) or `aria-label`. Placeholder is _not_ an accessible name and disappears on type.
*   **`<input type="search">`** for the correct role and mobile keyboard (`enterkeyhint="search"`).
*   **Combobox contract (when suggestions exist):**
    *   Input: `role="combobox"`, `aria-expanded` (true/false), `aria-controls="<listbox id>"`, `aria-autocomplete="list"`.
    *   Popup: `role="listbox"`; each row `role="option"` with a stable `id` and `aria-selected`.
    *   **`aria-activedescendant`** on the input points at the highlighted option's id. **DOM focus stays in the input** — options are never tab stops.
*   **Keyboard map:**

| Key | Action |
| ---| --- |
| `/` or `Cmd/Ctrl-K` | Focus / open search from anywhere |
| Type | Filter; open suggestions |
| `↓` / `↑` | Move the active option (via `aria-activedescendant`) |
| `Enter` | Select active option, or submit the query |
| `Esc` | Close suggestions; second press clears the field |
| `Tab` | Leave the search bar (does not move within the listbox) |
| `Home` / `End` | (Optional) jump to first/last option |

*   **Announce results with a live region:** `<div aria-live="polite">12 results</div>` and `"No results for 'x'"` / `"Searching…"`. Sighted users see the count; screen-reader users must _hear_ it.
*   **The clear ✕ needs a name** (`aria-label="Clear search"`) and must return focus to the input.
*   **Contrast ≥4.5:1** for placeholder, typed text, and the option highlight. Placeholder text failing contrast is one of the most common search a11y bugs.
*   **Touch target ≥44px** for the field, the submit, the clear, and every suggestion row.
*   **Don't trap focus** in the suggestions (except a command-palette modal, which _should_ trap and restore focus on close).

## 11\. Innovative & Emerging Ideas
Search looks solved and keeps moving:
*   **AI answer above results:** an LLM-generated summary sits atop the ranked links; the bar becomes a question box. Streaming/generative loading states replace the spinner.
*   **Natural-language & semantic search:** vector embeddings match meaning, not just keywords, so "somewhere warm in December" returns destinations. Hybrid (keyword + vector) is the 2026 default for quality.
*   **The command palette as the app's front door:** `Cmd-K` searches content, actions, navigation, and settings from one modal — "search then act" without leaving the keyboard.
*   **Scoped, agentic results:** operate on a result inline (assign, archive, open) directly from the dropdown.
*   **Predictive / zero-query suggestions:** the moment you focus (before typing) the bar shows recent searches, trending queries, and personalized shortcuts.
*   **Multimodal search:** voice input (mic in the bar) and image/visual search (camera) sharing one query pipeline.
*   **Instant, index-on-the-edge search:** Typesense/Meilisearch/Algolia return typo-tolerant results in <50ms, making true search-as-you-type feel native.

## 12\. Conversion & UX Killers (mistakes that bleed money silently)
None throw an error. They just quietly send high-intent users away.
*   **No debounce / no cancellation.** You fire a request per keystroke and race the responses, so users see flickering, stale, wrong results. Feels broken; is broken. Debounce + AbortController is non-negotiable.
*   **Placeholder as the only label.** It vanishes the moment they type, fails contrast, and leaves screen-reader users with an unnamed field. Always ship a real (visually-hidden) label.
*   **Dead-end "0 results."** "No results" with no spelling suggestion, no scope broadening, no popular items = the user leaves. A no-results state is a _designed_ state with a recovery path.
*   **No loading feedback.** User types, nothing visibly happens, they assume it's dead. A subtle in-field spinner and a "Searching…" live announcement keep them waiting instead of bouncing.
*   **Zero typo tolerance.** `LIKE '%query%'` can't handle "recieve" or "iphone" vs "i phone." One typo = zero results = a lost sale. Use an engine with fuzzy matching.
*   **Losing the query on back.** Query in component state instead of the URL means the back button, refresh, and sharing all lose the search. Put `q` in the URL.
*   **Suggestions that fight the keyboard.** Options that are tab stops, no arrow-key nav, click that closes before it selects (the `mousedown` bug). Keyboard users can't use your search.
*   **Tiny mobile targets & iOS zoom.** Sub-16px input font zooms the page on focus; cramped ✕ and submit cause mis-taps. Most search is done on thumbs.
*   **A search that isn't findable.** Hiding search behind an unlabeled icon on desktop, or not advertising `Cmd-K`. If they can't find search, your best conversion path is invisible.

**The through-line:** these fail _quietly_. No crash, just a lower search-conversion number that's easy to blame on "traffic quality." Audit your search bar before you audit your ad spend.

## 13\. Advanced Patterns
Techniques that lean on the platform and the type system instead of custom glue.
### Query-in-the-URL as the single source of truth
Store the query, scope, and page in the URL search params; render results from that. The input is a controlled reflection of the URL, not a parallel state. You get shareable searches, working back/forward, and refresh-persistence for free. (See §9.12.)

### Recent searches + scoped search
Persist the last N queries in `localStorage`, show them on focus before a keystroke, and let users pin a scope. A scope chip renders inside the field:

```plain
<form role="search">
  <span class="scope-chip">in Products <button aria-label="Clear scope">✕</button></span>
  <input type="search" aria-label="Search products" />
</form>
```

Recent searches are a combobox popup like any other (`role="listbox"`), just sourced from history instead of the server. Scope becomes a `scope` param on the endpoint (§9.13).

### Keyboard shortcut to focus (`/` and `Cmd-K`)
Two conventions, two behaviors. `/` **focuses an existing inline search** (GitHub, YouTube). `Cmd/Ctrl-K` **opens a command-palette modal**. Wire the global listener, and — critically — **don't hijack the key while the user is typing in another field**:

```javascript
document.addEventListener("keydown", (e) => {
  const typing = /^(input|textarea|select)$/i.test(document.activeElement?.tagName ?? "")
    || document.activeElement?.isContentEditable;
  if (e.key === "/" && !typing) { e.preventDefault(); searchInput.focus(); }
  if (e.key === "k" && (e.metaKey || e.ctrlKey)) { e.preventDefault(); openPalette(); }
});
```

The `typing` guard is the senior detail: without it, pressing `/` to type a URL or a message steals focus and infuriates users.

### Design tokens for the field

```css
:root {
  --search-h: 44px;
  --search-radius: 10px;
  --search-bg: #14101c;
  --search-border: #3a2d4a;
  --search-ring: #DCA424;          /* Goldenrod */
  --search-option-active: rgba(220,164,36,.18);
}
```

Retheme every search bar (and its popup) by swapping the block. Dark mode is a token swap, not new CSS.

### TypeScript: make suggestions and results distinct types
A combobox that predicts _queries_ and one that jumps to _results_ are different contracts. Model them so you can't render one as the other:

```typescript
type Suggestion = { kind: "query"; text: string };
type Hit        = { kind: "result"; id: string; label: string; href: string };
type Row = Suggestion | Hit;
// Enter on a Suggestion re-runs search; Enter on a Hit navigates. The union forces you to handle both.
```

## 14\. Performance & Bundle Cost
A search bar feels free until it's firing 8 requests a word across a million rows.
*   **Debounce is the first perf lever.** 250ms cuts request volume by ~5–10x versus per-keystroke. It's a UX _and_ an infra decision.
*   **Cancel superseded requests** (AbortController) so you don't pay for work the user has already moved past — on the client _and_ (via `req.on("close")`) the server.
*   **Cache hot queries.** Short `Cache-Control` (10–30s) plus a CDN/edge cache means popular prefixes ("i", "ip", "iph"…) don't re-hit the DB on every user.
*   **Index for prefix + full-text.** A leading-wildcard `LIKE '%q%'` can't use a B-tree index — it scans. Use a GIN/tsvector index, a trigram index, or a dedicated search engine.
*   **Virtualize long result lists.** Rendering 500 option rows in the DOM janks the dropdown; windowing (react-window) renders only what's visible.
*   **Tree-shake the search engine client.** Import only what you use from Algolia/Meilisearch/Typesense SDKs; a namespace import pulls the whole client.
*   **Don't animate layout on each keystroke.** Animating the dropdown's `height` reflows every frame; animate `transform`/`opacity`, and keep the field's width fixed so the loading spinner doesn't shift the layout.
* * *

## 15\. Security (the query is a direct line to your data layer)
A search endpoint takes attacker-controlled text and runs it straight against your datastore, over a `GET` that's trivial to probe at scale — treat every query as hostile input. Parameterize it: bind the query as a value in a prepared statement (the `$1`/`$2` and `%(q)s` forms in §9.13 and §9.14) and never string-concatenate it into SQL, and for NoSQL reject object-shaped params so `q[$ne]=` can't smuggle an operator — validate that `q` is a string. When you echo the query back into the results ("Showing results for '…'"), escape it on output; an unescaped `<script>` in that "you searched for" line is textbook reflected XSS. Bound the request on three axes — cap its length, set a per-request timeout, and rate-limit per IP _and_ per user — because autocomplete multiplies load (eight keystrokes can mean eight requests even debounced) and an unbounded query is a cheap DoS. Guard the matching itself: never feed raw user text into a regex or a query DSL, where a crafted pattern triggers catastrophic backtracking (ReDoS), and never let a leading-wildcard `LIKE '%q%'` force an on-demand full-table scan. Authorize at the row level, inside the query — search must return only records the user could already reach from the list view (`AND owner_id = $uid OR is_public`), never fetch-then-filter in application code, and never trust an index that has forgotten per-row ACLs; that silent leak, where a user searches up documents they were never allowed to open, is the single most common search vulnerability. Finally, treat the suggest/autocomplete endpoint as an enumeration oracle: suggestions sourced from other users' data leak usernames, emails, and private titles one prefix at a time, so scope them to public data or the current user's own history, and scrub PII from query logs.

## 16\. Senior-Level Checklist (ship-ready)
Before a search bar is "done":
- [ ] `<form role="search">` (or `<search>`) landmark; real, associated `<label>` even if visually hidden.
- [ ] `<input type="search">` with `enterkeyhint="search"`, `autocomplete="off"`, ≥16px font on mobile.
- [ ] Debounced input (150–300ms) **and** `AbortController` cancellation; `AbortError` swallowed.
- [ ] Stale responses can never overwrite fresh ones (proven by a race test).
- [ ] Clear ✕: real `<button type="button">`, `aria-label="Clear search"`, returns focus to input, only shown when non-empty.
- [ ] Suggestions use the full combobox contract: `role="combobox"`/`aria-expanded`/`aria-controls`/`aria-autocomplete`, `role="listbox"`/`role="option"`, `aria-activedescendant`, DOM focus stays in the input.
- [ ] Keyboard: `↓↑` navigate, Enter selects/submits, Esc closes then clears, `/` or `Cmd-K` focuses/opens (guarded against firing while typing elsewhere).
- [ ] Loading, empty, no-results (with recovery), and error states all designed — no silent dead input.
- [ ] Result count announced via `aria-live`.
- [ ] Query in the URL (`?q=`) for shareable, back-button-correct search.
- [ ] Endpoint: input validated + length-bounded, **parameterized** queries, per-row ACL filtering, rate-limited, ranked (relevance + recency), never `eval`s the query.
- [ ] Touch targets ≥44px; contrast ≥4.5:1 on placeholder, text, and option highlight.
- [ ] `prefers-reduced-motion` honored on the loading spinner and any animated ring.

## 17\. Visual Styles Reference (the eleven, skin-only)
The same search bar, eleven aesthetics. Behavior — landmark, combobox semantics, keyboard, focus ring, 44px target — is identical across all of them. Full guidance lives in the [Design Styles doc](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200551).
*   **Flat:** solid field, 1px border, crisp glyph, no shadow.
*   **Material:** filled field that elevates into a "search view"; motion-aware.
*   **Glassmorphism:** translucent field + `backdrop-filter` over a vivid backdrop; guard placeholder contrast.
*   **Liquid Glass:** refractive pill with a specular rim and moving sheen; the popup is its own glass layer. SwiftUI emits native `.searchable()` + `.glassEffect()`; web is an honest approximation.
*   **Neumorphism:** inset dual-shadow "well" — the rare place neumorphism reads right, since an input _should_ look recessed. Guard text contrast.
*   **Skeuomorphism:** beveled search well with an inner shadow, old-OS-X flavor.
*   **Neo-Brutalism:** thick border, hard offset shadow, zero radius, unapologetic glyph.
*   **Claymorphism:** puffy pill, big radius, soft inner light. Friendly/consumer.
*   **Aurora / Gradient:** animated gradient focus ring on dark; honor `prefers-reduced-motion`.
*   **Minimal / Swiss:** an underline and a glyph; typography carries it. Protect the hit target.
*   **UJG Brand:** Goldenrod glyph and focus ring on a deep Eminence/Night field, warm focus glow, Night suggestions popup with a Goldenrod active-row highlight.

**Guardrails that never bend:** glass/liquid-glass/neumorphism must pass contrast on the placeholder, typed text, and the caret; aurora/liquid-glass must respect `prefers-reduced-motion`.
* * *

**Bottom line:** a search bar is the highest-intent input you own and the one most often mistaken for three other components. Nail the distinction (search landmark vs combobox vs select vs command palette), ship the async lifecycle correctly (debounce, cancel, drop stale, feed a live region), obey the full combobox and landmark a11y contract, and harden the endpoint (parameterize, bound, rank, ACL-filter, rate-limit, never `eval`). Do that and you've built the difference between a search that converts and a box that quietly loses your best-qualified users.
