# Back to Top

# Back to Top

A "Back to Top" control is the small, fixed affordance that appears once a user has scrolled far enough down a long page and, when activated, returns them to the top — and, done correctly, returns their _keyboard focus and screen-reader position_ too, not just the viewport. It looks trivial. It is one of the most commonly botched accessibility components on the web, because 90% of implementations move the pixels and forget the person.
* * *

## 1\. What It Actually Is

Back to Top is a persistent utility control — almost always a native `<button>`, occasionally a skip-style anchor to `#top` — that becomes visible after the user scrolls past a threshold and, on activation, returns the page to the very top. The correct implementation does three things at once: (1) scrolls the viewport up, respecting the user's motion preference; (2) moves keyboard/assistive-tech focus to a real target at the top of the document (the `<h1>`, the `<main>`, or a `tabindex="-1"` sentinel) so that non-sighted and keyboard users are actually transported, not stranded at the bottom of the DOM; and (3) reveals/hides itself based on scroll position using a performance-cheap mechanism (an IntersectionObserver on a top sentinel), not a constantly-firing scroll listener.

**The 2-4 things people confuse it with, named and distinguished:**

*   **Floating Action Button (FAB):** A FAB is a _primary, contextual action launcher_ (compose, add, new) — it initiates domain work. Back to Top is a _navigation utility_ — it moves the reader, it doesn't create anything. They share the "fixed circle, bottom-right" silhouette, which is exactly why they collide. If your page already has a FAB, Back to Top must not sit on top of it; offset it, stack it, or fold it into a speed-dial.
*   **Scroll-to-anchor / in-page jump link:** An anchor jumps to a _named section_ mid-document. Back to Top always targets the document origin. The anchor lives inline in content; Back to Top floats.
*   **Sticky header / persistent nav:** A sticky header keeps navigation visible _at all times_ so the user never has to return to the top to navigate. If you have one, you frequently don't need Back to Top at all.
*   **Scroll progress indicator:** A progress bar _reports_ how far down the page you are; it's passive. Back to Top _acts_. They're often paired (progress ring wrapping the button), which is fine, but they answer different questions.

**Rule of thumb:** If the control's only job is "take me back to the origin of _this_ page," and the page is long enough that a user could plausibly get lost or fatigued scrolling back, it's a Back to Top. If it launches an action, it's a FAB. If it navigates to a named place, it's an anchor. If navigation is always on screen, you probably don't need it.
* * *

## 2\. Why It Matters

*   **Accessibility (the real stakes, and the most-missed detail):** Keyboard and screen-reader users navigate by _focus and reading position_, not by scrollbar. A naive `window.scrollTo(0,0)` visually moves the page but leaves focus exactly where it was — often deep in the footer. The next `Tab` press then jumps them back down, and screen readers keep reading from the footer. A correct Back to Top moves _focus_ to a top target, so the person is genuinely relocated. Getting this wrong turns a "helpful" button into a keyboard trap that actively harms the users it was meant to help. This is a WCAG 2.4.3 Focus Order concern, and it is the single differentiator between a real component and a decoration.
*   **Performance / Core Web Vitals:** The lazy implementation binds a `scroll` handler that fires dozens of times per second, and if it also reads `scrollY` or calls `getBoundingClientRect()` inside that handler, it forces synchronous layout on the main thread during the exact moment the user is scrolling — causing jank and hurting INP (Interaction to Next Paint). Using an IntersectionObserver on a sentinel moves the "am I past the threshold?" decision off the main thread entirely. On a content-heavy landing page this is the difference between buttery scroll and a stuttering one.
*   **Trust & task completion:** On long-scroll landing pages, blogs, docs, and infinite feeds, reaching the bottom and facing a manual scroll back up is friction that reads as "this site doesn't respect my time." A predictable, well-placed Back to Top signals polish. Conversely, a Back to Top that overlaps the cookie banner, covers the footer's legal links, or hides the "Add to cart" FAB _destroys_ trust — it's an obstruction wearing a helpful mask.
*   **Layout stability (CLS):** Toggling the button with `display:none`/`display:block` or by inserting/removing it from the DOM can shift surrounding content and hurt Cumulative Layout Shift. Because the button is `position: fixed` it's usually out of flow, but people still get this wrong by animating `height` or `top` instead of `opacity`/`transform`, causing paint thrash near the viewport edge.
* * *

## 3\. Anatomy

*   **The button element (****`<button type="button">`****):** The interactive core. Native `<button>` for free keyboard operability, focusability, and the implicit `button` role. Never a bare `<div>` with an onclick. Circular or pill, fixed to the viewport.
*   **The icon (chevron / arrow-up):** The universally understood up-arrow (`↑`) or double-chevron. Presentational only — marked `aria-hidden="true"` — because the accessible name comes from the label, not the glyph.
*   **The accessible name:** Either visible text ("Back to top") or, for icon-only variants, an `aria-label="Back to top"`. This is non-optional; an icon-only button with no name is a screen-reader dead end ("button, button").
*   **The scroll sentinel:** A zero-height, visually-hidden element placed at the very top of the page (or the top of the scroll container). An IntersectionObserver watches it; when it leaves the viewport, the button is shown; when it re-enters, the button hides. This is the performance heart of the component — it replaces the scroll listener.
*   **The focus target:** A real element at the top the button sends focus to — the `<h1>`, the `<main id="main">`, or a dedicated `<span id="top" tabindex="-1">`. Without this, the button is visually functional but broken for keyboard/AT users.
*   **The visibility wrapper / transition layer:** The opacity + transform transition that fades and lifts the button in without layout shift. Toggled via a class or `data-visible` attribute, honoring `prefers-reduced-motion`.
*   **Optional progress ring:** An SVG stroke around the circle showing scroll depth. Decorative; `aria-hidden`.
*   **Optional visible label:** A "Top" caption under the icon on wider layouts, improving discoverability and target size.
* * *

## 4\. Sizes / Scale / Density

Target size is the governing constraint: the button must clear the 44×44px (WCAG 2.5.8 / Apple HIG) minimum touch target, even when the visible circle is smaller, via padding or an invisible hit area.

| Tier | Token | Visible size | Hit target | Icon | Offset from edges | Use case |
| ---| ---| ---| ---| ---| ---| --- |
| Compact | `--btt-size-sm` | 40px circle | 44px (pad) | 20px | 16px | Dense dashboards, docs sidebars, desktop-only |
| Standard | `--btt-size-md` | 48px circle | 48px | 24px | 20–24px | Default — blogs, marketing, most sites |
| Comfortable | `--btt-size-lg` | 56px circle | 56px | 28px | 24–32px | Touch-first mobile, large-format displays, accessibility-forward builds |

Rules that matter:

*   **Safe-area insets:** On notched / gesture-bar devices, offset with `max(20px, env(safe-area-inset-bottom))` on the bottom and `env(safe-area-inset-right)` on the right, or the button hides behind the home indicator.
*   **Never below 44px hit target.** A 40px visible circle is fine only if padding pushes the _interactive_ area to 44px+.
*   **Spacing tokens, not magic numbers.** Edge offsets come from the spacing scale (`--space-4` = 16px, `--space-6` = 24px), so the button aligns with other fixed UI (toasts, cookie bars).
*   **Responsive placement:** bottom-right on desktop (right thumb / mouse), can move to bottom-center or bottom-right-above-nav on mobile so it clears a bottom tab bar.
*   **Stacking with other fixed UI:** reserve a `--z-fixed-utility` tier so Back to Top, toasts, and FABs have a defined order and never overlap ambiguously.
* * *

## 5\. States

*   **Hidden (default, at top):** The user is above the threshold. The button is not visible _and is removed from the tab order_ (`visibility: hidden` collapses focusability, or `inert`). Critical: a button that's faded to `opacity: 0` but still focusable is a phantom tab stop.
*   **Entering (revealing):** Triggered when the sentinel leaves the viewport. Fades in via `opacity` + a small `translateY` lift over ~200ms. Under `prefers-reduced-motion: reduce`, it appears instantly with no transform.
*   **Visible (idle):** Fully shown, in the tab order, ready. Rests at elevation-2.
*   **Hover:** Slight elevation lift and/or color shift (Goldenrod brightens on Eminence). Cursor `pointer`. Non-essential — must not be the only affordance signal.
*   **Focus / focus-visible:** A clearly visible focus ring (2px offset outline in a contrasting color) when reached by keyboard. Must survive theme changes and meet 3:1 non-text contrast against both the button and the page behind it.
*   **Active / pressed:** Brief scale-down (`scale(0.94)`) or elevation drop for tactile feedback on press.
*   **Scrolling (in-progress):** Between activation and arrival at top. Optionally the button can enter a subtle "working" state; more importantly, focus is being moved and, if smooth-scroll is on, the page is animating. The button should ignore repeat clicks during this window (or they're harmless because the target is idempotent).
*   **Disabled:** Rare — Back to Top is either present or absent, not disabled. If it exists it should work. (A disabled state only makes sense in a builder/preview context.)
*   **Exiting (hiding):** When the sentinel re-enters (user scrolled back near top), the button fades out and leaves the tab order. Guard against fading out _while focused_ — if the user is focused on it, move focus first or the ring disappears into nothing.
*   **Reduced-motion:** All enter/exit transitions and the scroll itself collapse to instant. No `translateY`, no smooth scroll.
* * *

## 6\. Types / Variants

*   **Icon-only circle (standard):** A circular `<button>` with an up-arrow and an `aria-label`. The default; compact and universally understood. Requires the label because there's no visible text.
*   **Icon + visible label:** Pill-shaped, "↑ Top" or "Back to top" text beside/under the icon. Higher discoverability, larger target, self-describing to screen readers via its text content. Preferred when space allows and for accessibility-forward builds.
*   **Progress-ring button:** The circle wrapped by an SVG ring that fills as the user scrolls, doubling as a scroll-depth indicator. The ring is `aria-hidden`; the button underneath is a normal labeled control.
*   **Inline text link (non-floating):** A plain `<a href="#top">Back to top</a>` (or a `<button>`) placed at the _end_ of content — e.g., after each long docs section or in the footer. No fixed positioning, no scroll observer, zero obstruction risk. The most robust, lowest-surface variant; degrades perfectly without JS.
*   **FAB-merged / speed-dial member:** On pages that already have a FAB, Back to Top becomes one entry in a stacked speed-dial rather than a competing floating circle, avoiding overlap.
*   **Auto-hiding on idle:** A floating variant that also fades after N seconds of no scrolling and reappears on the next scroll, minimizing obstruction of content beneath it.
* * *

## 7\. When to Use (and When Not To)

**Use when:**

*   The page is genuinely long — a rule of thumb is taller than ~2–3 viewports (blogs, long-form articles, documentation, marketing landing pages, changelogs).
*   Infinite-scroll or "load more" feeds where the content beneath the fold keeps growing and manual scroll-back becomes punishing.
*   Reading-heavy content where users reach the bottom and predictably want to restart, re-navigate, or reach top-of-page controls.

**Don't use / use something else when:**

*   **The page is short** (< 2 viewports). A Back to Top here is clutter that solves a problem no one has. Just delete it.
*   **A sticky header / persistent nav is always visible.** The user can navigate up any time; the redundant button adds obstruction. Use the sticky nav instead.
*   **App shells with fixed toolbars** already offer "home"/top affordances — use those, not a floating duplicate.
*   **Virtualized lists** where "top" is ambiguous (which list, which scroll container?). Use the list's own scroll-to-index API and a clearly-scoped control, not a page-level Back to Top.
*   **When it would overlap essential UI** (cookie consent, chat FAB, sticky "Add to cart" bar) and you can't cleanly offset it — an inline text link at the bottom of content is the safer alternative.

**Placement heuristics:** bottom-right on desktop; keep clear of the FAB, the chat widget, and the footer's actionable region; respect safe-area insets; keep a consistent offset that aligns with your other fixed UI; never let it cover text the user is actively reading.

## 8\. Across Design Systems

*   **Material Design (Google):** No dedicated "Back to Top" component; Material treats it as a _small FAB_ or an _extended FAB_ used for the scroll-to-top pattern, with elevation, a ripple on press, and the up-arrow icon. Material's guidance stresses not competing with the primary FAB — hence the "secondary/mini FAB" treatment. Material 3 "Expressive" adds springier motion to its enter/exit.
*   **Apple HIG:** iOS has a _system-level_ Back to Top: tapping the status bar scrolls the active scroll view to the top — so native iOS apps rarely ship a custom button. On the web / iPadOS, when a custom control is used, HIG expects a 44pt target, respect for Reduce Motion, and Liquid Glass material in iOS 26 / macOS Tahoe.
*   **Fluent (Microsoft):** No first-class component; realized as a `CommandBar` button or a floating `Button` with the `ChevronUp` icon, following Fluent's focus-visible and reduced-motion tokens. Fluent emphasizes keyboard reachability and high-contrast-mode support.
*   **Ant Design:** Ships an explicit **`BackTop`** component (now folded into `FloatButton` with `FloatButton.BackTop`) — `visibilityHeight` prop for the threshold, a customizable target scroll container, and a default up-arrow. One of the few systems with this as a named primitive.
*   **Tailwind CSS:** No component; you compose it — `fixed bottom-6 right-6`, `opacity-0`/`opacity-100` transitions toggled by a tiny script or a `peer`/`group` trick, `motion-reduce:transition-none`. Tailwind gives the utilities; you own the observer logic.
*   **shadcn/ui + Radix:** No dedicated primitive; you build it from a shadcn `Button` (`size="icon"`, `variant="secondary"`) plus your own IntersectionObserver hook. Radix contributes the accessible button behavior; the scroll/focus logic is yours.
*   **Bootstrap 5:** No component, but the docs themselves ship a "back to top" example — a `.btn` positioned `position-fixed bottom-0 end-0`, toggled by a scroll handler, with the `bi-arrow-up` icon. Utility-class driven.

**Takeaway:** only Ant Design treats Back to Top as a named component; everyone else composes it from a button + observer. That's exactly why implementations diverge so wildly on the accessibility details — there's no framework guardrail forcing focus management.

### 8b. What's Trending in 2026

*   **Liquid Glass buttons:** Apple's iOS 26 / macOS Tahoe material is the dominant aesthetic — the floating circle as a translucent, light-refracting pill with a specular rim, replacing flat glassmorphism. The web approximates it with layered `backdrop-filter` and highlight gradients, always guarded for contrast.
*   **Scroll-driven animations (CSS):** The `animation-timeline: scroll()` / `view()` APIs (now broadly shipping) let the button reveal, and a progress ring fill, be driven _entirely in CSS off the main thread_ — no JS observer needed for the pure-visual layer. This is the biggest 2026 shift for this component.
*   **Progress-ring fusion:** Back to Top increasingly merges with the reading-progress indicator into one control — the ring shows depth, the center returns you up.
*   **Motion-forward but restrained:** springy micro-interactions on enter, but universally gated behind `prefers-reduced-motion` — the 2026 norm is "expressive by default, calm on request."

### 9.3 React + TypeScript (full reusable component with focus management)

```tsx
import { useCallback, useEffect, useRef, useState } from "react";

export interface BackToTopProps {
  /** CSS selector for the focus target at the top. */
  targetSelector?: string;
  /** CSS selector for the focus target at the top. */
  label?: string;
  className?: string;
}

export function BackToTop({
  targetSelector = "#top",
  label = "Back to top",
  className,
}: BackToTopProps) {
  const [visible, setVisible] = useState(false);
  const sentinelRef = useRef<HTMLDivElement | null>(null);

  useEffect(() => {
    const sentinel = sentinelRef.current;
    if (!sentinel || typeof IntersectionObserver === "undefined") return;
    const io = new IntersectionObserver(
      ([entry]) => setVisible(!entry.isIntersecting),
      { rootMargin: "0px", threshold: 0 }
    );
    io.observe(sentinel);
    return () => io.disconnect();
  }, []);

  const handleClick = useCallback(() => {
    const reduce = window.matchMedia("(prefers-reduced-motion: reduce)").matches;
    window.scrollTo({ top: 0, behavior: reduce ? "auto" : "smooth" });

    // The a11y heart: move focus to a real top target, not just the viewport.
    const target = document.querySelector<HTMLElement>(targetSelector);
    if (target) {
      // Ensure it can receive focus without adding a persistent tab stop.
      if (!target.hasAttribute("tabindex")) target.setAttribute("tabindex", "-1");
      target.focus({ preventScroll: true });
    }
  }, [targetSelector]);

  return (
    <>
      <div
        ref={sentinelRef}
        aria-hidden="true"
        style={{ position: "absolute", top: 0, height: 1, width: 1 }}
      />
      <button
        type="button"
        className={`btt${className ? " " + className : ""}`}
        aria-label={label}
        data-visible={visible}
        onClick={handleClick}
      >
        <svg className="btt__icon" viewBox="0 0 24 24" aria-hidden="true" focusable="false">
          <path d="M12 5l-7 7h4v7h6v-7h4z" fill="currentColor" />
        </svg>
        <span className="btt__label">Top</span>
      </button>
    </>
  );
}
```

### 9.4 Vanilla JavaScript (no framework, full keyboard + focus)

```js
(function initBackToTop() {
  const btn = document.getElementById("back-to-top");
  const sentinel = document.getElementById("btt-sentinel");
  const target = document.getElementById("top");
  if (!btn || !sentinel) return;

  const io = new IntersectionObserver(
    ([entry]) => btn.setAttribute("data-visible", String(!entry.isIntersecting)),
    { threshold: 0 }
  );
  io.observe(sentinel);

  btn.addEventListener("click", () => {
    const reduce = window.matchMedia("(prefers-reduced-motion: reduce)").matches;
    window.scrollTo({ top: 0, behavior: reduce ? "auto" : "smooth" });
    if (target) {
      if (!target.hasAttribute("tabindex")) target.setAttribute("tabindex", "-1");
      target.focus({ preventScroll: true });
    }
  });

  // If focus is on the button when it hides, release it so the ring never orphans.
  const mo = new MutationObserver(() => {
    if (btn.getAttribute("data-visible") === "false" &&
        document.activeElement === btn) {
      btn.blur();
    }
  });
  mo.observe(btn, { attributes: true, attributeFilter: ["data-visible"] });
})();
```

### 9.6 Next.js (App Router — client component)

```tsx
// components/back-to-top.tsx
"use client";
import { useEffect, useRef, useState, useCallback } from "react";

export default function BackToTop({ target = "#main" }: { target?: string }) {
  const [visible, setVisible] = useState(false);
  const ref = useRef<HTMLDivElement>(null);

  useEffect(() => {
    const el = ref.current;
    if (!el) return;
    const io = new IntersectionObserver(([e]) => setVisible(!e.isIntersecting));
    io.observe(el);
    return () => io.disconnect();
  }, []);

  const onClick = useCallback(() => {
    const reduce = matchMedia("(prefers-reduced-motion: reduce)").matches;
    scrollTo({ top: 0, behavior: reduce ? "auto" : "smooth" });
    const t = document.querySelector<HTMLElement>(target);
    t?.setAttribute("tabindex", "-1");
    t?.focus({ preventScroll: true });
  }, [target]);

  return (
    <>
      <div ref={ref} aria-hidden style={{ position: "absolute", top: 0, height: 1 }} />
      <button type="button" aria-label="Back to top" data-visible={visible}
        onClick={onClick} className="btt">
        <span aria-hidden>↑</span>
      </button>
    </>
  );
}
// app/layout.tsx — mount once, it floats over every route
import BackToTop from "@/components/back-to-top";
export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en">
      <body>
        <main id="main">{children}</main>
        <BackToTop target="#main" />
      </body>
    </html>
  );
}
```

## 10\. Accessibility

Standalone, and the section that separates a real Back to Top from a broken one. The pattern's failure mode is uniquely cruel: it _looks_ fine to sighted mouse users while being useless-to-harmful for everyone else.

**Roles & ARIA:**

*   Use a native `<button type="button">` — implicit `role="button"`, focusable, Space/Enter operable for free. If you must use an anchor (`<a href="#top">`), that's a valid link, but then don't add `role="button"`.
*   Accessible name is mandatory: visible text, or `aria-label="Back to top"` for icon-only. The icon (`<svg>`/glyph) is `aria-hidden="true"` and `focusable="false"`.
*   The sentinel and any progress ring are `aria-hidden="true"` — pure mechanism/decoration.
*   Do **not** slap `role="button"` on a `<div>`; you'll reinvent keyboard handling and get it wrong.

**Keyboard map:**

| Key | Action |
| ---| --- |
| `Tab` | Moves focus to the button only when it is visible; skips it entirely when hidden |
| `Shift+Tab` | Moves focus away (button is a single stop, not a widget with internal navigation) |
| `Enter` | Activates: scrolls to top and moves focus to the top target |
| `Space` | Activates (native button behavior — same as Enter) |
| `Esc` | No-op (nothing to dismiss) |

**Focus management (the crux):** On activation, after scrolling, call `.focus({ preventScroll: true })` on a real top target — the `<h1>`, `<main>`, or a `tabindex="-1"` anchor. `preventScroll` avoids fighting the smooth-scroll animation. Never rely on `window.scrollTo` alone: it moves pixels, not focus, so keyboard/SR users stay stranded and the next `Tab` yanks them back down. When the button hides while focused, release focus (blur or move it) so the focus ring doesn't vanish into an invisible element.

**Contrast:** Icon/text vs. button fill ≥ 4.5:1 for the glyph as meaningful text (or 3:1 if treated strictly as a large graphical object — but treat it as text to be safe). The button silhouette vs. the page behind it, and the focus ring vs. both surfaces, must clear 3:1 non-text contrast (WCAG 1.4.11). Goldenrod `#DCA424` on Eminence `#5F2C82` passes; verify per theme.

**Target size:** 44×44px minimum interactive area (WCAG 2.5.8 AA / Apple HIG). A 40px visible circle is only acceptable if padding/hit-area reaches 44px.

**Reduced motion:** Under `prefers-reduced-motion: reduce`, the scroll becomes an instant jump (`behavior: "auto"`) and the enter/exit transition drops the `translateY` and duration. Vestibular-sensitive users must never be smooth-scrolled 8000px against their preference.

**Common failures specific to this component:**

*   Scrolling the viewport but not moving focus — the #1 defect.
*   Icon-only button with no `aria-label` — reads as "button, button."
*   Button stays in the tab order while invisible (`opacity:0` without `visibility:hidden`/`inert`) — a phantom tab stop.
*   Smooth scroll ignoring `prefers-reduced-motion`.
*   Using a `<div onclick>` — no keyboard, no role.
*   Focus ring removed (`outline:none`) with nothing replacing it.
*   Fading the button out while it holds focus — the ring disappears into thin air.

## 11\. Innovative / Emerging Ideas

*   **Pure-CSS reveal with scroll-driven animations (2026):** Use `animation-timeline: scroll(root)` to fade and lift the button in based on scroll position with _zero JavaScript_ for the visual layer — off the main thread, no observer, no jank. JS remains only for the focus-move on click. This is the state of the art for the reveal mechanism this year.
*   **`::scroll-button()`** **and CSS carousel/scroll primitives:** Emerging CSS scroll-button pseudo-elements let the browser generate scroll controls natively; watch this space for a first-class declarative "scroll to start" that the platform manages, including focus.
*   **Progress-ring fusion with** **`view-timeline`****:** Drive an SVG progress ring's `stroke-dashoffset` directly from a scroll timeline so the ring fill and the button reveal share one declarative source of truth.
*   **View Transitions on jump:** Wrap the scroll-to-top in the View Transitions API so returning to the top can morph the header/hero back into place rather than snapping, giving a spatial "I went up" cue — always gated behind reduced-motion.
*   **Predictive / adaptive visibility:** Show the button only when engagement signals suggest the user is done reading a section (dwell time, reversal of scroll direction) instead of a naive pixel threshold, reducing obstruction.

## 12\. Conversion / UX Killers

*   **Obstructing the primary CTA or FAB.** The classic: the floating circle parks itself over "Add to cart," the chat launcher, or a sticky checkout bar on mobile. Users can't complete the action; you lose the sale. Fix: define a fixed-UI stacking/offset system so utilities never overlap conversion controls; suppress Back to Top when a sticky action bar is present.
*   **Covering the footer's actionable region.** At the bottom — exactly where Back to Top is most visible — it sits atop legal links, unsubscribe, contact, or newsletter signup. Fix: hide or offset the button when the footer enters the viewport (observe the footer too).
*   **Appearing too early / too aggressively.** Showing after 100px on a short page is noise that signals "generic template." It erodes the perception of quality. Fix: threshold tied to real content length (past 1.5–2 viewports), or don't render it on short pages at all.
*   **Scrolling pixels but stranding focus.** Keyboard/SR users click, the page appears to move, then `Tab` throws them back to the footer — a silent accessibility failure that also fails audits and invites legal exposure (ADA/AODA). Fix: move focus to a top target every time.
*   **Janky reveal that stutters scroll.** A `scroll` listener reading layout on every frame makes the whole page feel cheap during the exact interaction it's meant to improve. Fix: IntersectionObserver or scroll-driven CSS.
*   **No reduced-motion path.** Smooth-scrolling a vestibular-sensitive user thousands of pixels can cause literal nausea — they'll leave and not come back. Fix: honor `prefers-reduced-motion` with an instant jump.
*   **Layout shift from** **`display`** **toggling.** Toggling visibility with `display`/`height` or DOM insertion near the viewport edge causes CLS and paint thrash. Fix: animate `opacity`/`transform` on an always-present, `position:fixed` element.

## 13\. Advanced Patterns

*   **TypeScript-enforced accessible API (required-name via discriminated union).** Make it impossible to ship an unnamed icon-only button:

```ts
type Labelled =
  | { children: React.ReactNode; "aria-label"?: string }   // visible text supplies the name
  | { children?: never; "aria-label": string };             // icon-only MUST pass aria-label

export type BackToTopProps = Labelled & {
  targetSelector?: string;
  threshold?: number;
};
// Icon-only with no aria-label now fails to compile.
```

*   **Design-token tiers for fixed UI.** Express placement, elevation, and the stacking order as tokens so every floating control shares one system and can never ambiguously overlap:

```css
:root {
  --z-content: 1;
  --z-sticky-header: 900;
  --z-fixed-utility: 1000;   /* Back to Top lives here */
  --z-fab: 1100;             /* primary FAB always above the utility */
  --z-toast: 1200;
  --space-fixed-offset: clamp(16px, 3vw, 24px);
}
```

*   **Container-scoped Back to Top for virtualized/nested scrollers.** For an in-app scroll container (not the document), observe a sentinel _inside_ the container and call `container.scrollTo({ top: 0 })` plus focus the container's first heading — so "top" is unambiguous even with multiple scroll regions.
*   **Idempotent, interrupt-safe activation.** Because rapid repeat presses all target `top: 0`, the action is naturally idempotent; guard smooth-scroll interruption by allowing a new click to cancel the in-flight animation (`behavior:"auto"` fallback) rather than queueing.

## 14\. Performance & Bundle Cost

*   **IntersectionObserver over scroll listeners.** A `scroll` handler fires continuously and, if it reads `scrollY`/`getBoundingClientRect()`, forces layout during scroll — the worst time. IO computes intersection off the main thread and fires only on threshold crossings. If you _must_ use a scroll listener, throttle with `requestAnimationFrame` (not `setTimeout`) and never read layout synchronously inside it.
*   **Compositor-only animation.** Animate `opacity` and `transform` only — both are GPU-composited and skip layout/paint. Never animate `top`, `height`, `width`, or `box-shadow` spread for the reveal; those thrash paint at the viewport edge and tank INP.
*   **Prefer CSS scroll-driven animation for the reveal.** Moving the reveal to `animation-timeline: scroll()` removes the observer and the React state churn entirely for the visual layer — no re-renders on scroll.
*   **Tree-shaking / import discipline.** Import a single icon (`import { ArrowUp } from "lucide-react"`), never the whole icon set. Keep the component free of heavy scroll/animation libraries — the entire thing is a few dozen lines; a smooth-scroll polyfill or a springs library is unjustified bundle weight for one button.
*   **Mount once, not per route.** Render Back to Top once in the layout/shell so it isn't re-created and re-observed on every navigation; disconnect the observer on unmount to avoid leaks.
*   **Nothing to virtualize here, but don't cause virtualization bugs.** In a virtualized list, don't scan all rows to decide visibility — use the list state's index (`firstVisibleItemIndex`) or a sentinel row, not a manual measure.

## 15\. Security

Back to Top has an almost non-existent attack surface: it's a client-side navigation control that renders no user-supplied content, submits no form, and gates nothing. There is no XSS vector as long as the label is a static string and not interpolated from untrusted input, and no authorization concern because it protects nothing.

The only surfaces worth a sentence: (1) if you make the scroll _target_ configurable from a URL fragment or query param and feed it into `document.querySelector`, validate/allow-list it so a crafted selector can't be abused to focus an unexpected element or throw — never pass raw user input into a selector. (2) If you wire the optional scroll-depth analytics endpoint (§ 9.13), treat the client-reported depth as untrusted: bound it server-side (Pydantic clamps 0–100 in the example), rate-limit the endpoint, and store only aggregates — a malicious client can spam fabricated depth values, so never use them for anything security- or billing-relevant. Beyond that, this component introduces no meaningful risk.

## 16\. Senior-Level Checklist

*   **Semantics:** It's a native `<button type="button">` (or a valid `<a href="#top">`), never a `<div onclick>`.
*   **Accessible name:** Visible text or `aria-label="Back to top"`; icon is `aria-hidden="true"` `focusable="false"`.
*   **Focus management:** On activation, focus moves to a real top target (`h1`/`main`/`#top[tabindex="-1"]`) with `preventScroll:true` — not just the viewport.
*   **Keyboard:** Reachable by `Tab` only when visible; operable with `Enter` and `Space`; removed from tab order when hidden (`visibility:hidden`/`inert`).
*   **Reveal mechanism:** IntersectionObserver on a sentinel (or CSS scroll timeline) — no constantly-firing scroll listener reading layout.
*   **Reduced motion:** `prefers-reduced-motion` → instant jump and no transform transition.
*   **Contrast & target size:** Icon ≥ 4.5:1, silhouette & focus ring ≥ 3:1 non-text, interactive area ≥ 44×44px.
*   **No layout shift:** Toggled via `opacity`/`transform` on a `position:fixed` element; never `display`/`height`/DOM insertion.
*   **No obstruction:** Doesn't cover the FAB, chat widget, sticky CTA, cookie bar, or footer actions; respects `env(safe-area-inset-*)`.
*   **Performance:** Compositor-only animation; single icon import; mounted once in the shell; observer disconnected on unmount.
*   **Right context:** Only rendered on genuinely long pages; suppressed when a persistent nav/sticky header already covers "up."
*   **Focus never orphaned:** Button releases focus if it hides while focused.

## 17\. Visual Styles

The same semantic button — labeled, focusable, 44px, focus management intact — wears any of these skins.

*   **Flat:** A solid Eminence circle, crisp edge, no shadow, flat Goldenrod up-arrow. Reads instantly, cheapest to paint, ideal for content-dense sites where the button shouldn't call attention to itself.
*   **Material:** The circle as a small/mini FAB with layered elevation shadow and a ripple radiating from the tap point; the arrow in a tonal container, lifting one elevation step on hover.
*   **Glassmorphism:** A translucent circle with `backdrop-filter: blur()` letting the article blur through behind the up-arrow — striking over a photographic hero, but verify the arrow keeps 4.5:1 against whatever scrolls behind it.
*   **Liquid Glass (2026):** Apple iOS 26 / Tahoe treatment — the circle as refractive glass with a specular rim highlight and a sheen that shifts as the page moves, the arrow floating inside the material; pill-shaped if a "Top" label is present.
*   **Neumorphism:** The circle extruded from a same-color surface with dual light/dark shadows, the arrow debossed into it. Soft and tactile but contrast-poor — only viable if the arrow itself carries a real accent color, never as the sole affordance.
*   **Skeuomorphism:** A beveled, gradient-filled physical "chip" with an inner top highlight and a carved arrow, pressing inward on `:active` like a real elevator "up" button.
*   **Neo-Brutalism:** A hard-edged square-ish circle with zero-radius option, a thick black border, a 4px offset hard drop shadow, and a clashing Spanish-Orange arrow — the button as a loud, unmissable sticker in the corner.
*   **Claymorphism:** A big-radius, puffy circle with an inner top-light and bottom-shadow and a soft outer glow, the arrow rounded and chunky — friendly and toy-like, at home on playful marketing pages.
*   **Aurora / Gradient:** The circle filled with an animated multi-hue gradient (Eminence→Spanish Orange→Goldenrod) on a dark page, the arrow in Platinum; premium feel, but the gradient animation honors `prefers-reduced-motion`.
*   **Minimal / Swiss:** No circle at all — a small "↑ Top" set in Urbanist, tight tracking, hairline rule or nothing, letting type and whitespace do the work; the entire affordance is typographic.
*   **UJG Brand (house default):** Goldenrod `#DCA424` up-arrow on a deep Eminence `#5F2C82` circle, confident 999px radius, a warm low-spread glow, and a Platinum focus ring — the Urban Jungle Goddess floating utility.

**The rule that never changes:** the style is skin, the behavior is the skeleton. Across all eleven, the button stays a real `<button>` with an accessible name, moves _focus_ to the top and not just the viewport, keeps a visible focus ring, holds its 44px target, and honors `prefers-reduced-motion`. Change the paint; never change the bones.
