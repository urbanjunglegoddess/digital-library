The heaviest interactive component on the web. A spreadsheet living inside your app — and the place where naive builds go to die at 10,000 rows.

## 1\. What a Data Grid Actually Is
A data grid is an **interactive, two-dimensional editing and navigation surface for tabular data** — think of the browser's version of Excel or Google Sheets embedded in your product. The word "grid" hides three very different things people constantly conflate:

*   **Table (presentational):** semantic `<table>` markup that _displays_ rows and columns. Maybe it sorts. It's read-mostly, laid out by the browser, and it uses the ARIA **table** pattern (`role="table"`, or better, native `<table>`). Static pricing tables, invoice line items, a leaderboard. See the sibling [Table](https://app.clickup.com/8495850/docs/838qa-81211/838qa-216811) doc.
*   **Data Grid (interactive widget):** a _composite widget_ the user drives with the keyboard like a spreadsheet — 2D arrow-key navigation, a single roving focus, inline cell editing, range selection, copy/paste. It uses the ARIA **grid** pattern (`role="grid"`/`row`/`gridcell`/`columnheader`/`rowheader`), which is a fundamentally different contract from a table. AG Grid, MUI DataGrid, TanStack Table + a renderer, Glide Data Grid.
*   **Spreadsheet (formula engine):** a data grid _plus_ a cell-reference formula language (`=SUM(A1:A10)`), dependency graph, and recalculation engine. Every spreadsheet is a data grid; not every data grid is a spreadsheet. Building the formula engine is a separate discipline (Handsontable/HyperFormula, Univer, Luckysheet).

**The distinction that trips up the most engineers:** _table pattern vs grid pattern are not interchangeable, and picking the wrong one breaks screen readers._ A `<table>` announces "table, 40 rows, 6 columns" and lets AT users read it with table-navigation commands — but it has **no concept of a focused cell you move with arrow keys**. The moment you want spreadsheet keyboard behavior, you must switch to `role="grid"`, which _takes over_ arrow keys and demands you implement roving `tabindex` yourself. Use the grid role and _don't_ wire the keyboard, and you've built something strictly worse than a plain table: it claims to be operable and isn't.

Rule of thumb: **if the user reads it, it's a Table; if the user drives it cell-by-cell with the keyboard, it's a Data Grid; if it has formulas, it's a Spreadsheet — and each one is a different ARIA contract you cannot fake with a** **`<div>`** **soup.**

## 2\. Why It Matters
The data grid is where your app becomes a _tool_ instead of a _page_. That makes it disproportionately expensive to get wrong:

*   **It's the productivity core of B2B software.** Admin panels, CRMs, analytics dashboards, ERPs, back-office ops — the grid _is_ the product for these users. They live in it eight hours a day. A grid that's 100ms laggy on every keystroke isn't an annoyance; it's a churned enterprise contract. For UJG's Data Alchemy and Command Core suites, the grid is frequently the deliverable.
*   **Performance is a correctness issue, not a nice-to-have.** A table renders 40 rows and nobody notices. A data grid is _expected_ to hold 10k, 100k, a million rows, and the naive "map over the array into `<tr>`" approach mints 6 million DOM nodes and freezes the tab. Virtualization isn't optimization here — it's the price of admission. More on this in §14.
*   **Accessibility is genuinely hard and usually broken.** The grid pattern is one of the most complex in the entire ARIA spec. Custom grids ship with unreachable cells, focus that evaporates after an edit, virtualized bodies that lie to screen readers about row counts, and edits that are never announced. Getting it right is a real competitive moat because so few teams do (§10).
*   **It's a data-integrity surface.** Inline editing means users write to your database through the UI. Validation-in-cell, optimistic updates that roll back, server round-trips for sort/filter/paginate — every one is a place to leak, corrupt, or expose data (§9, §15). A grid that lets a user PATCH a row they don't own is a breach, not a bug.

## 3\. Anatomy of a Data Grid
Every serious grid decomposes into predictable parts. Learn the vocabulary; every library uses these names.

*   **Column definitions (****`colDefs`****):** the schema — field key, header label, width, type, sortable/filterable/editable flags, custom cell renderer, value getter/formatter. This is the heart of the API; a grid is configured, not hand-written.
*   **Header row:** `columnheader` cells. Holds the label, sort indicator, filter affordance, resize handle, reorder drag target, and the pin/menu controls.
*   **Body / viewport:** the scrollable region that holds rows. In a virtualized grid this is a _window_ over the data, not the whole dataset.
*   **Row:** a `row` containing cells. May have a **row header** (`rowheader`) — the sticky first cell that labels the row (an ID, a name) the way a spreadsheet's row number does.
*   **Cell (****`gridcell`****):** the atom. Has a display value, an edit mode, a type, validation state, and selection state. Cells are where 90% of the complexity lives.
*   **Pinned/frozen columns & rows:** columns locked left/right (usually an ID column and an actions column) and rows locked top/bottom (headers, totals) that don't scroll with the body.
*   **Selection layer:** the overlay that renders the selected cell, row, or range highlight and the "active cell" outline — the spreadsheet cursor.
*   **Editing layer:** the input/editor that pops over a cell when you commit to edit (text field, number spinner, select, date picker, custom).
*   **Footer / pagination / status bar:** page controls, row counts, aggregation totals ("Sum: $42,150"), selection summary.
*   **Overlays:** loading skeleton/spinner, "no rows" empty state, column menu, filter popovers, context menu.
*   **The performance spine (invisible):** the virtualizer (windowing), the memoization boundaries, and the row/cell key strategy. You can't see it, but it's the difference between a grid and a frozen tab.

## 4\. Sizes, Scale & Density
Density is the single most requested grid feature from power users — they want more rows on screen, always. Give them a density toggle.

| Density | Row height | Cell padding (V/H) | Font | Use |
| ---| ---| ---| ---| --- |
| Compact | 28px | 2px / 8px | 12px | Power-user data work, trading/ops screens, max rows on screen |
| Standard | 36px | 6px / 12px | 13px | Default for most admin/CRM grids |
| Comfortable | 44px | 10px / 16px | 14px | Touch, casual users, grids with wrapping content |
| Tall / auto | 56px+ | 12px / 16px | 14px | Multiline cells, embedded chips/avatars, cards-in-cells |

Rules that matter:

*   **Fixed row height is a performance decision, not just visual.** A constant `rowHeight` lets the virtualizer compute `scrollTop → firstVisibleRow` with pure arithmetic (`Math.floor(scrollTop / rowHeight)`). Variable/auto height forces measurement and a running offset cache, which is _dramatically_ more code and slower. Default to fixed height; reach for dynamic height only when the content truly demands it.
*   **Touch targets still apply to interactive cells.** Row-action buttons, checkboxes, and editable affordances keep a ≥44px effective hit area even in a 28px compact row — expand the target with padding/pseudo-elements rather than shrinking the button.
*   **Column min-width guards readability.** Below ~48px a column is unreadable; enforce a `minWidth` so resizing can't destroy the layout.
*   **Drive everything from tokens.** Row height, header height, and padding should be spacing tokens so a density switch is a token swap, not a per-cell rewrite.

## 5\. States (where grids get enormous)
A button has ~8 states. A data grid has states at **four levels** — grid, column, row, and cell — and they combine. This is why grids are heavy.

**Grid-level:**
1. **Loading (initial)** — skeleton rows or a spinner overlay; never a blank white box.
2. **Loading (refetch)** — data already shown, a new page/sort/filter is in flight. Show a subtle top progress bar and keep old rows visible (stale-while-revalidate) rather than blanking.
3. **Empty (no data)** — a real empty state with cause + next action ("No orders yet — create one"), not an empty grid.
4. **Empty (filtered to nothing)** — distinct from "no data." "No rows match your filters" + a **Clear filters** button. Confusing these two is a classic UX miss.
5. **Error** — the fetch failed. Inline retry, keep the chrome, don't dump users to a blank screen.

**Column-level:**
6\. **Sorted** (asc/desc, plus **multi-sort priority** badges: `1↑ 2↓`), **filtered** (active-filter indicator), **resizing** (live width + guideline), **reordering** (drag ghost + drop indicator), **pinned** (left/right, with a shadow seam), **hidden**.

**Row-level:**
7\. **Selected** (checkbox + row highlight), **hovered**, **expanded** (master/detail or tree child rows visible), **disabled/read-only**, **new/optimistic** (just added, pending server confirm), **dirty** (edited, unsaved), **error** (a cell in this row failed validation/save).

**Cell-level (the deep end):**
8\. **Default / read** — displaying a formatted value.
9\. **Focused / active** — the spreadsheet cursor; exactly **one** cell owns it, with a visible outline.
10\. **Selected** — part of a range/row/column selection (distinct from focused).
11\. **Editing** — an editor is open over the cell; value is being typed.
12\. **Invalid (in-cell validation)** — the typed value failed a rule; red ring + inline message, and a decision about whether to _block_ commit or allow-and-flag.
13\. **Saving** — the committed edit is round-tripping to the server (spinner in-cell or row-level).
14\. **Save error** — the PATCH failed; revert or keep-and-retry, always announced.

The senior insight: **focused ≠ selected ≠ editing.** These are three independent states a spreadsheet keeps straight (you can have one focused cell inside a 200-cell selection, none of them editing). Collapsing them is the #1 tell of an amateur grid — it's why so many custom grids feel "off" to anyone who's used Excel.

## 6\. Types & Variants
Grids specialize by capability. Most products need a point on this spectrum, not the maximal grid.

*   **Read-only data grid:** sortable/filterable/resizable but not editable. The most common — a queryable view over data. (If it's not even sortable, you want a [Table](https://app.clickup.com/8495850/docs/838qa-81211/838qa-216811).)
*   **Editable grid:** inline cell editing with validation. Now you own optimistic updates, dirty tracking, and server writes.
*   **Tree data / grouping grid:** hierarchical rows (org charts, file trees, BOMs) or runtime row grouping ("group by Region, then Status") with expandable group rows and aggregation.
*   **Master/detail grid:** each row expands to a detail panel or a nested sub-grid.
*   **Pivot grid:** rows _and_ columns are both generated from data dimensions with aggregated measures at the intersections. The heaviest variant.
*   **Spreadsheet grid:** ranges, fill-handle drag, copy/paste blocks, and often a formula engine. Handsontable/Univer territory.
*   **Virtualized / infinite grid:** windowed rendering with infinite scroll or "load more" against a server. Table-stakes for large data.
*   **Server-side row model:** sort, filter, paginate, and group all happen on the server; the grid holds one page at a time. Mandatory past ~100k rows (§9.7).

**Sizing the build:** most teams overbuild. Ask _does the user edit? navigate cell-by-cell? exceed ~1k rows? need Excel copy/paste?_ If the answer to all four is no, you want a sortable [Table](https://app.clickup.com/8495850/docs/838qa-81211/838qa-216811), and you just saved yourself the hardest component in the app.
* * *

## 7\. When to Use One (and When Not To)
Use a data grid when users must **operate on tabular data in place** — edit, navigate cell-by-cell, select ranges, sort by multiple columns, or work through more rows than a page can hold. Do _not_ reach for one when:

*   **The data is presentational.** Read-only rows that at most sort → a semantic [Table](https://app.clickup.com/8495850/docs/838qa-81211/838qa-216811). You get accessibility for free and skip the hardest component in the stack.
*   **There are a handful of records.** Under ~50 rows with no editing, a table or even a list of Cards reads better and ships in an afternoon.
*   **Each record is rich and card-like.** Photos, long descriptions, varied fields per item → a card grid or list, not a cell grid.
*   **It's really a form.** If users edit _one record's many fields_, that's a form, not a grid. Grids are for _many records, few fields each_.
*   **Mobile is the primary surface.** A 12-column grid on a 375px screen is a horizontal-scroll nightmare. On mobile, transform the grid into stacked cards or a prioritized 2–3 column view; don't ship the desktop grid shrunk.

Placement heuristics: give the grid **as much viewport as possible** (it's the workspace); keep filters/search in a sticky toolbar above it; pin the primary identifier column left and the actions column right; keep pagination/status in a sticky footer so users never scroll to find it.

## 8\. Data Grids Across Design Systems
Same widget, very different philosophies and price tags. Knowing these makes you fluent — and keeps you from hand-rolling what you should buy.

*   **AG Grid (the enterprise default):** the 800-lb gorilla. Community (MIT) covers sort/filter/edit/virtualization; **Enterprise** (paid) adds server-side row model, pivoting, grouping, range selection, Excel export, integrated charts. Framework-agnostic core with React/Vue/Angular wrappers. If a client says "make it like Excel," this is usually the answer.
*   **MUI X DataGrid (React, Material):** clean Material look, great DX. **DataGrid** (MIT) is free; **DataGridPro** (paid) adds column pinning, tree data, master/detail; **DataGridPremium** adds row grouping, aggregation, Excel export. The pragmatic choice for React/Material shops.
*   **TanStack Table (headless):** _not_ a grid — a headless _table logic_ engine (sorting, filtering, grouping, pagination, column model) with **zero markup**. You render every cell yourself and pair it with **TanStack Virtual** for windowing. Maximum control, maximum ownership, MIT. The shadcn-era default when you want to own the DOM (§9.3).
*   **Glide Data Grid:** canvas-rendered (not DOM). Handles millions of cells at 60fps because it paints pixels instead of nodes. The escape hatch when DOM virtualization still isn't fast enough — at the cost of reimplementing accessibility yourself, since there's no DOM to expose.
*   **Handsontable / Univer / Luckysheet:** spreadsheet-first — formulas, fill handle, cell merging. Reach for these when users expect _Excel_, not just a grid. (Handsontable is non-free for commercial use; check the license.)
*   **Ant Design Table / Fluent DataGrid / Material Web:** framework-native grids tuned to their design language. Ant's is dense and enterprise-flavored; Fluent's is Microsoft-consistent; good when you're already in that system.
*   **Tailwind / shadcn:** no grid ships in the box — shadcn's "data table" is a _recipe_ pairing TanStack Table + your own Tailwind markup + TanStack Virtual. Full ownership, no license, but you build (and a11y-audit) it yourself.

**The build-vs-buy reality:** a production data grid with virtualization, editing, server-side data, and real accessibility is _months_ of specialist work. For anything past "sortable table," buying (AG Grid / MUI X) or adopting a headless engine (TanStack) is almost always the right call. Hand-rolling from scratch is a decision to make deliberately, usually only when you have a hard reason DOM/canvas libraries can't meet.

## 8b. Visual Styles (the same grid, eleven skins)
Design systems are _whose_ rules; visual styles are _which look_. The same semantic grid wears any of these — and grids stress-test a skin harder than any other component because there are so many surfaces (header, body, row-stripe, pinned seam, selection, focus ring). The **rule that never changes: style is skin, behavior is the skeleton.** Zebra striping, glass headers, and neu-shadows never alter the ARIA grid pattern, the roving `tabindex`, the arrow-key map, or the 44px target. Full guidance lives in the [Design Styles (visual languages)](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200551) doc; the eleven in brief for a grid:

*   **Flat:** hairline row dividers, solid header fill, a subtle row-stripe. Reads instantly, scales to huge datasets, the safe default for data work.
*   **Material:** elevated header, ripple on row/sort click, a shadow seam under pinned columns, bold sort arrows.
*   **Glassmorphism:** translucent frosted header over a colored page; watch text contrast on the blur — data density punishes low contrast fast.
*   **Liquid Glass (the 2026 trend):** Apple's iOS 26 / macOS Tahoe material — a refractive, specular-rimmed sticky header and selection overlay that bends the rows scrolling beneath it. Gorgeous on a pinned header/toolbar; keep the _body_ flat and legible. Web is an honest approximation; SwiftUI emits native `.glassEffect()`.
*   **Neumorphism:** soft same-color extruded headers and cells. Beautiful in a mockup, contrast-poor and impractical for dense data — accent surfaces only.
*   **Skeuomorphism:** the literal ledger/spreadsheet look — beveled cells, inset grid lines, green-bar accounting stripes. Nostalgic, heavy.
*   **Neo-Brutalism:** thick black grid lines, hard offset shadow on the active cell, unapologetic mono headers. High personality for internal tools.
*   **Claymorphism:** rounded, puffy row cards with soft glow. Fights the density a grid wants; reserve for light, card-like grids.
*   **Aurora / Gradient:** animated gradient header band on a dark grid. Premium dashboards; honor `prefers-reduced-motion` and don't animate behind scrolling rows.
*   **Minimal / Swiss:** typography and alignment do all the work — no vertical rules, generous number alignment, a single hairline under the header. The connoisseur's data grid.
*   **UJG Brand:** Goldenrod header text and sort arrows on deep Eminence/Night surfaces, a warm-glow focus ring, Goldenrod selection highlight at low alpha over Dark Green stripes. The Afro-Futurist house look — dark, saturated, and (bonus) dark surfaces make Liquid-Glass header accents sing.

Guard the usual suspects: glass/liquid-glass/neu need a contrast check against real data; aurora/liquid-glass respect `prefers-reduced-motion`; a pinned-column seam needs _some_ visible boundary (shadow or line) in every skin so users see the freeze.

## 9\. The Code
The biggest section, because the grid _is_ mostly code. We'll build up from the raw ARIA skeleton to a virtualized React+TS grid, then the library approaches, then the server contract, then tests.

### 9.1 HTML — the ARIA grid skeleton (the foundation everyone skips)
Before any framework, understand the markup a data grid _must_ produce. This is the **grid** pattern, not the table pattern.

```plain
<!-- Interactive grid: role=grid, NOT a plain table -->
<div role="grid" aria-label="Orders" aria-rowcount="10000" aria-colcount="5">
  <div role="rowgroup">
    <div role="row" aria-rowindex="1">
      <span role="columnheader" aria-colindex="1" aria-sort="ascending" tabindex="-1">Order</span>
      <span role="columnheader" aria-colindex="2" tabindex="-1">Customer</span>
      <span role="columnheader" aria-colindex="3" aria-sort="none" tabindex="-1">Total</span>
    </div>
  </div>
  <div role="rowgroup">
    <!-- aria-rowindex is the ABSOLUTE index in the full dataset, not the DOM -->
    <div role="row" aria-rowindex="42" aria-selected="false">
      <!-- the row's identifying cell is a rowheader, like a spreadsheet row label -->
      <span role="rowheader"  aria-colindex="1" tabindex="-1">UJG-1042</span>
      <span role="gridcell"   aria-colindex="2" tabindex="-1">Acme Co</span>
      <!-- exactly ONE cell in the whole grid is tabindex=0: the roving focus -->
      <span role="gridcell"   aria-colindex="3" tabindex="0">$420.00</span>
    </div>
  </div>
</div>
```

The rules that make this a _grid_ and not a `<div>` costume:

*   **`aria-rowcount`****/****`aria-colcount`** **on the grid,** **`aria-rowindex`****/****`aria-colindex`** **on rows/cells.** In a _virtualized_ grid the DOM holds ~30 rows but the data has 10,000 — these attributes tell the screen reader the _real_ totals and the _absolute_ position, so it announces "row 42 of 10,000" instead of "row 3 of 30." Omitting them is the single most common virtualized-grid a11y bug.
*   **Exactly one cell has** **`tabindex="0"`****\*\*\*\*\*\*\*\*; every other is** **`tabindex="-1"`****\*\*\*\*\*\*\*\*.** This is **roving tabindex**: the grid is one Tab stop; arrow keys move the `0` around inside it. (Same pattern as the Button doc's toolbar, scaled to 2D.)
*   **The identifying cell is** **`role="rowheader"`****\*\*\*\*\*\*\*\*,** the rest `role="gridcell"`. Column labels are `role="columnheader"` with `aria-sort`.
*   **Sortable column headers must be keyboard-reachable.** Give each `columnheader` `tabindex="-1"` so it joins the roving tabindex (arrowing up into the header row reaches it), and activate the sort with Enter/Space. A sortable header behind a mouse-only `onClick` with no tabindex is unreachable by keyboard.
*   **Native** **`<table>`** **markup can also carry the grid role** (`<table role="grid">`), and for accessibility that's often _better_ because you inherit table semantics — but you still own the keyboard and roving focus yourself.

### 9.2 CSS — sticky header, pinned columns, states done right
The grid's layout is a CSS problem before it's a JS one. CSS Grid + `position: sticky` does the structural heavy lifting.

```css
.grid {
  display: grid;
  /* pinned-left | flexible middle | pinned-right, driven by tokens */
  grid-template-columns: 120px repeat(var(--col-count), minmax(96px, 1fr)) 88px;
  overflow: auto;
  max-block-size: 70vh;
  --row-h: 36px;
  contain: content;             /* layout+paint+style isolation, but NOT size — `strict` adds size containment and collapses the grid to 0 height (see §14) */
}

/* Sticky header row */
.grid [role="columnheader"] {
  position: sticky;
  inset-block-start: 0;
  z-index: 2;
  background: var(--grid-header-bg);
}

/* Pinned first + last columns */
.grid .pin-left  { position: sticky; inset-inline-start: 0;  z-index: 1; background: var(--grid-bg); }
.grid .pin-right { position: sticky; inset-inline-end: 0;    z-index: 1; background: var(--grid-bg); }
.grid .pin-left  { box-shadow: 2px 0 0 var(--seam); }   /* the freeze seam users need to SEE */

/* Cell states */
.grid [role="gridcell"] { block-size: var(--row-h); padding: 0 12px; display: flex; align-items: center; }
.grid [role="row"]:nth-child(even) [role="gridcell"] { background: var(--stripe); }
.grid [role="row"][aria-selected="true"] [role="gridcell"] { background: var(--row-selected); }

/* The active-cell cursor — keyboard focus only */
.grid [role="gridcell"]:focus-visible,
.grid [role="rowheader"]:focus-visible {
  outline: 2px solid var(--focus);       /* UJG Goldenrod */
  outline-offset: -2px;                   /* inset so it doesn't clip under sticky neighbors */
  z-index: 3;
}
/* Range/selection layer */
.grid .cell--in-range { background: color-mix(in oklch, var(--focus) 18%, transparent); }
/* Validation-in-cell */
.grid .cell--invalid { box-shadow: inset 0 0 0 2px var(--danger); }

@media (prefers-reduced-motion: reduce) {
  .grid, .grid * { transition: none !important; scroll-behavior: auto; }
}
```

Note `outline-offset: -2px` on the focus ring — a grid's cells sit flush against sticky headers and pinned columns, so an _outset_ ring gets clipped. Inset it. This is the kind of detail that separates a grid that _looks_ focused from one that actually shows the cursor.

### 9.3 React + TypeScript — a virtualized, keyboard-navigable grid (the core build)
This is the longest block because it's the real thing: windowed rendering + roving 2D focus + inline edit. It uses `@tanstack/react-virtual` for windowing; the keyboard model is hand-built so you can see exactly what a grid owes the user.

```plain
import { useRef, useState, useCallback, useEffect, useId, KeyboardEvent } from "react";
import { useVirtualizer } from "@tanstack/react-virtual";

type Row = Record<string, string | number>;
interface Column<T> {
  key: keyof T & string;
  header: string;
  width: number;
  editable?: boolean;
  validate?: (v: string) => string | null; // return error message or null
}

interface DataGridProps<T extends Row> {
  columns: Column<T>[];
  rows: T[];
  rowHeight?: number;
  onCommit?: (rowIndex: number, key: keyof T & string, value: string) => Promise<void>;
}

export function DataGrid<T extends Row>({
  columns, rows, rowHeight = 36, onCommit,
}: DataGridProps<T>) {
  const scrollRef = useRef<HTMLDivElement>(null);
  // The single source of truth for the roving focus: {row, col} in ABSOLUTE coords.
  const [active, setActive] = useState({ row: 0, col: 0 });
  const [editing, setEditing] = useState<{ row: number; col: number } | null>(null);
  const [draft, setDraft] = useState("");
  const [error, setError] = useState<string | null>(null);
  const errorId = useId();                 // stable id to wire aria-describedby on invalid cells
  const cancelledRef = useRef(false);      // set on Escape so the editor's onBlur (which fires on unmount) doesn't SAVE the draft
  const movedRef = useRef(false);          // becomes true on the first user navigation; gates auto-focus so mount doesn't steal page focus

  const rowVirtualizer = useVirtualizer({
    count: rows.length,
    getScrollElement: () => scrollRef.current,
    estimateSize: () => rowHeight,   // fixed height => O(1) math, no measurement
    overscan: 8,                     // render a few extra rows above/below for smooth scroll
  });

  // Relative move — a PURE updater (no side-effects inside setState); scrolling lives in the effect below.
  const move = useCallback((dRow: number, dCol: number) => {
    movedRef.current = true;
    setActive(({ row, col }) => ({
      row: Math.max(0, Math.min(rows.length - 1, row + dRow)),
      col: Math.max(0, Math.min(columns.length - 1, col + dCol)),
    }));
  }, [rows.length, columns.length]);

  // Absolute jumps (Home / End / Ctrl+Home / Ctrl+End) all go through one clamped helper.
  const goTo = useCallback((row: number, col: number) => {
    movedRef.current = true;
    setActive({
      row: Math.max(0, Math.min(rows.length - 1, row)),
      col: Math.max(0, Math.min(columns.length - 1, col)),
    });
  }, [rows.length, columns.length]);

  // Keep the active row scrolled into the virtual window — as an EFFECT, not a side-effect
  // buried in the setActive updater (impure updaters double-fire in StrictMode). This is what
  // makes Home/End/Ctrl+Home/Ctrl+End land on a rendered cell instead of dropping focus to <body>.
  useEffect(() => {
    rowVirtualizer.scrollToIndex(active.row, { align: "auto" });
  }, [active.row, rowVirtualizer]);

  const commit = useCallback(async () => {
    if (cancelledRef.current) { cancelledRef.current = false; return; } // Escape cancelled the edit: discard the draft, never save
    if (!editing) return;
    const col = columns[editing.col];
    const err = col.validate?.(draft) ?? null;
    if (err) { setError(err); return; }        // block commit on invalid
    setError(null);
    const target = editing;
    setEditing(null);
    await onCommit?.(target.row, col.key, draft); // may optimistically update + round-trip
  }, [editing, draft, columns, onCommit]);

  const onKeyDown = (e: KeyboardEvent<HTMLDivElement>) => {
    if (editing) {
      if (e.key === "Enter") { e.preventDefault(); commit().then(() => move(1, 0)); }
      // CANCEL, don't commit: flag the cancel so the input's onBlur bails out of commit on unmount.
      if (e.key === "Escape") { e.preventDefault(); cancelledRef.current = true; setEditing(null); setError(null); }
      return; // let the editor input handle typing
    }
    switch (e.key) {
      case "ArrowDown":  e.preventDefault(); move(1, 0); break;
      case "ArrowUp":    e.preventDefault(); move(-1, 0); break;
      case "ArrowRight": e.preventDefault(); move(0, 1); break;
      case "ArrowLeft":  e.preventDefault(); move(0, -1); break;
      case "Home":       e.preventDefault(); e.ctrlKey ? goTo(0, 0) : goTo(active.row, 0); break;
      case "End":        e.preventDefault(); e.ctrlKey ? goTo(rows.length - 1, columns.length - 1) : goTo(active.row, columns.length - 1); break;
      case "PageDown":   e.preventDefault(); move(20, 0); break;
      case "PageUp":     e.preventDefault(); move(-20, 0); break;
      case "Enter": case "F2": {
        const col = columns[active.col];
        if (col.editable) { e.preventDefault(); cancelledRef.current = false; setDraft(String(rows[active.row][col.key] ?? "")); setEditing(active); }
        break;
      }
    }
  };

  return (
    <div
      ref={scrollRef}
      role="grid"
      aria-label="Data"
      aria-rowcount={rows.length + 1}      /* +1 for the header row */
      aria-colcount={columns.length}
      tabIndex={0}
      onKeyDown={onKeyDown}
      style={{ overflow: "auto", maxHeight: "70vh", position: "relative" }}
    >
      {/* Header rowgroup (row index 1) — the rowgroup preserves grid -> row ownership (aria-required-children) */}
      <div role="rowgroup">
        <div role="row" aria-rowindex={1} style={{ display: "flex", position: "sticky", top: 0, zIndex: 2 }}>
          {columns.map((c, ci) => (
            <span role="columnheader" aria-colindex={ci + 1} key={c.key}
                  style={{ width: c.width, flex: "0 0 auto", fontWeight: 600 }}>
              {c.header}
            </span>
          ))}
        </div>
      </div>

      {/* Virtualized body rowgroup: only ~30 rows exist in the DOM at once. The sizing div carries
          role="rowgroup" so the virtualized rows stay owned by the grid instead of a bare <div>. */}
      <div role="rowgroup" style={{ height: rowVirtualizer.getTotalSize(), position: "relative" }}>
        {rowVirtualizer.getVirtualItems().map((vRow) => {
          const r = vRow.index;
          return (
            <div role="row" key={vRow.key}
                 aria-rowindex={r + 2}          /* +2: header is 1, data is 1-based after it */
                 style={{ position: "absolute", top: vRow.start, height: vRow.size, display: "flex", width: "100%" }}>
              {columns.map((c, ci) => {
                const isActive = active.row === r && active.col === ci;
                const isEditing = editing?.row === r && editing?.col === ci;
                return (
                  <span role={ci === 0 ? "rowheader" : "gridcell"} key={c.key}
                        aria-colindex={ci + 1}
                        aria-invalid={isEditing && !!error}
                        aria-describedby={isEditing && error ? errorId : undefined}
                        tabIndex={isActive ? 0 : -1}     /* ROVING tabindex */
                        /* Re-assert focus after the virtualizer remounts the row — but ONLY after the
                           user has navigated, so mount doesn't yank page focus onto cell {0,0}. */
                        ref={(el) => { if (isActive && !isEditing && movedRef.current) el?.focus(); }}
                        onClick={() => { movedRef.current = true; setActive({ row: r, col: ci }); }}
                        onDoubleClick={() => c.editable && (cancelledRef.current = false, setDraft(String(rows[r][c.key] ?? "")), setEditing({ row: r, col: ci }))}
                        style={{ width: c.width, flex: "0 0 auto", padding: "0 12px",
                                 outline: isActive ? "2px solid var(--focus, #DCA424)" : "none", outlineOffset: -2 }}>
                    {isEditing ? (
                      <input autoFocus value={draft} aria-label={`Edit ${c.header}`}
                             aria-invalid={!!error}
                             aria-describedby={error ? errorId : undefined}
                             onChange={(e) => setDraft(e.target.value)}
                             onBlur={commit}
                             style={{ width: "100%", font: "inherit" }} />
                    ) : String(rows[r][c.key] ?? "")}
                  </span>
                );
              })}
            </div>
          );
        })}
      </div>

      {/* Announce edits/errors to screen readers without moving focus. The id also wires
          aria-describedby on the invalid cell + its editor, so the error text is read on the cell. */}
      <div id={errorId} aria-live="polite" style={{ position: "absolute", width: 1, height: 1, overflow: "hidden", clip: "rect(0 0 0 0)" }}>
        {error ?? ""}
      </div>
    </div>
  );
}
```

Why this is the senior version, not the junior one:

*   **The roving focus is a single** **`{row, col}`** **in absolute coordinates**, and exactly one cell gets `tabindex={0}` + `.focus()`. That's the whole spreadsheet-cursor model. Everything else — selection, range, editing — layers on top of this one idea.
*   **Focus follows the virtualizer.** A `useEffect` keyed on the active row calls `scrollToIndex` — kept _out_ of the `setActive` updater so it stays a pure side-effect (an impure updater double-fires in StrictMode) — so arrowing down, PageDown, or Ctrl+End scrolls the new active row into the window before the `ref` callback re-focuses it. Without the scroll, Home/End/Ctrl+Home/Ctrl+End target a row that isn't rendered and focus silently drops to `<body>` — _the bug that kills 90% of hand-rolled grids._ The `ref` re-asserts focus after the virtualizer remounts the row, but **only after the user has navigated** (a `movedRef` gate), so mounting the grid doesn't steal page focus onto cell {0,0} (WCAG 3.2.1).
*   **`aria-rowcount`****/****`aria-colcount`****/****`aria-rowindex`** **reflect the FULL dataset**, not the ~30 rendered rows. Without this, AT users are told the grid has 30 rows. This is the non-negotiable virtualization-a11y contract.
*   **Fixed** **`rowHeight`** **→** **`estimateSize`** **is O(1).** No per-row measurement, no offset cache. This is _why_ it stays smooth at 100k rows.
*   **Edit is a separate state with its own commit/validate path**, and Enter commits-then-moves-down (the spreadsheet muscle memory). Escape _cancels_ — because the editor's `onBlur` also fires when the input unmounts, a `cancelledRef` set in the Escape branch makes `commit` bail out so the discarded draft is never saved; focus returns to the cell. Invalid blocks commit, sets `aria-invalid`, and announces via the `aria-live` region wired to the cell through `aria-describedby`.

This ~120-line component is a _starting skeleton_. Range selection, copy/paste, column resize/reorder/pin, and multi-sort each add real code on top — which is exactly why most teams reach for a library (§9.5).

### 9.4 Vanilla JS — event delegation for a grid
A grid may render thousands of cells; you never bind thousands of listeners. **One delegated listener** on the grid container handles clicks and keys, reading coordinates off `data-*` attributes.

```plain
const grid = document.querySelector('[role="grid"]');
let active = { row: 0, col: 0 };

grid.addEventListener("click", (e) => {
  const cell = e.target.closest('[role="gridcell"],[role="rowheader"]');
  if (!cell) return;
  active = { row: +cell.dataset.row, col: +cell.dataset.col };
  focusActive();                      // move the single tabindex=0
});

grid.addEventListener("keydown", (e) => {
  const map = { ArrowDown:[1,0], ArrowUp:[-1,0], ArrowRight:[0,1], ArrowLeft:[0,-1] };
  const delta = map[e.key];
  if (!delta) return;
  e.preventDefault();                 // stop the grid from scrolling the page
  active = { row: active.row + delta[0], col: active.col + delta[1] };
  focusActive();
});

function focusActive() {
  grid.querySelectorAll('[tabindex="0"]').forEach((c) => (c.tabIndex = -1));
  const next = grid.querySelector(`[data-row="${active.row}"][data-col="${active.col}"]`);
  if (next) { next.tabIndex = 0; next.focus(); next.scrollIntoView({ block: "nearest" }); }
}
```

One listener, N cells. Works for dynamically-virtualized rows because it queries by coordinate at event time rather than holding stale references. This is the same delegation economy the Button doc argues for, and in a grid it's the difference between one closure and ten thousand.

### 9.5 TanStack Table + TanStack Virtual (the headless standard)
The modern "own your DOM" approach: TanStack Table computes the table _model_ (sorting, filtering, grouping, column sizing, pagination); TanStack Virtual windows the rows; you render the markup. This is what shadcn's "data table" recipe is under the hood.

```plain
import {
  useReactTable, getCoreRowModel, getSortedRowModel,
  getFilteredRowModel, flexRender, type ColumnDef, type SortingState,
} from "@tanstack/react-table";
import { useVirtualizer } from "@tanstack/react-virtual";
import { useRef, useState } from "react";

export function TanstackGrid<T>({ data, columns }: { data: T[]; columns: ColumnDef<T>[] }) {
  const [sorting, setSorting] = useState<SortingState>([]);  // multi-sort array => priority order
  const table = useReactTable({
    data, columns, state: { sorting }, onSortingChange: setSorting,
    getCoreRowModel: getCoreRowModel(),
    getSortedRowModel: getSortedRowModel(),
    getFilteredRowModel: getFilteredRowModel(),
    enableMultiSort: true,          // shift-click a header to add a secondary sort
  });

  const parentRef = useRef<HTMLDivElement>(null);
  const rows = table.getRowModel().rows;
  const virtualizer = useVirtualizer({
    count: rows.length, getScrollElement: () => parentRef.current,
    estimateSize: () => 36, overscan: 10,
  });

  return (
    <div ref={parentRef} role="grid" style={{ overflow: "auto", height: "70vh" }}>
      {table.getHeaderGroups().map((hg) => (
        <div role="row" key={hg.id} style={{ display: "flex", position: "sticky", top: 0 }}>
          {hg.headers.map((h) => (
            <span role="columnheader" key={h.id}
                  aria-sort={h.column.getIsSorted() === "asc" ? "ascending"
                           : h.column.getIsSorted() === "desc" ? "descending" : "none"}
                  onClick={h.column.getToggleSortingHandler()}   /* shift-click => multi-sort */
                  style={{ cursor: "pointer", userSelect: "none" }}>
              {flexRender(h.column.columnDef.header, h.getContext())}
              {{ asc: " ↑", desc: " ↓" }[h.column.getIsSorted() as string] ?? ""}
            </span>
          ))}
        </div>
      ))}
      <div style={{ height: virtualizer.getTotalSize(), position: "relative" }}>
        {virtualizer.getVirtualItems().map((vi) => {
          const row = rows[vi.index];
          return (
            <div role="row" key={row.id}
                 style={{ position: "absolute", top: vi.start, height: vi.size, display: "flex", width: "100%" }}>
              {row.getVisibleCells().map((cell) => (
                <span role="gridcell" key={cell.id}>
                  {flexRender(cell.column.columnDef.cell, cell.getContext())}
                </span>
              ))}
            </div>
          );
        })}
      </div>
    </div>
  );
}
```

What TanStack gives you _free_: multi-column sort (the `sorting` array is literally the priority order — shift-click appends), filtering, column visibility/sizing, grouping/pagination models. What it does **not** give you: any markup, the roving-tabindex keyboard model, or ARIA — you own all of §9.1/§9.3's keyboard code on top. That's the headless bargain: total control, total responsibility.

### 9.7 The Server-Side Row Model (Node & Python endpoints)
Past ~100k rows you cannot ship the dataset to the browser — sort, filter, and paginate must happen on the **server**, and the grid round-trips one page at a time. The grid sends a _request describing the view_; the server returns _just that slice_ plus a total count.

**The request the grid sends:**

```sql
GET /api/orders?start=200&limit=100
    &sort=total:desc,customer:asc          // multi-sort, priority left->right
    &filter[status]=Paid&filter[total_gte]=100
```

**Node / Express endpoint — the safe version:**

```plain
import { z } from "zod";

// Allow-lists: the ONLY defense against SQL injection via sort/filter columns.
const SORTABLE = new Set(["order", "customer", "total", "status", "created_at"]);
const FILTERABLE = new Set(["status", "customer"]);

const Query = z.object({
  start: z.coerce.number().int().min(0).default(0),
  limit: z.coerce.number().int().min(1).max(200).default(100),   // CAP the page size
  sort: z.string().optional(),
});

app.get("/api/orders", requireAuth, async (req, res) => {
  const q = Query.safeParse(req.query);
  if (!q.success) return res.status(422).json(q.error.issues);

  // Parse "total:desc,customer:asc" -> validated ORDER BY, column names allow-listed.
  // Omitted sort -> default; empty `sort=` or an unlisted column -> 422 (a client error), NEVER a 500 throw.
  if (q.data.sort !== undefined && q.data.sort.trim() === "") {
    return res.status(422).json({ error: "empty sort parameter" });
  }
  const orderParts: string[] = [];
  for (const seg of (q.data.sort ?? "created_at:desc").split(",")) {
    const [col, dir] = seg.split(":");
    if (!SORTABLE.has(col)) return res.status(422).json({ error: `bad sort column: ${col}` }); // reject, don't interpolate
    orderParts.push(`${col} ${dir === "asc" ? "ASC" : "DESC"}`);        // dir is a fixed enum, safe
  }
  const orderBy = orderParts.join(", ");

  // Filters -> PARAMETERIZED where clause. Never string-concat user values.
  // Express's default `qs` parser turns filter[status]=Paid into req.query.filter = { status: "Paid" },
  // so read the nested object directly — the old /^filter\[(\w+)\]$/ test against a flat key never matched.
  const where = ["org_id = $1"];      // tenant scoping: users only see THEIR org
  const params: unknown[] = [req.user.orgId];
  for (const [col, val] of Object.entries((req.query.filter ?? {}) as Record<string, unknown>)) {
    if (FILTERABLE.has(col)) { params.push(val); where.push(`${col} = $${params.length}`); }
  }

  const sql = `SELECT *, count(*) OVER() AS _total FROM orders
               WHERE ${where.join(" AND ")}
               ORDER BY ${orderBy}
               LIMIT $${params.length + 1} OFFSET $${params.length + 2}`;
  const { rows } = await db.query(sql, [...params, q.data.limit, q.data.start]);

  res.json({ rows, total: rows[0]?._total ?? 0, start: q.data.start });
});
```

**Python / FastAPI equivalent:**

```python
from fastapi import FastAPI, Depends, HTTPException, Query
from sqlalchemy import text

SORTABLE = {"order", "customer", "total", "status", "created_at"}
FILTERABLE = {"status", "customer"}

@app.get("/api/orders")
def list_orders(
    start: int = Query(0, ge=0),
    limit: int = Query(100, ge=1, le=200),          # cap the page
    sort: str = "created_at:desc",
    status: str | None = None,
    user=Depends(require_auth),
):
    order_parts = []
    for seg in sort.split(","):
        col, _, direction = seg.partition(":")
        if col not in SORTABLE:                      # allow-list or reject
            raise HTTPException(400, f"bad sort column: {col}")
        order_parts.append(f"{col} {'ASC' if direction == 'asc' else 'DESC'}")

    where = ["org_id = :org"]                        # tenant isolation
    params = {"org": user.org_id, "limit": limit, "start": start}
    if status and "status" in FILTERABLE:
        where.append("status = :status"); params["status"] = status

    sql = text(f"""SELECT *, count(*) OVER() AS _total FROM orders
                   WHERE {' AND '.join(where)}
                   ORDER BY {', '.join(order_parts)}
                   LIMIT :limit OFFSET :start""")     # cols are allow-listed; values parameterized
    rows = db.execute(sql, params).mappings().all()
    return {"rows": rows, "total": rows[0]["_total"] if rows else 0, "start": start}
```

**The security note that makes or breaks this endpoint:** a grid's sort/filter come straight from the client, and column names _cannot_ be parameterized (they're SQL identifiers, not values). So **column names go through an allow-list Set; filter values go through parameterized queries.** Skip the allow-list and interpolate the sort column, and you've built `ORDER BY {anything the attacker types}` — a live SQL-injection hole. Two more non-negotiables baked into the code above: **cap the page size** (`limit <= 200`, or a malicious `limit=10000000` DoSes your DB), and **scope every query to the tenant** (`org_id = user.org`) so a user can't page into another customer's rows by changing `start`. More in §15.

Keyset (cursor) pagination — `WHERE (total, id) < ($lastTotal, $lastId)` — beats `OFFSET` for deep pages and infinite scroll, because `OFFSET 500000` still scans and discards half a million rows. Use offset for jump-to-page UIs, keyset for infinite scroll.

### 9.8 Next.js (App Router: server data, client interaction)
Next splits cleanly: fetch the first page in a **Server Component** (fast, cached, no client JS for data), hand it to a **Client Component** grid that owns interaction and refetches subsequent pages.

```plain
// app/orders/page.tsx  — Server Component: initial data on the server
import { OrdersGrid } from "./OrdersGrid";
export default async function Page() {
  const first = await fetch(`${process.env.API}/api/orders?start=0&limit=100`,
    { cache: "no-store" }).then((r) => r.json());

}

// app/orders/OrdersGrid.tsx  — Client Component: sort/filter/scroll round-trips
"use client";
import { useState } from "react";
export function OrdersGrid({ initial, total }: { initial: Row[]; total: number }) {
  const [rows, setRows] = useState(initial);
  async function loadPage(start: number, sort: string) {
    const res = await fetch(`/api/orders?start=${start}&limit=100&sort=${sort}`);
    const page = await res.json();
    setRows((prev) => [...prev, ...page.rows]);      // append for infinite scroll
```

The win: the first paint is server-rendered and instant; only interaction ships JS. The grid itself _must_ be a Client Component (it has state and `onKeyDown`), but the data contract lives in the server layer.

### 9.9 Vue, Svelte, Angular (same skeleton, different syntax)
The `role="grid"` markup, roving tabindex, and virtualization concepts are identical; only the reactivity syntax changes. Each ecosystem also has mature grid libraries so you rarely hand-roll.

**Vue 3** — headless via `@tanstack/vue-table` + `@tanstack/vue-virtual`, or drop in **AG Grid Vue** / **Vuetify's** **`v-data-table-virtual`**:

**Svelte** — `@tanstack/svelte-table` + `@tanstack/svelte-virtual`, or **svelte-headless-table**. State is just reactive `let`s; the `role="grid"` element gets `on:keydown`.

**Angular** — first-class **AG Grid Angular** (`<ag-grid-angular>`) is the default, or the CDK `cdk-virtual-scroll-viewport` for the windowing primitive plus your own grid semantics. Angular Material's table adds sorting/paging but is closer to a Table than a full Data Grid.

The through-line: every ecosystem gives you (a) a headless model engine, (b) a virtualization primitive, and (c) a batteries-included commercial grid. Pick the layer that matches how much control you need — and never re-derive virtualization by hand unless you must.

### 9.10 Web Component (framework-agnostic)
A grid exposed as a custom element so _any_ stack can drop it in. Real production grids (AG Grid included) ship framework-agnostic cores exactly so they can render anywhere.

```plain
class UIDataGrid extends HTMLElement {
  static observedAttributes = ["rowheight"];
  #rows = [];
  set rows(v) { this.#rows = v; this.#render(); }   // property, not attribute, for array data
  connectedCallback() {
    this.attachShadow({ mode: "open" });
    this.shadowRoot.addEventListener("keydown", this.#onKey);   // one delegated listener
    this.#render();
  }
  #onKey = (e) => { /* roving 2D nav, identical model to §9.4 */ };
  #render() {
    this.shadowRoot.innerHTML = `<style>/* scoped grid CSS, no leakage */</style>
      <div role="grid" tabindex="0" aria-rowcount="${this.#rows.length}"><!-- virtualized rows --></div>`;
  }
}
customElements.define("ui-data-grid", UIDataGrid);
// Usage anywhere: const g = document.querySelector("ui-data-grid"); g.rows = data;
```

Note the array data comes in via a **property** (`g.rows = data`), not an attribute — attributes are strings and serializing 10k rows through the DOM would be absurd. Shadow DOM scopes the grid's dense CSS so it can't leak into or be broken by the host page.

**Jetpack Compose (Android)** — `LazyColumn` (virtualized rows) with a `Row` per record, or `LazyVerticalGrid` for cell grids. `LazyColumn` _is_ the virtualizer — it only composes visible items.

**Flutter** — `DataTable` for small sets; for large data, `Table` or a `ListView.builder` (lazy) of row widgets, or the `two_dimensional_scrollables` `TableView` for true 2D virtualized scrolling.

The through-line: every platform ships a **lazy/virtualized list** primitive (`LazyColumn`, `List`, `ListView.builder`) — that's your row virtualization for free. Real 2D cell-grid behavior with sticky headers and pinned columns is more work and often the signal to switch to a card layout on small screens.

A grid is behavior at scale, so test the behavior a user relies on — keyboard navigation, editing, sort/filter round-trips, and virtualization correctness — not cell class names.

## 10\. Accessibility (the hard part — and the moat)
Custom grids are one of the most-failed patterns in all of web accessibility. Getting this right is genuinely hard and genuinely rare, which makes it worth real engineering time.

**Roles & structure:**
*   `role="grid"` on the container (or `<table role="grid">`), `role="row"` on rows, `role="columnheader"`/`role="rowheader"` on headers, `role="gridcell"` on cells. A `role="rowgroup"` wraps header vs body.
*   **`aria-rowcount`** **/** **`aria-colcount`** on the grid and **`aria-rowindex`** **/** **`aria-colindex`** on rows/cells — set to the **full dataset totals and absolute positions**, because in a virtualized grid the DOM is lying about how much data exists. This is the single most important — and most skipped — grid-a11y attribute set.
*   `aria-sort="ascending|descending|none"` on the sorted column header. For multi-sort, also expose priority in the accessible name ("Total, sorted ascending, sort priority 2").
*   `aria-selected="true"` on selected rows/cells; `aria-expanded` on group/tree parent rows; `aria-level`/`aria-posinset`/`aria-setsize` for tree data depth.

**Keyboard map (the ARIA grid pattern — memorize this):**

| Key | Action |
| ---| --- |
| Arrow keys | Move the focused cell one cell in that direction (2D) |
| Tab / Shift+Tab | Move out of the grid to the next widget — the whole grid is one tab stop |
| Home / End | First / last cell in the row |
| Ctrl+Home / Ctrl+End | First cell of first row / last cell of last row |
| PageUp / PageDown | Scroll a viewport of rows and move focus |
| Enter / F2 | Enter edit mode on the focused cell |
| Escape | Cancel the edit, restore the value, keep focus on the cell |
| Enter (in edit) | Commit and move down one cell (spreadsheet muscle memory) |
| Shift+Arrow | Extend a cell range selection |
| Ctrl+A / Ctrl+C / Ctrl+V | Select all / copy / paste the range |
| Space | Toggle row selection (when the grid supports it) |

**Focus management — where grids die:**
*   **Roving tabindex, not managed-nothing.** Exactly one cell has `tabindex="0"`; arrows move it; everything else is `-1`. Never leave all cells tabbable (traps keyboard users) and never leave none focusable (unreachable).
*   **Focus MUST survive virtualization.** When the active row scrolls out and its DOM node is recycled, you must re-assert focus onto the active cell (the `ref`\-callback trick in §9.3). The failure mode — focus silently drops to `<body>`, the user loses their place — is the #1 real-world grid a11y bug.
*   **Focus MUST survive an edit commit.** After Enter commits, focus returns to a _cell_ (usually the one below), never vanishes into the void.

**Announcing changes:**
*   Edits, validation errors, sort changes, and "loaded 100 more rows" should be announced via an `aria-live="polite"` region _without_ moving focus. A silent grid leaves screen-reader users guessing whether their edit took.
*   Editable cells need an accessible name on the editor (`aria-label="Edit Total"`), and invalid cells set `aria-invalid="true"` with the error text wired via `aria-describedby`.

**Contrast & targets:** cell text ≥ 4.5:1; the active-cell outline and selection highlight must be visible against every row-stripe and skin; interactive cell affordances (checkboxes, action buttons) keep a ≥44px effective target even in compact rows; **never signal validity by color alone** — pair the red ring with an icon/text.

The honest summary: a fully accessible custom data grid is _hard_ — it's why buying AG Grid / MUI X (which ship this) is often the accessible choice. If you build your own, budget real time for the keyboard model and test it with an actual screen reader, not just axe.

## 11\. Innovative & Emerging Ideas (2026-aware)
The grid looks solved but is moving fast:

*   **Canvas & GPU rendering:** Glide Data Grid and newcomers paint cells to `<canvas>`/WebGL instead of the DOM, holding _millions_ of cells at 60fps — the escape hatch when DOM virtualization taps out. The tradeoff is you re-implement accessibility and text selection by hand.
*   **AI-native grids:** natural-language query ("show me Q3 orders over $500, grouped by region"), AI-suggested cell fills, auto-detected column types, and "explain this row" popovers. The grid becomes a conversational data surface, not just a table.
*   **Real-time collaborative grids:** multiplayer cursors, presence, and CRDT/OT-backed live cell sync (Liveblocks, Yjs) — Google-Sheets-style co-editing embedded in products.
*   **Server-driven / streaming grids:** rows stream in over WebSocket/SSE as they compute; the grid renders partial results progressively instead of blocking on a full page.
*   **Spatial / Liquid-Glass chrome:** iOS 26-style refractive sticky headers and floating toolbars that bend the data scrolling beneath (skin only — the grid pattern underneath is unchanged).
*   **Wasm data engines:** DuckDB-Wasm / Arrow in the browser lets the grid sort/filter/aggregate _millions_ of rows client-side without a server round-trip, blurring the client/server row-model line.
*   **Auto-density & responsive transforms:** grids that detect touch vs. mouse and viewport, switching density and collapsing to card layouts automatically.

## 12\. Conversion / UX Killers (the silent grid failures)
None of these throw an error. They just make power users quietly hate your product and churn.

*   **No virtualization.** The cardinal sin. It works in the demo with 50 rows, ships, and freezes the tab the day a real customer loads 20,000. Virtualize from day one if the row count is unbounded.
*   **Blanking on refetch.** Sorting or filtering wipes the grid to white for 400ms, then repaints. It reads as broken. Keep the old rows visible with a subtle loading bar (stale-while-revalidate).
*   **Losing focus/scroll on update.** The user edits row 4,000, the grid refetches, and they're slammed back to row 1. Preserve scroll position and focused cell across data updates.
*   **Editing with no feedback.** User types a value, tabs away, nothing signals whether it saved. No spinner, no toast, no dirty indicator. They don't trust it and re-check in the database. Show saving → saved → (or) error, always.
*   **Silent validation.** An invalid edit is accepted and silently dropped, or rejected with no message. Either way the user's data "disappears." Validate in-cell, block or flag visibly, announce it.
*   **Horizontal scroll with no pinned column.** 15 columns, the user scrolls right, and loses track of _which row is which_ because the ID column scrolled away. Pin the identifier column left.
*   **Confusing "empty" states.** "No data" and "no rows match your filters" look identical, so a user with an over-tight filter thinks their data is _gone_. Distinguish them and offer **Clear filters**.
*   **Sort that doesn't say it's sorting.** Click a header, 800ms pass, no spinner, no arrow — the user clicks again and re-toggles the sort. Show the sort arrow + a pending indicator immediately.
*   **Everything editable by default.** Read-only fields that look editable (or vice-versa) waste clicks and erode trust. Make editability visually obvious.

The through-line, same as the Button doc: these fail _quietly_. No crash, just a grid that feels sluggish and untrustworthy — and B2B users who live in the grid all day notice within minutes.

## 13\. Advanced Patterns
The senior-move versions of grid features.

**Optimistic editing with rollback.** Commit the edit to the UI instantly, fire the PATCH, and revert + toast if the server rejects — the grid feels instant while staying correct:

```plain
async function commitCell(rowId: string, key: string, value: string, prev: string) {
  setRows((r) => patch(r, rowId, key, value));       // optimistic: update now
  try {
    await fetch(`/api/orders/${rowId}`, { method: "PATCH",
      headers: { "Content-Type": "application/json", "Idempotency-Key": crypto.randomUUID() },
      body: JSON.stringify({ [key]: value }) });
  } catch {
    setRows((r) => patch(r, rowId, key, prev));       // rollback on failure
    announce(`Couldn't save ${key}. Reverted.`);
  }
}
```

**Copy/paste a range like a spreadsheet.** Read the selection into TSV on `copy`, and parse pasted TSV back into a block of cells on `paste` — this is what makes a grid interoperate with Excel/Sheets:

```plain
grid.addEventListener("copy", (e) => {
  const tsv = selection.rows.map((r) => r.cells.map((c) => c.value).join("\t")).join("\n");
  e.clipboardData.setData("text/plain", tsv); e.preventDefault();
});
grid.addEventListener("paste", (e) => {
  const block = e.clipboardData.getData("text/plain").split("\n").map((r) => r.split("\t"));
  applyBlockAtActiveCell(block);                       // validate each cell as you write it
  e.preventDefault();
});
```

**Column resize / reorder / pin** — persist the user's layout (widths, order, pins, visibility, sort) to `localStorage` or the server so their configured grid survives reload. Power users configure once and expect it to stick.

**Dynamic row height done right** — when you truly need variable heights, cache measured sizes by row key and feed them to the virtualizer's `measureElement`; never re-measure on every scroll frame. Fixed height is still the default for a reason.

**TS-enforced column contracts** — type `Column<T>` so `field` must be `keyof T`, and a `valueFormatter` receives `T[field]`, catching "column points at a field that doesn't exist" at compile time:

```plain
type Column<T> = { [K in keyof T]: {
  key: K; header: string; format?: (v: T[K]) => string; editable?: boolean;
}}[keyof T];   // a column can only reference a real field of T, with a correctly-typed formatter
```

**Aggregation & grouping** — compute group totals server-side for large data (the server-side row model returns group rows), client-side only when the full set is already in memory.

## 14\. Performance & Bundle Cost (the spine)
This is _the_ section for grids. A button feels free; a grid at scale absolutely is not, and performance here is a correctness property.

**Why naive grids die at 10k rows.** Render 10,000 rows × 6 cells as DOM and you mint **60,000+ nodes** (often 6× that with wrappers). Layout, paint, and memory all scale with node count; the browser chokes, scrolling stutters, and every state change re-lays-out the whole tree. The fix is not "optimize the render" — it's **render fewer nodes.**

**Virtualization (windowing) is the answer.** Only render the rows in (and just around) the viewport — ~30 DOM rows for a 1,000,000-row dataset. A spacer element sized to `totalRows × rowHeight` fakes the scrollbar; as the user scrolls, you swap which slice of data the ~30 rows display. `@tanstack/react-virtual`, `react-window`, `react-virtuoso` do this; every serious grid library has it built in. **This is the price of admission, not an optimization.**

**Fixed row height keeps it O(1).** Constant height means `firstVisibleRow = Math.floor(scrollTop / rowHeight)` — pure arithmetic. Variable height forces per-row measurement and a cumulative offset cache: far more code, measurable jank. Default to fixed.

**Memoization boundaries.** The row is the natural memo boundary: wrap the row component in `React.memo` keyed by row id + a version, so scrolling/editing one row doesn't re-render the other 29. Memoize cell renderers and wrap handlers in `useCallback`. Over-memoizing has its own cost — the row and cell are the boundaries that actually pay off.

**Don't thrash layout.** Animate/position rows with `transform: translateY()` (compositor-only, no reflow), never `top`/`margin`. Keep the loading state at fixed width so it doesn't reflow the grid. Apply `contain: content` (i.e. `layout paint style`) to the grid so its internal churn can't invalidate the rest of the page's layout — _not_ `contain: strict`, whose added size containment collapses the scroll container to 0 height (§9.2).

**Event-listener economy.** One delegated listener on the grid, not one per cell (§9.4). At 10k cells that's the difference between 1 closure and 10,000 in memory.

**The icon/library import trap (bundle cost).** The grid libraries are _big_ — AG Grid is hundreds of KB, MUI X DataGrid is large too. Import only what you use, lazy-load the grid route (it's rarely above the fold), and prefer the community/headless tier unless you truly need the enterprise features. For a headless build, TanStack Table + Virtual is a few KB — you pay in code you write, not bytes you ship.

**Measure the right thing.** The metric that matters is **scroll frame rate** and **keystroke-to-paint latency**, not initial load. A grid that loads in 200ms but drops to 20fps on scroll is a failed grid. Profile with the row count a real customer will actually have, not your seed data.

## 15\. Security (the grid writes to your database)
An editable, server-backed grid is a wide attack surface — it exposes sort, filter, pagination, _and_ write endpoints straight to the client.

*   **SQL injection via sort/filter (the grid-specific one).** Column names in `ORDER BY`/`WHERE` are SQL identifiers and **cannot be parameterized** — so an attacker who controls the sort/filter column string can inject SQL. Defense: an **allow-list Set** of sortable/filterable columns, reject anything else; parameterize all _values_ (§9.7). This is the vulnerability unique to grids and the one most often missed.
*   **Broken object-level authorization (BOLA/IDOR).** The grid sends `start`/`limit` and row IDs; without server-side tenant scoping, a user changes `start` or a row ID and pages into _another tenant's_ data. Every query must filter by `org_id = user.org`, and every edit must verify the user owns _that_ row. The UI showing only their rows is not security.
*   **Cap the page size.** An uncapped `limit` (or a `pageSize=10000000`) is a trivial DoS against your DB and a memory bomb in the browser. Clamp server-side (`limit <= 200`).
*   **Validate every edit server-side.** In-cell validation is UX; the server re-validates types, ranges, and business rules on the PATCH. Never trust the value the grid sends.
*   **Idempotent edits & CSRF.** Cell edits are state-changing — send an idempotency key so a double-commit doesn't double-apply, use `SameSite` cookies / anti-CSRF tokens, and rate-limit the write endpoints.
*   **Don't over-return.** `SELECT *` into a grid leaks columns the user shouldn't see (internal cost, PII, soft-delete flags). Return only the fields the grid needs; enforce column-level authorization for sensitive data.
*   **Audit the writes.** Inline edits change data with less ceremony than a form — log who edited which cell, when, from what value to what, so a bad bulk-edit is traceable and reversible.

## 16\. Senior-Level Checklist (ship-ready)
Before a data grid is "done":

- [ ] Correct pattern chosen: `role="grid"` for an interactive grid, native `<table>` for a read-only one — not a `<div>` costume.
- [ ] Virtualized from day one if the row count is unbounded; profiled at realistic (10k+) scale, not seed data.
- [ ] Roving tabindex: exactly one cell tabbable; arrow keys move it in 2D; grid is a single Tab stop.
- [ ] Focus survives virtualization _and_ edit commit — never drops to `<body>`.
- [ ] `aria-rowcount`/`aria-colcount`/`aria-rowindex`/`aria-colindex` reflect the FULL dataset, not the DOM window.
- [ ] Full keyboard map: arrows, Home/End, Ctrl+Home/End, PageUp/Down, Enter/F2 edit, Escape cancel, Shift+Arrow range, Ctrl+C/V.
- [ ] Inline edit has validation-in-cell (block or flag), a saving state, and a save-error path — all announced via `aria-live`.
- [ ] Identifier column pinned left; actions pinned right; a visible freeze seam in every skin.
- [ ] Distinct empty states: "no data" vs "no rows match filters" (with Clear filters).
