## 1\. What an Avatar Actually Is
An avatar is the small, self-contained visual that represents a **person or entity** in a UI — a user, a team, a bot, an organization, a workspace. It answers one question at a glance: _whose is this?_ Comment, message, assignee, member row, presence indicator — the avatar is the identity anchor.

The word gets muddied because people conflate three different things:
**Avatar (the component):** the container + shape + fallback logic + optional status/badge. This is what you build. It is a _system_, not an `<img>`.
**Profile photo (the content):** the actual uploaded image. It's one of _several possible inputs_ to the avatar, not the avatar itself. It can be missing, broken, or slow — which is exactly why the component exists.
**Icon / Gravatar / identicon (a fallback):** a generic person glyph or a generated pattern. These are what the avatar shows when there's no photo.

The single most common mistake: shipping `<img src={user.photo} class="avatar" />` and calling it done. That's not an avatar — it's a broken-image-icon generator waiting for the first user without a photo. **A real avatar is defined by what it shows when the photo isn't there.** The photo is the happy path; the fallback chain is the component.

One more distinction that trips people up: an avatar represents an _identity_; an icon represents an _action or object_. A trash can is an icon. A person's face is an avatar. If it stands in for "who," it's an avatar; if it stands in for "what," it's an icon.
* * *

## 2\. Why It Matters
An avatar is small, so teams treat it as cosmetic. It isn't. It punches far above its pixel count.
**Recognition and trust.** Faces are the fastest thing the human brain parses. An avatar lets a user find _their_ comment, _their_ assignee, _their_ teammate in a dense list without reading a single word. Strip avatars out of a chat or a review thread and cognitive load spikes immediately.
**The broken-image tax.** A cracked-image glyph or an empty gray square reads as _broken app_, not _missing photo_. It silently erodes trust on exactly the surfaces (profiles, team pages, comment threads) where trust matters most. Most users never upload a photo — so the fallback isn't an edge case, it's the **majority state**. Engineering the fallback well is engineering the common case well.
**Presence and social proof.** Status dots (online/away), stacked group avatars ("+12 others"), and reviewer faces on a product page all convert. "People are here / people did this" is one of the oldest trust signals in software, and the avatar is how it's rendered.
**Accessibility and identity.** Screen-reader users navigate people-dense UIs through avatar labels. A row of twelve unlabeled avatars is twelve "image" announcements — noise. Labeled correctly (or correctly hidden when the name is already adjacent), the same row is silent where it should be and clear where it counts.

## 3\. Anatomy of an Avatar
Every well-built avatar is composed of predictable parts, most of which are optional but all of which have rules:
**Container:** the clip boundary. Fixed square aspect ratio, `overflow: hidden`, a `border-radius` that defines the shape (full circle vs. rounded-square). Everything else layers on top of or inside this.
**Image:** the photo, object-fit-cover so it fills the circle without distortion. The primary content of the happy path — and the thing most likely to fail.
**Fallback layer:** what renders when the image is missing or errors. Usually **initials on a generated background color**, dropping to a **generic person icon** when there's no name either. This layer is the component's real job.
**Ring / border:** an optional outline for emphasis, selection, story-style ("unread"), or separation from the background (critical when the avatar sits on a same-color surface or in a stack).
**Status indicator:** a small dot (online/away/busy/offline), usually bottom-right, with a ring cut out of the avatar so it reads as separate. Never color-only — see §10.
**Badge / notification overlay:** a count or icon overlapping a corner (unread messages, verified check, a role marker). Handled by the sibling **Badge** component, positioned relative to the avatar container.
**Group context:** when avatars stack (overlapping, with a "+N" overflow chip), the container gains negative spacing and z-index ordering. Brief here; full treatment in **Avatar Group**.

## 4\. Sizes
Avatar size communicates hierarchy and context — a comment author is small, a profile hero is large. A typical scale, with real values:

| Token | Size | Font (initials) | Status dot | Typical use |
| ---| ---| ---| ---| --- |
| xs | 20px | 8px | 6px | Dense tables, inline mentions, breadcrumb author |
| sm | 24px | 10px | 6px | Comment lists, compact rows, group stacks |
| md | 32px | 13px | 8px | Default — nav bars, list items, most UI |
| lg | 40px | 16px | 10px | Cards, member rows, message threads |
| xl | 48px | 18px | 12px | Profile headers, detail panels |
| 2xl | 64px+ | 24px+ | 14px+ | Profile hero, settings page, empty-state prompts |

Rules that matter:
**Size is one dimension, not two.** An avatar is always a square (then clipped). Set `width` and `height` to the _same_ token; never let it become an ellipse because a parent flexed it. `aspect-ratio: 1` and `flex-shrink: 0` are your guardrails.
**Scale the whole system, not just the box.** Initials font size, status-dot size, and ring width should all derive from the avatar size token so a `sm` avatar doesn't get an `lg` dot bolted onto it.
**Retina from day one.** A 32px avatar needs a 64px source (`2x`) to stay crisp. Request the right size from your image service; don't ship a 512px original into a 24px slot (see §9 and §14).
**Interactive avatars still need a 44px hit target.** If the avatar is a link or a menu trigger, the _visible_ circle can be 24px but the tappable area must reach ≥44px via padding — same rule as Button.

## 5\. States
An avatar has more states than its size suggests, and the fallback-driven ones are the whole point.
**Loading (skeleton).** Before the image resolves, show a neutral shimmer/skeleton circle — not a flash of the fallback, not empty space. Prevents layout shift and the "pop-in" of a late image.
**Loaded (image).** The happy path: photo rendered, object-fit-cover, correctly clipped.
**Error → fallback.** The image `src` 404s, times out, or is empty. The component **must** catch `onError` and swap to the initials layer without ever showing the browser's broken-image glyph. This is the state juniors forget and the one that defines the component.
**Initials fallback.** No usable image, but a name exists → deterministic background color + 1–2 initials. Covered in depth in §9.
**Icon fallback.** No image _and_ no name (an anonymous or not-yet-loaded entity) → a generic person glyph on a neutral background. The floor of the chain.
**With status.** Any of the above plus a presence dot. Status is orthogonal to the image/fallback state — a user can be online whether you have their photo or not.
**Selected / active.** In pickers and toolbars, a ring or elevation marks the chosen avatar. Uses `aria-pressed`/`aria-current` if interactive.
**Interactive (hover/focus).** When the avatar is a button or link, it gets hover feedback and a visible `:focus-visible` ring, exactly like any control.

The fallback chain, stated as one rule: **photo → (on error or missing) initials-on-color → (no name) generic icon.** Never a broken image. Never a blank square. The chain always resolves to _something_ identity-shaped.
* * *

## 6\. Types & Variants
**Image avatar:** the photo. Primary variant when you have one.
**Initials avatar:** 1–2 letters on a generated color. The workhorse fallback and, for many products (Slack, Google, Linear), a first-class look in its own right.
**Icon avatar:** generic person/robot/building glyph. Anonymous users, bots, orgs without a logo, deleted accounts.
**Shape — circle vs. rounded-square.** Circle is the dominant convention for _people_ (warm, social, universal). Rounded-square (a "squircle") is increasingly used for _entities_ — organizations, workspaces, bots, apps — because it visually distinguishes "a thing" from "a person." Pick one convention per entity type and hold it system-wide. Mixing circle-people and squircle-orgs is a feature; mixing them at random is a bug.
**With status dot:** online/away/busy/offline presence. See §10 for the non-color-only requirement.
**With badge:** a count, a verified check, a role marker overlapping a corner. Delegated to the **Badge** component.
**With ring:** emphasis, selection, or story-style (a gradient ring signaling "unread"/"new," Instagram-style).
**Group / stack:** overlapping avatars with a "+N" overflow. Brief here; full treatment in **Avatar Group**.

## 7\. When to Use One (and When Not To)
Use an avatar wherever a **specific identity** appears and recognition speeds the user up: comment authors, assignees, message senders, member lists, presence indicators, reviewer proof, "signed in as" menus.

Don't reach for one when:
**There's no real identity behind it.** A decorative circle-cropped stock photo is not an avatar; it's an image. Don't invoke the fallback machinery for content that isn't a person/entity.
**The name alone is enough and space is tight.** In some dense data tables a text name outperforms a 16px blob nobody can parse. Measure.
**You'd show the same generic icon for everyone.** If literally every avatar is the identical gray person glyph (no photos, no initials), you've added visual noise with zero recognition value. Use text, or generate distinct initials/identicons so they're actually distinguishable.

Placement heuristics:
**Leading position** in a row (left of the name/content in LTR), because it's the identity anchor the eye lands on first.
**Consistent size per surface** — one avatar size for all comment authors, one for all list rows. Random sizing reads as broken hierarchy.
**Status dot bottom-right, badge top-right** by convention, so the two never collide.

## 8\. Avatars Across Design Systems
Same component, different house rules. Knowing them makes you fluent anywhere.
**Material Design (Google):** Circular by default. Strong first-class "initials avatar" with a generated background — Google's own products lean on it constantly. Sizes tied to the density system. Avatars appear in list items, chips, and cards as defined slots.
**Apple HIG (iOS/macOS):** Circular, restrained. Contacts and Messages use monogram (initials) fallbacks on a subtle gradient. iOS 26 pushes the Liquid Glass treatment onto profile surfaces. SF Symbols provide the person-glyph floor.
**Fluent (Microsoft):** The `Persona` / `Avatar` component is explicit and mature: image → initials → icon fallback baked in, a defined `presence` (status) system with named states, and a documented set of ring/badge treatments. One of the most complete avatar specs in any system.
**Ant Design / enterprise:** `Avatar` with `shape="circle|square"`, size presets plus number, an `Avatar.Group` with `maxCount` overflow, and a `gap` prop for initials fit. Built for dense admin UIs.
**Tailwind / utility-first:** No prescribed avatar; you compose `rounded-full`, `object-cover`, fixed size, and `ring` utilities. Freedom plus the risk that the fallback logic gets forgotten — so teams wrap it in a component.
**shadcn/Radix (2024+ web standard):** `@radix-ui/react-avatar` gives you `Avatar` / `AvatarImage` / `AvatarFallback` with the load/error state machine handled for you — the fallback shows only after the image fails or while it loads. This is the current best-practice primitive; see §9.
**Chakra / MUI:** Both ship a batteries-included `Avatar` with `name`\-driven initials, auto-generated background color, `AvatarGroup` with `max`, and a `badge`/`Badge` slot for status.

The through-line: every serious system models the avatar as **image + initials + icon fallback**, plus optional **presence** and **group**. Learn that shape once; remap the API per library.

```plain
  <img class="avatar__img" src="/u/42.jpg" alt="" onerror="this.remove()" />

```

```plain
<!-- Decorative context: name is already next to it, so the avatar is hidden from AT -->
<span class="avatar" aria-hidden="true">
  <img class="avatar__img" src="/u/42.jpg" alt="" />
  <span class="avatar__fallback">JR</span>
</span>
<span class="name">Jordan Rivers</span>
```

Key HTML rules:
**The** **`alt`** **decision is semantic, not cosmetic** — put the name in `alt` (or `aria-label` on the wrapper) _only_ when the name isn't already announced right next to it. When the name text sits adjacent, `alt=""` / `aria-hidden` prevents a double-announcement ("Jordan Rivers, image, Jordan Rivers"). See §10.
The image's own `alt` is empty (`alt=""`) when a wrapper carries the label, so the name isn't read twice.
`onerror` handling is the whole ballgame — never let the browser render its default broken-image icon.

### 9.4 Initials + deterministic color (the utility that makes fallbacks not look random)
The fallback's quality lives in these two pure functions. The color **must be deterministic** — the same name always yields the same color, across renders, sessions, and users, so "Jordan Rivers" is _always_ the same purple. Random-per-render color is the tell of a broken build.

```plain
/** 1–2 initials from a name. Handles single names, extra whitespace, and unicode. */
export function getInitials(name?: string): string {
  if (!name) return "";
  const parts = name.trim().split(/\s+/).filter(Boolean);
  if (parts.length === 0) return "";
  if (parts.length === 1) return firstGrapheme(parts[0]).toUpperCase();
  // first + last, not first-two-words, so "Mary Ann Smith" -> "MS"
  return (firstGrapheme(parts[0]) + firstGrapheme(parts[parts.length - 1])).toUpperCase();
```

}

```plain
/** Grab the first visual character, safe for emoji/combined glyphs. */
function firstGrapheme(s: string): string {
  return [...s][0] ?? "";
```

}

```plain
/** Deterministic hue from a name via a small string hash → HSL.
 *  Fixed S/L keeps every generated color legible with white text. */
export function colorFromName(name?: string): string {
  if (!name) return "#5F2C82";          // UJG Eminence as the neutral default
  let hash = 0;
  for (let i = 0; i < name.length; i++) {
    hash = name.charCodeAt(i) + ((hash << 5) - hash);  // classic djb2-ish rolling hash
    hash |= 0;                          // force 32-bit int
  }
  const hue = Math.abs(hash) % 360;
  return `hsl(${hue} 55% 40%)`;         // S/L fixed so contrast with #fff stays ~AA
}
```

The two things that separate this from the amateur version:
**First + last initial, not first two letters or first two words** — "Mary Ann Smith" is "MS," matching how humans abbreviate. Getting this wrong is a subtle, common tell.
**Fixed saturation and lightness.** Hashing the _hue_ only, while pinning S and L, guarantees every generated color has enough contrast for white initials. Hashing all three channels eventually produces a pale yellow with unreadable white text. For a stricter guarantee, snap `hue` to a curated palette (e.g., the UJG Eminence/Goldenrod/Sienna/Dark-Green set) instead of the full wheel, so brand color is never violated.

### 9.5 Vanilla JavaScript (no framework)
The same fallback state machine without React. Worth knowing cold.

```plain
function mountAvatar(el, { src, name }) {
  const initials = getInitials(name);
  el.style.setProperty("--avatar-bg", colorFromName(name));
  const fallback = document.createElement("span");
  fallback.className = "avatar__fallback";
  fallback.setAttribute("aria-hidden", "true");
  if (initials) fallback.textContent = initials;   // textContent escapes the user name → no XSS (§15)
  else fallback.innerHTML = personSvg();            // trusted, static SVG string only
  el.replaceChildren(fallback);
```

if (name) el.setAttribute("aria-label", name), el.setAttribute("role", "img");

```plain
if (!src) return;                         // no photo: initials/icon already showing
  const img = new Image();
  img.className = "avatar__img";
  img.alt = "";
  img.loading = "lazy";
  img.decoding = "async";
  img.onload = () => el.appendChild(img);   // only attach once it actually loaded
  img.onerror = () => {};                    // do nothing → fallback stays visible
  img.src = src;
}
```

The pattern flips the usual order: instead of showing the image and catching failure, it **preloads off-DOM and only attaches on success**. A failed image is never inserted, so the browser's broken glyph can't appear even for a frame. This is the most robust fallback strategy of all.

### 9.7 shadcn/ui + Radix (the 2024+ standard)
Radix's `Avatar` primitive handles the load/error state machine for you: `AvatarFallback` renders while the image loads and stays if it errors. You own the styling; Radix owns the timing.

```plain
import * as AvatarPrimitive from "@radix-ui/react-avatar";
```

import { cn } from "@/lib/utils";

```plain
export function Avatar({ src, name, className }: { src?: string; name: string; className?: string }) {
  return (
    <AvatarPrimitive.Root
      className={cn("relative inline-flex h-10 w-10 shrink-0 overflow-hidden rounded-full", className)}
    >
      <AvatarPrimitive.Image
        src={src}
        alt=""                                  /* label lives on context text, not here */
        className="h-full w-full object-cover"
      />
      <AvatarPrimitive.Fallback
        delayMs={300}                            /* avoid flashing initials during a fast load */
        className="flex h-full w-full items-center justify-center text-white"
        style={{ background: colorFromName(name) }}
      >
        {getInitials(name)}
      </AvatarPrimitive.Fallback>
    </AvatarPrimitive.Root>
  );
}
```

The `delayMs` is a nice touch most people miss: on a fast connection the image arrives in ~100ms, so showing initials for that blink then swapping is a jarring flicker. A short delay lets a quick image win, and only slow/failed loads ever reveal the fallback.

```plain
        <Image src={src} alt="" width={size * 2} height={size * 2}   /* 2x source for retina */
               onError={() => setErrored(true)}
               style={{ width: "100%", height: "100%", objectFit: "cover" }} />
      ) : (
        <span aria-hidden="true">{getInitials(name)}</span>
      )}
    </span>
  );
}
```

Request a `2x` source (`width={size*2}`) and let Next downscale/optimize — a 40px slot gets an 80px image so it stays sharp on retina without shipping the full original. Remember to allowlist the avatar host in `next.config.js` `images.remotePatterns`, or `<Image>` throws.

### 9.11 Web Component (framework-agnostic)

```plain
class UIAvatar extends HTMLElement {
  static observedAttributes = ["src", "name"];
  connectedCallback() { if (!this.shadowRoot) this.attachShadow({ mode: "open" }); this.render(); }
  attributeChangedCallback() { if (this.shadowRoot) this.render(); }
  render() {
    const src = this.getAttribute("src");
    const name = this.getAttribute("name") ?? "";
    this.setAttribute("role", "img");
    this.setAttribute("aria-label", name);
    const root = this.shadowRoot!;
    // Only the trusted, static <style> goes through innerHTML — never user data (see §15).
    root.innerHTML = `<style>/* scoped avatar styles */ :host{display:inline-flex}</style>`;
    const fallback = document.createElement("span");
    fallback.className = "fallback";
    fallback.textContent = getInitials(name);   // textContent escapes the name → no XSS
    root.append(fallback);
    if (!src) return;                            // no photo: initials already showing
    const img = new Image();                     // src set as a property, never parsed as HTML markup
    img.alt = "";
    img.onload = () => root.append(img);         // attach only on success; a failed src is never inserted
    img.onerror = () => {};                      // do nothing → the fallback stays visible
    img.src = src;
  }
}
customElements.define("ui-avatar", UIAvatar);
// <ui-avatar name="Jordan Rivers" src="/u/42.jpg"></ui-avatar>
```

## 10\. Accessibility (non-negotiable)
The avatar's a11y is almost entirely about **the alt-text decision** and **not signaling with color alone**. Both are easy to get wrong and easy to get right.

**The alt-text decision — the thing that matters most.** An avatar's accessible name should exist _exactly once_ in the announcement. Two cases:
**Avatar stands alone** (no adjacent name text — e.g., a bare avatar in a toolbar, a stacked group): put the name on the avatar. `role="img"` + `aria-label="Jordan Rivers"`, or `alt="Jordan Rivers"` on the `<img>`.
**Avatar sits next to the name** (comment rows, member lists, "signed in as Jordan"): the name is _already_ announced by the adjacent text, so the avatar must be **`aria-hidden="true"`** (or `alt=""`). Otherwise the screen reader says "Jordan Rivers, image, Jordan Rivers" — the double-announcement that plagues comment threads.

That's the whole rule: **name in the label, or hidden — never both, never neither.** The `decorative` prop in §9.3 encodes exactly this choice.

**Status indicator — never color-only.** WCAG 1.4.1: a green dot vs. a red dot is meaningless to colorblind users and invisible to screen readers. The dot must carry a text label (`aria-label="Status: online"`) _and_ ideally a shape or position difference. Color is a redundant cue, not the only one.

**Decorative images stay silent.** The `<img>` inside a labeled wrapper gets `alt=""` so it isn't announced separately from the wrapper's label. A generic person-icon fallback is always decorative (`aria-hidden`) — "person icon" is noise.

**Interactive avatars are controls.** If the avatar opens a menu or navigates, it's a `<button>`/`<a>`, not a `<span>` — real keyboard support, a visible `:focus-visible` ring, and a ≥44px hit target, exactly like Button. An avatar-as-menu-trigger also needs `aria-haspopup` / `aria-expanded`.

**Contrast for initials.** White initials on a generated background must clear ~4.5:1. This is _why_ §9.4 pins saturation/lightness instead of hashing all three color channels — an unconstrained hash will eventually produce a pale background that fails contrast.

## 11\. Innovative & Emerging Ideas
The avatar looks solved but keeps moving:
**Liquid Glass profile surfaces.** Apple's iOS 26 / macOS Tahoe treatment on profile headers and presence rings — a refractive translucent ring around the avatar that reacts to motion. The 2026 headline look; honor `prefers-reduced-motion`.
**Generative identicons beyond initials.** Deterministic geometric/gradient art (GitHub-style, or Boring Avatars, or diffusion-generated) as a richer no-photo fallback that's still unique per user — more distinguishable than a wall of gray glyphs.
**AI-generated & animated avatars.** Products offering a generated stylized portrait, or subtle "live" avatars (Apple Memoji-style, or looping video avatars) for premium/social surfaces.
**Presence as more than a dot.** Typing shimmer rings, "active in this doc" pulses, and rich status (custom emoji + text, Slack-style) layered onto the avatar.
**View Transitions.** Native morphing of an avatar from a list into a profile hero on navigation, no heavy JS.
**Story rings / activity rings** carried from social into SaaS ("unread," "new since you last looked") as a gradient ring state.

## 12\. UX & Trust Killers (the quiet ones)
None of these throw an error. They just make the app feel broken or noisy.
**The broken-image glyph.** The cardinal sin. One user without a photo and a missing `onError` handler turns your clean UI into a cracked-icon graveyard. This is the #1 avatar bug in production, and it's one line to fix.
**Random-per-render fallback color.** "Jordan" is purple on Monday and green on Tuesday because the color was `Math.random()` instead of a hash of the name. Destroys the recognition value the avatar exists to provide. Color must be **deterministic**.
**Ellipse avatars.** A flex parent squashes the avatar because `flex-shrink: 0` / `aspect-ratio: 1` is missing. Circular faces become egg-shaped and it looks amateur instantly.
**First-two-letters initials.** "Mary Ann Smith" → "MA" instead of "MS." Humans read the second letter as the surname; getting it wrong is a subtle, pervasive tell.
**Layout shift on load.** No skeleton/reserved box, so the avatar pops in late and shoves the row. Reserve the space; show a skeleton.
**Double-announcement.** The avatar and the adjacent name both read out, so every comment is "Name, image, Name." Fix with `aria-hidden` when the name is adjacent.
**Color-only status.** Green/red presence dots with no label — meaningless to colorblind and screen-reader users.
**Shipping the full-size original into a 24px slot.** A 512px photo downloaded for a tiny slot — wasted bandwidth, janky scroll, no retina benefit. Request the right size.
* * *

## 13\. Advanced Patterns
**Group stacking (brief — full treatment in Avatar Group).** Overlapping avatars use negative margin and reversed z-index (leftmost on top), a ring in the page background color to separate them, and a "+N" overflow chip past a `max`. The overflow chip should be labeled ("and 12 others") and, if interactive, open the full list. The stack as a whole often gets one group label rather than N individual ones.
**Deterministic color from a curated palette.** Instead of the full HSL wheel, hash the name into an _index_ into the brand palette (UJG: Eminence, Goldenrod, Sienna, Dark Green, Spanish Orange). Guarantees on-brand fallbacks and guaranteed contrast, at the cost of more collisions.
**Squircle-for-entities convention.** Circle for people, rounded-square for orgs/bots/workspaces — a system-wide semantic. Encode it as a `shape` prop keyed off entity type, not a per-usage choice.
**Ring as a state channel.** Selection, story/unread, and emphasis all ride the ring. Keep them distinguishable (solid gold = selected, gradient = unread) and never make the ring the _only_ signal for something important.
**Design tokens.** Size, ring width, status-dot ratio, and the fallback palette all live as tokens so a rebrand or a density change is a token swap, not a hunt through components. Mirrors Button's token tiers.
* * *

## 14\. Performance & Bundle Cost
Avatars feel free. In a member list or an activity feed, a hundred of them aren't.
**Request the right size.** A 32px avatar wants a ~64px source, not the 1024px original. Use your image CDN's resize params (`?w=64&h=64&fit=cover`) or Next `<Image>`. Shipping full-size originals into tiny slots is the most expensive avatar mistake at scale.
**Lazy-load below the fold.** `loading="lazy"` + `decoding="async"` on every avatar `<img>` so a 500-row list doesn't fire 500 requests on mount. Only the visible avatars load.
**Format negotiation.** Serve AVIF/WebP with a JPEG fallback; avatars are small but they multiply.
**Don't animate layout.** Skeleton shimmer should animate `background-position` (compositor-only), not `width`/`height`. Keep the reserved box fixed so a late image never reflows the row.
**Memoize the utils, not the component.** `getInitials` and `colorFromName` are cheap and pure — `useMemo` them per avatar. In a large frequently-updating list, memoize the avatar component so a parent re-render doesn't recompute every fallback.
**Icon-import discipline.** The generic person-glyph should be a single inline SVG or a named import, never `import * as Icons` — same tree-shaking trap as Button.
* * *

## 15\. Security
An avatar's security surface is its image source and any user-controlled name data.

**Avatar** **`src`** **URLs are user-controlled.** If users upload photos or provide URLs, the `src` is attacker-influenceable. Validate uploaded images by decoding (not by extension/MIME), strip EXIF (GPS, device serials), cap dimensions/bytes (decompression bomb defense), and serve from a CDN domain separate from your app origin. Never let an arbitrary user-supplied URL render as an `<img src>` without allowlisting the host — an attacker-crafted `src` can beacon data, track users, or trigger SSRF if your server proxies it.

**Initials are rendered from user names.** Names come from user input or a directory. If you render initials via `innerHTML` instead of `textContent`/framework interpolation, a name containing `<script>` becomes stored XSS. Framework interpolation escapes by default; never bypass it.

**The deterministic color hash is not security-sensitive.** The hash in `colorFromName` is a visual convenience, not a cryptographic function. It doesn't need to be collision-resistant or secret. Mentioning this so nobody over-engineers it.

**Avatar images and CSP.** If avatars load from user-uploaded origins or Gravatar/third-party services, your `Content-Security-Policy` `img-src` directive must allowlist those origins. A misconfigured CSP silently blocks avatar images, making them all fall back to initials with no console error visible to non-dev users.

**Don't leak user existence via avatar URLs.** If your avatar URL scheme is predictable (`/avatars/{userId}.jpg`), an attacker can enumerate user IDs by checking which URLs return 200 vs 404. Serve avatars via a hash/token-based URL, or return a default image for all requests regardless of existence.

## 16\. Senior-Level Checklist (ship-ready)
Before an avatar is "done":
Broken/missing `src` degrades to initials — `onError` handled, browser glyph never shows.
No name AND no image degrades to a generic person icon (the chain always resolves).
Fallback color is **deterministic** from the name (same name → same color, always).
Initials are first + last (`Mary Ann Smith` → `MS`), uppercased, unicode-safe.
Initials contrast ≥ 4.5:1 against the generated background (fixed S/L or curated palette).
`flex-shrink: 0` / `aspect-ratio: 1` so it never becomes an ellipse.
Name in the label when standalone; `aria-hidden` when the name is already adjacent — never both.
Status dot is labeled and not color-only.
Skeleton/reserved box prevents layout shift on load.
Right-sized, retina (`2x`), lazy-loaded image source — not the full original.
Interactive avatars are real `<button>`/`<a>` with focus ring + ≥44px hit target.
Circle vs. squircle follows the system's people-vs-entity convention.

## 17\. Visual Styles (the same avatar, eleven aesthetics)
Design systems are _whose_ rules; visual styles are _which look_. The same semantic avatar wears any skin. **The rule that never changes:** the fallback chain, the label semantics, the status label, the 44px hit target, and the focus ring stay identical across all eleven. Style is skin; behavior is the skeleton. Full guidance in the 🎨 Design Styles (visual languages) ([https://app.clickup.com/8495850/docs/838qa-81211/838qa-200551](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200551)) reference.
**Flat:** solid fill, crisp circle, no shadow. Initials fallback in a flat brand color. Reads instantly, scales fast.
**Material:** subtle elevation on interactive avatars, the classic initials-on-generated-color monogram, ripple if it's a button. Google's own avatar look.
**Glassmorphism:** translucent ring/badge with `backdrop-filter: blur()` over a vivid backdrop. Watch initials contrast — the blur eats it.
**Liquid Glass (2026 trend):** Apple iOS 26 / macOS Tahoe — a refractive translucent presence ring with a specular rim and moving sheen around the avatar. Sings over deep Eminence. Web = honest approximation; SwiftUI emits native `.glassEffect()`. Guard for `prefers-reduced-motion`.
**Neumorphism:** the avatar sits in a soft dual-shadow well on a same-color surface. Pretty, contrast-poor — accent use only, and never for the initials text.
**Skeuomorphism:** inner bevel + glossy highlight, like a physical badge photo. Tactile, heavy.
**Neo-Brutalism:** hard offset shadow, thick black border, zero-radius _square_ avatar. High personality; great for the org/entity squircle taken to an extreme.
**Claymorphism:** big soft radius (squircle), inner top-light + bottom-shadow, puffy friendly glow. Warm for community products.
**Aurora / Gradient:** an animated multi-hue gradient ring (story-style) on a dark surface. Premium; honor `prefers-reduced-motion`.
**Minimal / Swiss:** near-zero decoration, thin hairline ring or none, initials in a restrained mono/grotesk. Typography does the work.
**UJG Brand:** Afro-Futurist house style — Goldenrod initials or ring on deep Eminence/Night, confident radius, warm glow. Circle for people, squircle for the UJG entity marks. The house default.
* * *

**Bottom line:** an avatar is a tiny circle with an outsized job — it carries identity, and it fails in public. The `<img>` is the easy 20%; the component is the other 80%: a fallback chain that never shows a broken glyph, a deterministic color so faces stay recognizable, initials that read the way humans abbreviate, a status cue that isn't color-only, and an alt-text decision that announces the name exactly once. Get those right and a wall of avatars feels alive, trustworthy, and quiet in all the right places. Get the fallback wrong and one photo-less user cracks the whole surface.
