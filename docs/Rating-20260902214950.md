## 1\. What a Rating Actually Is
A rating is a compact control that expresses a **value on a bounded scale** — usually 0–5, rendered as stars, hearts, or a number. That's the easy half. The hard half, the one that separates a correct build from a broken one, is that "rating" names **two completely different components** that people constantly conflate:

*   **Input rating (interactive):** the user _sets_ a value. Clicking the third star submits "3 out of 5." It's a form control. It has focus, keyboard, hover-preview, a submit path, and a value that leaves the browser. Under the hood it is **a single-select group** — a radio group — not five buttons.
*   **Display rating (read-only):** the widget _shows_ an aggregate someone else produced. "4.3 out of 5 stars, 1,240 reviews." Nobody clicks it. It has no focus, no keyboard, no state. Its entire job is to render a number faithfully — and to expose that number as **text** to assistive tech and to search engines.

**These are not the same component with a** **`readonly`** **prop bolted on.** They have different DOM, different semantics, different accessibility contracts, and different failure modes. An input rating that's actually read-only traps keyboard users in a control that does nothing. A display rating wired as five interactive stars lies to screen readers and to Google. The single most common mistake in rating engineering is **shipping one when you needed the other** — or worse, shipping one code path that half-does both.

Draw the line hard and early: **is the user producing this number, or consuming it?** Every decision downstream forks on that answer. This doc keeps the two modes visibly separated the whole way through, because the moment you let them blur, the bugs start.

One more distinction people get wrong: a rating is not a **slider** and not a **like button**. A slider is continuous over a range (0–100 volume); a rating is a small set of discrete steps (1–5, occasionally half-steps). A like/favorite is a single **toggle** (`aria-pressed`), not a scale — if there's exactly one star and it flips on/off, that's a toggle button, and it belongs in the Button family, not here. See [Button](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200231) for the toggle pattern.

## 2\. Why It Matters
The rating is a trust instrument, and trust converts.

*   **Social proof is the highest-leverage pixel on a product page.** "4.6 stars, 2,100 reviews" does more selling than any amount of body copy. When it renders as star glyphs a screen reader announces as "star star star star star," a blind user gets _no_ social proof — you've hidden your single strongest conversion asset from a whole segment of buyers. That's a revenue bug wearing an accessibility costume.
*   **Star ratings are an SEO weapon.** Google renders review stars in search results when you emit valid `AggregateRating` structured data. Those gold stars in the SERP lift click-through measurably against ten plain blue links. Get the JSON-LD wrong (or omit it) and you're invisible in exactly the moment a buyer is comparing you to a competitor.
*   **The input rating is a conversion funnel of its own.** Post-purchase "rate your order" flows feed the display ratings that sell the _next_ customer. If the input is clumsy — no hover preview, no keyboard, no way to undo a mis-tap — completion drops and your review corpus starves.
*   **It sets the honesty tone.** A rating that rounds 4.2 up to five full stars, or renders 3.5 as four, reads as manipulation the instant a user does the math. Faithful fractional rendering is a trust signal; sloppy rounding is a tell.

## 3\. Anatomy of a Rating
The parts differ by mode, which is itself the lesson. Shared parts first:

*   **Scale / max:** the ceiling. Almost always 5. Occasionally 10 (IMDb), rarely 3 (Michelin). Fixed and labeled.
*   **Symbol:** the repeated glyph — star, heart, circle, thumb. Meaningfully sized, meaningfully spaced.
*   **Fill:** how much of each symbol is "on." Binary per-symbol for whole stars; **partial** for fractional values (a 43%-filled fourth star for 4.3).
*   **Value:** the number itself. This is the real payload; the glyphs are just its costume.

**Input-only parts:**
*   **The group container:** semantically a `radiogroup` (or native `fieldset`). One tab stop, arrows move within — see [Radio Buttons](https://app.clickup.com/8495850/docs/838qa-81211/838qa-216471) for the identical roving-selection pattern.
*   **Each option:** one `radio` per star value (`role="radio"` + `aria-checked`, or a real `<input type="radio">` visually styled as a star).
*   **Hover-preview layer:** the transient fill that follows the pointer _before_ commit, showing "this is what you'd pick."
*   **Clear / remove affordance:** the way to get back to _no_ rating (value 0 / null) after setting one. The part juniors forget entirely.

**Display-only parts:**
*   **The accessible text label:** "Rated 4.3 out of 5" — the actual announced content. The stars are `aria-hidden` decoration layered on top.
*   **The count:** "(1,240 reviews)" — part of the trust signal, and part of the structured data.
*   **The structured-data block:** `AggregateRating` JSON-LD, invisible to humans, load-bearing for search.
* * *

## 4\. Scale, Precision & Density
Real values. Precision is the axis people underthink — it drives both the rendering and the a11y complexity.

| Property | Common values | Notes |
| ---| ---| --- |
| Max scale | 5 (default), 10, 3 | 5 is the web default; changing it demands a visible label |
| Input precision | 1 (whole stars) | Half-star input is a UX minefield — see §5 |
| Display precision | 0.1 (e.g. 4.3) | Aggregates are fractional by nature; render them honestly |
| Symbol size | 16–20px dense · 24–32px default · 40px+ hero | Input needs ≥44px hit target even at 20px visual |
| Gap between symbols | 2–4px | Too tight = mis-taps on input; too loose = reads as separate |
| Rounding (display) | nearest 0.1 for text, nearest 0.5 for glyph snap (optional) | Text value is the truth; glyph may snap for legibility |

Rules that matter:
*   **Input hit target ≥44px even when the star draws at 20px.** Expand with padding, not a bigger glyph. Cramped stars are the top mobile mis-tap in the whole component.
*   **Display value is text-first.** Compute "4.3 out of 5" once; the fill is derived from it, never the other way around.
*   **Pick your display rounding and state it.** Rounding 4.3 → 4 stars visually is fine _if_ the text still says 4.3. Rounding the text itself to 4 is a lie.
* * *

## 5\. States
Two state machines, because two components. Missing states are the tell of an amateur build — and here the missing state is almost always "how do I un-rate?"

**Input rating states:**
1. **Empty / unrated** — value 0 or null, no fill. The honest default; do not pre-select 5.
2. **Hover-preview** — pointer over the Nth star: stars 1..N fill _transiently_. Not committed. Vanishes on mouse-leave, snapping back to the real value.
3. **Focus** — keyboard focus on the group; visible ring on the focused option. `:focus-visible`, never removed.
4. **Selected / committed** — the user clicked or pressed; value is set, fill is permanent until changed.
5. **Changing** — arrow keys move the value up/down live; each step is a new committed value (or a preview-until-blur, your call — pick one and be consistent).
6. **Cleared** — value returned to 0/null via the clear affordance. Must be reachable by keyboard, not just a tiny × only a mouse can hit.
7. **Submitting / async** — value sent to the server; disable re-entry, show progress, keep width stable.
8. **Disabled** — not currently ratable. Reduced opacity, `aria-disabled`, no pointer.
9. **Error** — submit failed or "rating required" on a form. Announce it via a live region, don't just tint the stars red.
10. **Success** — "Thanks for rating!" transient confirmation.

**Display rating states:** far fewer, by design.
1. **Rated** — value + fractional fill + text + count.
2. **No ratings yet** — the empty-aggregate case people forget. Don't render five hollow stars that read as "0 out of 5, terrible." Render "No ratings yet" as text and skip the `AggregateRating` schema entirely (emitting a `ratingCount` of 0 is a Google structured-data error).
3. **Loading** — skeleton or shimmer while the aggregate fetches; never flash empty stars first.

The half-star note belongs here because it lives in the state model. **Half-star** **_display_** **is easy** — it's just a fractional fill (§9.2). **Half-star** **_input_** **is hard**, and here's why: to let a pointer pick 3.5, you split each star into a left and right hit zone, which halves your already-small tap target and makes precise selection on touch genuinely painful. Worse, it explodes the a11y model — a radio group of "1, 2, 3, 4, 5" is clean; "0.5, 1, 1.5, 2, 2.5 …" is ten options crammed into five glyphs, and announcing them clearly is awkward. **Default recommendation: whole-star input, fractional display.** If a stakeholder insists on half-star input, budget real time for the keyboard and screen-reader model, and always provide a number-input fallback.

## 6\. Types & Variants
*   **Star (5-scale):** the universal default. Recognized instantly, needs no legend.
*   **Heart / thumb / emoji:** re-skinned stars for warmth or brand. Same semantics; the glyph is cosmetic.
*   **Numeric (x/10, x/100):** IMDb, review aggregators. Higher resolution, less emotional. Often paired with stars.
*   **Faces / NPS-style (1–5 or 0–10):** satisfaction surveys. Technically a rating scale; often better as a labeled radio group with words, not glyphs.
*   **Single-star toggle:** one star that flips on/off. **This is a favorite/like toggle, not a rating** — build it as a Button with `aria-pressed`, not as this component.
*   **Read-only aggregate:** the display variant. The one that ships the JSON-LD.
*   **Distribution bar chart:** the "5★ ▓▓▓▓ 62%" histogram under a product's average. A visualization of ratings, not a rating control itself — worth mentioning because people file it here.

Emphasis pairs with the [Badge](https://app.clickup.com/8495850/docs/838qa-81211/838qa-217711) component constantly: the compact "4.6 ★" chip on a card is a Badge _wrapping_ a display rating. Keep the rating's text-value contract intact inside the badge — a badge is a skin, not an excuse to drop the accessible label.

## 7\. When to Use One (and When Not To)
Use a rating when a value on a **small, well-understood, bounded scale** needs to be captured or shown, and the scale carries shared meaning (five stars = quality, everyone knows this). Don't use one when:

*   **You need nuance the scale can't hold.** "How was your experience?" with five stars throws away _why_. Pair the rating with a comment field, or use it only as the quick top-line.
*   **The choice isn't ordinal.** Rating implies more = better. For unordered options (pick a category, pick a color) use radio buttons or a select, not stars.
*   **It's a binary reaction.** Like/dislike is a toggle, not a 5-scale.
*   **The scale is large or continuous.** 0–100 satisfaction is a slider or number input, not 100 stars.

Placement heuristics:
*   **Display ratings go where the buy decision happens:** product title area, card corner, search-result row. High, early, near price.
*   **Input ratings go post-experience:** after purchase, after a session, in the review flow — never blocking the primary task.
*   **Never make an input rating a required gate** with no "skip." Forced ratings produce garbage data and rage-quits.

## 8\. Ratings Across Design Systems
Same value-on-a-scale idea, different house rules and — tellingly — different honesty about the input/display split.

*   **Material Design (Google):** No first-class 5-star input in core Material 3; you compose it. Display stars pair with the review distribution bar. Material's guidance leans on numeric aggregate + count, stars as reinforcement.
*   **Apple HIG (iOS):** `UIStepper`\-style and rating controls in App Store review flows; SwiftUI has no stock star rating, so you build it from `Image(systemName: "star.fill")` with a tap/drag gesture. Apple's App Store display rating is the canonical "4.7 · 12K Ratings" text-first pattern.
*   **Fluent (Microsoft):** Ships a real `Rating` component with `max`, `value`, `allowZeroStars`, size, and an explicit `readOnly` — and crucially it renders an `aria-label` describing the value. A good reference for doing the split right.
*   **Ant Design / enterprise:** `<Rate />` with `allowHalf`, `allowClear` (click the current value again to clear — a clean affordance), `character` (swap the glyph), and `disabled`. Dense, feature-complete, admin-grade.
*   **Tailwind / utility-first:** No prescribed rating; composed from utilities. Usually wrapped in a component so the a11y contract isn't re-derived per page.
*   **shadcn/Radix:** No official Rating primitive as of 2026; the community pattern builds it on a Radix `RadioGroup` (input) or plain semantic markup (display) with Tailwind fill. This is the _right instinct_ — reach for the radio group, not five buttons.
*   **Bootstrap:** No native component. Needs custom CSS + radio inputs — say so plainly rather than faking a `.rating` class that doesn't exist.

## 8b. Visual Styles (the same rating, eleven skins)
The value, the radio semantics, the keyboard map, the 44px target, and the accessible text label stay **identical** across every skin below. The skin only touches the glyph and its fill. See them live in [Design Styles](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200551).

*   **Flat:** solid gold fill, hollow gray empty, crisp edges. Reads instantly; the safe default.
*   **Material:** filled star with a subtle ripple on tap (input), tonal empty state.
*   **Glassmorphism:** translucent stars over a vivid backdrop with `backdrop-filter: blur()`. Watch contrast — a gold star on frosted glass can wash out; keep a border.
*   **Liquid Glass (the 2026 trend):** Apple iOS 26 / macOS Tahoe language. Stars as refractive pill-lozenge glyphs with a specular rim and a sheen that shifts as the value changes. Gorgeous on a deep Eminence field. Guard for `prefers-reduced-motion` — kill the moving sheen.
*   **Neumorphism:** stars pressed into or raised from a same-color surface via dual shadows. Pretty, contrast-poor — accent use only, never the primary conversion rating.
*   **Skeuomorphism:** beveled, gradient-filled gold stars with an inner highlight. The "real award sticker" look.
*   **Neo-Brutalism:** thick black star outlines, hard offset shadow, flat fill, zero softness. High personality for a campaign page.
*   **Claymorphism:** puffy rounded stars with inner top-light and soft glow. Friendly, playful, good for consumer apps.
*   **Aurora / Gradient:** stars filled with an animated multi-hue gradient on dark. Premium; honor `prefers-reduced-motion`.
*   **Minimal / Swiss:** possibly no stars at all — "4.3/5" in clean type, a thin rule, near-zero decoration. Type does the work.
*   **UJG Brand:** Goldenrod (`#DCA424`) stars on deep Eminence (`#5F2C82`) / Night (`#0A0A0A`), confident radius, a warm gold glow on the filled portion. The house default — the saturated dark backdrop makes the gold sing.

**Rule that never changes:** the style is skin, the behavior is the skeleton. A brutalist star and a liquid-glass star announce the same "Rated 4.3 out of 5" and answer the same arrow keys.

## 9\. The Code
The section that matters. We keep input and display visibly separate the whole way — because in code, blurring them is exactly where the bugs breed.

### 9.1 HTML (the foundation, both modes)
**Input — a real radio group styled as stars.** This is the accessible build: native radios carry keyboard, focus, name/value, and single-select semantics for free. You visually hide the inputs and style the labels as stars.

```plain
<!-- INPUT: native radios, visually styled as stars. Reverse order enables
     a pure-CSS "fill up to hovered" trick (see 9.2). -->
<fieldset class="rating-input">
  <legend>Rate this product</legend>

  <input type="radio" id="r5" name="rating" value="5" />
  <label for="r5"><span class="sr-only">5 stars</span>★</label>
  <input type="radio" id="r4" name="rating" value="4" />
  <label for="r4"><span class="sr-only">4 stars</span>★</label>
  <input type="radio" id="r3" name="rating" value="3" />
  <label for="r3"><span class="sr-only">3 stars</span>★</label>
  <input type="radio" id="r2" name="rating" value="2" />
  <label for="r2"><span class="sr-only">2 stars</span>★</label>
  <input type="radio" id="r1" name="rating" value="1" />
  <label for="r1"><span class="sr-only">1 star</span>★</label>
</fieldset>
```

**Display — decorative glyphs + one real text label.** The value is announced as text; the stars are hidden from assistive tech entirely.

```plain
<!-- DISPLAY: read-only aggregate. The stars are decoration; the LABEL is the truth. -->
<div class="rating-display" role="img" aria-label="Rated 4.3 out of 5 stars, 1,240 reviews">
  <span class="stars" style="--fill: 86%" aria-hidden="true">★★★★★</span>
  <span class="rating-text">4.3</span>
  <span class="rating-count">(1,240)</span>
</div>
```

Key HTML rules:
*   **Input uses real** **`<input type="radio">`** (or `role="radio"` if you must). One `name`, one value each, single-select for free. **This is the non-negotiable a11y core** — a rating input _is_ a radio group.
*   **`allowZeroStars`****\*\*\*\*?** Native radios have no "unselect" via keyboard — that's why the clear affordance in §9.3 is deliberate, not optional.
*   **Display never uses interactive elements.** No `<button>`, no `<input>`. `role="img"` + `aria-label` turns five glyphs into one spoken sentence. Without it a screen reader says "star star star star star" — meaningless. **This single line is the difference between an accessible display rating and a broken one.**
*   **`86%`** = 4.3 / 5. The fill is derived from the value, computed once.

### 9.2 CSS (fractional fill + hover preview done right)
**Display fractional fill** — the 4.3-stars problem. Two solid techniques.

**Technique A — gradient clip (single element, precise):**

```css
.rating-display .stars {
  --fill: 86%;                     /* 4.3 / 5 = 86% */
  display: inline-block;
  font-size: 20px;
  line-height: 1;
  background: linear-gradient(
    90deg,
    #DCA424 var(--fill),           /* Goldenrod up to the fill point */
    #4a4458 var(--fill)            /* muted empty after it */
  );
  -webkit-background-clip: text;
  background-clip: text;
  color: transparent;
}
```

One element, exact percentage, no layout math per star. This is the cleanest fractional renderer — the whole "4.3 stars" problem collapses to setting one custom property.

**Technique B — layered overlay with** **`clip-path`****\*\*\*\*/width (when you need per-star shapes):**

```css
.stars-wrap { position: relative; display: inline-block; color: #4a4458; }
.stars-wrap .filled {
  position: absolute; inset: 0; overflow: hidden;
  width: var(--fill);              /* clip the gold layer to the fill width */
  color: #DCA424; white-space: nowrap;
}
```

**Input hover-preview + selection** — the CSS-only "fill up to hovered star." The reverse DOM order in §9.1 is what makes this work: `~` (subsequent-sibling) selectors fill the hovered star _and everything after it in source order_, which is everything _before_ it visually.

```css
.rating-input { display: inline-flex; flex-direction: row-reverse; border: 0; gap: 2px; }
.rating-input input { position: absolute; opacity: 0; width: 1px; height: 1px; } /* visually hidden, still focusable */
.rating-input label {
  font-size: 28px; color: #4a4458; cursor: pointer;
  padding: 8px 2px;                /* pads the 28px glyph out to a >=44px hit target */
  transition: color .12s, transform .05s;
}
/* Hover-preview: the hovered star + all after it (visually: it and everything left) */
.rating-input label:hover,
.rating-input label:hover ~ label { color: #DCA424; }
/* Committed selection persists after mouse leaves */
.rating-input input:checked ~ label { color: #DCA424; }
/* Keyboard focus ring — never removed */
.rating-input input:focus-visible + label { outline: 2px solid #DCA424; outline-offset: 2px; border-radius: 4px; }
/* Reduced motion: kill the springy scale */
@media (prefers-reduced-motion: reduce) { .rating-input label { transition: none; } }
```

The interplay to understand: `:hover` gives the _preview_, `:checked` gives the _commit_, and because hover styling wins while the pointer is down, releasing on a star leaves `:checked` holding the fill. On mouse-leave, preview evaporates and the committed value snaps back — exactly the state model from §5.

### 9.3 React + TypeScript (the accessible input, with clear + half-star display)
The reusable component. Input mode is a real radio group; display mode is text-first. One file, two honest paths — never one path pretending to be both.

```typescript
import { useId, useState, KeyboardEvent } from "react";

/* ---------- INPUT: interactive, radio-group semantics ---------- */
interface RatingInputProps {
  name: string;
  max?: number;
  value: number;                       // 0 = unrated
  onChange: (value: number) => void;
  label: string;
  disabled?: boolean;
  allowClear?: boolean;                // let the user return to 0
}

export function RatingInput({
  name, max = 5, value, onChange, label, disabled, allowClear = true,
}: RatingInputProps) {
  const groupId = useId();
  const [preview, setPreview] = useState<number | null>(null);
  const shown = preview ?? value;      // preview wins while hovering/focusing

  // Arrow keys change the value; Home/End jump to bounds; 0 or Delete clears.
  function onKeyDown(e: KeyboardEvent<HTMLDivElement>) {
    if (disabled) return;
    let next = value;
    if (e.key === "ArrowRight" || e.key === "ArrowUp") next = Math.min(max, value + 1);
    else if (e.key === "ArrowLeft" || e.key === "ArrowDown") next = Math.max(allowClear ? 0 : 1, value - 1);
    else if (e.key === "Home") next = allowClear ? 0 : 1;
    else if (e.key === "End") next = max;
    else if ((e.key === "0" || e.key === "Delete" || e.key === "Backspace") && allowClear) next = 0;
    else return;
    e.preventDefault();
    onChange(next);
  }

  return (
    <div
      role="radiogroup"
      aria-label={label}
      aria-disabled={disabled || undefined}
      onKeyDown={onKeyDown}
      onMouseLeave={() => setPreview(null)}
      className="rating-input"
    >
      {Array.from({ length: max }, (_, i) => {
        const starValue = i + 1;
        const checked = value === starValue;
        const filled = starValue <= shown;
        return (
          <span
            key={starValue}
            role="radio"
            aria-checked={checked}
            aria-label={`${starValue} ${starValue === 1 ? "star" : "stars"}`}
            tabIndex={disabled ? -1 : checked || (value === 0 && starValue === 1) ? 0 : -1}
            onClick={() => !disabled && onChange(starValue)}
            onMouseEnter={() => !disabled && setPreview(starValue)}
            onFocus={() => !disabled && setPreview(starValue)}
            onBlur={() => setPreview(null)}
            className={`star ${filled ? "star--on" : ""}`}
          >
            ★
          </span>
        );
      })}
      {/* Explicit, keyboard-reachable clear — the part juniors forget */}
      {allowClear && value > 0 && !disabled && (
        <button type="button" className="rating-clear" onClick={() => onChange(0)}>
          <span className="sr-only">Clear rating</span>×
        </button>
      )}
      {/* Hidden field so the value posts in a plain form submit */}
      <input type="hidden" name={name} value={value} id={groupId} />
    </div>
  );
}

/* ---------- DISPLAY: read-only, text-first, fractional ---------- */
interface RatingDisplayProps {
  value: number;                       // e.g. 4.3
  max?: number;
  count?: number;                      // number of reviews
  precision?: number;                  // decimals to show, default 1
}

export function RatingDisplay({ value, max = 5, count, precision = 1 }: RatingDisplayProps) {
  if (count === 0) return <span className="rating-none">No ratings yet</span>;
  const rounded = value.toFixed(precision);
  const fillPct = `${(value / max) * 100}%`;
  const label =
    `Rated ${rounded} out of ${max} stars` +
    (count != null ? `, ${count.toLocaleString()} reviews` : "");
  return (
    <span className="rating-display" role="img" aria-label={label}>
      <span className="stars" style={{ ["--fill" as string]: fillPct }} aria-hidden="true">
        {"★".repeat(max)}
      </span>
      <span className="rating-text" aria-hidden="true">{rounded}</span>
      {count != null && <span className="rating-count" aria-hidden="true">({count.toLocaleString()})</span>}
    </span>
  );
}
```

Why this is the senior version, not the junior one:
*   **Input is a real** **`radiogroup`** **of** \*\*`radio`\*\***s** with roving `tabIndex` (one tab stop, arrows move within) — the same pattern as [Radio Buttons](https://app.clickup.com/8495850/docs/838qa-81211/838qa-216471). Not five buttons, not five checkboxes.
*   **Preview state is separate from committed value.** Hover/focus paints `preview`; only click/keypress calls `onChange`. Mouse-leave and blur clear the preview so the real value always wins at rest.
*   **Clear is explicit and keyboard-reachable** (`0` / `Delete`, plus a visible ×). Native radios can't be unchecked by keyboard, so we build the escape hatch deliberately.
*   **Display refuses to lie.** `count === 0` short-circuits to "No ratings yet" instead of five hollow stars, and the accessible label is a full sentence, not glyphs. The stars are `aria-hidden` decoration.
*   **The two components share no code path** — because they share no contract.

### 9.5 The structured data (AggregateRating JSON-LD — the SEO payload)
The invisible half of a display rating, and the reason your stars show up in Google. Emit this in the page `<head>` or inline for any product/page with an aggregate. **Only emit it when you genuinely have ratings** — a `ratingCount` of 0, or fabricated numbers, is a structured-data violation Google penalizes.

```plain
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "Product",
  "name": "Urban Jungle Goddess — Command Core Setup",
  "aggregateRating": {
    "@type": "AggregateRating",
    "ratingValue": "4.3",
    "bestRating": "5",
    "worstRating": "1",
    "ratingCount": "1240",
    "reviewCount": "1187"
  }
}
</script>
```

Rules that keep you out of trouble:
*   **The visible rating and the JSON-LD must match.** Google's guidance: structured data must reflect what a user actually sees on the page. Emit "4.3" in the schema _and_ render "4.3" — mismatches get the rich result revoked.
*   **`ratingCount`** **vs** **`reviewCount`****\*\*\*\*:** `ratingCount` = total ratings (including star-only, no text); `reviewCount` = ratings with written reviews. Use both when you have both; don't invent one from the other.
*   **Attach it to a real thing** — `Product`, `LocalBusiness`, `Recipe`, `Course`, etc. A floating `AggregateRating` with no parent is invalid.
*   **Individual** **`Review`** **objects** can nest their own `reviewRating`; the aggregate summarizes them. Don't double-count.
*   **Validate** with Google's Rich Results Test before shipping — a single missing required field silently kills the stars.

### 9.9 Next.js (App Router — server display, client input)
Display ratings are ideal Server Components: they're read-only data, so render them on the server and ship zero JS for them. The input is interactive, so it's a Client Component, and its submit runs as a Server Action.

```typescript
// app/product/[id]/Stars.tsx  — SERVER COMPONENT, no "use client"
import { RatingDisplay } from "@/components/RatingDisplay";
export default async function Stars({ productId }: { productId: string }) {
  const agg = await getAggregate(productId);          // runs on server
  return <RatingDisplay value={agg.value} count={agg.count} />;
}

// app/product/[id]/RateForm.tsx  — CLIENT COMPONENT
"use client";
import { useActionState } from "react";
import { submitRating } from "./actions";
import { RatingInput } from "@/components/RatingInput";
import { useState } from "react";

export function RateForm({ productId }: { productId: string }) {
  const [state, action] = useActionState(submitRating, { ok: false });
  const [value, setValue] = useState(0);
  return (
    <form action={action}>
      <input type="hidden" name="productId" value={productId} />
      <RatingInput name="rating" value={value} onChange={setValue} label="Rate this product" />
      <button type="submit" disabled={value === 0}>Submit rating</button>
      <p aria-live="polite">{state.ok ? "Thanks for rating!" : state.error}</p>
    </form>
  );

// app/product/[id]/actions.ts  — SERVER ACTION
"use server";
import { z } from "zod";
import { revalidatePath } from "next/cache";

const Schema = z.object({
  productId: z.string(),
  rating: z.coerce.number().int().min(1).max(5),      // never trust the client
});

export async function submitRating(_prev: unknown, formData: FormData) {
  const parsed = Schema.safeParse(Object.fromEntries(formData));
  if (!parsed.success) return { ok: false, error: "Pick 1–5 stars." };
  const user = await requireAuth();
  await db.rating.upsert({                              // upsert => one rating per user
    where: { productId_userId: { productId: parsed.data.productId, userId: user.id } },
    update: { value: parsed.data.rating },
    create: { productId: parsed.data.productId, userId: user.id, value: parsed.data.rating },
  });
  revalidatePath(`/product/${parsed.data.productId}`); // display re-aggregates
  return { ok: true };
}
```

The `upsert` is the load-bearing detail: **one rating per user per item**, or your aggregate is a ballot-stuffing target.

### 9.10 Node.js (the endpoint behind the input)

```typescript
import { z } from "zod";
const RateBody = z.object({ productId: z.string(), value: z.number().int().min(1).max(5) });

router.post("/api/ratings", requireAuth, rateLimit, async (req, res) => {
  const parsed = RateBody.safeParse(req.body);
  if (!parsed.success) return res.status(422).json(parsed.error.issues);

  // One rating per user per product: upsert, not insert. Prevents stuffing.
  const rating = await db.ratings.upsert({
    userId: req.user.id, productId: parsed.data.productId, value: parsed.data.value,
  });

  // Recompute aggregate atomically (or via a materialized view / trigger)
  const agg = await db.ratings.aggregate(parsed.data.productId); // { avg, count }
  return res.status(200).json({ rating, aggregate: agg });
});
```

Backend concerns a rating silently depends on:
*   **One vote per user per item** — upsert on `(userId, productId)`. Without it the average is meaningless.
*   **Server-side range validation** — reject anything outside 1..max. A `value: 999` from `curl` must not land.
*   **Aggregate integrity** — recompute `avg`/`count` transactionally, or keep a running sum + count so you don't rescan the table on every read. This is the number your JSON-LD publishes; it has to be right.
*   **Abuse / rate limiting** — rating endpoints are review-bombing targets. Throttle per user and per IP.

## 10\. Accessibility (non-negotiable)
The whole component lives or dies here, and the two modes have _different_ contracts. Do not merge them.

**Input rating:**
*   **It is a radio group.** Container `role="radiogroup"` (or a native `<fieldset>`), each star `role="radio"` + `aria-checked` (or a real `<input type="radio">`). Not buttons, not checkboxes — single-select is the whole point.
*   **Keyboard map:** Tab reaches the group (one stop, via roving `tabindex`). **Arrow keys change the value** (Right/Up = +1, Left/Down = −1). Home = min, End = max. **A clear key** (0 / Delete) returns to unrated. Space/Enter commits the focused star.
*   **Every star has a label:** `aria-label="4 stars"`, so focus announces "4 stars, radio, 4 of 5," not "star."
*   **Focus visible:** `:focus-visible` ring on the focused star, never removed.
*   **Errors announced:** "Rating required" goes through an `aria-live` region, not just a red tint.

**Display rating:**
*   **Expose the value as text — this is the cardinal rule.** `role="img"` + `aria-label="Rated 4.3 out of 5 stars, 1,240 reviews"`, with the star glyphs `aria-hidden="true"`. **Never** let a screen reader read five star characters as "star star star star star" — that conveys nothing and is the single most common rating a11y failure in the wild.
*   **No focus, no keyboard, no interactive roles.** It's not operable; making it focusable is a bug that promises interaction it can't deliver.
*   **Count is part of the label,** because "4.3 stars" without "from 1,240 reviews" is a weaker, and sometimes misleading, signal.

**Both:**
*   **Contrast ≥ 3:1** for the filled-vs-empty star distinction (it's non-text UI); the numeric text ≥ 4.5:1. Gold-on-dark clears this; gold-on-white often doesn't — check it.
*   **Never rely on color alone.** Fill amount (shape) must distinguish filled from empty, not just hue, for color-blind users.
*   **Touch target ≥ 44px** per input star, even at a 20px glyph. Pad it out.

## 11\. Innovative & Emerging Ideas (2026-aware)
*   **AI-summarized aggregates:** "Most reviewers praise durability, some flag sizing" generated above the stars. The rating becomes an entry point to a synthesized summary, not just a number.
*   **Weighted / verified ratings:** verified-purchase ratings weighted higher, recency-decayed averages, so the display value reflects _trustworthy_ signal. The glyph is the same; the math behind it is smarter.
*   **Sentiment-linked fractional fill:** partial fills driven by NLP sentiment on the review text, not just the star tally.
*   **Multi-dimensional ratings:** separate scales for value, quality, shipping — rendered as a small radar or stacked bars, each an accessible display rating.
*   **Liquid Glass rating chips** (§8b): refractive star lozenges on Apple 2026 surfaces, with the fill sheen animating on value change — behind a `prefers-reduced-motion` guard.
*   **Haptic input on mobile:** a light tap per star as the finger drags across the scale, confirming each step physically.

## 12\. Conversion & Trust Killers (the silent ones)
None throw an error. They just bleed trust and CTR.

*   **Stars read as "star star star" to screen readers.** You hid your strongest social proof from a whole audience. Fix: `role="img"` + text `aria-label`. The number-one killer.
*   **Dishonest rounding.** Rendering 4.2 as five full gold stars, or the text saying "5" when the value is 4.6. Users do the arithmetic and stop trusting every number on the page. Render fractional fill; keep the text exact.
*   **Empty stars for zero reviews.** Five hollow stars reads as "0/5 — awful." Show "No ratings yet" and suppress the schema.
*   **No hover preview on input.** Users can't tell which star they're about to pick, mis-tap, and either submit wrong or abandon. Preview is table stakes.
*   **No way to un-rate.** Mis-tap five stars, no clear affordance, forced to submit a lie or reload. Ship the clear path.
*   **JSON-LD that doesn't match the page.** Google revokes the rich result; your SERP stars vanish exactly when you need them. Keep schema and visible value identical.
*   **Cramped mobile stars.** Sub-44px targets jammed together = constant mis-taps = garbage data. Pad the hit area.
*   **Fabricated / stuffed ratings.** No one-vote-per-user rule, or invented counts in the schema. Beyond the ethics, it's a Google penalty and a lawsuit vector.

**The through-line:** every one fails quietly — a slightly lower CTR, a slightly thinner review corpus, a slowly eroding trust number that's easy to blame on "the market." Audit your ratings before your ad spend.

## 13\. Advanced Patterns
*   **Fractional fill via one custom property** (§9.2 Technique A): the entire "4.3 stars" problem reduces to `--fill: 86%`. Compute the percentage from the value once; never hand-place per-star clips.
*   **TS-enforced mode separation:** make `RatingInput` and `RatingDisplay` distinct exports with non-overlapping props, so no one can pass `onChange` to a display rating or forget `aria-label` on it. The type system enforces the input/display line the docs draw in §1.
*   **Token-driven skinning:** `--rating-fill`, `--rating-empty`, `--rating-size` as component tokens referencing semantic tokens. Rebrand from Goldenrod to any accent by swapping one primitive — see the token tiers in [Button §9.23](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200231).
*   **Aria-live readout for input:** pair the group with `<p aria-live="polite">You rated 4 out of 5</p>` so keyboard/SR users hear each change, not just see the fill.
*   **Badge-wrapped compact display:** the "4.6 ★" chip on a card is a [Badge](https://app.clickup.com/8495850/docs/838qa-81211/838qa-217711) around a `RatingDisplay` — keep the full text `aria-label` even when the visible glyph count shrinks to one.
*   **Server-materialized aggregate:** keep `sum` + `count` columns updated on write, so display reads are O(1) and the JSON-LD value is always fresh without a table scan.

## 14\. Performance & Bundle Cost
*   **Don't import an icon library for a star.** A star is one glyph — a Unicode `★`, an inline SVG path, or a single named import. `import * as Icons` for a checkmark-shaped star pulls hundreds of KB. Named import or raw SVG only.
*   **Display ratings are static — render them on the server** (§9.9). A read-only aggregate should ship zero client JS.
*   **Fill via CSS custom property, not per-star DOM.** One gradient element beats five stacked absolutely-positioned overlays for both bytes and paint cost.
*   **Delegate input listeners** in long lists (a table of rate-able rows): one delegated handler on the container, not one per row's five stars. See [Button §9.16](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200231).
*   **Animate** **`transform`****/****`opacity`** **only** on hover-preview and commit — never `width`/`margin`, which reflow every frame.
* * *

## 15\. Security (the input reaches the server)
*   **Validate range server-side.** 1..max, integer, always. A `value: 999` or `value: -3` from `curl` must be rejected — the UI's five stars are a hint, never a boundary.
*   **One vote per user per item.** Upsert on `(userId, itemId)`; without it, the average is a ballot box with no lock.
*   **Rate-limit and detect bursts.** Rating endpoints are review-bombing and astroturf targets. Throttle per user and per IP; flag anomalous bursts.
*   **Authorize the actor and the target.** Can _this_ user rate _that_ item? (Verified purchase? Enrolled in the course?) Don't trust the `productId` the client sent.
*   **The UI is not a security boundary.** Disabling the submit until a star is picked is UX; the endpoint re-checks everything (see [Button §9.24](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200231)).
*   **Never publish fabricated aggregates in JSON-LD.** Beyond Google penalties, inflated review counts are an FTC-actionable misrepresentation.

## 16\. Senior-Level Checklist (ship-ready)
Before a rating is "done":
- [ ] **Mode is explicit:** input vs display chosen deliberately, built as separate components, not one with a `readonly` flag.
- [ ] **Input is a radiogroup** of radios (native `<input type=radio>` or `role=radio` + `aria-checked`) — not buttons, not checkboxes.
- [ ] **Keyboard:** Tab reaches the group (one stop), arrows change value, Home/End jump, 0/Delete clears.
- [ ] **Hover-preview** paints transiently and snaps back to the committed value on leave.
- [ ] **Clear affordance** exists and is keyboard-reachable.
- [ ] **Display exposes the value as text:** `role="img"` + `aria-label="Rated 4.3 out of 5…"`, glyphs `aria-hidden`. No "star star star."
- [ ] **Zero-review case** renders "No ratings yet," not empty stars, and emits no schema.
- [ ] **Fractional fill** is honest (4.3 looks like 4.3); text value is exact, never rounded to a lie.
- [ ] **AggregateRating JSON-LD** present, attached to a real entity, matching the visible value, validated in Rich Results Test.
- [ ] **Server:** range-validated, one-vote-per-user (upsert), rate-limited, authorized.
- [ ] **Touch target ≥ 44px** per input star; filled/empty distinguished by shape + ≥3:1 contrast, not color alone.
- [ ] **`prefers-reduced-motion`** kills preview/fill animation and any glass sheen.

## 17\. Visual Styles (recap)
Every skin in §8b is **skin only**. A Neo-Brutalist star and a UJG-Brand Goldenrod-on-Eminence star share one skeleton: the input is a radiogroup with arrow-key control and a 44px target; the display announces "Rated 4.3 out of 5" and emits matching JSON-LD. Skin governs glyph shape, fill treatment, glow, and motion — never semantics, keyboard, focus, target size, or the text-value contract. Guard glass/liquid-glass/neumorphism for contrast; guard aurora/liquid-glass for `prefers-reduced-motion`. Full guidance in [Design Styles](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200551).
* * *

**Bottom line:** a rating is two components wearing the same glyph. Decide — every single time — whether the user is _producing_ the number or _consuming_ it, then build the matching contract: a radio group with keyboard and a clear path for input, or a text-first, `role="img"`, schema-backed display for output. Blur that line and you ship stars that trap keyboard users, lie to screen readers, and go invisible in Google. Draw it hard and the rest — fractional fill, hover preview, structured data — falls into place.
