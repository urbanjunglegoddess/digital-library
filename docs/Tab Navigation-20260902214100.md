# Tab Navigation

# Tab Navigation: A Senior Engineer's Complete Breakdown
Tabs that change the URL and swap the page. Looks like the ARIA tabs widget, is nothing like it under the hood — and confusing the two is the single most common accessibility failure in modern app shells.

**The one distinction to burn in first:** this doc is about **routed** tab navigation — a row of tabs where each one is a _link_ to a different URL (`/settings/profile`, `/settings/billing`), the browser's back button works, and the address bar changes as you move. It is **not** the in-page `role="tablist"` widget that swaps panels without touching the URL. That widget lives in the sibling **Tabs** doc. They render almost identically. They are semantically opposite. Getting this wrong is the whole reason this page exists.

**Try it live:** the companion playground will let you tune the tab style (underline, pill, segmented), the router (React Router / Next.js App Router), the active-detection strategy, and mobile overflow behavior, then read live code for every target below. It's built in a later pass, so there's no URL yet — the code in §9 is the source of truth until then.

**Audit a tab bar:** the companion audit will paste your nav markup and flag the #1 failure — `role="tab"` on something that navigates — plus missing `aria-current`, missing landmark label, and arrow-key handlers that shouldn't be there. Also a later pass.

Sibling docs: [Button](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200231) · [Cards](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200471) · [Component Asset Template](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200531) · [Design Styles (visual languages)](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200551). Cross-reference the **Tabs** widget doc (the ARIA `tablist`), **Navigation** (top-level site nav), and **Bottom Tabs** (mobile tab bar) throughout.

## 1\. What Tab Navigation Actually Is
Tab navigation is a set of **links** that look like tabs and switch between **routes** (URLs), where each route renders a different page or view. Click "Billing" and the URL becomes `/settings/billing`, the browser history gets an entry, the page content changes, and the tab shows as current. It is navigation wearing a tab costume.

The word "tabs" collapses two genuinely different components that share a visual language and nothing else:

*   **Tab Navigation (routing — THIS doc):** each tab is an `<a>` / router `<Link>`. Activating it changes the URL, pushes browser history, and renders a different route. It is **deep-linkable** (paste the URL, land on that tab), **shareable**, and **back-button-correct**. Semantics: a `<nav>` landmark full of links, the active one marked `aria-current="page"`.
*   **Tabs, the ARIA widget (the sibling doc):** a `role="tablist"` containing `role="tab"` buttons that show/hide `role="tabpanel"` regions **within the same page**. The URL does not change. It is not deep-linkable by default, arrow keys move between tabs (roving tabindex), and it exists to organize content on _one_ screen — a product page's "Description / Reviews / Shipping," a settings card with three sub-forms that all live at the same route.

Here is the mistake, stated plainly: **people reach for the ARIA tabs pattern to build routed navigation.** They put `role="tab"` and `role="tablist"` on their router links, wire up arrow-key roving, and manage `aria-selected`. Now they have a screen reader announcing "tab, 2 of 4, selected" for something that is actually a page navigation, the back button is broken or lying, the URL doesn't reflect the view, and keyboard users get an arrow-key model that fights the browser's own link model. It is more code, worse semantics, and a broken address bar — all to reimplement what an `<a href>` does for free.

**The rule:** _if activating it changes the URL and renders a different route, it is navigation — use links in a_ _`<nav>`__\_\_, mark the current one with_ _`aria-current="page"`__\_\_, and never put_ _`role="tab"`_ _on it. If it swaps panels on the same URL, that's the Tabs widget — go read that doc._ The visual can be identical. The semantics must not be.

One more distinction people trip on — **Tab Navigation vs the Navigation component vs Bottom Tabs:**
*   **Navigation** (sibling doc) is the top-level site/app nav: the primary menu that gets you between major sections. Tab navigation is usually _within_ a section — sub-navigation for the settings area, the profile area, a dashboard's views.
*   **Bottom Tabs** (sibling doc) is the mobile pattern: a fixed bar at the bottom with 3–5 top-level destinations, thumb-reachable. It is _also_ routed navigation (same semantics as this doc) but with different placement, sizing, and platform conventions. On native, it maps to `UITabBar` / Material `NavigationBar`.

Tab navigation is the horizontal (occasionally vertical) row of routed sub-nav that sits under a page header. That's the component.

## 2\. Why It Matters
Tab navigation is where users build a mental map of _where they are_ in a section of your product. It carries weight out of proportion to its size:

*   **It's a URL contract.** Because each tab is a real route, the URL is now part of your UX. Users bookmark `/dashboard/analytics`, share it in Slack, and expect to land exactly there. Support says "go to the Billing tab" and pastes a link. Get the routing right and the whole product becomes linkable, screenshot-able in bug reports, and navigable by history. Fake it with a stateful widget and every one of those breaks silently.
*   **Back-button trust.** The single fastest way to make a web app feel broken is a back button that doesn't do what the user expects. If your tabs swap content without history entries, "back" leaves the whole section — or worse, does nothing. Routed tabs make back/forward move between tabs, which is what users on the web have expected for thirty years.
*   **Accessibility correctness.** A screen-reader user hitting a `role="tablist"` expects arrow-key roving and same-page panels. Hitting a `<nav>` of links they expect Tab-to-move and a page change. Mismatch the announced role and the actual behavior and you've built a trap. The correct semantics are _less_ work — this is the rare case where the accessible build is the cheaper build.
*   **Perceived performance.** Routed tabs let you **code-split** per tab (each panel is a lazy chunk), **prefetch** on hover, and **restore scroll** on back — the levers that make navigation feel instant. A monolithic tabs widget loads everything up front. The routing model is what unlocks the performance work.
* * *

## 3\. Anatomy of Tab Navigation
Every well-built routed tab bar decomposes into predictable parts:

*   **Nav container:** a `<nav>` landmark with an accessible name (`aria-label="Settings"`). This is what makes it a navigation region a screen reader can jump to, and distinguishes it from every other `<nav>` on the page.
*   **Tab list / track:** the visual row (a `<ul>` of links, or just the links). Holds the tabs, handles overflow/scroll on narrow screens.
*   **Tab (link):** an `<a href>` or router `<Link>`. Has a label, optional leading icon, optional count badge ("Inbox 12"). The active one carries `aria-current="page"`.
*   **Active indicator:** the visual mark of the current route — an underline bar, a filled pill, a left border (vertical). Purely presentational; the _semantic_ truth is `aria-current`, not the color.
*   **Overflow affordance:** on narrow viewports, either a horizontal scroll track with edge fades, a "More ▾" menu, or a collapse-to-select. The tabs that don't fit still need to be reachable.
*   **Routed panel / outlet:** the region that renders the matched route's content (`<Outlet>` in React Router, `{children}` in a Next.js layout, `<router-outlet>` in Angular). _Not_ part of the nav — it's the destination the nav points at.

The thing juniors under-build: the **nav container's accessible name**. A page with three tab bars (main nav, settings sub-nav, a filter row) that are all just `<nav>` with no label gives a screen-reader user three identical "navigation" landmarks and no way to tell them apart. `aria-label` on each is non-negotiable.

## 4\. Sizes & Density
Tab bars scale by context. Real values:

| Size | Tab height | Padding (H) | Font | Gap | Use |
| ---| ---| ---| ---| ---| --- |
| SM | 32px | 12px | 13px | 4px | Dense dashboards, nested sub-nav, desktop toolbars |
| MD | 40px | 16px | 14px | 8px | Default section sub-nav |
| LG | 48px | 20px | 15px | 8px | Primary section nav, touch-first desktop |
| XL | 56px | 24px | 16px | 12px | Mobile bottom tabs, marketing/section headers |

Rules that matter:
*   **Tap target stays ≥44px even when the visual height is smaller.** A 32px underline tab still needs 44px of _hit_ area — expand it with vertical padding or a pseudo-element, don't ship a 32px-tall tap target to a phone.
*   **Height is a spacing token, not a magic number,** so the whole nav system scales with the type ramp.
*   **The active indicator gets its own tokens** (thickness, offset, color) so underline vs pill is a theme swap, not a rewrite.
*   **Label length drives overflow strategy.** Short, stable labels ("Profile," "Billing") can use fixed-width equal tabs; variable labels ("Team members," "API") should size to content and plan for horizontal scroll.

## 5\. States
Routed tabs have a state model that overlaps the button's but adds route-specific states. Missing states are the amateur tell.

1. **Default (rest)** — a link not currently active. Muted color, no indicator.
2. **Active / current** — the tab whose route is showing. Full-contrast label + visible indicator (underline/pill/border) **and** `aria-current="page"`. The indicator is decoration; `aria-current` is the truth.
3. **Hover** — pointer over an inactive tab. Subtle color lift or faint indicator preview. Absent on touch — never the only signal.
4. **Focus** — reachable by keyboard. Visible `:focus-visible` ring on the _link_. This is a real focus ring on a real anchor, not a roving-tabindex fake.
5. **Pending / loading route** — the tab was clicked and the next route is loading (data fetch, lazy chunk). Show an inline spinner or a top progress bar, and reflect it with `aria-busy` on the outlet or a live region. This state does not exist in the ARIA tabs widget — it's unique to routing, because navigation can be async.
6. **Disabled** — a tab the user can't currently reach (unpurchased feature, incomplete prerequisite). Render as non-link text or `aria-disabled` with a tooltip explaining _why_. Don't just gray it out silently.
7. **Visited** — usually irrelevant for tabs (you don't want the browser's purple-visited link styling here) — reset it deliberately.
8. **Overflow / hidden** — a tab that exists but is scrolled off or collapsed into a "More" menu. Still reachable, still in the tab order.

Bonus: **badge/count** state — "Inbox 12," "Alerts •" — a live indicator on the tab that updates without a route change.

The one juniors forget: the **pending route** state. In an SPA, clicking a tab and waiting 400ms for the panel to fetch with _zero_ feedback feels broken — the user clicks again, thinks it froze. Every router below (§9) exposes a pending/transition signal for exactly this. Wire it.

## 6\. Types & Variants
By visual treatment (all share identical link semantics):

*   **Underline tabs:** the default. A bottom border/bar under the active tab. Reads as "sub-navigation," pairs with a page header. The web's most common tab-nav style.
*   **Pill / segmented tabs:** each tab is a rounded chip; the active one gets a filled background. Feels app-like, good for 2–4 options, common in mobile and settings toggles. (Distinct from a segmented _control_, which is usually the Tabs widget or a form input — see the distinction in §7.)
*   **Vertical / sidebar tabs:** tabs stacked in a left rail, active one marked with a left border or fill. Good for long lists of sub-sections (settings with 10+ areas). Still `<nav>` + links + `aria-current`.
*   **Icon + label tabs:** each tab pairs a glyph with text. Standard for bottom tabs; the icon aids scanning and recognition.
*   **Scrollable tabs:** more tabs than fit; the track scrolls horizontally with edge-fade affordances. Material's "scrollable tabs." Critical on mobile.
*   **Tabs with counts/badges:** labels carry live numbers ("Open 8 / Closed 142"). The count is a status, not a route change.

By functional placement:
*   **Section sub-nav:** under a page header, scoping a feature area. The prototypical tab nav.
*   **Bottom tab bar:** mobile top-level, thumb reach (see Bottom Tabs doc).
*   **Nested/hierarchical tabs:** a second tab row scoping _within_ an active first-level tab (e.g. Settings → Billing → \[Invoices / Payment methods / History\]). Each level is its own `<nav>` with its own label and its own URL segment.

## 7\. When to Use It (and When Not To)
Use routed tab navigation when the user moves between **sibling views that deserve their own URL** within a section, and you want each view deep-linkable, shareable, and back-button-navigable.

**Use tab navigation (routing) when:**
*   Each view is a distinct place the user might bookmark or link to (`/settings/billing`).
*   Back/forward should move between the views.
*   The views are heavy enough to benefit from code-splitting/lazy loading.
*   You want the current view reflected in the address bar for support, analytics, and screenshots.

**Use the Tabs widget (ARIA** **`tablist`****\*\*\*\*) instead when:**
*   The panels are lightweight, all belong to _one_ screen, and don't deserve their own URL (a product card's Description/Reviews/Specs).
*   You explicitly do _not_ want a history entry per switch.
*   Switching is a local content toggle, not a navigation.

**Use something else entirely when:**
*   **More than ~7 destinations** → that's a nav menu or sidebar, not tabs. Tabs don't scale to a big flat list.
*   **Top-level app sections** → that's the **Navigation** component (or Bottom Tabs on mobile), not sub-nav tabs.
*   **A single binary/one-of-few** **_input_** ("Monthly / Yearly" pricing toggle that changes displayed prices on the same page, no URL) → that's a segmented control / form input, closer to the Tabs widget or a radio group, _not_ routed navigation.
*   **Sequential steps** (checkout: Cart → Shipping → Payment) → that's a **stepper/wizard**, not tabs. Tabs imply free movement between peers; steppers imply order.

Placement heuristics:
*   **Directly under the section header,** so the tab bar scopes the header's subject.
*   **Left-align to content** on desktop; **full-width scroll** on mobile.
*   **Keep the tab bar sticky** on long panels so users can switch views without scrolling back up.
*   **Never nest more than two tab levels** — a third row of tabs is a sign the information architecture needs a rethink (menu, sidebar, or breadcrumb).

## 8\. Tab Navigation Across Design Systems
Same routed-links concept, different house rules:

*   **Material Design (Google):** "Tabs" are first-class — fixed vs scrollable, with an animated active indicator that slides between tabs. Material is explicit that tabs "organize content across different screens" and can be tied to navigation; the sliding underline is signature. Bottom `NavigationBar` is the mobile routed variant.
*   **Apple HIG (iOS/macOS):** `UITabBar` (bottom, routed, 2–5 items) is the canonical tab navigation and is _always_ top-level navigation, never in-page content switching — Apple is strict that tab bars are for navigation. On macOS, segmented controls handle in-view switching; tab views handle sub-navigation. iOS 26's Liquid Glass restyles the tab bar as a floating glass element.
*   **Fluent (Microsoft):** "Pivot" is the tab-nav control; `NavigationView` handles app-level routed nav with a rail/pane. Subtle materials, compact density.
*   **Ant Design / enterprise:** `Tabs` component doubles for both in-page and routed use; you wire the active key to your router yourself. Heavy admin UIs lean on it hard, often with closable/addable tabs (a browser-tab metaphor).
*   **Tailwind / utility-first:** no prescribed component — you compose a `<nav>` of links and style the active state via an `aria-current` selector or a router's active class. Freedom plus the responsibility to get semantics right yourself.
*   **shadcn/Radix:** ships a `Tabs` primitive (the ARIA widget) — which is _not_ what you want for routing. For routed tabs you build a `<nav>` of framework `<Link>`s and style with `cva`, reusing shadcn's token vocabulary. Radix's Tabs is a trap here if you need URLs (see §9.7).
*   **Bootstrap:** `.nav .nav-tabs` and `.nav-pills` are markup-first nav components meant to be used _with_ links for routing (or with JS for in-page). The `.active` class marks the current tab.

The through-line: every mature system separates "tabs that navigate" from "tabs that toggle panels." The frameworks that blur it (Ant, shadcn's single `Tabs`) hand you the wiring and expect you to know which one you're building. This doc is that knowledge.

## 9\. The Code
The biggest section. Routed tabs are **links in a landmark with an active-route class +** **`aria-current`** — everything below is that idea across targets. Notice what's _absent_ everywhere: no `role="tab"`, no `role="tablist"`, no arrow-key roving. That absence is the correctness.

### 9.1 HTML (the foundation — get this right and 80% is done)

```plain
<!-- Routed tab navigation: a LANDMARK of LINKS. No ARIA tab roles. -->
<nav aria-label="Settings" class="tab-nav">
  <ul class="tab-nav__list">
    <li>
      <a href="/settings/profile" class="tab" aria-current="page">Profile</a>
    </li>
    <li>
      <a href="/settings/billing" class="tab">Billing</a>
    </li>
    <li>
      <a href="/settings/team" class="tab">
        Team <span class="tab__badge" aria-hidden="true">3</span>
      </a>
    </li>
    <li>
      <a href="/settings/api" class="tab">API</a>
    </li>
  </ul>
</nav>

<!-- The destination the nav points at -->
<main id="panel">
  <!-- current route's content renders here -->
</main>
```

Key HTML rules:
*   **It's a** **`<nav>`** **with an** **`aria-label`****\*\*\*\*.** The label names the nav so multiple nav landmarks stay distinguishable. This is the piece people skip.
*   **Tabs are** **`<a href>`** **— real links.** Real URLs mean right-click "open in new tab," middle-click, copy-link, and browser prefetch all work for free. A `<button>` or `<div>` here throws all of that away.
*   **The active tab gets** **`aria-current="page"`** — _not_ `aria-selected`. `aria-selected` belongs to `role="tab"`; `aria-current="page"` is the correct signal for "this is the current page in a set of navigation links." This one attribute is the semantic heart of the component.
*   **Badges that are decorative get** **`aria-hidden`**, or fold the count into an accessible label (`aria-label="Team, 3 members"`) if it carries meaning.
*   **No** **`role`****\*\*\*\*, no** **`tabindex`****\*\*\*\*, no arrow-key script.** Links are already in the tab order and already keyboard-operable. Adding roving tabindex here is actively wrong.

### 9.2 CSS (active state + the sliding indicator done right)

```css
.tab-nav__list {
  display: flex;
  gap: 8px;
  list-style: none;
  margin: 0;
  padding: 0;
  border-bottom: 1px solid var(--tab-track, #e5e2ea);
}
.tab {
  --tab-indicator: transparent;
  display: inline-flex;
  align-items: center;
  gap: 6px;
  min-height: 44px;              /* tap target, even if visually shorter */
  padding: 10px 16px;
  color: var(--tab-fg, #6b6577);
  font: 500 14px/1 system-ui, sans-serif;
  text-decoration: none;
  border-bottom: 2px solid var(--tab-indicator);
  transition: color .15s, border-color .15s;
}
.tab:hover { color: var(--tab-fg-strong, #2a2333); }

/* Active state driven by aria-current — style the SEMANTIC truth, not a class */
.tab[aria-current="page"] {
  color: var(--tab-fg-active, #5F2C82);
  --tab-indicator: var(--tab-fg-active, #5F2C82);
  font-weight: 600;
}

/* Keyboard focus only */
.tab:focus-visible {
  outline: 2px solid #DCA424;
  outline-offset: 2px;
  border-radius: 4px;
}

/* Mobile: scrollable track instead of wrapping/overflow */
@media (max-width: 640px) {
  .tab-nav__list {
    overflow-x: auto;
    flex-wrap: nowrap;
    scrollbar-width: none;               /* hide bar, keep scroll */
    scroll-snap-type: x proximity;
  }
  .tab { scroll-snap-align: start; white-space: nowrap; }
}

@media (prefers-reduced-motion: reduce) {
  .tab { transition: none; }
}
```

The senior move: **style** **`[aria-current="page"]`****\*\*\*\*, not a** **`.active`** **class.** It forces the accessible attribute to exist (or the styling breaks, which you'll notice), and keeps the visual and the semantic in lockstep. If you style a `.active` class and forget `aria-current`, the tab _looks_ current to sighted users and is invisible to screen readers — a silent a11y bug. Bind them to the same selector and that can't happen.

The **sliding indicator** (Material-style) is a progressive enhancement: absolutely-position a single bar and animate its `transform: translateX()` / `width` to the active tab's box. Keep it `transform`/`opacity` only (compositor-only, no reflow), and gate the animation behind `prefers-reduced-motion`.

### 9.3 Vanilla JS (active detection without a framework)
No SPA router — just enhance real links. The "active" tab is whichever one matches the current URL.

```javascript
// Mark the tab matching the current path as current — on load and on nav.
function syncActiveTab() {
  const here = location.pathname;
  document.querySelectorAll(".tab").forEach((tab) => {
    const url = new URL(tab.href);
    // exact match, or "startsWith" for parent tabs owning nested routes
    const isCurrent = url.pathname === here;
    if (isCurrent) tab.setAttribute("aria-current", "page");
    else tab.removeAttribute("aria-current");
  });
}
syncActiveTab();

// If you intercept clicks for a soft SPA nav via the History API:
document.querySelector(".tab-nav")?.addEventListener("click", (e) => {
  const tab = e.target.closest("a.tab");
  if (!tab || e.metaKey || e.ctrlKey || e.shiftKey || e.button !== 0) return; // let new-tab/new-window through
  e.preventDefault();
  history.pushState({}, "", tab.href);   // update URL + history
  syncActiveTab();
  loadPanel(new URL(tab.href).pathname); // your async panel fetch
});

// Back/forward must re-sync — this is what makes the back button correct.
window.addEventListener("popstate", () => {
  syncActiveTab();
  loadPanel(location.pathname);
});
```

Two things this snippet gets right that hand-rolled versions miss: it **lets modifier-clicks through** (so "open in new tab" still works — the #1 casualty of naive click interception), and it **handles** **`popstate`** so back/forward actually re-render the panel and re-mark the tab. Skip `popstate` and your back button changes the URL but not the content — the classic broken SPA.

### 9.4 React Router (the canonical routed-tabs build)
React Router's `NavLink` was _made_ for this. It sets an `isActive` flag and, since v6.4+, `aria-current="page"` automatically on match.

```plain
import { NavLink, Outlet, useNavigation } from "react-router-dom";

const TABS = [
  { to: "/settings/profile", label: "Profile" },
  { to: "/settings/billing", label: "Billing" },
  { to: "/settings/team", label: "Team" },
  { to: "/settings/api", label: "API" },
];

export function SettingsTabs() {
  const navigation = useNavigation(); // "idle" | "loading" | "submitting"
  const pending = navigation.state === "loading";

  return (
    <section>
      <nav aria-label="Settings" className="tab-nav">
        <ul className="tab-nav__list">
          {TABS.map((t) => (
            <li key={t.to}>
              <NavLink
                to={t.to}
                // NavLink sets aria-current="page" on match automatically.
                // `end` prevents a parent route staying active on child routes.
                end
                className={({ isActive }) =>
                  isActive ? "tab tab--active" : "tab"
                }
              >
                {t.label}
              </NavLink>
            </li>
          ))}
        </ul>
      </nav>

      {/* The pending route state — unique to routing, easy to forget */}
      <main aria-busy={pending} className={pending ? "is-loading" : ""}>
        <Outlet />
      </main>
    </section>
  );
}
```

Why this is the senior version:
*   **`NavLink`** **handles** **`aria-current`** **for you** — you don't hand-manage it, and it can't drift out of sync with the visual active state.
*   **`end`** stops the classic bug where the parent tab (`/settings`) stays highlighted while you're on a child route. Use it on index/parent tabs.
*   **`useNavigation().state`** gives you the pending state for the loading indicator — the thing that makes tab switches feel responsive instead of frozen.
*   **`<Outlet>`** is the routed panel. The nav and the panel are decoupled — the router matches the URL and fills the outlet.

Data-router bonus: define each tab's route with a `loader` so data fetches _before_ the panel renders, and pair with `<Await>`/Suspense for streaming. Code-split each panel with `lazy:` on the route object so a tab's chunk loads only when visited (see §14).

### 9.5 Next.js App Router (layout + `usePathname`)
The App Router models tab navigation beautifully: a **layout** holds the tab bar and persists across tab switches; `{children}` is the routed panel; each tab is a `<Link>`; active detection uses `usePathname()`.

```plain
// app/settings/layout.tsx  (Server Component shell)
import { SettingsTabs } from "./settings-tabs";

export default function SettingsLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  return (
    <section>
      <SettingsTabs />
      {/* children = the active route's page.tsx — the routed panel.
          Because this lives in a layout, the tab bar does NOT re-render
          or lose state when you switch tabs. That persistence is the
          App Router's headline feature for this pattern. */}
      <main>{children}</main>
    </section>
  );
}
```

```plain
// app/settings/settings-tabs.tsx
"use client"; // needs the pathname hook + interactivity
import Link from "next/link";
import { usePathname } from "next/navigation";

const TABS = [
  { href: "/settings/profile", label: "Profile" },
  { href: "/settings/billing", label: "Billing" },
  { href: "/settings/team", label: "Team" },
  { href: "/settings/api", label: "API" },
];

export function SettingsTabs() {
  const pathname = usePathname();
  return (
    <nav aria-label="Settings" className="tab-nav">
      <ul className="tab-nav__list">
        {TABS.map((t) => {
          const isActive =
            pathname === t.href || pathname.startsWith(t.href + "/");
          return (
            <li key={t.href}>
              <Link
                href={t.href}
                aria-current={isActive ? "page" : undefined}
                className={isActive ? "tab tab--active" : "tab"}
                prefetch // Next prefetches the route on hover/viewport
              >
                {t.label}
              </Link>
            </li>
          );
        })}
      </ul>
    </nav>
  );
}
```

Next-specific wins:
*   **The tab bar lives in** **`layout.tsx`****\*\*\*\*, so it persists** across tab switches — no flash, no re-mount, and scroll position in the nav is preserved. This is why the App Router is the strongest home for routed tabs.
*   **`aria-current={isActive ? "page" : undefined}`** — set it explicitly since Next's `Link` doesn't auto-apply it like React Router's `NavLink`.
*   **`pathname.startsWith(t.href + "/")`** keeps the parent tab active on nested routes (mirror of React Router's `end`, inverted). Choose exact vs prefix per tab deliberately.
*   **`prefetch`** makes the next panel's code + data ready before the click — near-instant switches.
*   **Loading UI:** drop a `loading.tsx` in each tab's route folder and Next shows it (via Suspense) during the pending route state — the framework-native version of §9.4's `useNavigation`.

### 9.6 Tailwind CSS (utility-first)
No prescribed component; compose the `<nav>` and drive the active state off `aria-current` with Tailwind's arbitrary variant.

```plain
<nav aria-label="Settings">
  <ul className="flex gap-2 border-b border-zinc-200 overflow-x-auto">
    {tabs.map((t) => (
      <li key={t.href}>
        <a
          href={t.href}

            inline-flex items-center gap-1.5 min-h-11 px-4 py-2.5
```

The `aria-[current=page]:` arbitrary variant is the clean Tailwind idiom here: the active styling keys off the _accessible attribute_, so you literally cannot style the active tab without also making it accessible. Extract this into a `<Tab>` component with `cva` in a real app rather than repeating the string.

### 9.7 shadcn/ui — why its `Tabs` is the wrong tool (and what to do)
shadcn ships a `Tabs` component built on **Radix Tabs** — which is the ARIA `role="tablist"` widget. It is excellent, and it is **the wrong primitive for routed navigation**: it manages `aria-selected`, roving arrow-key focus, and same-page panel toggling with no URL involvement. Drop your router links into it and you get all the ARIA-tabs baggage (§1) on something that navigates.

**Honest answer: there is no shadcn "routed tabs" primitive — you compose one.** Reuse shadcn's tokens and `cva`, but build a `<nav>` of links:

```plain
import Link from "next/link";
import { usePathname } from "next/navigation";
import { cva } from "class-variance-authority";
import { cn } from "@/lib/utils";

const tab = cva(
  "inline-flex items-center gap-1.5 min-h-11 px-4 text-sm font-medium " +
    "border-b-2 transition-colors focus-visible:outline-none " +
    "focus-visible:ring-2 focus-visible:ring-ring",
  {
    variants: {
      active: {
        true: "text-primary border-primary font-semibold",
        false: "text-muted-foreground border-transparent hover:text-foreground",
      },
    },
    defaultVariants: { active: false },
  }
);

export function NavTabs({ tabs }: { tabs: { href: string; label: string }[] }) {
  const pathname = usePathname();
  return (
    <nav aria-label="Section" className="flex gap-2 border-b">
      {tabs.map((t) => {
        const active = pathname === t.href;
        return (
          <Link
            key={t.href}
            href={t.href}
            aria-current={active ? "page" : undefined}
            className={cn(tab({ active }))}
          >
            {t.label}
          </Link>
        );
      })}
    </nav>
  );
}
```

**Use shadcn's** **`Tabs`** **only when you genuinely want same-page panels with no URL change** — that's the Tabs widget doc's territory. The moment you need URLs, drop it and compose links. Say this out loud in code review; it's the single most common shadcn misuse.

### 9.8 Vue Router (`RouterLink` + `router-view`)
Vue Router's `<RouterLink>` auto-applies active classes and `aria-current="page"` on exact match.

```plain

  { to: "/settings/profile", label: "Profile" },
  { to: "/settings/billing", label: "Billing" },
  { to: "/settings/team", label: "Team" },

<template>
  <section>
    <nav aria-label="Settings" class="tab-nav">
      <ul class="tab-nav__list">

          <!-- exact-active-class marks the current route; RouterLink adds
               aria-current="page" for you when `exact` matches. -->
          <RouterLink
            :to="t.to"
            class="tab"
            active-class="tab--active"
            exact-active-class="tab--exact"
          >
            {{ t.label }}
          </RouterLink>
        </li>
      </ul>

    <!-- routed panel -->
    <RouterView v-slot="{ Component }">
      <Suspense>

      </Suspense>
    </RouterView>
  </section>
</template>
```

`<RouterLink>` distinguishes **active** (route is a prefix — good for parent tabs) from **exact-active** (route matches exactly), letting you highlight nested-route parents correctly. Wrap `<RouterView>` in `<Suspense>` for the pending-route state on async components.

Angular has the most declarative active-state story of any framework: `routerLinkActive` toggles a class _and_ `ariaCurrentWhenActive` sets the attribute.

### 9.12 Web Component (framework-agnostic routed tabs)
A reusable tab bar that reads the current location and renders links — works with any router that updates the URL.

```typescript
class NavTabs extends HTMLElement {
  // Stable reference so the same handler can be removed on teardown.
  private onPopState = () => this.render();

  connectedCallback() {
    if (!this.shadowRoot) this.attachShadow({ mode: "open" });
    this.render();
    // Re-render on history navigation so aria-current stays correct.
    window.addEventListener("popstate", this.onPopState);
  }
  disconnectedCallback() {
    // Remove the listener on teardown — otherwise every tab bar that mounts
    // and later unmounts leaks a popstate handler re-rendering a detached tree.
    window.removeEventListener("popstate", this.onPopState);
  }
  render() {
    const here = location.pathname;
    // Escape interpolated text + attributes before they hit innerHTML: the
    // `tabs` JSON (and label/href within it) is data, not trusted markup —
    // raw interpolation is HTML/attribute injection (XSS).
    const esc = (s: string) =>
      String(s).replace(
        /[&<>"']/g,
        (c) =>
          ({ "&": "&", "<": "<", ">": ">", '"': """, "'": "&#39;" }[
            c
          ]!)
      );
    const items = JSON.parse(this.getAttribute("tabs") || "[]") as {
      href: string;
      label: string;
    }[];
    this.shadowRoot!.innerHTML = `
      <style>/* scoped tab styles */</style>
      <nav aria-label="${esc(this.getAttribute("label") ?? "Section")}">
        <ul part="list">
          ${items
            .map(
              (t) => `<li><a part="tab" href="${esc(t.href)}"
                ${here === t.href ? 'aria-current="page"' : ""}>${esc(t.label)}</a></li>`
            )
            .join("")}
        </ul>
      </nav>`;
  }
}
customElements.define("nav-tabs", NavTabs);
// <nav-tabs label="Settings" tabs='[{"href":"/settings/profile","label":"Profile"}]'></nav-tabs>
```

The `popstate` listener is the load-bearing detail: without it the component highlights the wrong tab after a back-button press — and the matching `disconnectedCallback` removes it, so a tab bar that unmounts doesn't leak a handler onto `window`. The interpolated `label`/`href` values are escaped before they reach `innerHTML`, because the `tabs` JSON is data, not trusted markup — building option/link strings from raw input is the classic injection foot-gun. Links inside shadow DOM still navigate normally, so real anchors keep all their native behavior.

### 9.14 Testing (routing behavior + a11y)
Test what a user experiences: the right tab is marked current, clicking navigates, the URL changes, back works, and there's **no** tab role.

**Component / integration (Vitest + React Testing Library + a memory router):**

```plain
import userEvent from "@testing-library/user-event";

    renderAt("/settings/profile");
```

## 10\. Accessibility (non-negotiable)
This is where the routing-vs-widget distinction becomes concrete. The two components have **opposite** accessibility contracts.

**Semantics:**
*   Wrap the tabs in `<nav aria-label="…">`. The label distinguishes this nav from every other landmark. Multiple unlabeled navs = a screen-reader user lost among identical "navigation" regions.
*   Each tab is an `<a href>` (`role="link"`). **Do not** add `role="tab"`, `role="tablist"`, or `role="tabpanel"`. Those roles announce a widget contract (arrow keys, same-page panels) your component doesn't honor.
*   Mark the active tab with **`aria-current="page"`** — the correct token for "current item in a set of navigation links." Not `aria-selected` (that's for `role="tab"`), not just a class.

**Keyboard model — the hard difference from the Tabs widget:**

|  | Tab Navigation (this doc) | Tabs widget (`role=tablist`) |
| ---| ---| --- |
| Move between tabs | Tab / Shift+Tab (each link is a stop) | Arrow keys (roving tabindex; the list is one tab stop) |
| Activate | Enter (it's a link) | Enter/Space, or automatically on arrow (auto-activation) |
| tabindex | none needed — links are focusable | exactly one `tabindex="0"`, rest `-1` |
| Result of activation | URL changes, page navigates | panel toggles, same URL |

Read that table twice. **Routed tabs use the normal link tab-order — you do NOT implement arrow-key roving.** If you find yourself writing an arrow-key handler for tab navigation, you've built the wrong component. Roving tabindex belongs to the widget; links belong to navigation. This is the most-failed part of the whole pattern.

**Focus:**
*   Each link shows a visible `:focus-visible` ring. Never `outline: none` without a replacement.
*   On navigation, manage where focus lands. In an SPA, after a tab click the panel content changes but focus may stay on the link (fine) — but if the panel is a distinct page, consider moving focus to the panel heading or an `<h1 tabindex="-1">` and announcing the change via a live region, so screen-reader users know the view changed. Route-change focus management is the SPA a11y detail teams forget.

**Labels & state:**
*   Icon-only tabs (rare in nav, common in bottom bars) need an accessible name — visible text or `aria-label`.
*   Count badges: fold into the accessible name if meaningful (`aria-label="Inbox, 12 unread"`), or `aria-hidden` if purely decorative.
*   Pending route: reflect with `aria-busy` on the panel and/or a polite live region ("Loading Billing").

**Contrast & target:**
*   Active/inactive tab text ≥ 4.5:1 on the background (WCAG AA). Don't rely on the indicator color alone to signal "current" — dim the inactive labels too, so the state survives for low-vision and color-blind users.
*   Tap target ≥ 44px even if the tab looks shorter.

## 11\. Innovative & Emerging Ideas
Routed tabs keep gaining new browser-native superpowers:

*   **View Transitions API (cross-document + SPA):** the browser natively cross-fades or morphs between the old and new panel when you navigate — including a shared-element transition where the _active indicator slides_ between tabs as a real browser transition, not a JS animation. `@view-transition { navigation: auto; }` gets you cross-document transitions on plain multi-page sites; the SPA API (`document.startViewTransition`) covers routers. This is the 2026 way to get Material's sliding-underline feel with almost no JS.
*   **Streaming / partial routes:** React Server Components + Suspense stream a tab's panel in progressively — the shell and tab bar paint instantly, panel data fills in. The pending state becomes a skeleton that resolves, not a spinner blocking the whole view.
*   **Speculative prefetch:** the Speculation Rules API (`<script type="speculationrules">`) can _prerender_ the likely-next tab so switching is genuinely instant. Pair with hover/viewport heuristics.
*   **URL as full state:** encoding not just the active tab but its sub-state (filters, sort) in the URL/search params, so a deep link restores the _exact_ view. Next.js `nuqs`, React Router search params, and TanStack Router's typed search make this ergonomic.
*   **Scroll-driven active indicator:** on scroll-spy tab navs (tabs that track a long scrolling page), CSS scroll-driven animations move the indicator natively without a scroll listener.
*   **Container queries for overflow:** the tab bar decides scroll-vs-menu-vs-wrap based on _its own_ width via `@container`, not the viewport — so a tab bar in a narrow sidebar behaves correctly regardless of screen size.
* * *

## 12\. Conversion & UX Killers
None throw an error. They just quietly erode trust and task completion.

*   **`role="tab"`** **on routed links (the cardinal sin).** Announces a widget contract the component breaks: screen readers promise arrow keys and same-page panels; the user gets a page navigation instead. Fix: `<nav>` + links + `aria-current`. This is the #1 tab-nav bug in the wild.
*   **The lying back button.** Tabs that swap content without a history entry mean "back" skips past the tabs entirely — the user expected to return to the previous tab and instead left the whole section. Use real routes so history is correct.
*   **Not deep-linkable.** The active tab lives only in component state, so a shared/bookmarked URL always opens on the default tab. Support says "check the Billing tab," pastes a link, it opens on Profile. Encode the tab in the URL.
*   **Active tab isn't obvious.** Relying on a faint indicator alone — no color/weight change on the label — leaves users unsure where they are. Dim inactive tabs _and_ mark the active one clearly, and never with color alone.
*   **Intercepted clicks that break new-tab.** Naive `e.preventDefault()` on every click kills middle-click, Cmd/Ctrl-click, and "open in new tab." Let modified clicks through (§9.3).
*   **No pending state.** Click a tab, 500ms of nothing, user clicks again or bounces. Show a spinner/progress/skeleton on route load.
*   **Overflow that hides tabs.** More tabs than fit, and the extras just vanish off-screen with no scroll affordance or menu. Every tab must stay reachable — scroll track with edge fades or a "More" menu.
*   **Losing scroll position on back.** User scrolls down a long tab panel, clicks into a detail, hits back — and lands at the top of the panel, place lost. Restore scroll on history navigation (§13).
*   **Parent tab stays highlighted on child routes** (or nothing is highlighted). The `end` / `exact` mismatch. Two tabs look active, or none does — either way the user's location signal is broken.

The through-line: these fail _silently_. No crash, just users who can't tell where they are, can't share where they are, and can't get back. Audit your tabs' URLs and history before you blame "confusing navigation" on the design.
* * *

## 13\. Advanced Patterns
*   **Deep-linkable sub-state in search params.** Keep the tab in the path (`/reports/sales`) and the _within-tab_ state in the query (`?range=90d&sort=desc`). Now a pasted URL restores the exact view. Read/write with the router's search-param API; debounce writes so every keystroke doesn't spam history.

```plain
// React Router: tab in path, view-state in searchParams
const [params, setParams] = useSearchParams();
const range = params.get("range") ?? "30d";
// changing range: setParams(p => { p.set("range", next); return p; }, { replace: true })
// `replace: true` avoids a history entry per filter tweak — back still means "previous tab"
```

*   **Scroll position restoration.** On back/forward, restore the panel's scroll; on a _new_ tab click, scroll to top. Browsers do this for full page loads; SPAs must re-implement it. React Router's `<ScrollRestoration>`, Next's App Router (automatic, with `scroll` control on `<Link>`), and SvelteKit (automatic) handle it — know which your stack does and test it, because a lost scroll position on back is a top complaint.
*   **Per-tab code-splitting.** Each panel is a lazy chunk loaded only when its tab is visited. This is the payoff of routing over a monolithic widget: a 5-tab section ships 1 tab's JS on first paint, not 5.

```plain
// React Router data router: lazy route per tab
{ path: "billing", lazy: () => import("./BillingPanel") }
// Next.js: automatic per-route code-splitting; each page.tsx is its own chunk
// Angular: loadComponent: () => import("./billing").then(m => m.BillingPanel)
```

*   **Prefetch on intent.** Prefetch the next tab's code + data on hover/focus/viewport so the click resolves instantly. Next `<Link prefetch>`, SvelteKit `data-sveltekit-preload-data="hover"`, React Router `<Link prefetch="intent">`. Cheap latency win, near-zero cost.
*   **Design tokens for the indicator system.** Underline vs pill vs left-border becomes a token swap, not a rewrite:

```css
:root {
  --tab-fg: #6b6577;
  --tab-fg-active: #5F2C82;
  --tab-indicator-size: 2px;
  --tab-indicator-color: var(--tab-fg-active);
  --tab-radius: 0;              /* pills: bump to 999px + swap border for bg */
}
```

*   **TypeScript-enforced route safety.** Type the tab list to the router's known routes so a typo'd `href` won't compile (TanStack Router's typed routes, or a `satisfies readonly Route[]` union). Kills the "tab links to a 404" class of bug at build time.
*   **Persisted layout, swapped panel.** In Next's App Router (and Remix nested routes), the tab bar in `layout.tsx` persists while only `{children}` re-renders — so nav state, scroll, and focus in the bar survive tab switches with no flash. Structure your routes so the tab bar is in the layout, the panel is the page.

## 14\. Performance & Bundle Cost
Routed tabs are, done right, a _performance win_ over a monolithic tabs widget — but only if you use the routing:

*   **Code-split per tab (the headline win).** A widget renders all panels' components into one bundle. Routed tabs let each panel be its own lazy chunk — first paint ships only the active tab's code. For a heavy 6-tab admin section this can cut initial JS by 60–80%. This is _the_ reason to prefer routing when panels are non-trivial.
*   **Prefetch to hide the split cost.** Splitting adds a network round-trip on first visit to a tab. Prefetch-on-hover/viewport (§13) hides it — the chunk arrives before the click.
*   **Persist the shell, don't re-mount it.** Put the tab bar in a layout so switching tabs re-renders only the panel. Re-mounting the whole section on every tab click is wasted work and a visible flash.
*   **Don't animate layout properties.** The sliding indicator should animate `transform`/`opacity` only (compositor-only, no reflow) — never `left`/`width` in a hot path. Measure the target tab once, translate to it.
*   **Debounce URL writes.** Encoding within-tab state in search params is great until every keystroke pushes history and triggers a re-render. Use `replace` + debounce.
*   **Prerender the likely-next tab** (Speculation Rules) for genuinely instant switches on high-traffic flows — spend the compute where the analytics say users go next.
*   **Icon imports:** same trap as buttons — import icons by name (`import { CreditCard } from "lucide-react"`), never `import *`, or one tab's glyph drags in the whole library.

## 15\. Security
Lighter than a form button — tabs are navigation — but two real concerns because each tab is a route the server may render:

*   **The URL is not authorization.** A tab linking to `/settings/billing` and the route existing does not mean this user may see billing. Hiding a tab is UX, never a security boundary — the _route's loader/handler_ must independently check auth/permissions server-side. A user can type the URL directly; "the tab wasn't shown" must never mean "the page can't load."
*   **Don't leak the existence of gated views by tab presence alone.** If which tabs render reveals plan/role, that's usually fine — but make sure the _data_ behind a gated route is server-guarded, not just the tab hidden client-side.
*   **Open-redirect hygiene on return/\*\*\*\*****`next`** **params.** If a tab or its deep link carries a `?returnTo=` / `?next=` param, validate it against an allowlist server-side before redirecting — an unvalidated redirect target is a classic phishing vector.
*   **Deep-link params are attacker-controllable.** Tab sub-state in the URL (`?org=123`) is user-editable. Authorize server-side that this user may act on that resource; never trust the ID because it came from your own tab link.

## 16\. Senior-Level Checklist (ship-ready)
Before routed tab navigation is "done":
- [ ] It's a `<nav>` with a unique, descriptive `aria-label`.
- [ ] Tabs are real links (`<a href>` / router `<Link>`), not `<button>`/`<div>`.
- [ ] **No** `role="tab"`, `role="tablist"`, or `role="tabpanel"` anywhere.
- [ ] Active tab has `aria-current="page"`, bound to the same selector as the visual active state.
- [ ] Keyboard: Tab/Shift+Tab moves between tabs, Enter activates — **no** arrow-key roving.
- [ ] Each view has its own URL; the tab is deep-linkable and shareable.
- [ ] Back/forward move between tabs correctly (real history entries).
- [ ] Parent-vs-child active detection handled (`end` / `exact` / prefix chosen per tab).
- [ ] Pending/loading route state shows feedback (spinner/skeleton/`aria-busy`).
- [ ] Modifier-clicks (Cmd/Ctrl/middle) still open in a new tab — clicks aren't blindly intercepted.
- [ ] Overflow handled (scroll track with fades, or "More" menu) — every tab reachable.
- [ ] Scroll position restored on back; reset to top on new tab.
- [ ] Panels code-split per route; prefetch on intent where it matters.
- [ ] Visible `:focus-visible` ring; ≥44px tap target; active state not signaled by color alone; contrast ≥ 4.5:1.
- [ ] Route handlers re-check auth server-side regardless of which tabs rendered.
- [ ] Tests assert: named nav landmark, links (not tabs), `aria-current` tracks route, URL changes on click, back works, deep links land, axe clean.

## 17\. Visual Styles (the same tab bar, eleven skins)
Design systems are _whose_ rules; visual styles are _which look_. Every skin below changes only appearance — **the** **`<nav>`** **of links, the Tab-through keyboard model,** **`aria-current`****\*\*\*\*, the focus ring, and the 44px target are identical across all eleven.** Style is skin; behavior is the skeleton.

*   **Flat:** solid active-tab color, crisp 2px underline, no shadow. Reads instantly, the safe default for dense app nav.
*   **Material:** the sliding underline indicator animates between tabs; ripple on the active tab; uppercase or medium labels. The signature routed-tab look.
*   **Glassmorphism:** the tab bar is a translucent `backdrop-filter: blur()` strip over a vivid page; active pill is a frosted panel. Watch label contrast against whatever scrolls behind it.
*   **Liquid Glass (the 2026 trend):** Apple's iOS 26 / macOS Tahoe language — the tab bar floats as a refractive translucent capsule with a specular rim and a sheen that shifts with motion and content behind it. The active pill _is_ a liquid-glass lens. SwiftUI's `TabView` emits this natively; on the web it's an honest approximation with layered highlights + blur. Guard contrast and honor `prefers-reduced-motion`.
*   **Neumorphism:** the active tab is a soft-extruded (or inset-pressed) pill on a same-color surface via dual light/dark shadows. Pretty, contrast-poor — accent use only, never for primary nav where legibility is load-bearing.
*   **Skeuomorphism:** tabs as physical file-folder tabs — beveled, gradient-filled, the active one lifted forward and overlapping its neighbors. The original "tab" metaphor, literally.
*   **Neo-Brutalism:** thick black borders, a hard offset shadow on the active tab, zero radius, clashing fills. High personality for editorial/campaign UIs.
*   **Claymorphism:** big-radius puffy pills, inner top-light + bottom-shadow, soft glow on the active tab. Friendly, playful, app-onboarding energy.
*   **Aurora / Gradient:** an animated multi-hue gradient underline or active-pill fill on a dark bar. Premium feel — honor `prefers-reduced-motion` and keep label contrast over the gradient.
*   **Minimal / Swiss:** type and spacing do the work — a thin active underline, generous tracking, near-zero decoration, sharp corners. Editorial and dashboards.
*   **UJG Brand:** Goldenrod active indicator + label on a deep Eminence/Night bar, confident radius on pill variants, a warm glow under the active tab. Afro-Futurist house style — the dark saturated field makes a Liquid Glass active pill sing (per the Design Styles doc). Inactive tabs dim to a muted Platinum; focus ring is Goldenrod.

**Rule that never changes:** the skin is cosmetic. Semantics (`<nav>`/links/`aria-current`), the Tab-through keyboard model, focus visibility, and target size stay identical across every style. Full guidance in the [Design Styles (visual languages)](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200551) doc.
* * *

**Bottom line:** tab navigation is the component people build wrong because it _looks_ like the ARIA tabs widget and is its semantic opposite. Get one idea right and the rest follows — _tabs that change the URL are links in a_ _`<nav>`__\_\_, marked with_ _`aria-current="page"`__\_\_, moved through with Tab, never with_ _`role="tab"`_ _or arrow keys._ That single decision buys you deep links, a correct back button, shareable URLs, per-tab code-splitting, and accessibility that's _less_ work than the wrong version. Master the routing model, wire the pending state, restore the scroll, and you've built navigation that feels native to the web instead of fighting it.
