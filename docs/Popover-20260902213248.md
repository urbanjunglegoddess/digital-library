# The Popover: A Senior Engineer's Complete Breakdown
The floating panel that finally went native. Here's everything from first principles to production code — including the 2024–2026 platform shift that rewrote how we build this thing.

**Audit a popover:** the companion **popover a11y audit** (also a later pass) will paste-check any floating panel for the silent failures — missing `aria-expanded` on the trigger, focus that never returns to the trigger on close, a `role` that lies about what the panel is, a panel that traps focus like a modal when it shouldn't, and clipping/overflow bugs from the old absolute-position era.

**Read this first:** a popover is not one component — it's the _shared floating primitive_ underneath Select, Combobox, Menu/Dropdown, Date Picker, Color Picker, and the rich Tooltip. Master the popover and you've built the engine for a third of your component library. Every one of those is "a trigger + an anchored floating panel + a dismiss contract." That's a popover.

## 1\. What a Popover Actually Is
A popover is a **non-modal floating panel, anchored to a trigger, that can contain interactive content and dismisses lightly.** Unpack that sentence — every word is doing work, and every word is a distinction people get wrong:

*   **Floating** — it renders on top of the page in a stacking layer above normal content (natively, the _top layer_ — more on that in §9).
*   **Anchored to a trigger** — its position is computed _relative to_ the element that opened it (a button, an input, an icon). It follows that anchor.
*   **Non-modal** — the rest of the page stays live. No scrim that blocks interaction, no "you must deal with me first." You can click away and it just closes.
*   **Can contain interactive content** — buttons, inputs, links, a whole mini-form. This is the line against tooltips.
*   **Dismisses lightly** — click outside, press Escape, or open another one, and it closes. "Light dismiss."

The four things people constantly conflate:

*   **Popover vs. Tooltip.** A tooltip is a _passive, non-interactive_ label that appears on hover/focus and describes an element ("this icon means archive"). It holds no controls — you can't Tab into a tooltip. A popover is _interactive_ and is opened by a deliberate action (click), not a hover. If a user needs to click _inside_ the floating thing, it's a popover, not a tooltip. The #1 amateur move: putting a button inside a `title`\-style tooltip. Hover-to-open + interactive content is an accessibility trap (the panel vanishes the moment the pointer leaves the trigger to reach the button).
*   **Popover vs. Dialog (Modal).** A modal dialog is _blocking_ — it traps focus inside itself, renders an inert backdrop, and demands resolution before you touch anything else (`<dialog>.showModal()`). A popover is _non-blocking_ — it does **not** trap focus, the page behind stays interactive, and it closes the instant you click elsewhere. Rule: **if the task is important enough that the user must not do anything else until they answer, it's a modal. If they can walk away from it, it's a popover.** A "delete account, are you sure?" confirmation is a modal. A profile mini-menu is a popover.
*   **Popover vs. Menu/Dropdown.** A menu is a _specialization_ of a popover: a popover whose content is a list of commands (`role="menu"` + `role="menuitem"`, arrow-key roving focus). Every menu is a popover under the hood; not every popover is a menu. Don't slap `role="menu"` on a popover that holds a form — that lies to screen readers about the interaction model.
*   **Popover vs. Combobox/Select/Date Picker.** These are all _composed on top of_ a popover. A combobox is an input + a popover listbox. A select is a button + a popover listbox. A date picker is a field + a popover calendar grid. The popover handles positioning, top-layer stacking, and light-dismiss; the composite adds the specific ARIA pattern and keyboard model. **You build the popover once and reuse the floating machinery everywhere.**

Rule of thumb: **hover + passive = tooltip; click + interactive + non-blocking = popover; click + interactive + blocking = modal; popover + command list = menu.**

## 2\. Why It Matters
The popover is where _density meets clarity_ — it lets an interface hold enormous functionality without showing all of it at once. That makes it load-bearing:

*   **Progressive disclosure drives conversion.** Filters, options, "more actions," account menus, help hints — hiding secondary complexity behind a click keeps the primary path clean. A cluttered screen kills conversion; a well-placed popover keeps the CTA breathing while the power-user controls stay one tap away.
*   **It's an accessibility minefield.** Because a popover floats out of document flow, focus management, roles, and the trigger↔panel relationship are entirely on you (unless you use the native API, which is exactly why the native API exists). A popover that doesn't move focus correctly, doesn't announce state via `aria-expanded`, or traps focus like a modal is a silent lockout for keyboard and screen-reader users. This is the single most-failed WCAG area in real audits after color contrast.
*   **It sets the "does this app feel solid" tone.** Popovers that clip at the viewport edge, appear behind other content (`z-index` wars), jump on open, or don't close when you click away make an app feel amateur and broken. Correct anchoring, top-layer stacking, and light-dismiss are the difference between "polished product" and "someone's first React project."
*   **It's the 2026 platform-shift story.** For fifteen years every team hand-rolled this with `position: absolute`, portals, `z-index` hacks, scroll listeners, and click-outside handlers — thousands of lines, all subtly buggy. The browser now ships the popover natively (Popover API + CSS anchor positioning). Knowing both the native path _and_ the JS fallback is now a senior-level literacy test.

## 3\. Anatomy of a Popover
Every well-built popover is composed of predictable parts:

*   **Trigger (invoker):** the element that opens it — usually a `<button>`. Carries `aria-expanded` (true/false) and, natively, `popovertarget`. Must be a real interactive element, never a bare `<div>`.
*   **Panel (the popover surface):** the floating container. Has padding, border-radius, background, border, elevation (shadow), and a `role` that tells the truth about its contents (`dialog`, `menu`, `listbox`, or none for a plain label).
*   **Arrow / beak (optional):** the little pointer connecting panel to trigger. Nice-to-have, positioning-expensive (must track the anchor). Skip it if you don't need the visual tether.
*   **Content region:** whatever lives inside — a menu list, a form, a calendar grid, rich text. This is what a tooltip _can't_ have.
*   **Backdrop (optional, non-blocking):** natively a `::backdrop` pseudo-element behind the panel. For a popover it's usually transparent or absent (a _visible_ dimming backdrop pushes you toward modal territory).
*   **Anchor reference:** the element positioning is computed against. Usually the trigger, but can be a different element (`position-anchor` / `anchor-name`, or a Floating UI `reference`).
*   **Placement + fallback set:** the preferred side (top/bottom/left/right + alignment) _and_ the ordered fallbacks when the preferred side would overflow the viewport (`position-try`, or Floating UI's `flip`/`shift`).
*   **Dismiss affordances:** Escape key, click-outside (light dismiss), and — for menus — selecting an item. Focus return to the trigger on close is part of this contract.
* * *

## 4\. Sizes & Placement Scale
A popover's size is content-driven, but the _placement geometry_ has real, tokenizable values. The two numbers that matter most: the **offset** (gap between trigger and panel) and the **shift padding** (minimum gap from the viewport edge before it flips/shifts).

| Token | Value | Purpose |
| ---| ---| --- |
| Offset (main axis) | 8px | Gap between trigger edge and panel edge. |
| Offset (arrow present) | 12px | Extra room so the arrow has somewhere to sit. |
| Shift padding | 8–16px | Min gap the panel keeps from the viewport edge. |
| Arrow size | 8–10px | Square rotated 45°; half sits under the panel. |
| Panel radius | 8–12px | Match your card/menu radius token. |
| Panel min-width | 180px | Menus/selects; keeps items readable. |
| Panel max-width | 320–360px | Rich popovers; wrap text, don't sprawl. |
| Panel max-height | `min(400px, var(--available-height))` | Scroll inside past this; never overflow the screen. |
| Elevation | shadow lvl 2–3 | Lifts it off the page; signals "floating layer." |
| Z-index (JS path) | 50+ (or top layer) | Above app chrome; native top layer sidesteps this. |

Placement naming (12 positions, the Floating UI convention everyone borrows): `top`, `top-start`, `top-end`, `bottom`, `bottom-start`, `bottom-end`, `left`, `left-start`, `left-end`, `right`, `right-start`, `right-end`. The `-start`/`-end` suffix aligns the panel's edge to the trigger's start/end (and flips automatically in RTL when you use logical alignment).

Rules that matter:

*   **The panel must never exceed the viewport.** Cap `max-height` at the available space and scroll internally. A popover you can't scroll to the bottom of is a broken popover.
*   **Offset is a token, not a magic number** — so the whole system's floating gaps stay consistent.
*   **On mobile, a large popover should become a bottom sheet**, not a tiny anchored panel. Below ~480px, anchored positioning fights the keyboard and the thumb zone; switch strategies.

## 5\. States (the part juniors forget)
A production popover has far more states than "open" and "closed." Missing states are the #1 tell of an amateur build.

1. **Closed (rest)** — panel not rendered / `display: none` (native: not in top layer). Trigger shows `aria-expanded="false"`.
2. **Opening** — the transition in. Native supports animating from `display:none` via `@starting-style` + `transition-behavior: allow-discrete` (the part that used to be impossible in pure CSS).
3. **Open** — panel in the top layer, positioned, focus moved appropriately, trigger `aria-expanded="true"`.
4. **Positioned / repositioned** — after open, the panel may _flip_ or _shift_ because the preferred side overflowed. This is a real state: the final placement can differ from the requested one, and an arrow must track it.
5. **Focus-within** — a control inside the panel has focus. Must remain visibly styled; the trigger is no longer the focused element but stays "expanded."
6. **Hover (hint popovers only)** — for `popover="hint"` / rich tooltips, hover-intent open with a delay. Not for interactive `auto` popovers.
7. **Closing (light dismiss)** — click-outside or Escape fired; the transition out plays, focus returns to the trigger.
8. **Disabled trigger** — the trigger can't open the popover (`disabled` on the button). The panel simply never opens; no orphaned open state.
9. **Loading content** — the panel is open but its contents are still fetching (a menu of remote items, a preview card). Show a skeleton/spinner _inside_ the panel; keep the panel size stable so it doesn't jump.
10. **Error content** — the panel's async content failed. Show the error _in_ the panel with a retry; don't silently show an empty popover.
11. **Empty** — a filtered menu/combobox with zero matches. Show "No results," never a zero-height panel that looks broken.
12. **Nested / stacked** — a popover opened from inside another popover (submenu, "more" inside a menu). The top layer stacks these correctly; the light-dismiss contract must close _the right one_ (innermost first on Escape).

The state that separates senior from junior: **focus behavior on open and close.** For an `auto` popover with interactive content, focus moves _into_ the panel on open (to the first focusable element or the panel itself), and returns _to the trigger_ on close. Get this wrong and keyboard users are stranded.

## 6\. Types & Variants
Same floating primitive, different contracts. Knowing which you're building tells you the role, the keyboard model, and the dismiss behavior.

*   **Plain popover (rich content):** a form, settings, a preview card. `role="dialog"` if it's a self-contained task with a label; no role if it's a simple labeled panel. Focus moves in, returns on close.
*   **Menu / dropdown:** a list of commands. `role="menu"` + `role="menuitem"`, arrow-key roving focus, `Home`/`End`, type-ahead, Escape closes and returns focus. Selecting an item closes it.
*   **Listbox (select / combobox):** single or multi-select options. `role="listbox"` + `role="option"` with `aria-selected`; the trigger owns `aria-activedescendant` (combobox) or focus moves into the list (select). Built on the popover, plus the combobox/select ARIA pattern.
*   **Rich tooltip / hint:** hover-or-focus triggered, _may_ contain a link but stays largely passive. Native `popover="hint"` is purpose-built for this — it light-dismisses independently of `auto` popovers so a hint doesn't close your open menu.
*   **Date / color / emoji picker:** a popover wrapping a specialized grid widget. Popover handles float + dismiss; the grid handles its own 2D arrow-key navigation.
*   **Manual popover (****`popover="manual"`****):** does **not** light-dismiss. Stays open until _you_ close it in code. For toasts, persistent side panels, coach-marks, or a popover you want to control entirely yourself.
*   **Split-button / context menus:** a popover anchored to a caret or opened at the pointer position (right-click / long-press). The anchor may be a virtual point rather than an element.

The three native "types" you'll set on the `popover` attribute — `auto`, `manual`, and `hint` — are covered in depth in §9.1. They're the single most important knob: they decide the light-dismiss and stacking contract.
* * *

## 7\. When to Use One (and When Not To)
Use a popover when a user needs **secondary, interactive content anchored to a specific control**, and they can dismiss it freely without committing. Don't use one when:

*   **The content is passive description** → that's a tooltip. Don't make people click for a label.
*   **The task is blocking / must be resolved** → that's a modal `<dialog>`. Confirmations, destructive gates, "you must accept terms."
*   **The content is long or primary** → that's a page, a drawer, or an accordion, not a floating panel. Popovers are for _secondary_ content that fits in a small panel.
*   **There are many peer items to navigate** → a full menu bar or a nav, not a lone popover.
*   **On small screens with a large payload** → switch to a bottom sheet / full-screen sheet. Anchored positioning fights the mobile keyboard and thumb reach.

Placement heuristics:

*   **Open toward available space.** Default to `bottom-start` for menus (matches reading order), but _always_ provide flip fallbacks so it opens upward near the viewport bottom.
*   **Keep the trigger visible.** The panel should never cover its own trigger — that's disorienting. Offset it.
*   **Anchor to the thing it's about.** A filter popover anchors to the Filter button, not the center of the screen. The spatial connection is the whole point.
*   **One popover open at a time** in a given region — opening a second `auto` popover closes the first (the native top layer does this for you).

## 8\. Popovers Across Design Systems
Same primitive, different philosophies and vocabulary. Fluency here means you can read any codebase.

*   **Material Design (Google):** Splits the concept into **Menu** (command lists, elevation + ripple items) and **Rich tooltip** / **Dialog**. Menus use elevation z-levels and a specific enter/exit motion (scale + fade from the anchor). Material 3 "Expressive" adds springier open transitions.
*   **Apple HIG (iOS/macOS):** The **Popover** is a first-class, named pattern — an arrow-anchored panel, non-modal on iPad/macOS, that adapts to a **sheet** on compact iPhone widths automatically (`UIPopoverPresentationController` → sheet). Apple's guidance: popovers are transient and dismiss on outside tap. In SwiftUI, `.popover()` vs `.sheet()` is exactly the popover-vs-modal decision.
*   **Fluent (Microsoft):** **Flyout** (light-dismiss surface), **Callout**, and **Menu**. Flyout is Fluent's word for the light-dismiss popover; it explicitly documents the "click outside closes it, doesn't block the app" contract.
*   **Ant Design / enterprise:** Distinct `Popover`, `Popconfirm` (a popover with a built-in confirm/cancel — the non-modal alternative to a confirm dialog), `Dropdown`, `Tooltip`, and `Select`. Dense, many placement props, built for admin UIs. `Popconfirm` is a genuinely useful pattern most systems lack.
*   **Radix / shadcn (2024+ web standard):** Headless `Popover`, `DropdownMenu`, `Select`, `Combobox`, `HoverCard`, `Tooltip` — each a separate primitive but all built on the same Floating-UI-derived positioning engine and a shared portal/dismiss layer. Accessibility baked in, appearance yours. This is the current default for serious React apps.
*   **Bootstrap:** `Popover` and `Tooltip` as jQuery-free JS plugins (Popper.js under the hood). `data-bs-toggle="popover"` + JS init. Functional, dated positioning model compared to anchor positioning.
*   **Native platform (the 2026 baseline):** the **HTML Popover API** + **CSS anchor positioning**. No library. Top-layer stacking, light-dismiss, and focus management handled by the browser. This is where the whole web is heading, and where you should start any greenfield build.

## 8b. Visual Styles (the same popover, eleven skins)
Design systems are _whose_ rules; visual styles are _which look_. The same semantic popover — same trigger, same roles, same focus contract, same 44px targets — can wear any of these skins. See §17 for the full render across all eleven. Full guidance lives in the [Design Styles (visual languages)](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200551) reference.

The one rule that never bends: **style is the skin, behavior is the skeleton.** A glassmorphic popover and a neo-brutalist popover have identical keyboard maps, identical `aria-expanded` wiring, identical focus-return-on-close, and identical 44px hit targets. Only the paint changes.

### What's trending in 2026
The popover's headline story this year isn't a _look_ — it's the **native platform finally shipping the behavior**. The Popover API reached cross-browser baseline and CSS anchor positioning landed in Chromium and is arriving elsewhere, so 2026 is the year teams start _deleting_ their portal/positioning libraries for simple cases. On the aesthetic side:

*   **Liquid Glass panels** (Apple's iOS 26 / macOS Tahoe language): popover surfaces that refract the content behind them with a specular rim and a subtle moving sheen. On a dark, saturated backdrop the refraction sings — but guard contrast for the text inside, and honor `prefers-reduced-motion` for the sheen.
*   **Anchored micro-motion:** panels that scale-and-fade _from the trigger's edge_ (transform-origin at the anchor) using the new `@starting-style` + `allow-discrete` so the open/close animates in pure CSS with zero JS.
*   **Spatial depth-aware panels** carried over from visionOS: soft 3D layering, parallax, and shadow that implies real elevation off the page.
*   **AI-native popovers:** inline "explain this / do this for me" panels that stream a response inside the popover — the popover as the surface for agentic micro-interactions.
*   **Expressive Material 3 menus:** bolder shape morph and springier open motion.

**For UJG:** lean popover panels toward Liquid Glass or a clean Flat surface over deep Eminence, Goldenrod focus ring on every interactive item inside, and reserve the heavy skins (Brutalism/Aurora) for campaign moments. The accessibility caveats hold no matter how on-trend the skin: contrast inside the panel, reduced-motion for the open animation, and a visible focus ring on every control.

## 9\. The Code
This is the big section. The through-line: **there are now two legitimate paths — the native Popover API (+ CSS anchor positioning) and the JS path (Floating UI + a portal).** Senior engineers know both, know when each wins, and know they can be combined (native top layer + Floating UI positioning).

### 9.1 The Native Popover API (start here — this is the 2026 foundation)
The browser now ships the popover. The `popover` attribute promotes an element to the **top layer** (above everything, no `z-index` needed), gives it **light-dismiss** for free, and wires a trigger to it with **zero JavaScript**.

```plain
<!-- Zero-JS popover: button opens the panel, click-outside/Escape closes it -->
<button popovertarget="settings">Settings</button>

<div id="settings" popover>
  <h3>Display settings</h3>
  <label><input type="checkbox"> Dark mode</label>
  <button popovertarget="settings" popovertargetaction="hide">Done</button>
</div>
```

That's a fully working, accessible, top-layer, light-dismissing popover with **no script**. Break down every piece:

**The** **`popover`** **attribute has three values — this is the most important knob:**

*   **`popover`** **/** **`popover="auto"`** (default): **light-dismiss + one-at-a-time.** Clicking outside closes it, Escape closes it, and opening another `auto` popover closes this one (they don't stack as siblings — only nested ones stack). This is your default for menus, dropdowns, and most interactive panels. On open, focus is allowed to move into the panel; on close it returns to the invoker.
*   **`popover="manual"`**: **no light-dismiss, no auto-close.** It stays open until you explicitly hide it (via a `popovertargetaction="hide"` button or `.hidePopover()` in JS). Multiple `manual` popovers can be open at once. Use for toasts, persistent coach-marks, side panels you control.
*   **`popover="hint"`** (newest): a **third stacking level for tooltip-like hints.** A `hint` light-dismisses on pointer-out and does **not** close open `auto` popovers — so a hover-hint can appear _over_ an open menu without killing it. This is what fixed the old "my tooltip closes my dropdown" bug. `hint` popovers close other `hint` popovers but leave `auto` popovers alone.

**The invoker attributes:**

*   **`popovertarget="id"`** — points a `<button>` at the popover by id. The browser auto-manages `aria-expanded` and the toggle behavior. No `onclick` needed.
*   **`popovertargetaction`** — `"toggle"` (default), `"show"`, or `"hide"`. A "Done"/"Close" button _inside_ the panel uses `popovertargetaction="hide"` to dismiss it declaratively.

**The top layer.** A `popover` element renders in the browser's _top layer_ — the same layer as `<dialog>` and fullscreen. This is the single biggest reason to use the native API: **it ends** **`z-index`** **wars and clipping-by-\*\*\*\*\*\*\*\*****`overflow:hidden`** **forever.** The old absolute-positioned popover got clipped by any ancestor with `overflow: hidden` and fought every `z-index` on the page. A top-layer popover is above _all_ of it, escaping every clipping and stacking context automatically.

**`::backdrop`****\*\*\*\*\*\*\*\*.** A top-layer popover gets a `::backdrop` pseudo-element behind it. For a _modal_ you'd tint it; for a _popover_ you usually leave it transparent (a visible dim = modal semantics). But it's the correct hook if you want a subtle scrim:

```css
#settings::backdrop {
  background: transparent;        /* popover: no blocking dim */
}
/* Animate the panel from display:none — the part that used to be impossible */
[popover] {
  opacity: 0;
  transform: scale(.96);
  transition: opacity .15s, transform .15s, overlay .15s allow-discrete, display .15s allow-discrete;
}
[popover]:popover-open {
  opacity: 1;
  transform: scale(1);
}
@starting-style {
  [popover]:popover-open { opacity: 0; transform: scale(.96); }
}
```

`:popover-open` is the state selector (analogous to `:open`). `@starting-style` + `transition-behavior: allow-discrete` are what let a popover animate _in_ from `display: none` — pure CSS, no JS enter/exit classes. This is genuinely new and eliminates a whole category of animation library usage.

**JS control when you need it** (the API is scriptable, not just declarative):

```js
const panel = document.getElementById("settings");
panel.showPopover();     // open programmatically
panel.hidePopover();     // close
panel.togglePopover();   // toggle
panel.addEventListener("toggle", (e) => {
  // e.newState is "open" or "closed" — the one event for both directions
  if (e.newState === "open") loadMenuItems();
});
// beforetoggle fires BEFORE the state change — cancelable, good for lazy setup
panel.addEventListener("beforetoggle", (e) => { /* e.oldState / e.newState */ });
```

**What the native API gives you for free:** top-layer stacking, light-dismiss (click-outside + Escape), one-at-a-time `auto` behavior, focus return to the invoker on close, and `aria-expanded` toggling on the invoker. **What it does** **_not_** **do:** position the panel relative to the anchor. Out of the box a `popover` centers in the viewport. Positioning is the other half — and that's CSS anchor positioning.

### 9.2 CSS Anchor Positioning (the native way to place the panel)
The companion to the Popover API. It lets CSS position the floating panel _relative to another element_ — no JS measuring, no scroll listeners. This is the second half of "native popovers."

```css
/* 1. Name the anchor (the trigger) */
.trigger {
  anchor-name: --settings-trigger;
}

/* 2. Tie the popover to that anchor and place it */
#settings {
  position: fixed;
  position-anchor: --settings-trigger;

  /* Place below the trigger, aligned to its start edge */
  position-area: bottom span-right;
  margin-top: 8px;                       /* the offset token */

  /* Never exceed the space the browser reports is available */
  max-height: var(--available-height, 400px);
  overflow-y: auto;

  /* 3. Fallbacks: if the preferred side overflows, TRY these in order */
  position-try-fallbacks: flip-block, flip-inline, flip-block flip-inline;
  position-try-order: most-height;       /* prefer the fallback with the most room */
}
```

The four load-bearing properties:

*   **`anchor-name`** — declares an element as a named anchor (on the trigger).
*   **`position-anchor`** — points the popover at that anchor. (Native Popover API + `popovertarget` can auto-set an _implicit_ anchor, so a popover invoked by a button is anchored to it without naming — but explicit naming gives you control.)
*   **`position-area`** — the grid-based placement: `bottom`, `top`, `bottom span-right` (aligns to start), `top span-left`, etc. Replaces the old `top: 100%; left: 0` math.
*   **`position-try-fallbacks`** (and the `@position-try` at-rule for custom fallback blocks) — the ordered list of alternate placements the browser tries when the preferred one would overflow the viewport. This is **flip and shift, done natively.** `flip-block` = try the opposite vertical side; `flip-inline` = opposite horizontal side. `position-try-order` picks the roomiest fallback.

You can also use the `anchor()` function directly for fine control (`top: anchor(bottom); left: anchor(start);`) and `anchor-size()` to size the panel to the anchor (`min-width: anchor-size(width)` — a select menu matching its trigger's width, natively).

**Positioning the arrow:** the arrow tracks the anchor via `anchor()` too, though for a bulletproof arrow that follows through flips, many teams still reach for the JS path's arrow middleware. Anchor positioning's arrow story is the least-mature corner.

**Support reality (2026):** the Popover API is cross-browser baseline; anchor positioning shipped in Chromium and is rolling out elsewhere with a polyfill available. Sensible strategy: **native Popover API for the top-layer + dismiss behavior everywhere, native anchor positioning where supported, Floating UI as the positioning fallback** where anchor positioning isn't yet available. Which brings us to the JS path.

### 9.3 Floating UI (the JS path — the positioning workhorse)
Floating UI (the successor to Popper.js) is the battle-tested library for anchoring a floating element, computing flips/shifts, and tracking the anchor on scroll/resize. It's what Radix, shadcn, and most React systems use under the hood, and it's still the right call where anchor positioning isn't supported or where you need pixel-perfect arrow tracking.

```typescript
import {
  computePosition, flip, shift, offset, arrow, autoUpdate,
} from "@floating-ui/dom";

const trigger = document.querySelector("#trigger")!;
const panel   = document.querySelector("#panel")! as HTMLElement;
const arrowEl = panel.querySelector(".arrow")! as HTMLElement;

function update() {
  computePosition(trigger, panel, {
    placement: "bottom-start",
    middleware: [
      offset(8),                        // gap between trigger and panel
      flip(),                           // flip to the opposite side if it overflows
      shift({ padding: 8 }),            // slide along the axis to stay in view
      arrow({ element: arrowEl }),      // position the arrow
    ],
  }).then(({ x, y, placement, middlewareData }) => {
    Object.assign(panel.style, { left: `${x}px`, top: `${y}px` });

    // Place the arrow on the side opposite the panel's placement
    const side = placement.split("-")[0];
    const staticSide = { top: "bottom", right: "left", bottom: "top", left: "right" }[side]!;
    const { x: ax, y: ay } = middlewareData.arrow ?? {};
    Object.assign(arrowEl.style, {
      left: ax != null ? `${ax}px` : "",
      top:  ay != null ? `${ay}px` : "",
      [staticSide]: "-4px",
    });
  });
}

// autoUpdate re-runs on scroll, resize, and layout shifts — the crucial part
const cleanup = autoUpdate(trigger, panel, update);
// call cleanup() when the popover closes to stop listening
```

The three middleware everyone needs — `offset` (the gap), `flip` (opposite side on overflow), `shift` (slide to stay in view) — are exactly `position-try`'s job, done in JS. `autoUpdate` is the piece hand-rolled implementations always forget: without it the panel drifts away from its anchor the moment the user scrolls.

**The pro move in 2026:** use the _native top layer + light-dismiss_ from the Popover API, and use _Floating UI only for positioning_. Best of both — the browser handles stacking, dismiss, and focus; Floating UI handles the pixel math and arrow. `<div popover>` for the layer, `computePosition` for the placement.

### 9.4 React + TypeScript (a proper reusable component)
The real-world React popover: a headless hook wrapping Floating UI, exposing an accessible trigger and panel. This is the shape Radix formalizes; building it once teaches you what every popover library is doing.

```typescript
import {
  useFloating, offset, flip, shift, autoUpdate,
  useClick, useDismiss, useRole, useInteractions, FloatingFocusManager, FloatingPortal,
} from "@floating-ui/react";
import { useState, cloneElement, isValidElement, ReactElement, ReactNode } from "react";

interface PopoverProps {
  trigger: ReactElement;          // the invoker; we clone it to inject props
  children: ReactNode;            // panel content
  placement?: "top" | "bottom" | "left" | "right" | "bottom-start";
  role?: "dialog" | "menu" | "listbox";
}

export function Popover({ trigger, children, placement = "bottom-start", role = "dialog" }: PopoverProps) {
  const [open, setOpen] = useState(false);

  const { refs, floatingStyles, context } = useFloating({
    open,
    onOpenChange: setOpen,
    placement,
    whileElementsMounted: autoUpdate,          // keep it glued to the anchor
    middleware: [offset(8), flip(), shift({ padding: 8 })],
  });

  // Behavior hooks — each returns prop-getters that wire the a11y contract:
  const click   = useClick(context);           // open on trigger click
  const dismiss  = useDismiss(context);         // Escape + click-outside (light dismiss)
  const roleProp = useRole(context, { role });  // sets role + aria-expanded/haspopup
  const { getReferenceProps, getFloatingProps } = useInteractions([click, dismiss, roleProp]);

  if (!isValidElement(trigger)) throw new Error("Popover trigger must be a single element");

  return (
    <>
      {cloneElement(trigger, {
        ref: refs.setReference,
        ...getReferenceProps(),
        // getReferenceProps injects aria-expanded + aria-haspopup automatically
      })}

      {open && (
        <FloatingPortal>
          {/* FloatingFocusManager moves focus IN on open and RETURNS it to the
              trigger on close — non-modal (modal={false}) so it does NOT trap focus */}
          <FloatingFocusManager context={context} modal={false} returnFocus>
            <div
              ref={refs.setFloating}
              style={floatingStyles}
              className="popover-panel"
              {...getFloatingProps()}
            >
              {children}
            </div>
          </FloatingFocusManager>
        </FloatingPortal>
      )}
    </>
  );
}
```

Why this is the senior version, not the junior one:

*   **`FloatingFocusManager`** **with** **`modal={false}`** — this is the whole popover-vs-modal distinction in one prop. Focus moves _into_ the panel on open and _returns to the trigger_ on close (`returnFocus`), but the page behind stays interactive and focus is **not trapped**. A `modal={true}` here would make it a dialog. This single boolean is the line between the two components.
*   **`useDismiss`** — gives you Escape + click-outside for free, the exact "light dismiss" contract, matching the native API's behavior.
*   **`useRole`** — sets the panel's `role` _and_ injects `aria-expanded`/`aria-haspopup` onto the trigger. The trigger↔panel ARIA relationship is handled, not hand-wired.
*   **`FloatingPortal`** — renders the panel at the document root so no ancestor `overflow: hidden` clips it — the JS equivalent of the native top layer.
*   **`whileElementsMounted: autoUpdate`** — the panel stays anchored through scroll and resize. The bug juniors ship without.

Usage:

```typescript
<Popover trigger={<button>Filters</button>}>
  <FilterForm onApply={/* ... */} />
</Popover>
```

### 9.6 Vanilla JS (native API + a thin positioning layer)
The from-scratch version, combining the native top layer with Floating UI positioning — the pattern you'd ship without a framework.

```html
<button id="menuBtn" popovertarget="menu" aria-haspopup="menu" aria-controls="menu" aria-expanded="false">Actions</button>
<div id="menu" popover role="menu">
  <button role="menuitem">Rename</button>
  <button role="menuitem">Duplicate</button>
  <button role="menuitem">Delete</button>
</div>
```

```js
import { computePosition, offset, flip, shift, autoUpdate } from "@floating-ui/dom";

const btn  = document.getElementById("menuBtn");
const menu = document.getElementById("menu");
let stopAutoUpdate = null;

// The native 'toggle' event tells us open/closed — hook positioning to it.
menu.addEventListener("toggle", (e) => {
  if (e.newState === "open") {
    btn.setAttribute("aria-expanded", "true");     // native sets this too; explicit for clarity
    stopAutoUpdate = autoUpdate(btn, menu, () => {
      computePosition(btn, menu, {
        placement: "bottom-start",
        middleware: [offset(8), flip(), shift({ padding: 8 })],
      }).then(({ x, y }) => Object.assign(menu.style, { left: `${x}px`, top: `${y}px`, margin: 0 }));
    });
    menu.querySelector('[role="menuitem"]')?.focus();   // move focus into the menu
  } else {
    btn.setAttribute("aria-expanded", "false");
    stopAutoUpdate?.();                              // stop listening — memory hygiene
    stopAutoUpdate = null;
    // native popover already returns focus to the invoker on light-dismiss
  }
});

// Roving arrow-key focus within the menu (the menu ARIA pattern)
const items = [...menu.querySelectorAll('[role="menuitem"]')];
menu.addEventListener("keydown", (e) => {
  const i = items.indexOf(document.activeElement);
  if (e.key === "ArrowDown") { e.preventDefault(); items[(i + 1) % items.length].focus(); }
  if (e.key === "ArrowUp")   { e.preventDefault(); items[(i - 1 + items.length) % items.length].focus(); }
  if (e.key === "Escape")    menu.hidePopover();      // native returns focus to btn
});
```

Note how little script this is _because_ the native API carries the top layer, light-dismiss, and focus return. Pre-native, this file would be triple the length with a hand-rolled click-outside listener, a `z-index` manager, and a focus-return shim — all subtly buggy.

### 9.7 Next.js (App Router: client vs. server)
A popover is interactive (open state, dismiss), so the panel wrapper is a **Client Component**. But its _content_ can be a Server Component streamed in, and any action it fires (a menu item that deletes a row) runs via a Server Action.

```typescript
// app/components/RowActions.tsx
"use client";                                   // has open state + onClick → client
import * as Popover from "@radix-ui/react-popover";
import { useTransition } from "react";
import { deleteRow } from "@/app/actions";

export function RowActions({ id, children }: { id: string; children: React.ReactNode }) {
  const [pending, startTransition] = useTransition();
  return (
    <Popover.Root>
      <Popover.Trigger asChild>
        <button aria-label="Row actions">⋯</button>
      </Popover.Trigger>
      <Popover.Portal>
        <Popover.Content role="menu" sideOffset={8} className="popover-panel">
          {/* children can be a Server Component: a streamed preview, remote menu items */}
          {children}
          <button
            role="menuitem"
            disabled={pending}
            onClick={() => startTransition(() => deleteRow(id))}
          >
            {pending ? "Deleting…" : "Delete"}
          </button>
        </Popover.Content>
      </Popover.Portal>
    </Popover.Root>
  );
}
```

```typescript
// app/actions.ts
"use server";
import { revalidatePath } from "next/cache";
import { auth } from "@/auth";

export async function deleteRow(id: string) {
  // AUTHORIZE server-side — the popover being hidden is never a security control.
  const session = await auth();
  if (!session?.user) throw new Error("Unauthorized");
  // Scope the mutation to a resource THIS user owns — never trust the id alone (IDOR).
  await db.row.delete({ where: { id, ownerId: session.user.id } });
  revalidatePath("/dashboard");
}
```

The key Next.js insight: **the popover is a client island, but its payload and its actions belong on the server.** Stream heavy popover content (a link preview, a rich hover card) as a Server Component so the client bundle stays lean; run mutations as Server Actions so authorization lives where it can't be bypassed.

### 9.12 Testing the Popover

**Unit / component (Vitest + React Testing Library):**

```typescript
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";

    render(<Popover trigger={<button>Menu</button>}><button>Item</button></Popover>);
    const trigger = screen.getByRole("button", { name: /menu/i });

    await userEvent.keyboard("{Escape}");

  it("does NOT trap focus (Tab escapes to the page — it's not a modal)", async () => {
    render(
      <>
        <Popover trigger={<button>Menu</button>}><button>Item</button></Popover>
        <button>Outside</button>
      </>
    );
    await userEvent.click(screen.getByRole("button", { name: /menu/i }));
    // In a non-modal popover, focus is NOT trapped inside — this is the modal distinction
    // (exact tab-order assertion depends on impl; the point: page stays reachable)
  });
});
```

## 10\. Accessibility (non-negotiable)
A floating panel that leaves the document flow puts the entire a11y burden on you — which is exactly why the native API and headless libraries exist. The contract:

*   **Real elements.** Trigger is a `<button>` (keyboard + focus + role for free). Never a `<div onClick>`.
*   **`aria-expanded`** **on the trigger.** `false` when closed, `true` when open. This is the single most-forgotten popover attribute and the one screen-reader users depend on to know the panel exists. The native API and Radix set it automatically; hand-rolled code must too.
*   **`aria-haspopup`** on the trigger to signal _what kind_ of popover opens: `menu`, `listbox`, `dialog`, `grid`, or `true`. Pair it with `aria-controls="panelId"` linking trigger to panel.
*   **The panel's** **`role`** **must tell the truth.** Rich interactive task → `role="dialog"` with an `aria-label`/`aria-labelledby`. Command list → `role="menu"` + `role="menuitem"`. Options → `role="listbox"` + `role="option"`. A plain labeled panel needs no role. **Never put** **`role="menu"`** **on a panel that contains a form** — it breaks the screen-reader interaction model.
*   **Focus management — the crux.** For an interactive `auto` popover: on open, move focus _into_ the panel (first focusable element, or the panel itself if it's a dialog). On close, **return focus to the trigger.** This is what native and `FloatingFocusManager` handle. Get it wrong and keyboard users are stranded in the void.
*   **Do NOT trap focus (this is not a modal).** A popover is non-modal: Tab can move out of it and the page behind stays reachable. Trapping focus turns your popover into a broken modal. (The exception: a menu, where arrow keys — not Tab — drive navigation and Tab closes it.)
*   **Keyboard map:**

| Key | Action |
| ---| --- |
| `Enter` / `Space` | On trigger: open the popover (and for a menu, focus the first item). |
| `Escape` | Close the popover, return focus to the trigger. Closes innermost first when nested. |
| `Tab` | Move through focusable content; in a plain popover it can leave (non-modal). In a menu, `Tab` closes it. |
| `Arrow keys` | In a menu/listbox: move between items (roving focus). In a plain popover: normal caret/scroll. |
| `Home` / `End` | Menu/listbox: jump to first/last item. |
| Type-ahead | Menu/listbox/select: jump to the item starting with the typed letters. |

*   **Light dismiss must be keyboard-reachable.** Escape is mandatory; don't make click-outside the _only_ way to close.
*   **Contrast & target size** inside the panel: every control ≥ 4.5:1 text contrast, ≥ 44px hit target, visible `:focus-visible` ring (Goldenrod for UJG). The panel floating over content makes contrast _more_ fragile, not less — check it over the real backdrop.
*   **Announce async content.** If the panel loads content after opening, wire an `aria-live` region so screen readers hear "3 results" rather than silence.

## 11\. Innovative & Emerging Ideas
The popover looks solved but is mid-transformation:

*   **The native migration itself** — the biggest shift. Teams are deleting portal libraries and `z-index` managers in favor of `<div popover>` + anchor positioning. The 2026 senior move is _knowing when the native path is enough_ and reaching for JS only for the gaps (arrow tracking, unsupported browsers).
*   **`@starting-style`** **+** **`allow-discrete`** — animating a popover in _from_ `display: none` in pure CSS, no enter/exit JS. This quietly obsoletes a whole class of animation-library usage for popovers.
*   **`interesttarget`** **/ hover-and-focus invocation** — an emerging HTML attribute to declaratively open a `hint` popover on hover/focus intent (the accessible, declarative successor to `title` tooltips and hand-rolled hover cards).
*   **`anchor-size()`** **for self-sizing panels** — a select menu that natively matches its trigger's width, or a popover capped to the anchor, with zero measuring JS.
*   **AI-native popovers** — inline "explain / rewrite / do it for me" panels that stream an agent's response inside the popover. The popover becomes the canonical surface for micro-agentic interactions.
*   **`position-visibility`** **and scroll-driven hiding** — natively hiding an anchored popover when its anchor scrolls out of view, instead of leaving it floating over nothing.
*   **View Transitions for popover open/close** — morphing the trigger into the panel with the View Transitions API for a seamless spatial connection.

## 12\. Conversion & UX Killers (mistakes that bleed money and trust silently)
None of these throw an error. They just quietly make the product feel broken. Every one is fixable in an afternoon.

*   **No** **`aria-expanded`** **/ wrong role.** Silent for sighted mouse users, a total lockout for screen-reader users who never learn the panel exists. The most common popover a11y failure in real audits.
*   **Focus never returns to the trigger.** User opens a menu with the keyboard, closes it, and focus is dumped at the top of the page. They lose their place. Rage-inducing, invisible in a mouse-only QA pass.
*   **Trapping focus like a modal.** A non-modal popover that traps focus makes the page feel frozen — users can't Tab back to what they were doing. You built a modal by accident.
*   **Clipping at the viewport edge.** A popover near the bottom/right that renders half-off-screen or gets clipped by an ancestor's `overflow: hidden`. The old `position: absolute` disease — cured by the top layer / a portal. If your menu items are unreachable, this is why.
*   **No flip/shift fallback.** Opens downward into a cut-off panel because there was no room and it never tried the other side. Always provide `position-try-fallbacks` / `flip()`.
*   **Hover-to-open on interactive content.** The panel vanishes the instant the pointer leaves the trigger to reach a button inside it. Interactive popovers open on _click_, not hover. Hover is for passive hints only.
*   **The panel covers its own trigger.** Disorienting — the thing you clicked disappears under the panel. Offset it.
*   **`z-index`** **wars.** Popover appears _behind_ a header or another panel because of a stacking-context fight. The native top layer ends this; on the JS path, portal to the root.
*   **Doesn't close on outside click.** Users expect light dismiss. A popover that lingers until you find the exact close button feels sticky and broken.
*   **Layout jump on open.** The panel's async content loads and resizes the panel, shifting everything. Reserve space / show a fixed-size skeleton.
*   **Mobile: a tiny anchored panel fighting the keyboard.** A big popover cramped into 40% of a phone screen, half-hidden by the on-screen keyboard. Switch to a bottom sheet below ~480px.

**The through-line:** every one of these fails _quietly_ — no crash, no log, just a keyboard user stranded or a mobile user rage-quitting. Audit your popovers' focus and dismiss behavior before you blame your funnel.

## 13\. Advanced Patterns
The "senior move" versions of the patterns above.

### Native top layer + Floating UI positioning (the hybrid)
The strongest 2026 pattern: `<div popover>` for top-layer stacking, light-dismiss, and focus return (free, native, no bugs), plus Floating UI _only_ for the pixel-perfect anchor math and arrow. You get the browser's correctness where it's hard (stacking, dismiss, focus) and the library's precision where the native positioning isn't there yet. Shown in §9.6.

### `position-try` with a custom `@position-try` block
Beyond the built-in `flip-*` fallbacks, define _named_ fallback positions with their own overrides — e.g. a fallback that also changes the panel's max-width or margin when it flips to the side:

```css
@position-try --side-flip {
  position-area: inline-end;
  margin: 0 0 0 8px;
  max-width: 240px;
}
#panel { position-try-fallbacks: flip-block, --side-flip; }
```

### The popover as a shared primitive (the architecture point)
Don't build Select, Combobox, Menu, and DatePicker as four unrelated components. Build **one** `Popover` primitive (trigger + anchored panel + dismiss + focus contract), then compose the specialized ARIA pattern on top:

*   `Menu` = `Popover` + `role="menu"` + roving focus + type-ahead.
*   `Select` = `Popover` + `role="listbox"` + `aria-selected` + focus into the list.
*   `Combobox` = `Popover` + a text input + `aria-activedescendant` + filtering.
*   `DatePicker` = `Popover` + a `role="grid"` calendar with 2D arrow navigation.
*   `HoverCard` = `Popover` (as `hint`) + hover-intent open delay.

One positioning engine, one dismiss contract, one focus manager — five components. This is why Radix ships them as separate packages that share a floating core, and it's the single biggest leverage point in a component library. **Fix a positioning bug once, fix it everywhere.**

### TypeScript: force the role↔content contract
A discriminated union can _require_ an `aria-label` whenever the popover is a `dialog`, and _forbid_ form children when it's a `menu`, catching a whole class of a11y bugs at compile time:

```typescript
type MenuPopover = { role: "menu"; children: React.ReactElement<MenuItemProps>[] };
type DialogPopover = { role: "dialog"; "aria-label": string; children: React.ReactNode };
type LabeledPopover = { role?: undefined; children: React.ReactNode };
type PopoverContent = MenuPopover | DialogPopover | LabeledPopover;
// Now <Popover role="dialog"> won't compile without an aria-label.
```

### Anchoring to a virtual point (context menus)
For a right-click / long-press context menu, the anchor isn't an element — it's the pointer coordinates. Floating UI accepts a _virtual element_ (`{ getBoundingClientRect: () => ({ x, y, width: 0, height: 0, ... }) }`), so the same popover machinery positions a menu at the cursor with no real anchor DOM.

## 14\. Performance & Bundle Cost
A popover feels free. At scale it isn't.

*   **Don't mount 500 popovers for 500 rows.** A data table with a "⋯ actions" popover per row should _not_ render 500 panels. Render **one** popover and re-anchor it to whichever row's trigger was clicked (a single portal, anchor swapped on open). Mounting a panel per row explodes the DOM and memory.
*   **Lazy-render the panel content.** Don't render the popover's (possibly expensive) contents until it's actually opened. `{open && <PanelBody/>}` — not always-mounted-and-hidden. A page with dozens of closed popovers shouldn't pay for all their bodies up front.
*   **`autoUpdate`** **is not free.** It attaches scroll/resize/ResizeObserver listeners. Attach it _only while open_ and **clean it up on close** (the `cleanup()` / `stopAutoUpdate()` call). A leaked `autoUpdate` per popover is a real memory + CPU leak on long-lived pages.
*   **The native top layer beats a JS portal on cost.** No React portal reconciliation, no `z-index` bookkeeping, no scroll-lock library — the browser does it in C++. Another reason the native path wins where supported.
*   **Animate only** **`transform`** **and** **`opacity`****\*\*\*\*\*\*\*\*.** The open transition should scale/fade, never animate `width`/`height`/`top` (those force reflow every frame). `transform-origin` at the anchor edge gives the "grows from the trigger" feel cheaply.
*   **Tree-shake the middleware.** Import `offset`, `flip`, `shift` by name from Floating UI, never the whole namespace. And you often _don't_ need `arrow` — drop it if there's no visual arrow.
*   **Bundle math:** the native API is **0 KB**. Floating UI core is small (~a few KB) but the React bindings + focus manager add up; on a page that only needs a couple of simple popovers, the native path can delete the dependency entirely.

## 15\. Security (only where the popover reaches the server)
A popover itself is presentational, but its _contents_ often trigger real actions (a menu item that deletes a record, a mini-form that posts data). The security rules are the same as any action surface:

*   **The popover being hidden is never a permission check.** "The Delete item wasn't in the menu" must never mean "the user can't delete." `disabled`/hidden menu items are trivially bypassed in devtools or by calling the endpoint directly. Re-check authorization server-side for every action a popover fires (see the Next.js Server Action in §9.7 — the `deleteRow` action authorizes on the server, not in the client island).
*   **Validate popover-carried data.** A menu item's `data-id`, a hidden input in a popover form — all attacker-controllable. Authorize that _this_ user may act on _that_ resource; don't trust the ID came from your UI.
*   **Rich hover-card content that's user-generated must be sanitized.** A popover previewing a user's bio or a link's page title is an XSS vector if you `innerHTML` untrusted content. Escape it or render as text.
*   **Rate-limit actions fired from popovers** just like button-triggered ones — a menu can be scripted as easily as a button.

## 16\. Senior-Level Checklist (ship-ready)
Before a popover is "done":

- [ ] Trigger is a real `<button>` with `aria-expanded` reflecting open/closed state.
- [ ] `aria-haspopup` (+ `aria-controls`) on the trigger names the popover type.
- [ ] Panel `role` tells the truth: `dialog` (labeled) / `menu` / `listbox` / none — never `menu` on a form.
- [ ] On open, focus moves into the panel; on close, focus **returns to the trigger**.
- [ ] Focus is **not trapped** — it's a popover, not a modal. (Menu Tab-to-close is the intended exception.)
- [ ] Escape closes it AND returns focus; click-outside (light dismiss) closes it.
- [ ] Renders in the top layer (native) or a portal (JS) — no clipping by `overflow:hidden`, no `z-index` war.
- [ ] Flip/shift fallbacks so it never renders off-screen; caps `max-height` and scrolls internally.
- [ ] Only one `auto` popover open at a time; nested popovers close innermost-first on Escape.
- [ ] Open animation uses `transform`/`opacity` only; honors `prefers-reduced-motion`.
- [ ] Every control inside: ≥44px target, ≥4.5:1 contrast over the real backdrop, visible focus ring.
- [ ] Panel content lazy-rendered; `autoUpdate`/positioning listeners cleaned up on close.
- [ ] On small screens, a large popover becomes a bottom sheet.
- [ ] Every action the popover fires is authorized and validated server-side, regardless of UI state.

## 17\. Visual Styles (the same popover, eleven skins)
Style is the skin; behavior is the skeleton. Across all eleven, the trigger keeps `aria-expanded`, focus moves in and returns on close, Escape and click-outside dismiss, focus is never trapped, and every control keeps its 44px target and visible focus ring. Only the paint changes.

*   **Flat:** solid panel fill, crisp 1px border, one flat shadow to lift it off the page, no gradients. Reads instantly; the safe default for dense/data UIs.
*   **Material:** elevation shadow (z-level 2–3), the panel scales-and-fades in from the anchor edge, ripple on menu items. Rounded corners, bold accent on the selected item.
*   **Glassmorphism:** translucent panel + `backdrop-filter: blur()` over the page behind it. Looks premium; **guard contrast** — text over a blurred busy background fails AA fast. Add a semi-opaque layer under the text.
*   **Liquid Glass (the 2026 trend):** Apple's iOS 26 / macOS Tahoe language — the panel _refracts_ what's behind it with a specular rim and a subtle moving sheen, not a static blur. Sings over deep Eminence. Honor `prefers-reduced-motion` for the sheen; keep the inner text on a solid-enough plate for contrast.
*   **Neumorphism:** the panel is the same color as the page with dual light/dark shadows, looking extruded. Pretty, contrast-poor — accent surfaces only, never for a panel full of readable options.
*   **Skeuomorphism:** beveled panel edge, inner highlight, gradient fill, a real drawn arrow/beak with its own shadow tethering it to the trigger. The tactile "real object" look.
*   **Neo-Brutalism:** thick black border, hard offset shadow (no blur), zero radius, clashing accent on hover items. High personality; great for campaign/editorial.
*   **Claymorphism:** big radius, soft inner top-light + bottom-shadow, puffy panel with a gentle glow. Friendly, playful — good for consumer/onboarding popovers.
*   **Aurora / Gradient:** animated multi-hue gradient border or backdrop on a dark panel. Premium; **honor** **`prefers-reduced-motion`** and keep the animation on the frame, not behind the text.
*   **Minimal / Swiss:** near-zero decoration — a hairline border, generous padding, type and grid do the work. Sharp corners, no arrow. The choice for editorial and content-forward products.
*   **UJG Brand:** deep Eminence (`#5F2C82`) / Night (`#0A0A0A`) panel surface, Platinum (`#E8E6E1`) text, Goldenrod (`#DCA424`) focus ring and selected-item accent, confident 10–12px radius, a warm soft glow for elevation. Liquid Glass accents welcome over the dark ground. The house default — Afro-Futurist, warm, and unmistakably ours.
