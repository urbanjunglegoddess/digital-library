## 1\. What a Select Actually Is
A select is a control that lets a user **pick one option (or several) from a known, finite list**, where the list is normally hidden until they open it. That's the whole job. But "select" is a word people smear across five different components, and getting them confused is the root of most bad implementations:

*   **Select / dropdown (this doc):** pick from a fixed list of _values_. The list collapses to save space. Backed by `<select>` or an ARIA `listbox`. The user chooses; they don't type.
*   **Combo box:** a select **with a text input that filters the list**. You type "cal", the list narrows to California. It's a listbox _plus_ a textbox, ARIA role `combobox`. If your control has a filter field, it is a combobox, not a select — see §7.
*   **Menu (****`role="menu"`****):** a list of **actions/commands**, not values ("Cut," "Copy," "Rename"). It doesn't hold a persistent selection. A right-click context menu or an app menubar. Using `menu` semantics for value-picking is a classic mislabel.
*   **Autocomplete / typeahead:** a text field that _suggests_ completions as you type, but you can often submit free text too. Combobox-family, but the list is advisory, not the only source of truth.
*   **Radio group / checkbox group:** the _same job_ as a select (pick one / pick many) but with **all options visible at once**. For ≤5 options this usually beats a select — no click to open, no hidden state.

The single most common architectural mistake: **reaching for a custom** **`<div>`****\*\*\*\*-based dropdown when a native** **`<select>`** **would do.** The native element gives you keyboard support, screen-reader semantics, mobile OS pickers, form participation, and typeahead — for free, in one tag. A custom listbox throws all of that on the floor and asks you to rebuild it by hand, correctly, forever. Rule of thumb: **native** **`<select>`** **until a hard requirement forces you off it. Then, and only then, build an ARIA listbox — and budget for the accessibility work, because it's real.**
* * *

## 2\. Why It Matters
A select is where a user commits a _decision_ into your system, so it sits directly on top of data quality, conversion, and trust.

*   **It's a conversion choke point.** Country pickers, shipping options, plan tiers, quantity, size — checkout and signup are stuffed with selects. A select that's slow to open, hard to scan, or impossible to use on a phone is friction on the exact screens where friction costs money. The "150-country `<select>` that scrolls forever" is a measurable drop-off.
*   **It's a data-integrity tool.** The reason selects exist at all is to _constrain input to valid values_. A free-text "State" field gives you "CA," "Cali," "California," and "califnoria." A select gives you one canonical value every time. That's cleaner analytics, fewer validation bugs, and less downstream data-cleaning.
*   **It's an accessibility cliff.** The native `<select>` is one of the most accessible controls in the browser. The moment you replace it with a custom widget, you inherit responsibility for roles, states, a full keyboard model, focus management, and screen-reader announcements. Most custom dropdowns on the web are subtly broken for keyboard and AT users. This is _the_ component where "we built our own" most often means "we shipped an accessibility regression."
*   **It sets the perceived-quality bar.** A select that opens instantly, positions itself without covering its own trigger, closes on Escape, and returns focus cleanly reads as _considered_. One that jumps around, traps focus, or won't close on Escape reads as broken even when the value it captures is correct.

## 3\. Anatomy of a Select
Whether native or custom, the same conceptual parts are present:

*   **Trigger / control:** the always-visible box the user clicks. Shows the current value (or a placeholder) and a **disclosure indicator** (the chevron ▾). In native land this is the `<select>` element itself.
*   **Value display:** the selected option's label rendered in the trigger. For multi-select, this becomes a count ("3 selected"), a token/chip list, or a summary.
*   **Placeholder:** the "Choose one…" prompt shown before a selection. Native-side this is a disabled first `<option>`; it is _not_ a real value.
*   **Disclosure indicator:** the chevron/caret signalling "this opens." Rotates or flips when open in most custom builds.
*   **Popup / listbox:** the overlay that appears on open, containing the options. Positioned relative to the trigger, must handle collision with viewport edges.
*   **Option:** a single choosable row. Has a label, an underlying value, and states (selected, active/highlighted, disabled).
*   **Option group (****`optgroup`****):** a labelled cluster of related options ("North America" → US, Canada, Mexico). The group label is _not_ selectable.
*   **Selected indicator:** a checkmark, filled dot, or highlight showing which option(s) are chosen — critical in multi-select where the trigger can't show everything.
*   **Active descendant / highlight:** the "virtual focus" row the keyboard is currently on inside an open listbox. Distinct from the actual selection.
*   **Empty / loading / no-results state:** what the popup shows when options are still loading, or when a filter (combobox territory) matches nothing.
* * *

## 4\. Sizes & Density
A select's control matches your input/button scale so forms line up. The popup rows follow their own density rules.

| Size | Control height | Padding (H) | Font | Row height (option) | Use |
| ---| ---| ---| ---| ---| --- |
| SM | 32px | 8–10px | 13px | 32px | Toolbars, dense filter bars, data grids |
| MD | 40px | 12px | 14px | 36–40px | Default for most forms |
| LG | 48px | 16px | 16px | 44–48px | Mobile-first, primary flows, checkout |

Rules that matter:

*   **Control height should track your text inputs and buttons exactly.** A select that's 2px taller than the input next to it is the tell of an ungoverned system. Drive all three off one height token.
*   **Option rows want ≥44px of tappable height on touch,** even if the visual row looks shorter — pad the hit area. A cramped 28px option list is a mis-tap generator on a phone.
*   **Popup width ≥ trigger width.** Options usually determine the natural width; never make the popup _narrower_ than the trigger or you get truncated labels under a wide control.
*   **Cap popup height and scroll inside it.** A 200-item list should not be a 200-row-tall overlay. Set a max-height (~40vh or ~8–10 rows) and scroll the interior. Past a few hundred rows, virtualize (§13).
*   **Font-size ≥16px on the mobile control** avoids iOS Safari's auto-zoom-on-focus. This bites forms constantly.
* * *

## 5\. States (where custom builds fall apart)
A select has more states than a button because it has _two_ surfaces (the trigger and the popup) and a notion of "highlighted vs. selected." Missing states are the #1 tell of an amateur custom dropdown.

**Trigger states**
1. **Default (rest)** — placeholder or current value, chevron down.
2. **Hover** — subtle background/border shift. (Doesn't exist on touch.)
3. **Focus** — visible `:focus-visible` ring. Native gets this free; custom must not forget it.
4. **Open / expanded** — popup is showing; chevron often flips; trigger reflects `aria-expanded="true"`.
5. **Filled vs. empty** — placeholder styling (muted) vs. real value (full-contrast). A placeholder that looks identical to a real value is a bug.
6. **Disabled** — not interactive. Reduced contrast, `cursor: not-allowed`, and — critically — still _announced_ so AT users know it exists but is off.
7. **Invalid / error** — failed validation ("Please choose a country"). Red border, `aria-invalid="true"`, message wired via `aria-describedby`.
8. **Read-only** — value shown, not changeable, but still focusable/announced. (Native `<select>` has no true readonly; you emulate with `disabled` + a hidden input, or lock it in JS.)
9. **Loading (async trigger)** — the control itself is waiting on its options; show a spinner and mark `aria-busy`.

**Option / popup states**
10\. **Option: default** — resting row.
11\. **Option: active / highlighted** — the keyboard's current row (`aria-activedescendant` or roving focus). Visually distinct from selection.
12\. **Option: selected** — the chosen value(s), `aria-selected="true"`, usually a checkmark.
13\. **Option: disabled** — not choosable, skipped by keyboard, `aria-disabled="true"`.
14\. **Popup: loading** — options are streaming in; show skeleton rows or a spinner.
15\. **Popup: empty / no results** — nothing to show (or, in combobox, nothing matched the filter). Never a blank void — say "No options."

The distinction juniors miss: **"active" (highlighted) is not "selected."** In an open listbox, the arrow keys move a highlight; the value only changes when the user commits (Enter, click, or — in single-select — sometimes on close). Two different visual treatments, two different ARIA attributes. Conflating them is the most common custom-listbox bug.
* * *

## 6\. Types & Variants
By _cardinality_ and by _shape_:

*   **Single-select:** pick exactly one. The default. Native `<select>`.
*   **Multi-select:** pick zero-to-many. Native `<select multiple>` exists but is genuinely awful UX (shift-click, no chevron, tiny scroll box) — almost everyone builds a custom checkbox-listbox instead. Trigger shows a count or chips.
*   **Grouped select:** options clustered under non-selectable headers via `<optgroup>` / `role="group"`. "Fonts → Sans-serif → …".
*   **Native select:** `<select>`. Reach here first. OS-rendered popup on mobile.
*   **Custom listbox:** ARIA `role="listbox"` + `role="option"`, styled by you, driven by JS. Full control, full accessibility responsibility.
*   **Combobox (adjacent, not this doc):** select + text filter. `role="combobox"`. See §7.
*   **Searchable select:** a select whose popup includes a filter field — that _is_ a combobox by role, even if the product calls it a "searchable dropdown."
*   **Async / remote select:** options fetched over the network (on open, or as you type). Adds loading, error, and empty states, plus debouncing.
*   **Creatable select:** lets the user add a value not in the list ("Add 'Afrofuturism' as a new tag"). Combobox-family; needs a clear "create" affordance.
*   **Editable/settings select:** the "segmented dropdown" used for a persistent app setting (theme, sort order) — same mechanics, different placement (not in a form).
* * *

## 7\. When to Use a Select — and When Not To
Use a select when the user must pick from a **known, finite set of values** and you want to **save vertical space** by hiding the list until asked. Don't use one when a better pattern exists:

*   **≤ 5 mutually-exclusive options → radio group.** All choices visible, one tap, no hidden popup. A select for "Yes / No / Maybe" is pure friction.
*   **≤ 5 non-exclusive options → checkbox group.** Same logic for multi-select. Don't hide four checkboxes behind a dropdown.
*   **2 options that toggle a setting → switch or segmented control.** "On/Off," "Grid/List."
*   **Very large, searchable set (countries, users, SKUs) → combobox** (select + filter). Nobody wants to scroll 195 countries. **This is the key fork:** the moment the list gets long enough that scanning it is painful, you need a text filter — and a text filter makes it a **combobox**, `role="combobox"`, not a plain listbox. The difference isn't cosmetic: a combobox has a focusable textbox that owns the input, the listbox is a popup it controls, and the ARIA + keyboard model changes (typing filters instead of typeahead-jumping). Calling a filtered dropdown a "select" and wiring it with listbox semantics is a real accessibility bug.
*   **The action does something rather than storing a value → menu, not select.** "Export as PDF / CSV" is a menu of commands.
*   **Free-form input is genuinely needed → text input** (with optional autocomplete). Don't jail an open-ended answer in a dropdown.

Placement heuristics:

*   **Label above the control** (not only a placeholder) so the field's purpose survives after a value is picked. Placeholder-as-label is an accessibility and usability antipattern.
*   **Order options meaningfully:** frequency, then alphabetical. Put "United States" at the top of a country list _and_ leave it in alphabetical order below if your audience is US-heavy.
*   **Default selection:** pre-select the safe/common value when one clearly dominates; leave an explicit placeholder when choosing is a real decision you don't want to bias.

## 8\. Selects Across Design Systems
Same control, very different philosophies and — importantly — different honesty about the native-vs-custom tradeoff.

*   **Material Design (Google):** the "Select" is a filled/outlined text-field shell with a floating label and a menu popup ("exposed dropdown menu"). Under the hood Material Web / MUI render a **custom listbox**, not a native `<select>`, to get the animated menu and floating label — and they carry the ARIA work to match.
*   **Apple HIG (iOS/macOS):** the **pop-up button** (shows current value, opens a menu at the control) and the **pull-down**. On iOS a `<select>` becomes the native wheel/sheet picker — one of the strongest arguments for staying native on mobile. SwiftUI's `Picker` adapts its presentation per platform automatically.
*   **Fluent (Microsoft):** distinguishes a native-backed **Dropdown** from a **Combobox** (filterable). Compact, neutral, form-dense. Fluent is careful about the role split.
*   **Ant Design / enterprise:** the `Select` is custom, feature-maximal — search, tags, multiple, async, virtualized long lists, grouping — built for data-heavy admin UIs where the native element can't keep up. The price is a large, JS-driven component.
*   **Tailwind / utility-first:** no select component ships in the box. You either style a native `<select>` (limited) or reach for Headless UI's `Listbox`/`Combobox` for the accessible behavior and paint it with utilities.
*   **shadcn/Radix (2024+ web standard):** `Select` is Radix primitives (fully accessible listbox behavior, typeahead, focus management, collision-aware positioning) + Tailwind skin, copied into your repo. The default modern answer when you've genuinely outgrown native.
*   **Bootstrap:** ships `.form-select`, which is a **styled native** **`<select>`** — accessible by default, limited in look. For anything richer Bootstrap punts to a JS plugin.

The throughline: mature systems are explicit about **"this variant is a real** **`<select>`** **(accessible, limited)" vs. "this one is a custom listbox (flexible, you own a11y)."** Amateur systems ship a `<div>` dropdown and call it done.

## 9\. The Code
### 9.1 HTML (start here — the native `<select>` is a superpower)
Before any framework, know exactly what the platform gives you for free. This single element is keyboard-accessible, screen-reader-labelled, form-associated, typeahead-searchable, and renders a native OS picker on mobile — with zero JavaScript.

```plain
<!-- Single select with a real label and a non-value placeholder -->
<label for="country">Country</label>
<select id="country" name="country" required>
  <option value="" disabled selected>Choose a country…</option>
  <option value="us">United States</option>
  <option value="ca">Canada</option>
  <option value="mx">Mexico</option>
</select>

<!-- Grouped options: optgroup gives free, accessible section headers -->
<label for="font">Typeface</label>
<select id="font" name="font">
  <optgroup label="Display">
    <option value="methanerse">Methanerse</option>
    <option value="mallong">Mallong</option>
  </optgroup>
  <optgroup label="Text">
    <option value="urbanist">Urbanist</option>
  </optgroup>
</select>

<!-- A disabled option is announced but not choosable -->
<option value="pro" disabled>Pro (upgrade required)</option>

<!-- Multi-select: native, but see the UX warning below -->
<label for="tags">Tags</label>
<select id="tags" name="tags" multiple size="6">
  <option value="afrofuturism">Afrofuturism</option>
  <option value="branding">Branding</option>
  <option value="ux">UX</option>
</select>

<!-- Whole control disabled -->
<select name="plan" disabled>
  <option>Team plan (contact sales)</option>
</select>
```

Key HTML rules:

*   **The placeholder is a** **`disabled selected`** **first option with an empty value.** `disabled` stops it being re-picked; `required` on the `<select>` then makes the empty value fail validation until a real option is chosen. This is the honest native pattern.
*   **`name`** **is what submits.** The selected `<option>`'s `value` (falling back to its text) is sent under the select's `name`. No `name`, no data.
*   **`optgroup`** **is the free win people forget.** It renders a bold, non-selectable header and is announced by screen readers as a group — accessibility you'd otherwise hand-build in a custom listbox.
*   **`<select multiple>`** **works but reads badly:** no chevron, shift/ctrl-click to multi-pick, an always-open scroll box. Great for a power-user admin screen, wrong for consumer UX — which is why everyone builds a custom checkbox listbox instead (§9.3).
*   **Styling the popup is the native element's one real limit.** You can style the closed control well; the open option list is OS-drawn and largely un-styleable — until `selectmenu`/customizable-select lands (§11).

### 9.2 CSS (styling native, and the states that matter)
Modern CSS styles a native `<select>`'s _control_ far better than the old days. The option list is still mostly OS-drawn (pre-`::picker`).

```css
.select {
  /* strip the default chrome so we can restyle the control */
  appearance: none;
  -webkit-appearance: none;
  display: inline-flex;
  align-items: center;
  width: 100%;
  min-height: 44px;          /* touch target */
  padding: 0 40px 0 12px;     /* room for our own chevron on the right */
  border: 1px solid #6b5b7e;
  border-radius: 8px;
  background: #140a1e;
  color: #E8E6E1;
  font: 400 16px/1.2 system-ui, sans-serif;  /* 16px avoids iOS zoom */
  cursor: pointer;

  /* our own chevron via background image (native one is gone with appearance:none) */
  background-image: url("data:image/svg+xml,%3Csvg .../%3E");
  background-repeat: no-repeat;
  background-position: right 12px center;
}

/* Keyboard focus only */
.select:focus-visible {
  outline: 2px solid #DCA424;   /* Goldenrod */
  outline-offset: 2px;
}

/* Placeholder-selected state: mute it so it doesn't read as a real value */
.select:has(option[value=""]:checked) { color: #9a8fa6; }

/* Invalid */
.select[aria-invalid="true"] { border-color: #E86100; }

/* Disabled */
.select:disabled {
  opacity: .55;
  cursor: not-allowed;
  background-color: #0f0916;
}

/* 2024+: style the option list on supporting engines */
@supports (appearance: base-select) {
  select, ::picker(select) { appearance: base-select; }  /* opt into customizable select */
  ::picker(select) { border-radius: 12px; }
  option:checked::after { content: "✓"; margin-inline-start: auto; }
}
```

Notes:

*   **`appearance: none`** **deletes the native chevron,** so you must draw your own (background SVG or a wrapper with a positioned icon) — forgetting this ships a select with no disclosure indicator.
*   **`:has(option[value=""]:checked)`** is the clean, JS-free way to detect the placeholder is still selected and mute the text.
*   **`appearance: base-select`** **+** **`::picker(select)`** is the new customizable-select opt-in (§11) — behind `@supports` so it enhances where available and stays a normal native select everywhere else.

### 9.3 React + TypeScript (a headless custom listbox, done right)
This is the block to study. When native truly won't do — you need styled options, checkmarks, custom rows — you build an ARIA `listbox`. Here's a production-shaped single-select with the full keyboard model, `aria-activedescendant` virtual focus, typeahead, and focus return. This is roughly 10x the code of `<select>`, which is the whole point of §1's warning.

```typescript
import {
  useRef, useState, useId, useEffect, useCallback, KeyboardEvent,
} from "react";

export interface SelectOption {
  value: string;
  label: string;
  disabled?: boolean;
}

interface SelectProps {
  label: string;
  options: SelectOption[];
  value: string | null;
  onChange: (value: string) => void;
  placeholder?: string;
}

export function Select({ label, options, value, onChange, placeholder = "Select…" }: SelectProps) {
  const [open, setOpen] = useState(false);
  const [activeIndex, setActiveIndex] = useState<number>(-1);
  const triggerRef = useRef<HTMLButtonElement>(null);
  const listRef = useRef<HTMLUListElement>(null);
  const typeahead = useRef({ str: "", timer: 0 });
  const listboxId = useId();
  const labelId = useId();
  const triggerId = useId();

  const selectedIndex = options.findIndex((o) => o.value === value);
  const selected = selectedIndex >= 0 ? options[selectedIndex] : null;

  // --- open/close with correct focus management -----------------------------
  const openList = useCallback(() => {
    setOpen(true);
    // highlight the current selection, or the first enabled option
    setActiveIndex(selectedIndex >= 0 ? selectedIndex : firstEnabled(options));
  }, [selectedIndex, options]);

  const closeList = useCallback((returnFocus = true) => {
    setOpen(false);
    setActiveIndex(-1);
    if (returnFocus) triggerRef.current?.focus();  // focus MUST return to the trigger
  }, []);

  const commit = useCallback((index: number) => {
    const opt = options[index];
    if (!opt || opt.disabled) return;
    onChange(opt.value);
    closeList();
  }, [options, onChange, closeList]);

  // keep the active option scrolled into view
  useEffect(() => {
    if (!open || activeIndex < 0) return;
    listRef.current
      ?.querySelector<HTMLElement>(`[data-index="${activeIndex}"]`)
      ?.scrollIntoView({ block: "nearest" });
  }, [open, activeIndex]);

  // move real DOM focus INTO the listbox on open so it receives the key events
  useEffect(() => {
    if (open) listRef.current?.focus();
  }, [open]);

  // clear any pending typeahead timer on unmount
  useEffect(() => () => window.clearTimeout(typeahead.current.timer), []);

  const move = (dir: 1 | -1) =>
    setActiveIndex((i) => nextEnabled(options, i, dir));

  // --- the full keyboard map ------------------------------------------------
  function onTriggerKeyDown(e: KeyboardEvent) {
    switch (e.key) {
      case "ArrowDown":
      case "ArrowUp":
      case "Enter":
      case " ":
        e.preventDefault();
        openList();
        break;
    }
  }

  function onListKeyDown(e: KeyboardEvent) {
    switch (e.key) {
      case "ArrowDown": e.preventDefault(); move(1); break;
      case "ArrowUp":   e.preventDefault(); move(-1); break;
      case "Home":      e.preventDefault(); setActiveIndex(firstEnabled(options)); break;
      case "End":       e.preventDefault(); setActiveIndex(lastEnabled(options)); break;
      case "Enter":
      case " ":         e.preventDefault(); commit(activeIndex); break;
      case "Escape":    e.preventDefault(); closeList(); break;       // close, keep value, return focus
      case "Tab":       closeList(false); break;                       // close, let focus move on
      default:          handleTypeahead(e); break;
    }
  }

  // typeahead: buffer keystrokes, jump to the first matching label
  function handleTypeahead(e: KeyboardEvent) {
    if (e.key.length !== 1) return;
    window.clearTimeout(typeahead.current.timer);
    typeahead.current.str += e.key.toLowerCase();
    const match = options.findIndex(
      (o) => !o.disabled && o.label.toLowerCase().startsWith(typeahead.current.str)
    );
    if (match >= 0) setActiveIndex(match);
    typeahead.current.timer = window.setTimeout(() => (typeahead.current.str = ""), 500);
  }

  return (
    <div className="select-field">
      <span id={labelId} className="select-label">{label}</span>

      <button
        ref={triggerRef}
        id={triggerId}
        type="button"
        className="select-trigger"
        aria-haspopup="listbox"
        aria-expanded={open}
        aria-labelledby={`${labelId} ${triggerId}`}
        onClick={() => (open ? closeList() : openList())}
        onKeyDown={onTriggerKeyDown}
      >
        <span className={selected ? "" : "is-placeholder"}>
          {selected ? selected.label : placeholder}
        </span>
        <svg className="chevron" aria-hidden="true" />
      </button>

      {open && (
        <ul
          ref={listRef}
          id={listboxId}
          role="listbox"
          tabIndex={-1}
          aria-labelledby={labelId}
          aria-activedescendant={activeIndex >= 0 ? `${listboxId}-opt-${activeIndex}` : undefined}
          className="select-listbox"
          onKeyDown={onListKeyDown}
        >
          {options.map((opt, i) => (
            <li
              key={opt.value}
              id={`${listboxId}-opt-${i}`}
              data-index={i}
              role="option"
              aria-selected={opt.value === value}
              aria-disabled={opt.disabled || undefined}
              className={
                "select-option" +
                (i === activeIndex ? " is-active" : "") +
                (opt.disabled ? " is-disabled" : "")
              }
              onMouseEnter={() => !opt.disabled && setActiveIndex(i)}
              onClick={() => commit(i)}
            >
              {opt.label}
              {opt.value === value && <span aria-hidden="true"> ✓</span>}
            </li>
          ))}
        </ul>
      )}
    </div>
  );
}

// --- helpers: skip disabled options when moving ----------------------------
function firstEnabled(opts: SelectOption[]) {
  return opts.findIndex((o) => !o.disabled);
}
function lastEnabled(opts: SelectOption[]) {
  for (let i = opts.length - 1; i >= 0; i--) if (!opts[i].disabled) return i;
  return -1;
}
function nextEnabled(opts: SelectOption[], from: number, dir: 1 | -1) {
  let i = from;
  for (let step = 0; step < opts.length; step++) {
    i = (i + dir + opts.length) % opts.length;
    if (!opts[i].disabled) return i;
  }
  return from;
}
```

Why this is the senior version, not the junior one:

*   **`aria-activedescendant`** **"virtual focus":** real DOM focus stays on the `<ul>`; a _data attribute + aria pointer_ tracks the highlighted row. This is the pattern screen readers expect for a listbox and it avoids the focus-thrashing of moving `tabindex` per option.
*   **Disabled options are** **_skipped_** **by arrows,** not just visually greyed. `nextEnabled` wraps around them. A keyboard user who lands on a dead row is a bug.
*   **Focus returns to the trigger on close** (Escape, select, click-away) — except on Tab, where you close _without_ stealing focus so Tab flows naturally to the next field. Getting this wrong traps the user or dumps focus to `<body>`.
*   **Typeahead** buffers keystrokes for 500ms so "ca" → Canada, not C then A. Native `<select>` does this for free; your custom one must reimplement it or power users will notice instantly.
*   **Open highlights the current selection,** so re-opening a select lands you on what's already chosen, not the top.

**What it does not show, and you'd add for production:** outside-click and Escape handling via a dismiss hook, `scroll-into-view` on typeahead jumps, and — for multi-select — `aria-multiselectable="true"` with Space toggling instead of committing. That "and you'd also add…" list is exactly the accessibility tax §1 warns about.

### 9.4 Multi-select (the native trap and the real pattern)
Native `<select multiple>` is accessible but universally disliked. The real-world multi-select is a custom listbox with `aria-multiselectable`, checkboxes, and a chip/count trigger.

```typescript
// Behavior deltas from the single-select above:
// 1. aria-multiselectable="true" on the <ul role="listbox">
// 2. each option keeps role="option" + aria-selected; render a checkbox glyph
// 3. Space / Enter TOGGLES the active option instead of committing + closing
// 4. the list stays OPEN after a toggle (you're picking several)
// 5. the trigger summarizes: "3 selected" or chips, not a single label
// 6. optional: Ctrl/Shift range-select for power users; a "Select all" row

function toggle(value: string, selected: string[], onChange: (v: string[]) => void) {
  onChange(
    selected.includes(value)
      ? selected.filter((v) => v !== value)   // deselect
      : [...selected, value]                   // add
  );
}
```

The count/chips trigger is not decoration — in multi-select the trigger physically cannot show every choice, so the **selected indicator inside the popup (checkmarks) becomes the source of truth**, and the trigger summarizes. Chips that are individually removable (an ✕ per chip) are the friendliest pattern; a plain "N selected" is the most compact.

### 9.8 Node.js (the endpoint behind the select)
A `<select>` submits one string per `name` (or an array for multiple). The server's job is to **never trust that the value is valid** — a client can send any string, disabled options and all.

```typescript
import express from "express";
import { z } from "zod";

const router = express.Router();

// Whitelist: the server owns the source of truth for allowed values
const ALLOWED_PLANS = ["studio", "core", "alchemy"] as const;
const ALLOWED_TAGS = ["afrofuturism", "branding", "ux"] as const;

const ProfileSchema = z.object({
  // z.enum rejects anything not in the list — the #1 select-security check
  plan: z.enum(ALLOWED_PLANS),
  // multi-select arrives as an array (or a single string if one was picked)
  tags: z.preprocess(
    (v) => (Array.isArray(v) ? v : v == null ? [] : [v]),
    z.array(z.enum(ALLOWED_TAGS)).max(10)
  ),
});

router.post("/api/profile", requireAuth, async (req, res) => {
  const parsed = ProfileSchema.safeParse(req.body);
  if (!parsed.success) return res.status(422).json(parsed.error.issues);

  // Even valid-shaped values must be authorized: can THIS user pick "core"?
  if (parsed.data.plan === "core" && !req.user.canSelectCorePlan) {
    return res.status(403).json({ error: "Plan not available on your account" });
  }

  await db.profile.update(req.user.id, parsed.data);
  res.status(200).json({ ok: true });
});

export default router;
```

The two server truths for selects: **validate the value is in the allowed set** (`z.enum` / a DB lookup — a disabled option in the UI is not a security control, a curl request skips it), and **authorize that this user may pick this value** (the "Pro plan" option being hidden is UX; the server must still refuse it). Multi-select adds the array-normalization wrinkle: HTML sends a single value as a string and multiple as an array, so coerce before validating — and every element is then checked against its own allow-list (`z.enum` / a `Tag` enum), not merely typed as a string.

### 9.9 Python (backend validation + a server-rendered select)
**Backend** (FastAPI) with an enum that mirrors the UI's option list:

```python
from enum import Enum
from fastapi import FastAPI, Depends, HTTPException
from pydantic import BaseModel, Field

app = FastAPI()

class Plan(str, Enum):          # the allowed option set, enforced by the type
    studio = "studio"
    core = "core"
    alchemy = "alchemy"

class Tag(str, Enum):           # multi-select allow-list - every element is checked
    afrofuturism = "afrofuturism"
    branding = "branding"
    ux = "ux"

class ProfileIn(BaseModel):
    plan: Plan                                   # rejects anything not in Plan
    tags: list[Tag] = Field(default_factory=list, max_length=10)   # each element is validated against Tag

@app.post("/api/profile")
def update_profile(body: ProfileIn, user=Depends(require_auth)):
    if body.plan is Plan.core and not user.can_select_core:
        raise HTTPException(403, "Plan not available")
    db.update_profile(user.id, plan=body.plan.value, tags=body.tags)
    return {"ok": True}
```

### 9.10 Vanilla JavaScript (enhancing a native select, no framework)
Often you don't need a custom widget — you need a native `<select>` with a little behavior wired on. Reading the value, reacting to change, and populating options dynamically:

```javascript
const select = document.querySelector("#country");

// React to selection — 'change' fires for mouse, keyboard, and mobile pickers alike
select.addEventListener("change", (e) => {
  const value = e.target.value;
  const label = e.target.selectedOptions[0]?.textContent;
  document.querySelector("#shipping").hidden = value === "";   // reveal dependent field
});

// Populate async options (e.g. cities after a country is chosen)
async function loadCities(countryCode) {
  const sel = document.querySelector("#city");
  sel.disabled = true;
  sel.innerHTML = `<option value="">Loading…</option>`;
  sel.setAttribute("aria-busy", "true");
  try {
    const cities = await fetch(`/api/cities?c=${encodeURIComponent(countryCode)}`).then((r) => r.json());
    // Build options with new Option() so fetched city data is set as text, never parsed as HTML
    sel.replaceChildren();
    const placeholder = new Option("Choose a city…", "");
    placeholder.disabled = true;
    placeholder.selected = true;
    sel.add(placeholder);
    for (const c of cities) {
      sel.add(new Option(c.name, c.id));   // 2nd arg = value; text content is auto-escaped by the DOM
    }
  } catch {
    sel.innerHTML = `<option value="">Couldn't load cities</option>`;
  } finally {
    sel.disabled = false;
    sel.removeAttribute("aria-busy");
  }
}
```

Bind to **`change`****\*\*\*\*, not** **`click`** **or** **`input`** — `change` is the one event that fires identically for mouse, keyboard, and the native mobile picker. Dependent/cascading selects (country → city) are the most common vanilla case, and the native element handles all the accessibility while you just swap options.

### 9.15 Testing the Select (unit + a11y)
A select is behavior, so test what the user does: open it, arrow to an option, commit it, and confirm the value + accessibility state — not class names.

```typescript
import { render, screen, within } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { axe } from "jest-axe";
import { describe, it, expect, vi } from "vitest";
import { Select } from "./Select";

const OPTS = [
  { value: "us", label: "United States" },
  { value: "ca", label: "Canada" },
  { value: "mx", label: "Mexico", disabled: true },
];

describe("Select", () => {
  it("exposes the listbox role and options when open", async () => {
    render(<Select label="Country" options={OPTS} value={null} onChange={() => {}} />);
    await userEvent.click(screen.getByRole("button", { name: /country/i }));
    expect(screen.getByRole("listbox")).toBeInTheDocument();
    expect(screen.getAllByRole("option")).toHaveLength(3);
  });

  it("is keyboard operable: arrow to an option and commit with Enter", async () => {
    const onChange = vi.fn();
    render(<Select label="Country" options={OPTS} value={null} onChange={onChange} />);
    const trigger = screen.getByRole("button", { name: /country/i });
    await userEvent.type(trigger, "{ArrowDown}");   // opens + highlights first
    await userEvent.keyboard("{ArrowDown}{Enter}"); // move to Canada, commit
    expect(onChange).toHaveBeenCalledWith("ca");
  });

  it("skips disabled options when arrowing", async () => {
    const onChange = vi.fn();
    render(<Select label="Country" options={OPTS} value="ca" onChange={onChange} />);
    await userEvent.click(screen.getByRole("button"));
    // Mexico is disabled; End should land on Canada (last enabled), Enter commits it
    await userEvent.keyboard("{End}{Enter}");
    expect(onChange).toHaveBeenCalledWith("ca");
  });

  it("closes on Escape and returns focus to the trigger", async () => {
    render(<Select label="Country" options={OPTS} value={null} onChange={() => {}} />);
    const trigger = screen.getByRole("button");
    await userEvent.click(trigger);
    await userEvent.keyboard("{Escape}");
    expect(screen.queryByRole("listbox")).not.toBeInTheDocument();
    expect(trigger).toHaveFocus();                  // focus MUST return
  });

  it("has no axe violations when open", async () => {
    const { container } = render(<Select label="Country" options={OPTS} value="us" onChange={() => {}} />);
    await userEvent.click(screen.getByRole("button"));
    expect(await axe(container)).toHaveNoViolations();
  });
});
```

What to assert (and skip):
*   **Do test:** the listbox/option roles exist, arrow keys move and skip disabled options, Enter/click commits the right value, Escape closes and returns focus, and `axe` finds no violations. These prove the accessibility contract.
*   **Don't test:** exact class names, the chevron SVG path, pixel positions. Implementation details that break tests without catching real bugs.
*   **E2E (Playwright):** test the collision-aware positioning and mobile native picker in a real browser — `page.getByRole("combobox")` for native `<select>`, or `selectOption()` which drives the OS control.

## 10\. Accessibility (non-negotiable, and the reason native usually wins)
This is where the native-vs-custom decision gets settled. **A native** **`<select>`** **is accessible by default.** A custom listbox is accessible only if you build every one of these correctly:

**Roles & structure**
*   Native: `<select>` + `<option>` + `<optgroup>`. Nothing to add.
*   Custom single-select: a trigger with `aria-haspopup="listbox"` and `aria-expanded`, opening a `role="listbox"` containing `role="option"` rows. Groups use `role="group"` with an `aria-label`.
*   Custom multi-select: add `aria-multiselectable="true"` to the listbox.
*   **Combobox (the adjacent pattern):** `role="combobox"` on the textbox, `aria-controls` pointing at the listbox, `aria-expanded`, `aria-autocomplete`. Different role, because there's a text input. Don't use combobox semantics for a plain select or vice-versa.

**The keyboard map (custom must reimplement all of it)**

| Key | Closed trigger | Open listbox |
| ---| ---| --- |
| Enter / Space | Open the list | Commit highlighted option (single) / toggle it (multi) |
| ArrowDown | Open, highlight selected/first | Move highlight down (skip disabled) |
| ArrowUp | Open, highlight selected/last | Move highlight up (skip disabled) |
| Home | — | Highlight first enabled option |
| End | — | Highlight last enabled option |
| Typeahead (letters) | (native: select next match without opening) | Jump to first option starting with buffered string |
| Escape | — | Close, keep current value, return focus to trigger |
| Tab | Move to next field | Close list, let focus move on (don't trap) |
| PageUp/PageDown | — | Move highlight by ~10 (long lists, optional) |

**Focus management**
*   On **open:** move focus into the listbox (or keep it on the trigger and use `aria-activedescendant` virtual focus — both are valid; pick one and be consistent), and highlight the current selection.
*   On **close:** **focus returns to the trigger** for Escape/select/click-away. On Tab, close without hijacking focus. Losing focus to `<body>` on close is the most common custom-select a11y bug.
*   **`aria-activedescendant`** points the listbox at the highlighted option's `id` so screen readers announce the highlight without real focus leaving the container.

**Labels & state**
*   **Always a real, persistent label** (`<label for>` or `aria-labelledby`) — never placeholder-only. Placeholder text vanishes on selection and isn't reliably announced.
*   `aria-selected="true"` on chosen options; `aria-disabled="true"` on unchoosable ones (and skip them with the keyboard).
*   `aria-invalid="true"` + `aria-describedby` wiring the error message when validation fails.
*   `aria-busy="true"` while async options load.

**Contrast & target**
*   Option text ≥ 4.5:1; the highlighted row's background must keep the text readable. Don't signal selection by color alone — pair it with a checkmark.
*   Option rows and the trigger keep a ≥44px touch target.

**The honest summary:** everything above is _free_ with `<select>` and _your job_ with a custom listbox. That's the accessibility cost of going custom, and it's the single strongest reason §1 says "native until forced off."

## 11\. Innovative & Emerging Ideas
The select is finally getting the platform love it needed:

*   **Customizable** **`<select>`** **(\*\*\*\*****`appearance: base-select`** **+** **`::picker(select)`****\*\*\*\*):** the big one. The 2024+ CSS proposal — an evolution of the earlier `<selectmenu>` experiment — lets you fully style the option list of a _native_ `<select>`, including arbitrary markup inside options, while keeping the element's built-in accessibility, form participation, and mobile picker. Opt in with `appearance: base-select`; style the popup via `::picker(select)` and `option::checkmark` / `::picker-icon`. Shipping in Chromium first, behind `@supports` elsewhere. **This is the endgame that could retire most custom listboxes** — you'd get the styling freedom of §9.3 with the free accessibility of §9.1. Watch it closely.
*   **CSS Anchor Positioning:** `anchor()` and `position-area` let a popup tether to its trigger and flip on collision _in pure CSS_, no JS positioning library. This is the standards-based replacement for Popper/Floating UI (§12).
*   **Popover API +** **`<select>`****\*\*\*\*-adjacent patterns:** the `popover` attribute and top-layer rendering mean custom dropdowns can escape `overflow: hidden` clipping without portals — the popup renders in the browser's top layer natively.
*   **Command-menu / ⌘K palette:** the power-user "select anything" pattern — a combobox that searches across all app entities. Blurs select, combobox, and navigation into one keyboard-driven surface.
*   **AI-assisted selection:** "smart defaults" that pre-select the most likely option from context, and natural-language filters ("show me plans under $100") layered onto a combobox.
*   **Virtualized + async as default:** long lists that fetch and render on demand are becoming the baseline expectation for enterprise selects, not a special case.

## 12\. Positioning, Anchoring & Collision Handling
A custom popup that opens _downward_ near the bottom of the viewport, gets clipped, and can't be scrolled to is a broken select. Anchoring is a real engineering problem the native element solves for you and you inherit when you go custom.

**The core requirements**
*   **Anchor to the trigger:** the popup's top edge aligns to the trigger's bottom edge (usually), matched or exceeding its width.
*   **Flip on collision:** if there isn't room below, open _upward_. If there isn't room right, shift left. Never let the popup render off-screen.
*   **Shift/clamp:** keep the popup within the viewport with a small margin; clamp its height and scroll internally rather than overflowing.
*   **Escape clipping:** if the select lives inside a container with `overflow: hidden` or a `transform`, the popup gets clipped. Solve by **portaling** the popup to `<body>` / a top-layer, or using the Popover API's top layer.
*   **Reposition on scroll/resize:** the popup must track the trigger if the page scrolls while open (or close on scroll — a valid, simpler choice).

**Two implementation paths:**

```typescript
// A) JS positioning library (today's default) — Floating UI
import { computePosition, flip, shift, offset, size } from "@floating-ui/dom";

async function place(trigger: HTMLElement, popup: HTMLElement) {
  const { x, y } = await computePosition(trigger, popup, {
    placement: "bottom-start",
    middleware: [
      offset(4),
      flip(),                              // open upward if no room below
      shift({ padding: 8 }),               // nudge to stay on-screen
      size({                               // cap height to available space, match width
        apply({ availableHeight, rects, elements }) {
          Object.assign(elements.floating.style, {
            maxHeight: `${availableHeight - 8}px`,
            minWidth: `${rects.reference.width}px`,
          });
        },
      }),
    ],
  });
  Object.assign(popup.style, { left: `${x}px`, top: `${y}px` });
}
```

```css
/* B) CSS Anchor Positioning (the emerging, JS-free path) */
.select-trigger { anchor-name: --sel; }
.select-listbox {
  position: absolute;
  position-anchor: --sel;
  position-area: block-end;            /* below the trigger */
  position-try-fallbacks: block-start; /* flip above on collision */
  max-height: 40vh;
  overflow: auto;
}
```

Radix, Headless UI, and MUI all use Floating UI (path A) under the hood, which is why `position="popper"` in §9.6 "just works." Path B is the future — once anchor positioning is broadly supported, the JS library disappears.

## 13\. Virtualization for Long Lists
A country list is 195 rows — fine. A user picker, a SKU list, or a timezone select can be 10,000+ rows, and rendering 10,000 `<li>` nodes janks the open animation and burns memory. **Virtualization** renders only the ~15 rows in view plus a small buffer, and translates the scroll.

```typescript
import { useVirtualizer } from "@tanstack/react-virtual";

function VirtualListbox({ options, activeIndex }: { options: SelectOption[]; activeIndex: number }) {
  const parentRef = useRef<HTMLUListElement>(null);
  const rowVirtualizer = useVirtualizer({
    count: options.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 36,          // row height
    overscan: 8,
  });

  return (
    <ul ref={parentRef} role="listbox" style={{ height: 320, overflow: "auto" }}>
      <div role="presentation" style={{ height: rowVirtualizer.getTotalSize(), position: "relative" }}>
        {rowVirtualizer.getVirtualItems().map((v) => {
          const opt = options[v.index];
          return (
            <li
              key={opt.value}
              role="option"
              aria-selected={v.index === activeIndex}
              aria-setsize={options.length}      // tell AT the REAL total, not the rendered count
              aria-posinset={v.index + 1}         // and this row's real position
              style={{ position: "absolute", top: 0, transform: `translateY(${v.start}px)`, width: "100%", height: v.size }}
            >
              {opt.label}
            </li>
          );
        })}
      </div>
    </ul>
  );
}
```

The accessibility catch that virtualization introduces: because only ~15 of 10,000 rows exist in the DOM, a screen reader would announce "option 3 of 15" — a lie. **You must set** **`aria-setsize`** **to the true total and** **`aria-posinset`** **to each row's real index** so AT reports "3 of 10,000." Miss that and you've traded jank for a worse accessibility bug. And the sizing/spacer `<div>` between the `role="listbox"` and its `role="option"` children must carry `role="presentation"`, or you break the required listbox→option ownership (axe `aria-required-children`). Also ensure keyboard navigation (Home/End, typeahead) operates on the _full_ data array, not the rendered window, and scrolls the target row into view before it can be highlighted.

For **async + virtual** (infinite lists), fetch pages as the user scrolls near the end, show skeleton rows for not-yet-loaded ranges, and debounce combobox filter input (~250ms) so you're not firing a request per keystroke.

## 14\. Performance & Bundle Cost
*   **Native** **`<select>`** **is ~free.** No JS, no popup library, no positioning math, no virtualization. The cheapest, fastest, most robust select you can ship. This is a performance argument for native, on top of the accessibility one.
*   **A custom select is not free:** the component code, a positioning library (Floating UI ~10–15KB), optionally a virtualizer, and the runtime cost of rendering/positioning the popup. Reserve that cost for when native genuinely can't do the job.
*   **Don't mount closed popups.** Render the listbox only when open (`{open && …}`) so a page with 40 selects isn't holding 40 hidden option lists in the DOM.
*   **Virtualize past a few hundred rows** (§13); below that it's overhead you don't need.
*   **Debounce async filters** so typing doesn't fire a request per keystroke; cancel in-flight requests when a newer one supersedes them.
*   **Memoize option lists** in React so a parent re-render doesn't rebuild thousands of option objects; key rows stably.
*   **Lazy-load the heavy variant.** If only one screen needs the searchable virtualized mega-select, code-split it so the other 90% of the app doesn't pay for it.

## 15\. Conversion & Data-Quality Killers (the silent ones)
None of these throw an error. They just quietly cost you completed forms and clean data.

*   **A custom dropdown that's broken for keyboard/AT.** The most expensive one, because it's invisible to the team building it (who all use a mouse) and it locks out real users. If you went custom and didn't do §10, you shipped a regression.
*   **Placeholder-as-label.** The label vanishes the moment a value is picked, and it's not reliably announced. Users forget what the field was; AT users never knew. Always a persistent label.
*   **A giant unsearchable list.** 195 countries or 10,000 users in a plain scroll dropdown is a rage-inducer. Past ~15–20 options, add a filter — which makes it a combobox — or you're taxing every user on every submit.
*   **No default when one obviously dominates.** Forcing a US-heavy audience to scroll to "United States" every time is needless friction. Smart defaults lift completion.
*   **A default when choosing is a real decision.** The inverse: pre-selecting "Basic plan" biases the choice and captures a value the user never consciously made — bad data _and_ bad ethics.
*   **iOS zoom-on-focus.** A sub-16px control font makes Safari zoom the whole page when the select is tapped, jarring the layout. 16px minimum on mobile.
*   **Popup that covers its own trigger** or opens off-screen. Collision handling isn't polish; a select you can't see the options of is a dead end.
*   **Silent async failure.** Options fail to load, the select sits empty with no message, the user assumes there are no options and abandons. Always show a loading state and an error-with-retry.
*   **Multi-select with no visible summary.** If the trigger doesn't show what's chosen (count or chips), users lose track and re-open repeatedly to check.

**The through-line:** selects fail quietly — a slightly lower form-completion rate, a slightly dirtier `state` column — and it's easy to blame the user or "the funnel." Audit your selects before you audit your copy.

## 16\. Security

A `<select>` is a client-side convenience, not a security boundary — it constrains what the _UI_ offers and nothing more. The server MUST re-validate every submitted value against the authoritative allow-list (`enum`, a DB lookup, or a policy check) on the way in, because a client can bypass the widget entirely and POST any string it likes straight to the endpoint. Trusting the field verbatim is a classic mass-assignment / privilege-escalation hole: an option you never rendered — a `role=admin`, another tenant's `account_id`, a `status` this user can't legitimately set — sails right through if the handler binds it blindly. When the options are populated from a remote endpoint, authorize _that_ endpoint too and scope it to the caller; otherwise the dropdown quietly leaks ids and names (users, projects, customers) the requester should never be able to enumerate. Multi-select posts an **array**, so validate _every_ element against the allow-list and cap the count — one poisoned entry, or a 10,000-item payload, is still an attack. And never lean on a `disabled` or hidden `<option>` as access control: it's an attribute the client fully owns and can strip in one line of DevTools. The dropdown is UX; the allow-list check and the authorization decision live on the server, on every request.

## 17\. Senior-Level Checklist (ship-ready)
Before a select is "done":
- [ ] **Native** **`<select>`** **unless a hard requirement forces a custom listbox** — and that decision is documented.
- [ ] Real, persistent `<label>` (or `aria-labelledby`) — never placeholder-only.
- [ ] Placeholder is a disabled, empty-value option; `required` catches "nothing chosen."
- [ ] All states styled: rest, hover, focus-visible, open, filled/empty, disabled, invalid, loading.
- [ ] (Custom) `role="listbox"` + `role="option"`, `aria-expanded`, `aria-haspopup`, `aria-selected`, `aria-activedescendant`.
- [ ] (Custom) Full keyboard map: Up/Down/Home/End/typeahead/Enter/Space/Escape/Tab — disabled options skipped.
- [ ] (Custom) Focus returns to the trigger on close; Tab doesn't trap; open highlights the current selection.
- [ ] Popup anchors to the trigger, flips on collision, clamps height + scrolls, escapes `overflow` clipping.
- [ ] Long lists (>few hundred) virtualized with correct `aria-setsize` / `aria-posinset`.
- [ ] Async options have loading, empty, and error-with-retry states; filters debounced.
- [ ] Multi-select summarizes selection (count/chips); Space toggles, list stays open.
- [ ] Server validates the value against an allow-list (`enum`/DB) and authorizes it — disabled/hidden options are UX, not security.
- [ ] Mobile: control font ≥16px; touch targets ≥44px; native picker respected where possible.
- [ ] Option text contrast ≥4.5:1; selection not signaled by color alone.

## 18\. Visual Styles (the same select, eleven skins)
Style is skin; behavior is skeleton. Across all eleven, the roles, keyboard map, focus return, and 44px targets are **identical** — only the paint changes. See them all in the 🎨 [Design Styles](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200551) doc.

*   **Flat:** solid trigger, 1px border, crisp chevron, plain popup with a flat highlight bar on the active row. Reads instantly, scales fastest.
*   **Material:** the "exposed dropdown" — filled/outlined field with a floating label that shrinks up on selection, a menu that elevates with a shadow and a subtle open animation, ripple on the trigger. Selected option gets a leading check.
*   **Glassmorphism:** translucent popup with `backdrop-filter: blur()` over a vivid backdrop. Watch option-text contrast hard — glass over a busy background is where selects become unreadable. Guard it.
*   **Liquid Glass (the 2026 trend):** Apple's iOS 26 / macOS Tahoe material — the popup is a refractive translucent sheet with a specular rim and a sheen that shifts with scroll, not a static blur. Pill-ish trigger, options lift on highlight. On the web it's an honest approximation (layered highlights + `backdrop-filter`); SwiftUI's `Picker` gets it natively via `.glassEffect()`. Guard for contrast and `prefers-reduced-motion` (kill the moving sheen).
*   **Neumorphism:** trigger is an extruded same-color pill with dual light/dark shadows; the popup looks pressed-in. Pretty, contrast-poor — accent use only, and never for the option text itself.
*   **Skeuomorphism:** beveled trigger with an inner highlight and gradient fill, a chevron that looks like a physical button, a popup styled like a real menu with divider grooves. The tactile "physical picker" look.
*   **Neo-Brutalism:** thick black border, hard offset drop-shadow on the popup, zero radius, a clashing highlight color on the active row. Loud, high-personality — campaign moments, not checkout.
*   **Claymorphism:** big-radius puffy trigger, soft inner top-light + bottom-shadow, a popup that looks moulded. Friendly, playful; keep the active-row contrast honest.
*   **Aurora / Gradient:** animated multi-hue gradient border or highlight on a dark popup. Premium feel — honor `prefers-reduced-motion` and don't let the gradient wash out option text.
*   **Minimal / Swiss:** near-zero chrome — a thin underline trigger, generous type, a hairline-separated popup. Typography and spacing do all the work. Excellent for dense/data selects.
*   **UJG Brand:** Goldenrod chevron and active-row highlight over deep Eminence/Night surfaces, confident 8–12px radius, a warm glow on `:focus-visible`, selected option marked with a Goldenrod check. The dark saturated field makes a Liquid-Glass popup sing — lean into that for hero moments, and drop to Flat/Swiss for data-dense filter bars. Every interactive row keeps its ≥44px target and Goldenrod focus ring.

**Rule that never changes:** the style is skin. Swap all eleven and a keyboard user, a screen-reader user, and a thumb on a phone must have the exact same experience. Guard glass / liquid-glass / neumorphism for contrast; guard aurora / liquid-glass for `prefers-reduced-motion`.
