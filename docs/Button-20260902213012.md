## 1\. What a Button Actually Is
A button is a control that triggers an action when activated. That's it. But the word hides three very different things people lump together:
*   **Button (action):** does something _now_ on the current page/app. Submit form, open modal, add to cart, play video.
*   **Link (navigation):** takes you _somewhere else_ (a URL). Styled like a button, but semantically an anchor.
*   **Toggle (state):** flips a persistent state on/off. Mute, follow, dark mode.

The single most common mistake in UI engineering: using the wrong one of these three. A "button" that navigates should be an `<a>`. A `<div onClick>` that acts like a button is an accessibility bug. Rule of thumb: **if it goes to a URL, it's a link; if it does an action, it's a button; never fake either with a div.**
* * *

## 2\. Why It's So Important
The button is the primary unit of _agency_ in an interface. Everything users accomplish, they accomplish by activating a control. That means the button carries disproportionate weight:
*   **Conversion lives here.** The gap between "Buy" and "Get started free" is measured in real revenue. Button copy, color, and placement are among the most A/B-tested elements on the planet.
*   **It's the accessibility frontier.** Keyboard users, screen readers, switch devices, voice control: they all interact with your app _through buttons_. Get the button right and huge swaths of accessibility come free.
*   **It sets the trust tone.** A button that gives no feedback (no hover, no loading, no disabled state) makes an app feel broken even when it works. Perceived responsiveness is mostly button feedback.
* * *

## 3\. Anatomy of a Button
Every well-built button is composed of predictable parts:
*   **Container:** the clickable box. Has padding, border-radius, background, border.
*   **Label:** the text. Verb-first, action-oriented ("Save changes," not "OK").
*   **Icon (optional):** leading (before text, reinforces meaning) or trailing (after text, implies direction/expansion).
*   **Hit target:** the actual tappable area. Minimum **44x44px** (Apple) / **48x48dp** (Material). Can be larger than the visible container via padding.
*   **Focus ring:** the outline shown on keyboard focus. Never remove it without replacing it.
*   **Loading/state indicator:** spinner, checkmark, progress.
* * *

## 4\. Sizes
Size communicates hierarchy and fits context. A typical scale:

| Size | Height | Padding (H) | Font | Use |
| ---| ---| ---| ---| --- |
| XS | 24px | 8px | 12px | Dense tables, tags, inline actions |
| SM | 32px | 12px | 13px | Toolbars, compact forms |
| MD | 40px | 16px | 14px | Default for most UI |
| LG | 48px | 24px | 16px | Primary CTAs, mobile-first |
| XL | 56px+ | 32px | 18px | Hero sections, landing pages |

Rules that matter:
*   **Touch targets stay ≥44px even when the visual is smaller** (expand hit area with padding/pseudo-elements).
*   Height should be driven by a spacing token, not a magic number, so the whole system scales.
*   **Full-width buttons** on mobile reduce mis-taps and read as more confident.
* * *

## 5\. States (the part juniors forget)
A production button has _at least_ eight states. Missing states are the #1 tell of an amateur build.
1. **Default (rest)** — the baseline.
2. **Hover** — pointer over it. Subtle bg/elevation shift. (Doesn't exist on touch, so never rely on it alone.)
3. **Focus** — reachable by keyboard. Must have a visible ring. Use `:focus-visible` so mouse clicks don't show it but Tab does.
4. **Active (pressed)** — the moment of click/tap. Slight scale-down or darken. Sells tactility.
5. **Loading** — async action in flight. Show spinner, keep width stable, block re-clicks.
6. **Disabled** — not currently allowed. Reduced opacity, `cursor: not-allowed`, `aria-disabled`. Explain _why_ nearby if possible.
7. **Success / done** — transient confirmation (checkmark, "Saved!").
8. **Error / destructive-confirm** — failed action or a "click again to confirm delete."

Bonus: **selected/toggled** for toggle buttons (`aria-pressed`).
* * *

## 6\. Types & Variants (by emphasis)
Visual weight = priority. A screen should have **one** primary button in a given context. More than one and you've told the user nothing is important.
*   **Primary (filled/solid):** the main action. High contrast, brand color. One per view.
*   **Secondary (outline/tonal):** supporting action. Border or muted fill.
*   **Tertiary / Ghost / Text:** low emphasis. Text-only, no background. "Cancel," "Learn more."
*   **Destructive:** red/danger variant for delete, remove, cancel-subscription. Often gated behind confirm.
*   **Icon button:** icon only, no label. _Must_ have an `aria-label`. Great for toolbars.
*   **FAB (Floating Action Button):** the round elevated button, Material's signature. Primary action of a whole screen.
*   **Split button:** a main action + a dropdown caret for related variants ("Save" | "▾ Save as...").
*   **Toggle button / segmented control:** persistent on/off or one-of-many selection.
*   **Link button:** looks like a button, semantically an `<a>`.
* * *

## 7\. When to Use One (and When Not To)
Use a button when the user needs to **commit an action** or **navigate deliberately**. Don't use one when:
*   The action should happen automatically (autosave beats a Save button in many flows).
*   You're offering more than ~5 equal choices (use a list, radio group, or menu).
*   It's actually navigation between many items (that's a nav/link pattern).
*   You'd have three primary buttons competing (collapse into one primary + menu).

Placement heuristics:
*   **Primary action goes where the eye ends:** bottom-right of forms/dialogs (Western reading), or bottom of a mobile screen in thumb reach.
*   **Destructive actions get distance** from primary ones to prevent misclicks.
*   **Keep the primary visible** (sticky footer on long forms) so users never scroll to find "Continue."
* * *

## 8\. Buttons Across Design Systems
Same component, very different philosophies. Knowing these makes you fluent in any codebase.
*   **Material Design (Google):** Elevation-driven. Filled, tonal, outlined, elevated, text. Ripple effect on press. FAB is core. Rounded corners, bold color.
*   **Apple HIG (iOS/macOS):** Restrained. Often text-only buttons (no borders) in nav bars. Bordered/filled reserved for prominence. SF Symbols for icons. Heavy use of tint color.
*   **Fluent (Microsoft):** Subtle depth, acrylic/mica materials, compact. Primary in accent color, lots of neutral secondary.
*   **Ant Design / enterprise:** Dense, many variants, ghost buttons for dark backgrounds, explicit `danger` prop. Built for data-heavy admin UIs.
*   **Tailwind / utility-first (modern web):** No prescribed look; composed from utility classes. Freedom + consistency risk. Usually wrapped in a `Button` component to enforce a system.
*   **Shadcn/Radix (2024+ web standard):** Headless behavior (Radix) + styled variants (cva/Tailwind). Accessibility baked in, appearance fully yours.
*   **Brand/expressive (landing pages):** Gradients, glow, micro-animations, oversized. Rules relax for hero CTAs, but accessibility still applies.
* * *

## 8b. Visual Styles (the same button, ten aesthetics)
Design systems are _whose_ rules; visual styles are _which look_. The same semantic button can wear any of these skins. Pick per project, client, and era. See them all live in the
undefined/8495850/f88d0e4d-698c-4439-afa7-eb303816cd23/design-styles-gallery.html
, and cross any variant, style, and language in the
undefined/8495850/97e3599a-25f8-43fb-ae57-dab8a7b7172e/button-playground.html
: every style skins every variant, from one shared token set.
*   **Flat:** solid fill, crisp edges, no shadow. Scales fast, reads instantly.
*   **Material:** layered elevation shadows, ripple on press, uppercase label.
*   **Glassmorphism:** translucent + `backdrop-filter: blur()` over a vivid background. Rare, and watch contrast.
*   **Liquid Glass (the 2026 trend):** Apple's iOS 26 / macOS Tahoe language, glassmorphism's successor. Translucent material that _refracts_ what's behind it with a specular highlight rim and a moving sheen, not just a static blur. Pill-shaped, dynamic, reactive to motion and content. See the 2026 note below.
*   **Neumorphism:** dual light/dark shadows on a same-color surface. Pretty, contrast-poor, accent only.
*   **Skeuomorphism:** bevels, inner highlights, gradient fill. The tactile "real object" look.
*   **Neo-Brutalism:** hard offset shadow, thick border, zero radius, clashing color. High personality.
*   **Claymorphism:** big radius, inner top-light + bottom-shadow, soft glow. Puffy and friendly.
*   **Aurora / Gradient:** animated multi-hue gradient on dark. Premium, honor `prefers-reduced-motion`.
*   **Minimal / Swiss:** typography and grid do the work, near-zero decoration, sharp corners.
*   **UJG Brand:** Goldenrod on deep Eminence, confident radius, warm glow. The house default.

**Rule that never changes:** the style is skin. The button's semantics, keyboard behavior, focus ring, and 44px target stay identical across all eleven. Full guidance on the 🎨 Design Styles (visual languages) ([https://app.clickup.com/8495850/docs/838qa-81211/838qa-200551](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200551)).

### What's trending in 2026
The dominant force this year is **Liquid Glass**: Apple shipped it across iOS 26, iPadOS, and macOS Tahoe in late 2025, and the web is racing to approximate it with `backdrop-filter`, layered highlights, and the emerging CSS `background-filter`/refraction proposals. It's glassmorphism grown up: real depth, light that bends, surfaces that respond to motion and to the content behind them.

Around it, the 2026 palette of trends:
*   **Liquid Glass everywhere** on Apple platforms; a lighter, performance-aware "frosted-lite" on the web.
*   **Spatial & depth-aware UI** carrying over from visionOS: parallax, soft 3D layering, content that reacts to device motion.
*   **Expressive Material 3** (Google's "Material Expressive"): bolder shape morphing, springier motion, larger emotional range.
*   **AI-native surfaces:** generative/streaming states, "do it for me" agentic buttons, and inline AI affordances as first-class UI, not bolt-ons.
*   **Motion-forward but restrained:** micro-interactions and morphing transitions with `prefers-reduced-motion` respected by default.
*   **Retro-tactile counter-current:** skeuomorphism and heavy texture returning as a rebellion against a decade of flat.

**For UJG:** lean your house style toward Liquid Glass accents over deep Eminence surfaces (the dark, saturated backdrop makes the refraction sing), keep Flat/Swiss for dense/data work, and reserve Brutalism/Aurora for campaign moments. The accessibility caveats hold: contrast and reduced-motion are non-negotiable no matter how on-trend the skin.

## 9\. The Code
### 9.1 HTML (the foundation everyone should master first)

```plain
<!-- Action: use a real button -->
<button type="button" class="btn btn--primary">
  Save changes
</button>

<!-- Submit inside a form -->
<form>
  <button type="submit">Create account</button>
</form>

<!-- Navigation: it's a link, styled as a button -->
<a href="/pricing" class="btn btn--secondary" role="button">
  See pricing
</a>

<!-- Icon-only: label is mandatory -->
<button type="button" aria-label="Delete item" class="btn-icon">
  <svg aria-hidden="true"></svg>
</button>

<!-- Toggle: state is announced -->
<button type="button" aria-pressed="false">Follow</button>

<!-- Disabled + loading -->
<button type="button" disabled aria-busy="true">
  <span class="spinner" aria-hidden="true"></span>
  Saving…
</button>
```

Key HTML rules:
*   **Always set** **`type`****.** A `<button>` inside a form defaults to `type="submit"` and will silently submit/reload. Explicitly set `type="button"` for non-submit actions.
*   `disabled` removes it from the tab order and blocks events. If you need it focusable-but-inert, use `aria-disabled="true"` and handle clicks in JS.
*   Icons that are decorative get `aria-hidden="true"`.

### 9.3 React + TypeScript (a proper reusable component)

```typescript
import { forwardRef, ButtonHTMLAttributes } from "react";

type Variant = "primary" | "secondary" | "ghost" | "destructive";
type Size = "sm" | "md" | "lg";

interface ButtonProps extends ButtonHTMLAttributes<HTMLButtonElement> {
  variant?: Variant;
  size?: Size;
  loading?: boolean;
  leadingIcon?: React.ReactNode;
}

export const Button = forwardRef<HTMLButtonElement, ButtonProps>(
  (
    {
      variant = "primary",
      size = "md",
      loading = false,
      leadingIcon,
      disabled,
      children,
      className = "",
      ...rest
    },
    ref
  ) => {
    const isDisabled = disabled || loading;
    return (
      <button
        ref={ref}
        type="button"
        disabled={isDisabled}
        aria-busy={loading}
        className={`btn btn--${variant} btn--${size} ${className}`}
        {...rest}
      >
        {loading && <span className="spinner" aria-hidden="true" />}
        {!loading && leadingIcon}
        <span>{children}</span>
      </button>
    );
  }
);
Button.displayName = "Button";
```

Why this is the senior version, not the junior one:
*   **`forwardRef`** so parents (menus, tooltips, forms) can reference the DOM node.
*   **Extends native** **`ButtonHTMLAttributes`** so `onClick`, `type`, `aria-*`, `data-*` all pass through for free. No reinventing props.
*   **`loading`** **implies** **`disabled`** so users can't double-submit.
*   **Typed** **`variant`****/****`size`** **unions** catch typos at compile time.

Usage with an async action (the real-world pattern):

```plain
function SaveButton() {
  const [saving, setSaving] = useState(false);

  async function handleSave() {
    setSaving(true);
    try {
      await api.saveProfile();     // network call
      toast.success("Saved");
    } catch (e) {
      toast.error("Couldn't save");
    } finally {
      setSaving(false);            // always reset
    }
  }

  return (
    <Button loading={saving} onClick={handleSave}>
      Save profile
    </Button>
  );
}
```

### 9.4 The Backend Side (yes, the button reaches the server)
The visible button is the tip. Clicking "Delete account" fires a chain that must be engineered defensively:

**1\. The request the button triggers**

```plain
// Frontend
await fetch("/api/orders", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "Idempotency-Key": crypto.randomUUID(), // critical, see below
  },
  body: JSON.stringify(order),
});
```

**2\. The endpoint that receives it (Node/Express-style)**

```plain
app.post("/api/orders", requireAuth, async (req, res) => {
  const key = req.header("Idempotency-Key");

  // Idempotency: a double-clicked button must NOT create two orders
  const existing = await db.findByIdempotencyKey(key);
  if (existing) return res.status(200).json(existing);

  // Authorization: is this user allowed to do this action?
  if (!can(req.user, "create", "order")) return res.sendStatus(403);

  // Validation: never trust the client
  const parsed = OrderSchema.safeParse(req.body);
  if (!parsed.success) return res.status(422).json(parsed.error);

  const order = await db.createOrder({ ...parsed.data, key });
  res.status(201).json(order);
});
```

Backend concerns every button silently depends on:
*   **Idempotency:** the classic "user clicked Pay twice, got charged twice" bug. Solved with an idempotency key so the second identical request returns the first result instead of re-running. This is _why_ the frontend also disables the button while loading: defense in depth.
*   **Authorization:** the UI hiding a button is UX, not security. The server must re-check permissions. Never assume "the button wasn't shown" means "the action can't happen."
*   **Validation:** the client's disabled/enabled logic is a hint; the server validates for real.
*   **Rate limiting / CSRF:** action buttons are attack surfaces. Protect state-changing endpoints.
*   **Optimistic UI:** advanced pattern where the button updates the UI instantly and rolls back if the server rejects. Feels instant, needs careful error handling.

### 9.5 Vanilla JavaScript (no framework)
The building block everything else abstracts. Worth knowing cold.

```javascript
const btn = document.querySelector("#save");

btn.addEventListener("click", async () => {
  if (btn.disabled) return;          // guard double-clicks
  const original = btn.textContent;

  btn.disabled = true;
  btn.setAttribute("aria-busy", "true");
  btn.textContent = "Saving…";

  try {
    const res = await fetch("/api/save", { method: "POST" });
    if (!res.ok) throw new Error(res.statusText);
    btn.textContent = "Saved ✓";
  } catch (err) {
    btn.textContent = "Try again";
    console.error(err);
  } finally {
    btn.disabled = false;
    btn.removeAttribute("aria-busy");
    setTimeout(() => (btn.textContent = original), 1500);
  }
});
```

### 9.7 shadcn/ui (the 2024+ standard)
Not a dependency you install: you copy the component into your repo and own it. Radix handles behavior/accessibility, cva handles variants, Tailwind handles looks.

```typescript
import * as React from "react";
import { Slot } from "@radix-ui/react-slot";
import { cva, type VariantProps } from "class-variance-authority";
import { cn } from "@/lib/utils";

const buttonVariants = cva(
  "inline-flex items-center justify-center gap-2 whitespace-nowrap " +
    "rounded-md text-sm font-medium transition-colors " +
    "focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-ring " +
    "disabled:pointer-events-none disabled:opacity-50",
  {
    variants: {
      variant: {
        default: "bg-primary text-primary-foreground hover:bg-primary/90",
        destructive:
          "bg-destructive text-destructive-foreground hover:bg-destructive/90",
        outline:
          "border border-input bg-background hover:bg-accent hover:text-accent-foreground",
        ghost: "hover:bg-accent hover:text-accent-foreground",
        link: "text-primary underline-offset-4 hover:underline",
      },
      size: {
        sm: "h-8 px-3",
        default: "h-10 px-4 py-2",
        lg: "h-11 px-8",
        icon: "h-10 w-10",
      },
    },
    defaultVariants: { variant: "default", size: "default" },
  }
);

export interface ButtonProps
  extends React.ButtonHTMLAttributes<HTMLButtonElement>,
    VariantProps<typeof buttonVariants> {
  asChild?: boolean;
}

const Button = React.forwardRef<HTMLButtonElement, ButtonProps>(
  ({ className, variant, size, asChild = false, ...props }, ref) => {
    // asChild lets a <Link> or <a> BECOME the button, keeping styles + a11y
    const Comp = asChild ? Slot : "button";
    return (
      <Comp
        ref={ref}
        className={cn(buttonVariants({ variant, size, className }))}
        {...props}
      />
    );
  }
);
Button.displayName = "Button";

export { Button, buttonVariants };
```

Usage: `<Button variant="destructive" size="lg">Delete</Button>`. The `asChild` trick is the clever part: it merges button styling onto a child element (like a Next.js `<Link>`) so a navigation link gets button looks _and_ correct semantics.
### 9.8 Next.js (App Router: client vs. server)
Next forces a distinction that trips people up: an interactive button (onClick) must be a **Client Component**, but the _action_ it fires can run on the **server** via Server Actions, no API route needed.

```typescript
// app/components/DeleteButton.tsx
"use client";                         // required: it has an onClick / state
import { useTransition } from "react";
import { deletePost } from "@/app/actions";

export function DeleteButton({ id }: { id: string }) {
  const [pending, startTransition] = useTransition();
  return (
    <button
      type="button"
      disabled={pending}
      onClick={() => startTransition(() => deletePost(id))}
    >
      {pending ? "Deleting…" : "Delete"}
    </button>
  );
}
// app/actions.ts
"use server";                         // runs on the server only
import { revalidatePath } from "next/cache";

export async function deletePost(id: string) {
  await db.post.delete({ where: { id } });
  revalidatePath("/posts");           // refresh the UI after
}
```

Progressive enhancement version (works even before JS loads) uses a `<form action={serverAction}>` with a submit button and the `useFormStatus` hook for pending state.
### 9.9 Node.js (the endpoint behind the button)
The full handler the button ultimately hits. Express-style, but the shape is universal.

```typescript
import express from "express";
import { z } from "zod";

const router = express.Router();
const CreateOrder = z.object({ sku: z.string(), qty: z.number().int().positive() });
const seenKeys = new Map<string, unknown>();  // real apps: Redis/DB

router.post("/api/orders", requireAuth, rateLimit, async (req, res) => {
  const key = req.header("Idempotency-Key");
  if (key && seenKeys.has(key)) return res.status(200).json(seenKeys.get(key));

  const parsed = CreateOrder.safeParse(req.body);   // never trust client
  if (!parsed.success) return res.status(422).json(parsed.error.issues);

  if (!req.user.can("create", "order")) return res.sendStatus(403);

  const order = await db.orders.create({ ...parsed.data, userId: req.user.id });
  if (key) seenKeys.set(key, order);
  return res.status(201).json(order);
});

export default router;
```

### 9.10 Python (backend + a rendered button)
**Backend** (FastAPI) receiving the click's request:

```python
from fastapi import FastAPI, Header, HTTPException, Depends
from pydantic import BaseModel, PositiveInt

app = FastAPI()
_seen: dict[str, dict] = {}   # real apps: Redis/DB

class CreateOrder(BaseModel):
    sku: str
    qty: PositiveInt          # validation for free, mirrors the client

@app.post("/api/orders", status_code=201)
def create_order(
    body: CreateOrder,
    user=Depends(require_auth),
    idempotency_key: str | None = Header(default=None),
):
    if idempotency_key and idempotency_key in _seen:
        return _seen[idempotency_key]           # dedupe double-clicks
    if not user.can("create", "order"):
        raise HTTPException(403, "Not allowed")
    order = db.create_order(sku=body.sku, qty=body.qty, user_id=user.id)
    if idempotency_key:
        _seen[idempotency_key] = order
    return order
```

**Rendering** a button server-side (Django/Jinja template):

```plain
<button type="submit" class="btn btn--primary"
        {% if not user.can_edit %}disabled{% endif %}>
  {% if saving %}Saving…{% else %}Save changes{% endif %}
</button>
```

Python note: even in a Python stack, the button still lives in HTML/JS. Python's job is to render it and to defend the endpoint (validation, auth, idempotency) exactly like Node does.
### 9.11 Testing the Button
A button is behavior, so you test behavior, not implementation. Three layers.

**Unit / component (Vitest + React Testing Library).** Test what a user experiences: label, click fires handler, disabled/loading works, it's reachable by role.

```typescript
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { describe, it, expect, vi } from "vitest";
import { Button } from "./Button";

describe("Button", () => {
  it("renders its label and is reachable by role", () => {
    render(<Button>Save</Button>);
    expect(screen.getByRole("button", { name: /save/i })).toBeInTheDocument();
  });

  it("calls onClick when activated", async () => {
    const onClick = vi.fn();
    render(<Button onClick={onClick}>Save</Button>);
    await userEvent.click(screen.getByRole("button"));
    expect(onClick).toHaveBeenCalledTimes(1);
  });

  it("is disabled and inert while loading", async () => {
    const onClick = vi.fn();
    render(<Button loading onClick={onClick}>Save</Button>);
    const btn = screen.getByRole("button");
    expect(btn).toBeDisabled();
    expect(btn).toHaveAttribute("aria-busy", "true");
    await userEvent.click(btn);
    expect(onClick).not.toHaveBeenCalled();   // no double-submit
  });

  it("is keyboard operable", async () => {
    const onClick = vi.fn();
    render(<Button onClick={onClick}>Save</Button>);
    await userEvent.tab();                     // focus the button
    await userEvent.keyboard("{Enter}");
    expect(onClick).toHaveBeenCalled();
  });
});
```

### 9.16 The Click Lifecycle & Event Handling
The engine under the button. Rendering it is half the job; knowing exactly what fires when is the other half.

**The event order on a single tap** (mouse/touch): `pointerdown` → `mousedown` → `focus` → `pointerup` → `mouseup` → `click`. Keyboard activation (Enter/Space) skips the pointer events and fires `click` directly. **Bind to** **`click`****, not** **`mousedown`****,** unless you have a specific reason: `click` is the one event that fires for mouse, touch, _and_ keyboard. Wiring `mousedown` silently breaks keyboard and assistive-tech users.

```plain

  // fires for mouse, touch, pen, AND keyboard (Enter/Space). One handler, all inputs.
```


**Bubbling & delegation.** Click events bubble up the DOM. Instead of binding 50 list-row buttons individually, bind one handler on the container and read which button was hit. Fewer listeners, works for dynamically-added buttons:

```plain

  const btn = e.target.closest("button[data-action]");

  handle(btn.dataset.action, btn.dataset.id);
```


**`preventDefault()`** **vs** **`stopPropagation()`** (constantly confused):
*   `preventDefault()` cancels the browser's default reaction (a `submit` button submitting the form, an `<a>` navigating). Does _not_ stop bubbling.
*   `stopPropagation()` stops the event climbing to parent handlers. Does _not_ cancel the default action.
*   They're independent. A submit button you want to handle in JS often needs `preventDefault()`; a button inside a clickable card often needs `stopPropagation()` so the card's handler doesn't also fire.

**Debouncing rapid clicks (the client half of idempotency).** Server idempotency (§9.9) is the safety net; disabling on first click is the front line. For non-submit rapid-fire (search-as-you-type, resize), debounce instead:

```plain
function debounce(fn, ms = 300) {
  let t;
  return (...args) => { clearTimeout(t); t = setTimeout(() => fn(...args), ms); };
}
searchBtn.addEventListener("click", debounce(runSearch, 300));
```

**Rule of thumb:** for _actions_ (submit, pay), disable-on-click + server idempotency. For _repeatable/cheap_ triggers, debounce or throttle. Never rely on the user "only clicking once."
### 9.17 System & Environment States
Production buttons respond to the user's environment, not just your design. These are the states tutorials skip and audits catch.

**Reduced motion.** Some users get motion sickness from animation. Kill the spinner spin and press transitions for them:

```css
@media (prefers-reduced-motion: reduce) {
  .btn { transition: none; }
  .btn .spinner { animation: none; }   /* show a static state or dots instead */
}
```

**Forced colors / Windows High Contrast.** In forced-colors mode the OS overrides your palette. Your carefully-chosen backgrounds vanish, so lean on system color keywords and keep a real border so the button doesn't disappear:

```css
@media (forced-colors: active) {
  .btn { border: 1px solid ButtonText; forced-color-adjust: none; }
  .btn.primary { background: ButtonText; color: ButtonFace; }
}
```

**RTL (right-to-left) layouts.** For Arabic, Hebrew, etc., leading icons flip to the right and directional icons (arrows, chevrons) must mirror. Use logical properties so it's automatic:

```css
.btn { padding-inline: 18px; }          /* not padding-left/right */
[dir="rtl"] .btn .chevron { transform: scaleX(-1); }  /* mirror directional icons */
```

**Print.** Action buttons are meaningless on paper. Hide the ones that can't work in print:

```css
@media print { .btn:not(.print-ok) { display: none; } }
```

### 9.18 Internationalization & Microcopy
A button that fits in English can shatter in another language. German runs ~35% longer ("Save" → "Speichern unter"), and CJK scripts change line metrics entirely.
*   **Never fix the width to the English label.** Let buttons grow; test with the longest expected translation, not the shortest.
*   **Never bake text into an icon or image.** It can't be translated and screen readers can't read it. Text is always live text.
*   **Externalize every label.** `t("button.save")`, never a hardcoded string, so translators can work without touching code.
*   **Watch the loading suffix.** "Saving…" is not just "Save" + "…" in every language; some need a different verb form. Translate the whole phrase.

**Microcopy rulebook** (the copy itself moves conversion, see §14):
*   Verb-first and specific: "Create account" > "Submit", "Get my plan" > "Continue".
*   Sentence case ("Save changes"), not Title Case, in most modern UIs.
*   Keep it to 1-3 words where possible; long labels read as friction.
*   The label names the _outcome_, not the mechanic ("Delete photo", not "OK").
*   Match the loading and success states to the label: Save → Saving… → Saved.

### 9.20 Button Groups & Toolbars (roving tabindex)
Single buttons are easy. A _group_ of related buttons (toolbar, segmented control, button bar) has an accessibility pattern most people get wrong: they leave every button in the tab order, forcing keyboard users to Tab through all twelve toolbar icons to escape.

The correct pattern is **roving tabindex**: the group is one Tab stop; arrow keys move _within_ it.
*   Container gets `role="toolbar"` (or `role="group"` / `role="radiogroup"` for segmented single-select).
*   Exactly one button has `tabindex="0"`; all others have `tabindex="-1"`.
*   Arrow keys move focus and shift which button holds `tabindex="0"`.

```plain
const btns = [...toolbar.querySelectorAll("button")];
let idx = 0;
toolbar.addEventListener("keydown", (e) => {
  if (e.key !== "ArrowRight" && e.key !== "ArrowLeft") return;
  btns[idx].tabIndex = -1;
  idx = e.key === "ArrowRight"
    ? (idx + 1) % btns.length
    : (idx - 1 + btns.length) % btns.length;
  btns[idx].tabIndex = 0;
  btns[idx].focus();                      // move real focus, not just visual
```

### 9.21 Performance & Bundle Cost
A button feels free. At scale it isn't. The "why is my button slow / heavy" chapter.

**The icon-import trap.** The single most common button perf mistake: importing a whole icon library for one glyph.

```typescript
import * as Icons from "lucide-react";        // BAD: pulls the entire library
<Icons.Check />

import { Check } from "lucide-react";          // GOOD: tree-shakeable, one icon
<Check />
```

Named imports let the bundler tree-shake everything you don't use. A namespace import (`import *`) defeats it and can add hundreds of KB for a single checkmark.

**Don't thrash layout on state change.** Animating or toggling properties like `width`, `height`, `margin`, or `top` forces the browser to recalculate layout (reflow) every frame. Animate only `transform` and `opacity` (compositor-only, no reflow). This is why the loading state should keep the button's width fixed rather than resizing to fit "Saving…".

**CSS containment** tells the browser a button's internals can't affect the outside layout, so it can skip work:

```css
.btn { contain: layout style; }               /* isolate reflow/recalc to the button */
```

**Event-listener economy.** 200 buttons with 200 individual listeners is 200 closures in memory. One delegated listener on the container (see §9.16) is one. For long lists and tables, delegation is a real memory and setup-time win.

**Render cost in frameworks.** In React, wrap stable click handlers in `useCallback` and memoize pure button components so a parent re-render doesn't re-render every button in a list. Don't over-apply it: memoization has its own cost, reach for it when a button lives in a large, frequently-updating list.
### 9.22 Forms Deep-Dive
Buttons and forms are joined at the hip, and the edge cases bite.

**`type`** **decides everything inside a form.** A `<button>` with no `type` defaults to `type="submit"`. Drop an unlabeled button in a form and clicking it submits (and reloads). Always set `type="button"` for non-submit actions. (Restated because it's the #1 form bug.)

**The implicit submit.** Pressing Enter in a text input submits the form via its _first_ submit button, even if that button is visually elsewhere. If the first button is "Delete", Enter just deleted something. Order your submit buttons deliberately, or set the safe one first.

**Per-button overrides.** A submit button can override the form's `action` and `method` for its own click, which powers multi-destination forms without JavaScript:

```plain
<form action="/save" method="post">
  <button type="submit">Save draft</button>
  <button type="submit" formaction="/publish">Publish</button>   <!-- posts to /publish -->
</form>
```

Related overrides: `formmethod`, `formenctype` (e.g. `multipart/form-data` for a file-upload submit), `formnovalidate` (skip HTML5 validation for a "Save draft" button so a half-filled form can still save), and `formtarget`.

**Multi-intent submits.** Give competing submit buttons the same `name` and different `value`; the server reads which one was clicked (see §15). This is the no-JS way to branch "Save" vs "Publish".

**Submit outside the form.** A button anywhere on the page can submit a form via the `form` attribute: `<button type="submit" form="signup">Create</button>`. Useful for sticky footers whose submit lives outside the `<form>` markup.
### 9.23 Theming & Design Tokens at Scale
How the button stops being a one-off and becomes part of a system that themes, rebrands, and dark-modes without a rewrite. This is the layer that connects a generic button to a real brand.

**Token tiers.** Mature systems use three levels, so a rebrand touches one line, not a thousand:

1. **Primitive** (raw values): `--purple-800: #5F2C82`.
2. **Semantic** (roles that reference primitives): `--color-action: var(--purple-800)`.
3. **Component** (button-specific, referencing semantic): `--btn-bg-primary: var(--color-action)`.

The button only ever references component tokens. Rebrand by swapping primitives; retheme a single component by swapping its component tokens. Nothing hardcodes a hex.

```css
:root {
  /* primitive */
  --purple-800: oklch(42% 0.145 305);
  --gold-500:   oklch(78% 0.135 82);
  /* semantic */
  --color-action: var(--purple-800);
  --color-focus:  var(--gold-500);
  /* component */
  --btn-bg-primary: var(--color-action);
  --btn-ring:       var(--color-focus);
}
.btn.primary { background: var(--btn-bg-primary); }
.btn:focus-visible { outline: 2px solid var(--btn-ring); }
```

**Dark mode without a rewrite.** Because the button reads tokens, dark mode is a token swap, not new button CSS:

```css
@media (prefers-color-scheme: dark) {
  :root { --color-action: oklch(62% 0.14 305); }   /* lift lightness, ease chroma */
}
```

Dark mode is _not_ inverted light mode: raise surface lightness for elevation instead of using shadow, and nudge accent lightness up so it reads on a dark field.

**Pipeline (Style Dictionary).** Design tools (Figma variables) export JSON tokens; Style Dictionary transforms that one source into CSS custom properties, iOS (Swift), Android (XML), and JS at build time. One token source, every platform's button stays in sync. This is how the SwiftUI/Compose/Flutter buttons in §9.14 share a palette with the web ones without anyone copying hex codes by hand.

**Use OKLCH for the ramp.** Perceptually-uniform lightness steps mean your hover/active/disabled shades look evenly spaced. Hold chroma + hue, vary lightness, and hover/pressed states derive predictably instead of being hand-picked per color.

## 10\. Accessibility (non-negotiable)
*   Use real `<button>`/`<a>` elements. They come with keyboard support, focus, and roles for free.
*   **Keyboard:** Enter and Space activate buttons; Enter activates links. Native elements handle this; `<div>` doesn't.
*   **Focus visible:** never `outline: none` without a replacement. Use `:focus-visible`.
*   **Labels:** icon-only buttons need `aria-label`. Text should be meaningful out of context ("Download report," not "Click here").
*   **State to screen readers:** `aria-pressed` (toggle), `aria-expanded` (opens menu), `aria-busy` (loading), `aria-disabled`.
*   **Contrast:** text vs. background ≥ 4.5:1 (WCAG AA). Don't rely on color alone to signal destructive.
*   **Touch target ≥ 44px.** Small-looking buttons can still have big hit areas.

## 11\. Innovative & Emerging Ideas
The button looks solved but keeps evolving:
*   **Optimistic + skeleton feedback:** actions feel instant; server confirms in background. Now standard in React Server Components / Next.js `useOptimistic`.
*   **Magnetic & spring buttons:** the button subtly moves toward the cursor or springs on press (Framer Motion, GSAP). Premium/expressive brands.
*   **Morphing buttons:** button transforms into the thing it created (button → progress bar → checkmark → the new item). Reduces perceived latency and jarring transitions.
*   **Confirm-in-place / hold-to-confirm:** destructive actions require press-and-hold, eliminating a whole modal step.
*   **Haptic buttons:** on mobile/native, a tap fires a subtle vibration (`navigator.vibrate`, iOS haptics) for physical confirmation.
*   **Voice & multimodal:** the same action exposed as a button _and_ a voice intent, sharing one handler.
*   **AI/agentic buttons:** "Do it for me" buttons that hand a task to an agent, with streaming progress replacing the old spinner.
*   **View Transitions API:** native browser morphing between states/pages triggered by a button, no heavy JS.

## 12\. Security
A button is the front door to a server action, and the only security that counts lives on the far side of that door: every state-changing click must be independently authenticated, authorized, and validated server-side, because the button being enabled, visible, or clickable is a UI affordance and never an authorization control — `disabled` is one devtools edit away from gone, and the endpoint answers `curl` exactly as readily as it answers your markup. Put a CSRF token on every state-changing submit — a per-session secret rendered into the form and verified server-side so a cross-origin page can't fire the action with the victim's cookies — and back it with `SameSite=Lax`/`Strict` cookies and non-GET methods for anything that mutates. Treat every click as potentially duplicated: disable the control on submit to stop honest double-taps, but make the operation idempotent on the server (an idempotency key, or dedupe against a natural unique constraint), because the client-side guard does nothing against a retried request, a flaky network, or a scripted attacker. On submit buttons specifically, remember that `formaction` and `formmethod` override the form's own `action`/`method` — anyone who can inject or tamper with a button can redirect the submission to a different endpoint or verb, so authorize the destination server-side and never trust that a POST landed where the form appeared to send it. For sensitive one-click actions — pay, delete, transfer, grant-access — defend against clickjacking with `Content-Security-Policy: frame-ancestors 'none'` (and legacy `X-Frame-Options: DENY`) so your real button can't be framed invisibly beneath a decoy UI, and re-confirm high-stakes intent server-side rather than trusting a single unattended click. Rate-limit and monitor the abuse-prone endpoints (login, password reset, payment) per user and per IP, and re-authenticate for the highest-stakes actions so a stolen session can't quietly drain an account. And never trust data the button carries — `data-id`, hidden inputs, and `value` are all fully attacker-controllable — so verify on the server that _this_ user may act on _that_ resource. The rule of thumb: the UI decides what's convenient to click; the server decides what's allowed to happen.

```plain
<form action="/account/delete" method="post">
  <input type="hidden" name="csrf_token" value="{{ csrf }}">
  <button type="submit" class="btn destructive">Delete account</button>
</form>
```

## 14\. Conversion Killers (mistakes that bleed money silently)
None of these throw an error. They just quietly drop your numbers, which makes them dangerous. Every one is fixable in an afternoon.
*   **Vague copy.** "Submit," "OK," "Click here" name the mechanic, not the outcome. Verb-first and specific wins: "Start free trial" > "Sign up," "Get my plan" > "Continue." The label should tell the user exactly what happens next.
*   **Competing primaries.** When three buttons all shout, none do. One primary CTA per screen; everything else drops to secondary/ghost. More equal choices = decision paralysis = they leave.
*   **No loading state.** User clicks "Pay," nothing visibly happens, so they click again (double charge) or bounce thinking it's broken. Disable + spinner on click is non-negotiable. Perceived speed is mostly button feedback.
*   **Dead-looking CTAs.** Ghost/outline styling that reads as disabled, low contrast that fails to catch the eye, or the primary action buried below the fold. If they have to hunt for it, they won't.
*   **Tiny mobile tap targets.** Sub-44px buttons or two actions crammed together = mis-taps = rage-quits. Most traffic is thumbs: go full-width and generous on mobile.
*   **Premature disabling.** Graying out "Continue" until the form is perfect, with no hint _why_, leaves users stuck and silent. Let them click and surface the error, or say what's missing inline.
*   **Destructive next to primary.** "Delete" one pixel from "Save" guarantees accidental clicks, refunds, and support tickets. Separate them; gate destruction behind confirm.
*   **Friction-heavy labels.** "Register your account now" is heavier than "Get started." Every extra word of commitment lowers click-through. Minimize the perceived cost of pressing it.

**The through-line:** these all fail _quietly_. No log, no crash, just a slightly lower conversion number that's easy to blame on "the market." Audit your buttons before you audit your ad spend.

## 15\. Advanced Patterns (native platform tricks)
Techniques that lean on the browser and the type system instead of custom JavaScript. These are the "senior move" versions of patterns above.
### Reset button + declarative commands
Beyond `submit` and `button`, `type="reset"` restores a form's controls to their initial values, no JS required. Modern HTML also lets buttons drive dialogs and popovers declaratively, cutting custom scripting entirely:

```plain
<!-- Restore a form -->
<button type="reset">Reset filters</button>

<!-- Open a popover with zero JS -->
<button type="button" popovertarget="menu">Open menu</button>
<div id="menu" popover>…</div>

<!-- Command a dialog declaratively -->
<button type="button" command="show-modal" commandfor="dialog">Edit</button>
```

The `command`, `commandfor`, `popovertarget`, and `popovertargetaction` attributes wire common UI (menus, modals) to buttons without an event listener. Less JS = fewer bugs.
### Multi-intent forms (one form, branching actions)
Two submit buttons in the same form can send _different_ `name`/`value` pairs, letting the server branch on which button was clicked. Elegant for "Save draft" vs. "Publish" without duplicate forms:

```plain
<form action="/posts/publish" method="post">
  <input type="hidden" name="postId" value="123">
  <button type="submit" name="intent" value="save">Save draft</button>
  <button type="submit" name="intent" value="publish">Publish now</button>
</form>
```

The server reads `intent` and routes accordingly. Works with zero JavaScript, degrades gracefully.
### CSS design tokens (theming + cross-platform reuse)
A scalable button is driven by tokens, not one-off values. This is what makes theming, dark mode, and cross-product consistency cheap:

```css
:root {
  --btn-font-size: 14px;
  --btn-radius: 10px;
  --btn-gap: 8px;
  --btn-h-sm: 32px;  --btn-h-md: 40px;  --btn-h-lg: 48px;
  --btn-px-sm: 12px; --btn-px-md: 16px; --btn-px-lg: 20px;
  --color-primary: #5F2C82;
  --color-primary-hover: #4c2368;
  --color-danger: #b42318;
  --focus: #DCA424;
}
.btn { min-height: 44px; padding: 0 var(--btn-px-md); border-radius: var(--btn-radius); }
.btn-sm { min-height: var(--btn-h-sm); padding-inline: var(--btn-px-sm); }
.btn-lg { min-height: var(--btn-h-lg); padding-inline: var(--btn-px-lg); }
```

Change one token, every button updates. Retheme the whole system by swapping the `:root` block.
### TypeScript: force accessibility at compile time
A discriminated union can _require_ an `aria-label` whenever a button has no visible text, catching a whole class of accessibility bugs before the code ever runs:

```typescript
type CommonProps = {
  variant?: "primary" | "secondary" | "ghost" | "danger";
  size?: "sm" | "md" | "lg";
  loading?: boolean;
};

type TextButtonProps = CommonProps &
  React.ButtonHTMLAttributes<HTMLButtonElement> & {
    children: React.ReactNode;
    iconOnly?: false;
  };

type IconOnlyButtonProps = CommonProps &
  React.ButtonHTMLAttributes<HTMLButtonElement> & {
    iconOnly: true;
    "aria-label": string;   // now MANDATORY when iconOnly is true
    children: React.ReactNode;
  };

type AccessibleButtonProps = TextButtonProps | IconOnlyButtonProps;
```

Now `<Button iconOnly>` won't compile without an `aria-label`. The type system enforces the a11y rule so a human doesn't have to remember it.
### aria-live status region for async feedback
For screen-reader users, a visual spinner isn't enough. Pair the button with a polite live region so results are _announced_, not just shown:

```plain
<button id="saveBtn" type="button">Save draft</button>
<p id="status" aria-live="polite"></p>
<!-- On success: status.textContent = "Draft saved successfully" -->
<!-- On failure: status.textContent = "Draft could not be saved" -->
```

### Next.js: `useActionState` for form-bound buttons
Beyond `useTransition`, `useActionState` binds a submit button to a server action _and_ surfaces validation errors through the same state object, with `aria-live` wiring the errors to assistive tech:

```typescript
"use client";
import { useActionState } from "react";

const [state, formAction] = useActionState(subscribeAction, { message: null, errors: {} });

// <form action={formAction}>
//   <input id="email" name="email" aria-describedby="email-error" />
//   <div id="email-error" aria-live="polite">{state.errors?.email?.map(e => <p key={e}>{e}</p>)}</div>
//   <button type="submit">Subscribe</button>
// </form>
```

### Testing the toggle's pressed state
Complementing the tests above: assert the _accessibility state_ of a toggle, not just its text. Query by `pressed` so the test proves screen readers see the change:

```typescript
test("toggles pressed state", async () => {
  const user = userEvent.setup();
  render(<FavoriteButton />);
  const button = screen.getByRole("button", { pressed: false });
  await user.click(button);
  expect(screen.getByRole("button", { pressed: true })).toBeInTheDocument();
});
```

### The systems view
Treat a button as a **system component**, not a visual fragment. A production-ready button has: clear semantics, a documented API (variant/size/state/behavior), accessibility guarantees baked into both implementation and tests, a predictable backend contract per action, and docs covering placement, hierarchy, labeling, and misuse. That's what separates a one-off button from a button _architecture_.
* * *

**Bottom line:** a button is a tiny component with an enormous blast radius. Master the semantics, the eight states, the accessibility, and the frontend-to-backend chain, and you've mastered a surprising amount of what separates a hobby build from production software.
