## 1\. What a Text Input Actually Is
A text input is a control that lets a user type a value your program will read. That's the whole job. But three words get used interchangeably by people who then build the wrong thing, so pin them down:
*   **Input (the element):** the raw `<input>` tag — a browser primitive. One DOM node. It has a `type`, a `value`, and a pile of attributes. It is not, by itself, a usable UI.
*   **Field (the unit):** the input _plus everything a human needs to use it correctly_ — a label, optional help text, an error slot, the wrapper that groups them. When a designer says "the email field," they mean the label + input + error, not the bare tag. This is the thing you actually ship.
*   **Form control:** the category. `<input>`, `<textarea>`, `<select>`, `<button>`, and custom widgets that behave like them are all form controls. "Text input" is one member of that family — the single-line text one.

The single most common mistake here is shipping an **input without a field**: a lonely box with placeholder text and no `<label>`. It looks done. It is broken for screen readers, for autofill, and for anyone who clears the box and forgets what it wanted. _Placeholder is not a label_ — that rule gets its own section (§10) because juniors break it every single time.

Second distinction people fumble: **single-line vs multi-line.** `<input type="text">` is one line; `<textarea>` is many. They are different elements. An `<input>` can't wrap. Don't reach for a `contenteditable` div to fake a growing input unless you enjoy re-implementing the caret, undo, and IME support the browser gives you for free.

Third: **`<input>`** **vs combobox/autocomplete.** The moment your text box suggests options as the user types, you've left plain-input territory and entered combobox territory (`role="combobox"`, `aria-expanded`, a popup listbox). That's a different component with its own keyboard contract. This doc is the plain, foundational text field — master it first; every richer text widget is this plus more.
* * *

## 2\. Why It Matters
The text input is where the user _gives_ and the system _receives_. Everything downstream — the account, the order, the search result, the support ticket — starts as characters typed into one of these boxes. That makes it load-bearing in three ways:
*   **Conversion lives in the field.** Every field is friction. Forms are where funnels die: a checkout with too many inputs, a signup that rejects a valid password, a phone field that won't accept the format the user typed. Cutting one unnecessary field or fixing one broken validation message measurably lifts completion. The input is the most-abandoned element in software.
*   **It's an accessibility and trust surface.** A field with no label is invisible to a screen reader — the user hears "edit text, blank" and has no idea what to type. A field that turns red with no explanation is a dead end. Autofill that doesn't fire because your `autocomplete` attributes are wrong turns a 4-second form into a 40-second one. Get labelling, error wiring, and autofill right and huge swaths of usability come free.
*   **It's the front door for attackers.** Every input is untrusted data entering your system. XSS, SQL injection, and header injection all arrive through fields. The rule that governs §9's server section — _never trust client validation_ — exists because the input is the single most attacked component you own.

## 3\. Anatomy of a Field
A bare `<input>` is not a field. A production field is composed of predictable parts, and skipping any of them is a bug you'll pay for:
*   **Label:** the persistent, visible name of the field, wired to the input via `for`/`id` (or wrapping). _Mandatory._ Not the placeholder.
*   **The input (control):** the box itself. Carries `type`, `value`, `inputmode`, `autocomplete`, `required`, `pattern`, and state.
*   **Placeholder (optional):** a _hint_ or example format shown when empty — "e.g. [jane@work.com](mailto:jane@work.com)". Disappears on type. Never the only label.
*   **Help / description text:** persistent guidance ("Use 8+ characters"), wired with `aria-describedby` so screen readers read it _with_ the field.
*   **Prefix / suffix / adornment:** an inline `$`, a unit `kg`, a leading search icon, a trailing show-password toggle. Visual, but must not swallow the input's focus ring or hit target.
*   **Error slot:** a reserved region for the validation message. Wired with `aria-describedby` and paired with `aria-invalid` on the input. Reserve its space so the layout doesn't jump when an error appears.
*   **Required / optional indicator:** an asterisk (with a legend explaining it) or the word "optional." Pick one convention and apply it consistently — mark the _minority_.
*   **Focus ring:** the visible outline on keyboard focus. Never removed without replacement.
*   **Hit target:** the clickable area. The label click should focus the input (free with correct `for`). Minimum 44px tall control.

The mental model: **label + control + description + error, wrapped in one group.** Build that group once as a component and you never think about the parts again.

## 4\. Sizes & Density
Input size sets rhythm and communicates density. A field in a data-dense admin table is not a field on a marketing signup page. A workable scale:

| Size | Height | Padding (H) | Font | Use |
| ---| ---| ---| ---| --- |
| XS | 28px | 8px | 13px | Dense tables, inline edit, filter bars |
| SM | 32px | 10px | 13px | Compact admin forms, toolbars |
| MD | 40px | 12px | 14px | Default for most forms |
| LG | 48px | 16px | 16px | Primary flows, mobile signup/checkout |
| XL | 56px | 20px | 18px | Hero/landing single-field capture |

Rules that matter:
*   **Font-size ≥ 16px on mobile inputs.** Below 16px, iOS Safari _zooms the page_ when the field is focused — a jarring, layout-breaking jump. `font-size: 16px` on the control is the fix. This is the single most common mobile-input bug.
*   **Height should be a spacing token, not a magic number,** so the whole form system scales together.
*   **Don't fix the width to the expected content** unless the content has a fixed length (a 5-digit ZIP, a 3-digit CVC). A name field sized "for a name" clips long names. When you _do_ size to content, use `ch` units and a `maxlength` that matches reality.
*   **Full-width fields on mobile** reduce mis-taps and read as calmer. Multi-column form layouts belong on desktop only.

## 5\. States (the part juniors forget)
A production field has far more than "empty" and "filled." Missing states are the #1 tell of an amateur form.
1. **Empty / default (rest)** — the baseline, showing label and optional placeholder.
2. **Focus** — keyboard or click focus. Must show a visible `:focus-visible` ring. This is where the user _is_.
3. **Filled** — has a value. Often styled subtly differently (e.g. floating label parked up).
4. **Hover** — pointer over the control. Subtle border shift. Never the only affordance (touch has no hover).
5. **Disabled** — not editable, not submitted, removed from tab order. Reduced opacity, `cursor: not-allowed`. Use for "not applicable right now."
6. **Read-only** — value shown, not editable, _but still focusable and still submitted_. Different from disabled. Use for "you can see and copy this, but not change it."
7. **Invalid / error** — failed validation. Red border, error icon, and a real message wired via `aria-describedby`; `aria-invalid="true"` on the input. Color is never the only signal.
8. **Valid / success** — passed a meaningful check (e.g. "username available"). Use sparingly — a green check on every trivially-filled field is noise.
9. **Loading / pending** — async validation in flight (checking availability), or the field is populating. Show a spinner adornment; don't block typing unless you must.
10. **Autofilled** — the browser filled it. Browsers apply their own background (that yellow tint). Don't fight it into invisibility; make sure your text stays legible on it.
11. **Required-but-empty (after submit)** — the specific error state of a skipped required field. "This field is required," tied to the field, focus moved to the first offender.

Bonus for masked/formatted fields: **partially-valid / in-progress** — the value is being typed and isn't yet a complete valid pattern (a half-typed phone number). Don't scream "invalid" mid-type; validate on blur or when the pattern completes.

## 6\. Types & Variants
Two axes here: the HTML `type` (semantic — what kind of data), and the field _variant_ (structural — how it's arranged). Get the `type` right and you unlock the correct mobile keyboard, browser validation, and autofill for free.

**By** **`type`** **(semantic — this is the high-leverage choice):**
*   **`text`** — the default. Names, arbitrary short strings. Pair with the right `autocomplete` (`name`, `given-name`, `organization`).
*   **`email`** — email addresses. Gets the `@`\-optimized mobile keyboard, free `type`\-level validity check, and `autocomplete="email"`. Use it; don't validate email with a hand-rolled regex on a `type="text"`.
*   **`password`** — obscures characters. Enables password-manager save/fill with `autocomplete="current-password"` or `"new-password"`. Pair with a visible show/hide toggle.
*   **`number`** — numeric with spinner. _Use with care_ — it rejects leading zeros, allows `e`/`+`/`-`, and its spinners annoy. For codes/IDs/phone, prefer `type="text"` + `inputmode="numeric"` + `pattern`. Reserve `type="number"` for true quantities you'd do math on.
*   **`tel`** — phone numbers. No format enforcement (phone formats vary globally), but triggers the phone keypad and `autocomplete="tel"`.
*   **`url`** — web addresses. URL-optimized keyboard (`/`, `.com` key), free URL validity check, `autocomplete="url"`.
*   **`search`** — search queries. Gets a clear (×) affordance in some browsers and a "Search" enter key. Semantic hint to AT.
*   Also: **`date`****/****`time`****/****`datetime-local`****/****`month`****/****`week`** (native pickers — powerful but styling is limited), **`color`**, **`range`** (slider), **`file`** (upload — its own beast).

**The** **`inputmode`** **+** **`autocomplete`** **pairing (the detail that separates senior from junior):**
`type` picks the _semantics_; `inputmode` picks the _on-screen keyboard_ without changing semantics; `autocomplete` tells the browser what to prefill. Get all three aligned:

| Purpose | `type` | `inputmode` | `autocomplete` |
| ---| ---| ---| --- |
| Email | `email` | `email` | `email` |
| Phone | `tel` | `tel` | `tel` |
| One-time code | `text` | `numeric` | `one-time-code` |
| ZIP / postal | `text` | `numeric` | `postal-code` |
| Credit card # | `text` | `numeric` | `cc-number` |
| Name | `text` | `text` | `name` |
| URL | `url` | `url` | `url` |
| Price/quantity | `number` | `decimal` | (off / custom) |

`inputmode="numeric"` gives a digits keypad without `type="number"`'s baggage. `inputmode="decimal"` adds the decimal point. `autocomplete="one-time-code"` lets iOS surface the SMS code above the keyboard — a genuinely magic UX win people forget exists.

**By variant (structural):**
*   **Standard (outlined / filled / underlined):** the border treatment. Outlined = box border. Filled = tinted background, bottom border (Material). Underlined = bottom rule only (minimal). Same semantics, different skin.
*   **With adornment:** leading icon, trailing icon, prefix (`$`), suffix (`.00`, unit, or a "Copy" button).
*   **Floating label:** label sits as placeholder, animates up on focus/fill. Space-efficient, trendy — and an a11y minefield (§10 covers the traps).
*   **Password with reveal:** trailing show/hide toggle button (`aria-pressed`, `aria-label` that changes).
*   **Search field:** leading magnifier, trailing clear, often debounced to a live result list.
*   **Masked / formatted:** displays formatting as you type (phone `(555) 123-4567`, card `4242 4242 4242 4242`, currency). The display and the stored value differ — that's the whole challenge (§9).
*   **Character-counted:** a live "42/280" counter, wired to `aria-live` so it's announced without spamming.

## 7\. When to Use One (and When Not To)
Use a text input when the answer is **open-ended text or a value the user must type** and you can't offer a small fixed set of choices. Don't reach for a text input when a better control exists:
*   **≤ ~5 mutually-exclusive options →** radio group or segmented control, not a text box the user has to guess the exact spelling for.
*   **A yes/no →** a checkbox or switch, not a "type yes" field.
*   **A date →** `type="date"` or a date picker, not a free-text "MM/DD/YYYY" box that fights every locale.
*   **A known long list (country, state) →** a `<select>` or combobox, not a text field that accepts "USA," "U.S.," and "united states" as three different values.
*   **A range or approximate number →** a slider (`type="range"`) when precision isn't required.
*   **Multi-line prose →** `<textarea>`, not an `<input>`.
*   **A value the system already knows →** don't ask. The cheapest field is the one you deleted. Prefill from account data, derive from other answers, or skip it.

Placement & ordering heuristics:
*   **Logical, human order:** name → email → password. Group related fields (address block). Don't scatter one address across the form.
*   **One column beats two** for completion on most forms; the eye tracks a single vertical path. Exception: naturally-paired short fields (City / State / ZIP) on desktop.
*   **Label above the input** is the safest default — it survives narrow screens, long translations, and zoom without breaking. Left-aligned labels look tidy but slow scanning and wrap badly.
*   **Ask the minimum.** Every field you cut lifts completion. If Legal doesn't require it and it doesn't change the experience, drop it or make it optional.

## 8\. Inputs Across Design Systems
Same element, very different philosophies. Fluency here means you can drop into any codebase.
*   **Material Design (Google):** the _filled_ and _outlined_ text field with the animated floating label is Material's signature. Label parks in the notch of the outline. Helper text and character counter are first-class slots below. Strong, opinionated motion. Material 3 ("Expressive") loosens shape and adds larger states.
*   **Apple HIG (iOS/macOS):** restrained. Rounded-rect text fields, often in grouped inset lists. Labels frequently sit to the _left_ in settings-style lists. Clear button (×) when editing. Heavy reliance on the correct keyboard type and `textContentType` (Apple's autofill hint) — the platform does a lot of the work.
*   **Fluent (Microsoft):** subtle depth, a bottom accent line that animates on focus, compact density for data-heavy enterprise apps. Clear affordances for required/optional and inline validation.
*   **Ant Design / enterprise:** dense, feature-rich. Prefix/suffix slots, addon-before/addon-after (the `https://` addon look), `status="error"`/`"warning"` props, built-in count. Designed for admin dashboards with dozens of fields.
*   **Tailwind / utility-first:** no prescribed look; you compose border, ring, padding utilities. Freedom plus consistency risk — real teams wrap it in a `Field` component so every input shares label/error wiring.
*   **shadcn/Radix (2024+ web standard):** headless `Label`/`Input`/`Form` primitives (Radix + react-hook-form + zod) with cva-styled variants. Accessibility (label association, `aria-invalid`, `aria-describedby`) is wired for you; the look is yours.
*   **Bootstrap:** `.form-control`, `.form-label`, `.form-text`, `.is-invalid`/`.is-valid`, `.invalid-feedback`. Ready-made, responsive, floating-label variant included. Convention over ownership.

**Rule that never changes:** the skin differs, the contract doesn't — a real `<label>`, a real `type`, visible focus, wired errors. Full visual guidance lives in the 🎨 [Design Styles (visual languages)](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200551) doc.

### What's trending in 2026
The 2026 currents that touch inputs specifically:
*   **Liquid Glass fields** (Apple iOS 26 / macOS Tahoe): the input sits on translucent, refractive material with a specular rim. Gorgeous over the deep Eminence/Night UJG surfaces — but contrast of the _text and border_ against the moving backdrop is the hard part. Guard it.
*   **AI-native inputs:** the field that also accepts a natural-language instruction, inline "improve this" affordances, and streaming validation ("this address looks off — did you mean…"). The plain field is now often the fallback of a smarter surface.
*   **One-tap fill everywhere:** passkeys and richer autofill mean the best login field increasingly isn't typed at all. Your `autocomplete` correctness is what unlocks it.
*   **Motion-forward but restrained:** floating labels and focus transitions with `prefers-reduced-motion` honored by default.
*   **On-device format/validation:** smarter client hints (address, phone by region) — always still re-validated on the server.

**For UJG:** Liquid Glass accents on inputs read premium over the dark saturated palette, but keep dense/data forms on Flat or Minimal/Swiss for legibility. The accessibility caveats never bend: label, contrast, focus, wired errors, no matter how on-trend the skin.

## 9\. The Code
### 9.1 HTML (the foundation everyone should master first)

```plain
<!-- The minimum viable FIELD: label + input, associated by for/id -->
<div class="field">
  <label for="email">Email</label>
  <input
    type="email"
    id="email"
    name="email"
    inputmode="email"
    autocomplete="email"
    placeholder="jane@work.com"   <!-- hint, NOT the label -->
    required
    aria-describedby="email-help email-error"
  />
  <p id="email-help" class="field__help">We'll only use this to send your receipt.</p>
  <p id="email-error" class="field__error" hidden></p>
</div>

<!-- Password with autofill hints -->
<label for="pw">Password</label>
<input type="password" id="pw" name="password"
       autocomplete="new-password" minlength="8" required
       aria-describedby="pw-req" />
<p id="pw-req">Use 8 or more characters.</p>

<!-- One-time code: numeric keypad + SMS autofill on iOS -->
<label for="otp">Verification code</label>
<input type="text" id="otp" name="otp"
       inputmode="numeric" autocomplete="one-time-code"
       pattern="[0-9]{6}" maxlength="6" />

<!-- Read-only (submitted, focusable) vs disabled (not submitted) -->
<input type="text" value="ACCT-19FX" readonly />
<input type="text" value="N/A" disabled />
```

Key HTML rules:
*   **Every input has a** **`<label>`** **with a matching** **`for`****/****`id`****\*\*\*\*.** No exceptions. Wrapping the input in the `<label>` also works and needs no `for`.
*   **`name`** **is what the server receives.** No `name`, no data submitted. `id` is for the label and scripts; `name` is for the wire. They're often equal but serve different masters.
*   **Set the right** **`type`****\*\*\*\*,** **`inputmode`****\*\*\*\*, and** **`autocomplete`** **together** (see §6 table). This trio is free UX most builds leave on the floor.
*   **`placeholder`** **is a hint, never a label.** It vanishes on type, fails contrast, and is invisible to autofill logic.
*   **`required`****\*\*\*\*,** **`minlength`****\*\*\*\*,** **`maxlength`****\*\*\*\*,** **`pattern`** give you free browser validation — a baseline, not your real defense (that's the server).

### 9.2 CSS (states done right)

```css
.field { display: flex; flex-direction: column; gap: 6px; }

.field label {
  font: 500 14px/1.2 system-ui, sans-serif;
  color: #2a2233;
}

.input {
  height: 44px;                 /* >= 44px tap target */
  padding: 0 12px;
  font-size: 16px;              /* prevents iOS zoom-on-focus */
  color: #17121d;
  background: #fff;
  border: 1px solid #b9b0c4;    /* neutral tinted toward the purple hue */
  border-radius: 8px;
  transition: border-color .15s, box-shadow .15s;
}
.input::placeholder { color: #8a8194; }   /* must still pass contrast */

/* Focus: keyboard AND mouse both deserve a visible ring here,
   because a text field's focus IS the editing position. */
.input:focus-visible {
  outline: none;                /* replaced, not removed */
  border-color: #5F2C82;
  box-shadow: 0 0 0 3px rgba(95, 44, 130, .25);
}

/* Invalid: never color alone — pair with the error text + icon */
.input[aria-invalid="true"] {
  border-color: #b42318;
  box-shadow: 0 0 0 3px rgba(180, 35, 24, .18);
}
.field__error { color: #b42318; font-size: 13px; }

/* Valid, used sparingly */
.input[data-valid="true"] { border-color: #087443; }

.input:disabled {
  opacity: .55; cursor: not-allowed; background: #f2eff5;
}
.input:read-only { background: #f7f5fa; cursor: default; }

/* Don't let the browser's autofill yellow bury your text */
.input:-webkit-autofill { -webkit-text-fill-color: #17121d; }
```

The two CSS mistakes that define an amateur field: `outline: none` with no replacement (kills keyboard users) and signalling errors with red border _only_ (invisible to colorblind users and screen readers). Both are fixed above.

### 9.3 React + TypeScript (a proper reusable field)
The longest block, because the reusable `Field` is what you actually ship. It bundles the label, the input, description, and error — wired correctly — so no one on the team can forget the `aria-describedby`/`aria-invalid` dance.

```typescript
import { forwardRef, useId, InputHTMLAttributes, ReactNode } from "react";

type FieldProps = InputHTMLAttributes<HTMLInputElement> & {
  label: string;              // MANDATORY — a field has no valid state without one
  description?: string;       // persistent help text
  error?: string;             // present => invalid
  leading?: ReactNode;        // adornment (icon, "$")
  trailing?: ReactNode;       // adornment (unit, reveal button)
};

export const Field = forwardRef<HTMLInputElement, FieldProps>(function Field(
  { label, description, error, leading, trailing, id, className = "", required, ...rest },
  ref
) {
  const auto = useId();
  const inputId = id ?? auto;
  const descId = description ? `${inputId}-desc` : undefined;
  const errId = error ? `${inputId}-err` : undefined;
  // describedby points at BOTH help and error, filtered for what exists
  const describedBy = [descId, errId].filter(Boolean).join(" ") || undefined;

  return (
    <div className={`field ${className}`}>
      <label htmlFor={inputId}>
        {label}
        {required && <span aria-hidden="true"> *</span>}
      </label>

      <div className="field__control">
        {leading && <span className="field__adorn" aria-hidden="true">{leading}</span>}
        <input
          ref={ref}
          id={inputId}
          className="input"
          required={required}
          aria-invalid={error ? true : undefined}
          aria-describedby={describedBy}
          {...rest}
        />
        {trailing && <span className="field__adorn" aria-hidden="true">{trailing}</span>}
      </div>

      {description && <p id={descId} className="field__help">{description}</p>}
      {/* role=alert so the error is announced the moment it appears */}
      {error && <p id={errId} className="field__error" role="alert">{error}</p>}
    </div>
  );
});
```

Why this is the senior version, not the junior one:
*   **`label`** **is a required prop**, not optional. The type system refuses a label-less field — the placeholder-as-label bug can't compile.
*   **`useId()`** generates a stable, SSR-safe unique id, so `for`/`id` and `aria-describedby` always match even with many fields on the page. Hardcoded ids collide.
*   **`describedBy`** **joins help + error** into one string and drops the empties — the exact wiring screen readers rely on to read the field _and_ its message together.
*   **`error`** **presence drives** **`aria-invalid`** — one source of truth, so the visual red and the ARIA state can never disagree.
*   **Extends native** **`InputHTMLAttributes`** so `type`, `inputmode`, `autocomplete`, `onChange`, `maxLength`, `data-*` all pass through for free.

**Controlled vs uncontrolled — the distinction that trips everyone.** A React input is _controlled_ when its `value` comes from state and every keystroke flows through `onChange`; _uncontrolled_ when the DOM holds the value and you read it via a ref (or on submit). Both are valid; mixing them is the classic bug.

```typescript
// Controlled: React state is the single source of truth.
function ControlledEmail() {
  const [email, setEmail] = useState("");
  return (
    <Field label="Email" type="email" value={email}
           onChange={(e) => setEmail(e.target.value)} />
  );
}

// Uncontrolled: the DOM owns the value; you read it on submit.
function UncontrolledEmail() {
  const ref = useRef<HTMLInputElement>(null);
  function submit() { console.log(ref.current?.value); }
  return <Field label="Email" type="email" defaultValue="" ref={ref} />;
}
```

The rules that end the confusion:
*   **Never pass both** **`value`** **and** **`defaultValue`****\*\*\*\*.** `value` = controlled, `defaultValue` = uncontrolled. Pick one per input.
*   **A controlled input needs an** **`onChange`** (or it's read-only and React warns). Passing `value={x}` with no handler freezes the box.
*   **Don't flip an input from** **`value={undefined}`** **to** **`value="..."`** — that switches it uncontrolled→controlled mid-life and React yells. Initialize to `""`, never `undefined`.
*   **Reach for uncontrolled (or a form library)** for big forms — re-rendering the whole form on every keystroke of a controlled field is a real perf cost. Libraries like react-hook-form keep inputs uncontrolled under the hood for exactly this reason.

### 9.4 Validation states & error wiring (do this right or don't bother)
Validation is the whole reason inputs are hard. The wiring, in order:
1. **`aria-invalid="true"`** on the input when it fails. This is what a screen reader announces as "invalid entry."
2. **The error message lives in an element referenced by** **`aria-describedby`****\*\*\*\*,** so focusing the field reads the field name _and_ the error.
3. **`role="alert"`** **(or an** **`aria-live="assertive"`** **region)** on the error so it's announced the instant it appears, even if focus is elsewhere.
4. **Color is never alone** — icon + text carry the meaning for colorblind users.
5. **Validate at the right time:** on _blur_ for first validation (don't scold someone mid-type), then on every keystroke _once the field has already errored_ (so they see it clear). Never validate required-empty until submit.
6. **On submit, move focus to the first invalid field** and, ideally, scroll it into view. A list of errors at the top with anchor links is the accessible pattern for long forms.

```typescript
function EmailField() {
  const [email, setEmail] = useState("");
  const [error, setError] = useState<string>();
  const [touched, setTouched] = useState(false);

  function validate(v: string) {
    if (!v) return "Email is required.";
    // A hint, not the real check — the server validates for real (§9.9)
    if (!/^[^@\s]+@[^@\s]+\.[^@\s]+$/.test(v)) return "Enter a valid email address.";
    return undefined;
  }

  return (
    <Field
      label="Email" type="email" inputmode="email" autocomplete="email" required
      value={email}
      onChange={(e) => {
        setEmail(e.target.value);
        if (touched) setError(validate(e.target.value)); // re-validate only after first blur
      }}
      onBlur={() => { setTouched(true); setError(validate(email)); }}
      error={touched ? error : undefined}
    />
  );
}
```

### 9.5 Floating-label pattern (and its a11y traps)
The label starts as placeholder-position text and animates up when the field is focused or filled. It's space-efficient and on-trend — and it's where accessibility quietly breaks. Do it like this:

```plain
<div class="float-field">
  <input type="email" id="fl-email" class="float-input"
         placeholder=" " autocomplete="email" />
  <label for="fl-email" class="float-label">Email</label>
</div>
```

```css
.float-field { position: relative; }
.float-input { height: 52px; padding: 20px 12px 6px; font-size: 16px; }
.float-label {
  position: absolute; left: 12px; top: 16px;
  color: #8a8194; pointer-events: none;
  transition: transform .15s, font-size .15s, color .15s;
}
/* Float up when focused OR when the field has content
   (:placeholder-shown is false once there's a value) */
.float-input:focus + .float-label,
.float-input:not(:placeholder-shown) + .float-label {
  transform: translateY(-12px);
  font-size: 12px;
  color: #5F2C82;
}
```

The traps, and how this avoids them:
*   **It must still be a real** **`<label for>`****\*\*\*\*.** Many floating-label builds fake the label with a `<span>` — now it's not associated, and it's the placeholder-as-label bug wearing a costume. Use a real `<label>`.
*   **The** **`placeholder=" "`** **trick** (a single space) is what lets `:placeholder-shown` detect "empty" without showing competing placeholder text. Don't put real hint text in the placeholder here — the floating label _is_ the label; a second string fights it.
*   **Resting-state contrast:** the label at rest sits over the input background at small size and light color — check it passes 4.5:1. Floating labels routinely fail this.
*   **Autofill breaks the animation:** browser autofill can fill the value _without_ triggering `:placeholder-shown` reliably in older engines, leaving the label overlapping filled text. Test autofill; add a JS fallback (`animationstart` on the autofill keyframe) if you support old browsers.
*   **No room for help text:** floating labels eat the vertical space help text would use. If a field needs persistent guidance, a static top label is the safer choice.

Blunt take: floating labels are a _cosmetic_ win with real a11y cost. For UJG marketing captures, fine. For dense or high-stakes forms, a static label above the input wins every time.

### 9.6 Masking & formatting (display vs stored value)
Masking shows human-friendly formatting as the user types — phone `(555) 123-4567`, card `4242 4242 4242 4242`, currency `$1,299.00` — while the value you _store_ is the clean one (`5551234567`, `4242424242424242`, `1299.00`). The gap between display and data is the entire challenge.

```typescript
// Lightweight phone mask: format for display, keep digits for the model.
function usePhoneMask(initial = "") {
  const [display, setDisplay] = useState(initial);
  const digits = display.replace(/\D/g, "");           // the value you SUBMIT

  function onChange(e: React.ChangeEvent<HTMLInputElement>) {
    const d = e.target.value.replace(/\D/g, "").slice(0, 10);
    const p = d.length > 6 ? `(${d.slice(0,3)}) ${d.slice(3,6)}-${d.slice(6)}`
            : d.length > 3 ? `(${d.slice(0,3)}) ${d.slice(3)}`
            : d.length > 0 ? `(${d.slice(0)}`
            : "";
    setDisplay(p);
  }
  return { display, digits, onChange };
}
```

Masking rules that save you:
*   **Store the unmasked value.** Submit `digits`, never the pretty string. Servers, databases, and other systems want canonical data; formatting is a view concern.
*   **Never block characters silently.** If a user pastes `+1 (555) 123-4567`, strip and reformat — don't reject the paste. Support paste of the full formatted value.
*   **Watch the caret.** Naive re-formatting jumps the cursor to the end mid-edit. Robust masks (libraries like `imask`, `cleave.js`, or `react-number-format`) preserve caret position; hand-rolled ones usually don't. Use a library for card/currency/date masks — the caret math isn't worth re-deriving.
*   **Don't mask emails or names.** Masking is for _structured_ values (phone, card, date, money, postal). Free text gets no mask.
*   **`inputmode="numeric"`** on masked numeric fields so mobile shows the keypad even though `type` is `text` (the punctuation forces `text`).

### 9.8 shadcn/ui (the 2024+ standard)

### 9.9 Next.js + the server endpoint (App Router, client vs server, validation & security)


**Server Action (runs only on the server — re-validates from scratch):**

```typescript
"use server";
import { z } from "zod";

// SAME schema shape the client uses — but this run is the one that counts.
const Schema = z.object({
  email: z.string().trim().toLowerCase().min(1, "Email is required.")
          .email("Enter a valid email address.").max(254),
});

export async function subscribe(_prev: unknown, formData: FormData) {
  const parsed = Schema.safeParse({ email: formData.get("email") });
  if (!parsed.success) {
    return { errors: { email: parsed.error.flatten().fieldErrors.email?.[0] } };
  }
  // Store ONLY parameterized — never string-concatenate user input into SQL.
  await db.subscriber.upsert({
    where: { email: parsed.data.email },
    update: {},
    create: { email: parsed.data.email },
  });
  return { errors: {} };
}
```

**A standalone Node/Express endpoint (the shape is universal):**

```typescript
import express from "express";
import { z } from "zod";
const router = express.Router();

const Schema = z.object({
  email: z.string().trim().toLowerCase().email().max(254),
  name:  z.string().trim().min(1).max(120),
});

router.post("/api/subscribe", rateLimit, requireCsrf, async (req, res) => {
  const parsed = Schema.safeParse(req.body);   // NEVER trust the client
  if (!parsed.success) return res.status(422).json({ errors: parsed.error.flatten().fieldErrors });

  // Parameterized query — the driver escapes the value; no concatenation.
  await db.query("INSERT INTO subscribers (email, name) VALUES ($1, $2) ON CONFLICT DO NOTHING",
                 [parsed.data.email, parsed.data.name]);
  return res.status(201).json({ ok: true });
});
export default router;
```

### 9.10 Vanilla JavaScript (no framework)
The primitive everything abstracts. Worth knowing cold — the Constraint Validation API gives you real validation without a library.

```javascript
const input = document.querySelector("#email");
const errorEl = document.querySelector("#email-err");

function showError() {
  input.setAttribute("aria-invalid", "true");
  // The browser's own localized message, or your custom one:
  errorEl.textContent = input.validity.valueMissing
    ? "Email is required."
    : input.validity.typeMismatch
    ? "Enter a valid email address."
    : "";
  errorEl.hidden = false;
}

input.addEventListener("blur", () => {
  if (!input.checkValidity()) showError();
});
input.addEventListener("input", () => {
  // Once errored, clear it live as they fix it.
  if (input.getAttribute("aria-invalid") === "true" && input.checkValidity()) {
    input.removeAttribute("aria-invalid");
    errorEl.hidden = true;
  }
});
```

`checkValidity()`, `validity.*`, and `setCustomValidity()` are the built-in Constraint Validation API — free, localized, and standards-based. Reach for a library when you need cross-field rules or async checks, not for basic "is this filled and shaped right."

### 9.15 Web Components (framework-agnostic)
A field that works in any framework or none. `formAssociated` lets a custom element participate in native forms — the advanced part most people skip.

```typescript
class UIField extends HTMLElement {
  static formAssociated = true;              // participates in <form> submission
  #internals = this.attachInternals();
  #input!: HTMLInputElement;

  connectedCallback() {
    const label = this.getAttribute("label") ?? "";
    const type = this.getAttribute("type") ?? "text";
    const root = this.attachShadow({ mode: "open" });

    // Build the DOM with textContent / property assignment — NEVER innerHTML with
    // attribute-derived data. innerHTML parses `label`/`type` as markup, so
    // label="<img src=x onerror=alert(1)>" would be reflected/stored XSS (see §15).
    const style = document.createElement("style");
    style.textContent = "/* scoped */";

    const labelEl = document.createElement("label");
    labelEl.setAttribute("part", "label");
    labelEl.textContent = label;             // text node — nothing to inject

    this.#input = document.createElement("input");
    this.#input.setAttribute("part", "input");
    this.#input.type = type;                 // property write coerces unknown values to "text"

    root.append(style, labelEl, this.#input);
    this.#input.addEventListener("input", () =>
      this.#internals.setFormValue(this.#input.value));   // value reaches the form
  }
}
customElements.define("ui-field", UIField);
// <form><ui-field label="Email" type="email" name="email"></ui-field></form>
```

### 9.16 Testing the Field (unit + a11y)
A field is behavior + accessibility, so test both. Query by the _label_ — if `getByLabelText` can't find it, neither can a screen reader.

```typescript
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { axe } from "jest-axe";
import { describe, it, expect } from "vitest";
import { Field } from "./Field";

describe("Field", () => {
  it("is reachable by its label", () => {
    render(<Field label="Email" type="email" />);
    // Proves the for/id association — the a11y contract.
    expect(screen.getByLabelText("Email")).toBeInTheDocument();
  });

  it("accepts typing (controlled or not)", async () => {
    render(<Field label="Email" type="email" defaultValue="" />);
    const input = screen.getByLabelText("Email");
    await userEvent.type(input, "jane@work.com");
    expect(input).toHaveValue("jane@work.com");
  });

  it("wires the error to the input via aria-describedby + aria-invalid", () => {
    render(<Field label="Email" error="Enter a valid email address." />);
    const input = screen.getByLabelText("Email");
    expect(input).toHaveAttribute("aria-invalid", "true");
    // The accessible description IS the error text.
    expect(input).toHaveAccessibleDescription(/valid email/i);
    expect(screen.getByRole("alert")).toHaveTextContent(/valid email/i);
  });

  it("has no automatic a11y violations", async () => {
    const { container } = render(<Field label="Email" type="email" />);
    expect(await axe(container)).toHaveNoViolations();
  });
});
```

What to assert (and skip):
*   **Do test:** it's found `byLabelText` (proves labelling), typing updates the value, `aria-invalid`/`aria-describedby` wire to the error, the error is `role="alert"`, and axe is clean.
*   **Don't test:** exact class names, border colors, pixel padding — implementation details that break tests without catching real bugs.
*   **E2E (Playwright):** `page.getByLabel("Email").fill(...)`, submit, assert the server error renders and focus lands on the offending field.

## 10\. Accessibility (non-negotiable)
The text field is where accessibility is most often silently broken. The contract:
*   **A real, associated** **`<label>`** **for every input** — `<label for="id">` + `id`, or wrap the input. This is the single most important rule in this doc.
*   **Placeholder is not a label.** It fails contrast, vanishes on type, isn't reliably announced, and disappears for users with cognitive load who needed the reminder. If you use a placeholder, it's an _example_ on top of a real label — never instead of one.
*   **Description & error via** **`aria-describedby`** so the field's name, help text, and error are announced together.
*   **`aria-invalid="true"`** on failure; **`aria-required`****/****`required`** for required fields; the error message in a live region (`role="alert"` or `aria-live`).
*   **Visible focus, always.** A text field's focus is literally where the caret is — `:focus-visible` with a clear ring/border. Never `outline: none` without replacement.
*   **The correct** **`type`****/****`inputmode`** so users get the right keyboard (a numeric keypad for a code, `@` for email) — an accessibility win, not just convenience.
*   **`autocomplete`** **set correctly** — WCAG 2.1 SC 1.3.5 (Identify Input Purpose) literally requires it for common fields; it's also what lets cognitively-disabled and motor-impaired users autofill instead of type.
*   **Contrast:** input text, placeholder, label, and border all ≥ the WCAG threshold (4.5:1 text, 3:1 for the border/UI). Placeholder text is the usual failure.
*   **Target size ≥ 44px** tall control; the label click focuses the input (free with `for`).
*   **Don't disable — explain.** A disabled field is invisible to some AT and gives no reason. Prefer read-only + a note, or leave it enabled and validate.
*   **Group related fields** with `<fieldset>` + `<legend>` (address block, name parts) so the group's purpose is announced.

Keyboard map for a text input (mostly free from the native element, listed so you can verify nothing's been broken):

| Key | Action |
| ---| --- |
| Tab / Shift+Tab | Move focus in/out of the field |
| Any character | Insert at caret |
| ←/→, Home/End | Move caret |
| Shift+←/→ | Extend selection |
| Ctrl/Cmd+A | Select all |
| Backspace/Delete | Delete char |
| Enter | Submit the form (single-line inputs) — the implicit submit |

## 11\. Innovative & Emerging Ideas
The plain field looks solved but keeps moving:

## 12\. Conversion / UX Killers (mistakes that bleed money silently)
None throw an error. They just quietly drop form completion — the most expensive silent leak in software.
*   **Placeholder as the only label.** The user types, the label's gone, they forget what the box wanted, they mistype, they bail. The #1 field conversion killer.
*   **Wrong keyboard on mobile.** A phone or code field that opens the full QWERTY instead of a keypad adds friction to every entry. `type`/`inputmode` fixes it in one attribute.
*   **iOS zoom-on-focus.** Sub-16px font makes Safari zoom and jump the layout on every field tap — feels broken. `font-size: 16px`.
*   **Over-eager validation.** Screaming "invalid email" while the user is still typing `jane@` — before they've finished — reads as hostile. Validate on blur, clear on fix.
*   **Rejecting valid input.** A phone field that won't accept spaces, a name field that rejects apostrophes (O'Brien), a password field with an undisclosed max length. Every false rejection is a lost user who _did nothing wrong_.
*   **Broken autofill.** Missing/wrong `autocomplete` means the browser can't fill saved data — turning a 4-second form into a 40-second one. Huge, invisible drag.
*   **No visible error, or error far from the field.** A red border with no text, or a summary at the top with no link to the field — the user can't find or fix the problem.
*   **Too many fields.** Every field is friction. Asking for what you don't need (or could derive) is the biggest lever you have and the easiest to ignore.
*   **Layout shift when errors appear.** The error text pushes everything down, the button moves, the user mis-clicks. Reserve the error slot's space.
*   **Premature disabling of submit** with no hint why — same trap as buttons; let them try and surface what's missing.

**The through-line:** these all fail _quietly_. No log, no crash — just a completion rate that's easy to blame on "the market." Audit your fields before you audit your ad spend.
* * *

## 13\. Advanced Patterns
Techniques that lean on the platform and the type system instead of custom JS.
*   **Constraint Validation API:** `pattern`, `min`/`max`, `step`, `checkValidity()`, `setCustomValidity()`, and the `:user-invalid` pseudo-class (styles only _after_ the user has interacted — no premature red) give real validation with near-zero JS.
*   **`autocomplete`** **tokens are a language:** `shipping street-address`, `billing postal-code`, `cc-exp`, `new-password`, `one-time-code`. Learn the vocabulary; it's what powers correct multi-address autofill.
*   **Type-enforced labelling:** as in §9.3, make `label` a required prop (or a discriminated union requiring `aria-label` when there's no visible label) so a label-less field can't compile.
*   **Design tokens, three tiers:** primitive (`--purple-800`) → semantic (`--color-border`, `--color-focus`, `--color-danger`) → component (`--input-border`, `--input-ring`). Rebrand or dark-mode by swapping tokens, never per-field CSS. Use OKLCH so hover/focus/disabled shades step perceptually evenly.
*   **`:has()`** **for field-level styling:** `.field:has(input:focus-within)` or `.field:has([aria-invalid=true])` styles the whole group (label + adornments) from the input's state — no JS state mirroring.
*   **Cross-field & async validation:** password-confirm matching, "username available?" checks — debounce the async ones, show a pending state, and _still_ re-check on the server.
*   **`aria-live`** **status for async:** a polite live region announces "username available" / "checking…" so screen-reader users get the same feedback the spinner gives sighted users.
*   **Progressive enhancement:** the field works as plain HTML with server validation before any JS loads; JS layers on the nicer inline experience. The form never _needs_ JS to submit.

## 14\. Performance & Bundle Cost
A field feels free. At scale it isn't.
*   **Controlled-input re-render cost.** A controlled field re-renders on _every keystroke_. One field, fine. A 40-field form where each keystroke re-renders the whole form is jank. Fix: uncontrolled inputs read on submit, or a form library (react-hook-form) that keeps inputs uncontrolled and subscribes surgically. This is the single biggest form perf lever.
*   **Debounce expensive reactions,** not the typing itself. Search-as-you-type, async availability checks, and live previews should debounce (250–400ms) so you fire one request per pause, not one per keystroke.
*   **Don't ship a masking/validation mega-library for one field.** `react-number-format` or `imask` for a card field is fine; pulling a full form framework for a single email input is waste. Match the tool to the surface.
*   **Icon-import trap** (same as buttons): `import { Search } from "lucide-react"`, never `import * as Icons` — the namespace import defeats tree-shaking and can add hundreds of KB for one magnifier.
*   **Animate only** **`transform`****/****`opacity`** on focus/float transitions — animating `height`/`padding`/`border-width` forces reflow every frame.
*   **`content-visibility`****/****`contain`** on large field-heavy forms lets the browser skip work for off-screen sections.

## 15\. Security (the input is your #1 attack surface)
A text input is the front line of untrusted data, so treat every value that crosses the wire as hostile until proven otherwise. Never trust client validation — `required`, `pattern`, and your client-side zod are UX conveniences an attacker skips by POSTing raw JSON with `curl`; validate, sanitize, and canonicalize on the server, because a rule that isn't enforced server-side isn't enforced. Parameterize every query — SQL, NoSQL, command, and LDAP alike — so the input value is always bound as data and never concatenated into executable code. When you echo a value back, encode it for its output context (React/Vue escape by default; never reach for `dangerouslySetInnerHTML`/`v-html` with user data) or you've shipped reflected or stored XSS. Bound length and rate on the server too — an unbounded text field is a cheap DoS and ReDoS vector, and a client `maxlength` does nothing to a scripted client. Type-specific surfaces carry their own risk: `type=url` and file-path fields are SSRF and path-traversal vectors that demand an allowlist plus normalization, and `type=email`/`tel` still need real server validation regardless of the browser's soft check. For sensitive inputs, keep `autocomplete` discipline (`new-password`/`current-password`, hand card data to a PCI tokenizer like Stripe Elements), never log raw values, and mask where the screen shouldn't hold the secret. The rule under all of these: client validation helps honest users; server validation stops attackers — they are different jobs and you need both.

## 16\. Senior-Level Checklist (ship-ready)
Before a field is "done":
- [ ] Real `<label>` associated by `for`/`id` (or wrapping) — every input, no exceptions.
- [ ] Placeholder is a hint on top of a label, never the label itself.
- [ ] Correct `type`, `inputmode`, and `autocomplete` all three set and aligned.
- [ ] `font-size: 16px+` on the control (no iOS zoom-on-focus).
- [ ] All states styled: focus-visible, filled, disabled, read-only, invalid, valid, loading.
- [ ] Errors wired: `aria-invalid` + `aria-describedby` + `role="alert"`; color never alone.
- [ ] Validate on blur, clear on fix; required-empty only flagged on submit; focus moves to first error.
- [ ] Controlled OR uncontrolled — not both; `value` never `undefined`.
- [ ] Masked fields store the unmasked value and preserve caret on edit/paste.
- [ ] Contrast ≥ 4.5:1 for text/label/placeholder, 3:1 for border; target ≥ 44px.
- [ ] Server re-validates every rule, uses parameterized queries, encodes output (XSS), bounds length, and never trusts the client.
- [ ] Error slot space reserved (no layout shift); ask the minimum number of fields.

## 17\. Visual Styles (the same field, eleven aesthetics)
Design systems are _whose_ rules; visual styles are _which look_. The same semantic field — real label, correct `type`, visible focus, wired errors, 44px target — can wear any of these skins. Style is skin; the skeleton never changes.
*   **Flat:** solid border, crisp corners, no shadow. The border thickens or recolors on focus. Reads instantly; the safe default for dense/data forms.
*   **Material:** filled or outlined field, animated floating label parking in the outline notch, bottom-line accent on focus, helper/counter slots below.
*   **Glassmorphism:** translucent field with `backdrop-filter: blur()` over a vivid background. Rare for inputs — guard text and border contrast hard, it's the first thing that fails.
*   **Liquid Glass (2026):** Apple's iOS 26 / macOS Tahoe material — the field on refractive translucent glass with a specular rim and subtle sheen. Sings over deep Eminence/Night. Web = honest approximation; SwiftUI emits native `.glassEffect()`. Guard contrast and `prefers-reduced-motion`.
*   **Neumorphism:** the input _inset_ into a same-color surface with dual light/dark inner shadows — the "pressed well" look. Pretty, contrast-poor; accent use only, never a whole form.
*   **Skeuomorphism:** inset bevel, inner top shadow, faint paper/linen texture — the "real recessed slot" look. Tactile, heavy.
*   **Neo-Brutalism:** thick black border, hard offset shadow, zero radius, a jarring focus color. High personality; test the focus contrast.
*   **Claymorphism:** big radius, soft inner top-light + bottom-shadow, puffy and friendly. Reads approachable; watch that the label stays high-contrast.
*   **Aurora / Gradient:** animated multi-hue gradient border or focus glow on dark. Premium; honor `prefers-reduced-motion` and keep the _inner_ field legible.
*   **Minimal / Swiss:** underline-only or hairline border, generous space, typography does the work. Excellent for long forms — calm and fast to scan.
*   **UJG Brand:** Goldenrod focus ring on a Platinum or deep-Eminence field, confident 8–10px radius, warm focus glow, neutrals tinted toward the purple hue. Labels in the display face, body in Urbanist. The house default.

**Rule that never changes:** the field's semantics, keyboard behavior, focus visibility, label association, error wiring, and 44px target stay identical across all eleven skins. Guard glass/liquid-glass/neu for contrast; guard aurora/liquid-glass for `prefers-reduced-motion`. Full guidance in the 🎨 [Design Styles (visual languages)](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200551) doc.

**Bottom line:** the text input is the smallest component with the highest stakes — it's where conversion is won or lost, where accessibility most often silently breaks, and where every attack on your system begins. Master the input/field distinction, the `type`+`inputmode`+`autocomplete` trio, controlled vs uncontrolled, the label-is-mandatory rule, error wiring via `aria-invalid`/`aria-describedby`, and the iron law that _client validation helps users while server validation stops attackers_, and you've mastered the foundation every other form control is built on.
