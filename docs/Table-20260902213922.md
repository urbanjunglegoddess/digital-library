# Table

# The Table: A Senior Engineer's Complete Breakdown
The oldest way to show structured truth on a screen — and the component juniors reach for to lay out a page, which is exactly the crime. Here's the semantic `<table>` from first principles to production code.

**Try it live:** every part of this doc — sortable headers, sticky rows, density toggles, the responsive collapse — will be wired up in the companion **Table playground**. It's built in a later pass, so for now read the code here as the source of truth; the playground will let you flip density, alignment, sort direction, and responsive strategy and watch the semantics hold across all targets, with one-click copy.

**Audit a table:** the companion **Table a11y audit** (later pass) will let you paste any table's markup and run live checks — is there a `<caption>`? do header cells use `scope`? is the sort state exposed with `aria-sort`? is a "responsive" table secretly a pile of `<div>`s? — then export a client-ready report.

One hard split before we start: **this doc is about the semantic data table** — the `<table>` element and everything that makes tabular data readable, sortable, and accessible. It is _not_ about the **Data Grid**, the interactive spreadsheet-style widget with inline editing, cell selection, virtualization, and frozen panes. That's a different beast with a different accessibility model (`role="grid"`, arrow-key cell navigation), and it has its own reference — see the [Data Grid doc](https://app.clickup.com/8495850/docs/838qa-81211/838qa-216791). When in doubt: if the user _reads and scans_, it's a Table; if the user _edits and navigates cell-by-cell like Excel_, it's a Data Grid.

Sibling references: [Button](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200231) · [Cards](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200471) · [Component Asset Template](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200531) · [Design Styles (visual languages)](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200551).

## 1\. What a Table Actually Is
A table presents data in a **two-dimensional relationship**: every cell is defined by the intersection of a row and a column, and its meaning comes from the header(s) that govern that row and column. That relationship — cell _belongs to_ this column header _and_ maybe this row header — is the entire point. If your data doesn't have that relationship, you don't have a table; you have a list wearing a grid.

Three things get lumped together and shouldn't be:
*   **Data table (****`<table>`****):** semantic HTML for presenting related data you _read and compare_. Rows are records, columns are fields. This doc. Static or lightly interactive (sort, paginate, select rows).
*   **Data grid (****`role="grid"`****):** an application widget that _behaves like a spreadsheet_ — focusable cells, arrow-key navigation, inline edit, virtualization, frozen panes, column resize/reorder as first-class interactions. Built on a table or on divs with grid roles. Its own doc.
*   **Layout table:** using `<table>` to _position_ page content (sidebar here, content there). **Dead. Do not.** We killed this in ~2010 with CSS, and it's an accessibility catastrophe — screen readers announce "table, 3 columns, 40 rows" over your marketing page. Use CSS Grid/Flexbox for layout, always.

The distinction that actually trips people: **a table is for tabular data, not for "things in a grid."** A photo gallery in a grid is not a table (no row/column _meaning_ — photo 5 isn't "in the March column"). A pricing comparison _is_ a table (each plan is a column, each feature a row, and the cell means "does this plan have this feature"). Ask: _does the cell's meaning depend on both its row and its column?_ Yes → table. No → list, grid of cards, or CSS layout.

Rule of thumb: **if a screen reader user would benefit from hearing "Revenue, Q3: $40,200" — column header plus row header plus value — it's a semantic table, and only** **`<table>`** **gives them that for free.**

## 2\. Why It Matters
Tables are where **decisions** get made. Dashboards, financial statements, admin panels, comparison pages, order histories — the table is the surface where a human looks at rows of reality and picks one. That makes it load-bearing in ways a marketing button never is.
*   **Comprehension is the conversion metric.** A table's job is to let someone find, compare, and trust a number _fast_. Misaligned columns, no visual rhythm, numbers that don't line up by decimal — every friction point adds scan time and doubt. On a pricing page, a confusing comparison table costs signups as directly as a broken CTA.
*   **It's an accessibility make-or-break.** A correct `<table>` with `<th scope>` and a `<caption>` lets a blind user navigate cell by cell and hear the relevant headers announced automatically. A "table" built from `<div>`s is a wall of unlabeled text — the single most common way data-heavy apps become unusable for screen-reader users. Get the semantics right and enormous accessibility comes free; fake them and no amount of ARIA fully rescues it.
*   **It carries data trust.** Right-aligned, tabular-figure numbers read as _engineered_; ragged, proportional-font numbers read as _sloppy_, and users extend that judgment to the data itself. A finance table that looks careless makes people distrust the underlying figures even when they're correct. Perceived rigor is mostly typographic discipline.

## 3\. Anatomy of a Table
The semantic `<table>` has a precise part list, and each part has a job. Most broken tables are broken because a part is missing or misused.
*   **`<table>`****\*\*\*\*\*\*\*\*:** the container. Establishes the row/column relationship model. Never for layout.
*   **`<caption>`****\*\*\*\*\*\*\*\*:** the table's accessible name and visible title, and it must be the **first child** of `<table>`. Screen readers announce it when the user enters the table ("Q3 Revenue by Region, table, 4 columns, 12 rows"). Skipping it is the most common a11y miss.
*   **`<thead>`****\*\*\*\*\*\*\*\*:** the header row group. Holds the column-header cells. Semantically distinct so it can repeat on print pagination and be styled/stuck independently.
*   **`<tbody>`****\*\*\*\*\*\*\*\*:** the body — the actual data rows. A table can have multiple `<tbody>` groups to segment data (e.g., by category) with a header row between.
*   **`<tfoot>`****\*\*\*\*\*\*\*\*:** the footer row group — totals, sums, aggregates. Semantically the summary of the columns above it. (In modern HTML it can go last in source and still render at the bottom.)
*   **`<tr>`****\*\*\*\*\*\*\*\*:** a table row — one record in the body, or one band of headers in the head.
*   **`<th>`****\*\*\*\*\*\*\*\*:** a header cell. Governs a column (`scope="col"`) or a row (`scope="row"`). Bold and centered by default; that's a hint, not the semantics — the semantics come from `scope`.
*   **`<td>`****\*\*\*\*\*\*\*\*:** a data cell — the actual value at a row/column intersection.
*   **`scope`****\*\*\*\*\*\*\*\*:** the attribute that wires a `<th>` to the cells it labels: `col`, `row`, `colgroup`, `rowgroup`. **This is the load-bearing accessibility attribute of the whole component.**
*   **`<colgroup>`** **/** **`<col>`****\*\*\*\*\*\*\*\*:** column-level grouping and styling hooks. Lets you style or span whole columns (width, background) without touching every cell, and semantically group columns.
*   **`headers`** **/** **`id`****\*\*\*\*\*\*\*\*:** the escape hatch for complex tables where `scope` isn't enough (multi-level headers) — each `<td>` lists the `id`s of every header that governs it.

For interactive tables, add: **sort buttons** inside `<th>` (with `aria-sort` on the `<th>`), a **selection column** (a leading `<th scope="col">` holding a "select all" checkbox, and `<td>` checkboxes per row), a **sticky header** region, and a **scroll container** with `role="region"` and a label.

## 4\. Density, Scale & Alignment
Tables live and die by rhythm. The numbers below are a sane starting scale — tie row height to a spacing token so the whole system scales, not to a magic number.

| Density | Row height | Cell padding (V × H) | Font | Use |
| ---| ---| ---| ---| --- |
| Compact | 32px | 6px × 12px | 13px | Dense dashboards, financial grids, power users |
| Default | 44px | 10px × 16px | 14px | Most admin UIs, general data |
| Comfortable | 56px | 16px × 20px | 15px | Marketing comparison tables, low-density reads |
| Touch | 48px+ | 12px × 16px | 16px | Mobile / touch-primary, ≥44px tap rows |

Alignment is not cosmetic — it's how a table becomes scannable:
*   **Numbers right-align.** Always. Right alignment lines up the ones, tens, hundreds so magnitudes are comparable at a glance. Left-aligned numbers are the #1 tell of an amateur data table.
*   **Use** **`font-variant-numeric: tabular-nums`** on numeric columns so every digit has equal width and columns of numbers line up perfectly, even in a proportional font. Pair with right alignment for currency/quantities.
*   **Text left-aligns** (in LTR). Names, descriptions, labels read from the left edge.
*   **Align headers to their data.** A right-aligned numeric column gets a right-aligned header. Mismatched header/data alignment reads as broken.
*   **Center only booleans/icons/status** — a checkmark, a status dot, a short badge. Never center-align running numbers or text.
*   **Decimal-align money** where possible (consistent decimal places + tabular-nums gives you this for free).

Density is a **user setting** in serious tools, not a fixed choice — power users want Compact, casual users want Comfortable. Offer a toggle; persist it. Zebra striping (alternating row backgrounds) helps horizontal tracking on wide tables, but it's optional and can be replaced by a hover row highlight, which many designers now prefer for cleaner tables.

## 5\. States (rows, cells, and the whole table)
A table has states at three levels — the table, the row, the cell — plus the async lifecycle. Missing states are where data tables feel broken.

**Table-level:**
1. **Default** — populated, resting.
2. **Loading (first load)** — no data yet. Show **skeleton rows** (shimmering placeholder rows that match the final column layout), _not_ a centered spinner that collapses the layout. Skeletons preserve dimensions and reduce perceived latency.
3. **Loading (refetch / sort / page change)** — data exists, new data coming. Keep the old rows, dim them or show a top progress bar, set `aria-busy="true"`. Never blank the table to a spinner on a re-sort.
4. **Empty (no data ever)** — a genuine empty state: illustration/icon, one line of explanation, and a primary action ("No invoices yet — Create your first invoice"). Never show bare column headers over a void.
5. **Empty (no results for filter)** — different message: "No results for 'xanadu' — Clear filters." Distinct from never-had-data, because the fix is different.
6. **Error** — the fetch failed. Show an inline error row/panel with a **Retry** action and keep the table chrome. Put `role="alert"` on that error row so screen-reader users hear the failure the moment it appears. Don't dump the user to a full-page error for a failed table load.

**Row-level:** default · **hover** (subtle background, aids tracking across a wide row) · **selected** (checkbox checked + tinted background + often a left accent bar) · **active/expanded** (row detail drawer open) · **disabled** (row not actionable) · **error/warning** (row failed validation or needs attention, flagged with color _and_ an icon, never color alone).

**Cell-level:** default · **editable-hover** (if lightly editable — though heavy editing means you want a Data Grid) · **focus** (keyboard focus ring on an interactive cell) · **invalid** (a cell whose value failed validation).

**Selection meta-states:** the "select all" header checkbox has three states — unchecked (nothing selected), checked (all selected), and **indeterminate** (some but not all selected). Indeterminate is set via the DOM property `el.indeterminate = true` (there is no HTML attribute for it) and must be paired with `aria-checked="mixed"`.

## 6\. Types & Variants
Same `<table>` skeleton, different jobs:
*   **Static data table:** read-only rows. Order history, a report, a schedule. No sort, no select.
*   **Sortable table:** column headers become sort controls. The workhorse admin table.
*   **Selectable table:** a checkbox column enabling bulk actions (delete, export, tag). Adds the select-all + indeterminate logic.
*   **Filterable/searchable table:** a toolbar above the table drives the visible rows. The table itself is unchanged; the data feeding it is filtered.
*   **Expandable-row table:** each row can expand to a detail panel (`aria-expanded` on the toggle, a spanning `<tr>` for the detail). Good for master/detail without leaving the page.
*   **Comparison table:** transposed mental model — _plans are columns, features are rows._ Common on pricing pages. Often uses `<th scope="row">` for the feature names down the left.
*   **Financial/summary table:** heavy `<tfoot>` use for totals; strict right-alignment and tabular-nums; often multi-`<tbody>` grouping by category with subtotals.
*   **Responsive/adaptive table:** one of the three responsive strategies in §7 kicks in below a breakpoint.
*   **Data grid (NOT this doc):** editable, virtualized, cell-navigable. When you need this, reach for TanStack Table + a virtualizer or AG Grid, and read the Data Grid reference.

## 7\. When to Use One (and the Responsive Problem)
Use a `<table>` when the cell's meaning depends on **both** its row and column and users need to **compare across rows or columns**. Don't use one when:
*   You're laying out a page → CSS Grid/Flexbox.
*   Each item is a self-contained object users browse, not compare field-by-field → a grid of **Cards**.
*   It's a single record's fields (one thing's properties) → a **description list** (`<dl>`) reads better than a 2-column table.
*   You have one column → that's a **list** (`<ul>`), not a table.

**The responsive problem is the hardest thing about tables.** A wide data table cannot physically fit a 375px phone. There is no free lunch — you pick a strategy per table based on what the user needs to _do_:

1. **Horizontal scroll (the honest default).** Wrap the table in a scroll container and let it scroll sideways. Preserves the real table — all relationships intact — and is the _only_ strategy that keeps cross-column comparison. The must-do: make the container a **labelled, focusable, keyboard-scrollable region** so keyboard and screen-reader users can reach the overflow (see §9.4/§10). Optionally freeze the first column so row identity stays visible while scrolling. Best for: dense data, power users, when comparison matters.
2. **Stacked cards (collapse to blocks).** Below a breakpoint, each row becomes a vertical card: every cell stacks with its column header shown as an inline label (via CSS `::before` from a `data-label`, or a real restructure). Readable on phones, but you **lose column-to-column comparison** — you can't scan a column anymore. Best for: browse-y data where users read one record at a time (orders, contacts). Watch the a11y trap: pure-CSS `display: block` on table elements _destroys the table semantics_ — screen readers stop announcing it as a table. Accept that tradeoff knowingly, or use `role` overrides carefully.
3. **Priority columns (hide + expand).** Show only the 2–3 most important columns on narrow screens; hide the rest behind a per-row expand toggle that reveals them. Keeps a scannable table _and_ full data on demand. More engineering. Best for: tables with a clear priority order (name + status always visible; metadata on expand).

Pick deliberately. The wrong pick — e.g., stacked cards for a financial comparison table — actively destroys the table's purpose. When comparison across rows is the _point_, horizontal scroll wins; when reading one record at a time is the point, stacked cards win.

## 8\. Tables Across Design Systems
Same semantics, very different defaults. Knowing these makes you fluent in any codebase.
*   **Material Design (Google):** Data tables are a first-class spec — 56px header / 52px rows, checkbox selection column, sort arrows that appear on header hover, and a distinct emphasis between "data table" and their heavier grid. Text left, numbers right is baked into the guidance.
*   **Apple HIG:** Less about web `<table>`, more about `List`/`Table` in SwiftUI. macOS `Table` is a true multi-column sortable control; iOS leans on grouped lists (the stacked-card model) because phones can't hold wide tables. HIG's instinct: on small screens, _don't_ show a wide table — restructure.
*   **Fluent (Microsoft):** Ships both a `Table` (simpler, semantic) and a `DataGrid` (interactive) — and is explicit about choosing between them, which is exactly the distinction this doc draws. Compact density by default; enterprise data focus.
*   **Ant Design / enterprise:** The heavyweight. `Table` with built-in sorting, filtering, pagination, row selection, expandable rows, fixed columns, and virtualization props out of the box. Optimized for dense admin dashboards; opinionated look. This is where most "just give me a working data table" enterprise apps land.
*   **Tailwind / utility-first:** No prescribed table look — you compose it. Tailwind's own UI kit shows the canonical pattern (overflow wrapper, `divide-y`, sticky header). Freedom plus the responsibility to get semantics and a11y right yourself.
*   **shadcn/Radix:** shadcn ships a styled `Table` (thin wrappers over `<table>`/`<thead>`/`<tr>`/`<td>`) and pairs it with **TanStack Table** for the logic (sorting, filtering, pagination, selection) — headless behavior + owned styling. The 2024+ web default for React data tables.
*   **Bootstrap:** `.table` and modifier classes (`.table-striped`, `.table-hover`, `.table-sm`, `.table-bordered`, `.table-responsive` wrapper). Instant, conventional, accessible-enough tables with zero custom CSS. Convention over ownership.

The style is a skin; the `<thead>`/`<th scope>`/`<caption>` skeleton underneath never changes. See §17 for the full walk. The rule that never changes: **semantics, keyboard navigation, focus rings, sort exposure, and the 44px row target are identical across all eleven** — you're only changing paint. ### What's trending in 2026
Tables are having a quiet renaissance. The dominant threads this year:
*   **AI-native tables:** natural-language query bars above the grid ("show me overdue invoices > $1k"), AI-generated summary rows, per-column "explain this trend" affordances, and streaming/skeleton states as the AI populates cells. The table is becoming a conversational surface, not just a static readout.
*   **Sub-grid and container queries:** CSS `subgrid` lets nested content align to the parent table's column tracks, and `@container` queries let a table choose its responsive strategy based on _its own_ width, not the viewport — so the same table component adapts correctly in a narrow sidebar and a wide main pane.
*   **`<selectlist>`****\*\*\*\*\*\*\*\*/customizable controls** landing in inline-edit cells, and native CSS `:has()` powering row-hover and selection styling with zero JS.
*   **Liquid Glass headers:** sticky `<thead>` rendered as Apple's iOS 26 / macOS Tahoe refractive glass — translucent, with a specular rim — floating over scrolling rows. Gorgeous on dark, dense data. Honor contrast and reduced-motion.
*   **Density and personalization as standard:** users expect to pick density, reorder/hide columns, and have it persist — table state is user state now.

**For UJG:** lean sticky-header tables toward a Liquid Glass or deep-Eminence header bar with Goldenrod sort indicators; keep Flat/Swiss for the dense Data Alchemy dashboards where scan speed beats decoration; reserve zebra striping for genuinely wide financial tables. Accessibility caveats hold no matter how on-trend the skin: contrast, reduced-motion, and real `<th scope>` semantics are non-negotiable.

## 9\. The Code
### 9.1 Semantic HTML (master this before anything else)
The foundation. If this isn't right, no framework saves you.

```plain
<table>
  <caption>Q3 2026 Revenue by Region</caption>

  <colgroup>
    <col />
    <col span="3" class="num-cols" />
  </colgroup>

  <thead>
    <tr>
      <th scope="col">Region</th>
      <th scope="col">July</th>
      <th scope="col">August</th>
      <th scope="col">September</th>
    </tr>
  </thead>

  <tbody>
    <tr>
      <th scope="row">North America</th>
      <td>$40,200</td>
      <td>$42,800</td>
      <td>$45,100</td>
    </tr>
    <tr>
      <th scope="row">Europe</th>
      <td>$28,400</td>
      <td>$30,100</td>
      <td>$31,900</td>
    </tr>
  </tbody>

  <tfoot>
    <tr>
      <th scope="row">Total</th>
      <td>$68,600</td>
      <td>$72,900</td>
      <td>$77,000</td>
    </tr>
  </tfoot>
</table>
```

Key HTML rules — the ones audits catch:
*   **`<caption>`** **is first, always.** It's the table's accessible name. Visually hide it if the design has a heading elsewhere, but keep it in the DOM.
*   **Column headers get** **`scope="col"`****\*\*\*\*\*\*\*\*; the first cell of each data row is a** **`<th scope="row">`**, not a `<td>`. That row-header is what lets a screen reader say "North America, July, $40,200." Most tables forget it and every value is announced context-free.
*   **`<thead>`****/****`<tbody>`****/****`<tfoot>`** are not decoration — they're the semantic groups. `<tfoot>` for totals is announced as summary data.
*   **Never** use `<table>` for layout, and never fake a table with `<div>`s unless you fully re-implement the roles (see §9 web-component note and §10).
*   For **multi-level headers** where `scope` can't express the relationship, switch to `id` + `headers`:

```plain
<th id="h-q3" colspan="2" scope="colgroup">Q3</th>
...
<td headers="h-q3 h-jul">$40,200</td>
```

### 9.2 CSS (alignment, density, zebra, sticky — done right)
The CSS that turns a raw table into a readable one.

```css
table {
  border-collapse: collapse;   /* single crisp borders, not doubled */
  width: 100%;
  font: 14px/1.4 system-ui, sans-serif;
}
caption {
  text-align: left;
  font-weight: 600;
  padding-block: 12px;
  color: #E8E6E1;
}
th, td {
  padding: 10px 16px;
  text-align: left;              /* default: text left */
  border-bottom: 1px solid #2a2333;
}
thead th {
  position: sticky;              /* sticky header */
  top: 0;
  background: #1a1523;
  z-index: 2;
  font-weight: 600;
  white-space: nowrap;
}

/* Numbers: right-align + tabular figures so digits line up */
.num, td.num, th.num {
  text-align: right;
  font-variant-numeric: tabular-nums;
}

/* Zebra striping (optional) */
tbody tr:nth-child(even) { background: rgba(255,255,255,0.03); }

/* Hover row highlight — often better than zebra */
tbody tr:hover { background: rgba(220,164,36,0.08); }

/* Selected row */
tbody tr[aria-selected="true"] {
  background: rgba(95,44,130,0.18);
  box-shadow: inset 3px 0 0 #DCA424;   /* left accent bar */
}

/* Density variants driven by a class on the table */
.density-compact th, .density-compact td { padding: 6px 12px; }
.density-comfy   th, .density-comfy   td { padding: 16px 20px; }
```

**Sticky first column** (freeze row identity while scrolling horizontally) needs the column to be sticky on _both_ axes — and the intersection cell to sit above both:

```css
th[scope="row"], td.rowhead {
  position: sticky;
  left: 0;
  background: #1a1523;   /* opaque, or scrolling cells show through */
  z-index: 1;
}
thead th:first-child {
  z-index: 3;            /* the corner cell beats both sticky axes */
}
```

The silent sticky bug: a sticky cell with a _transparent_ background lets the scrolling content bleed through it. Sticky cells must be opaque. Two more gotchas that make sticky "just stop working" in real layouts: an `overflow: hidden/auto/scroll` on any _ancestor_ between the sticky cell and the intended scroll container silently kills it (sticky positions relative to the nearest scrolling ancestor); and on long financial tables you can pin the summary row too — `tfoot th, tfoot td { position: sticky; bottom: 0; }` (same opaque-background rule) so running totals stay visible as rows scroll.

### 9.3 Sortable, accessible Table — React + TypeScript
The centerpiece. A real reusable, generically-typed, sortable, selectable, accessible table. This is the senior version, not the junior one.

```typescript
import { useMemo, useState, useCallback, useRef, useEffect } from "react";

type SortDir = "ascending" | "descending" | "none";

interface Column<T> {
  key: keyof T & string;
  header: string;
  numeric?: boolean;                 // drives right-align + tabular-nums
  sortable?: boolean;
  render?: (row: T) => React.ReactNode;
}

interface DataTableProps<T extends { id: string }> {
  caption: string;
  columns: Column<T>[];
  rows: T[];
  selectable?: boolean;
  onSelectionChange?: (ids: string[]) => void;
}

export function DataTable<T extends { id: string }>({
  caption, columns, rows, selectable = false, onSelectionChange,
}: DataTableProps<T>) {
  const [sortKey, setSortKey] = useState<keyof T & string | null>(null);
  const [sortDir, setSortDir] = useState<SortDir>("none");
  const [selected, setSelected] = useState<Set<string>>(new Set());

  const sorted = useMemo(() => {
    if (!sortKey || sortDir === "none") return rows;
    const dir = sortDir === "ascending" ? 1 : -1;
    return [...rows].sort((a, b) => {
      const av = a[sortKey], bv = b[sortKey];
      if (av === bv) return 0;
      return (av > bv ? 1 : -1) * dir;
    });
  }, [rows, sortKey, sortDir]);

  const toggleSort = useCallback((key: keyof T & string) => {
    if (sortKey !== key) { setSortKey(key); setSortDir("ascending"); return; }
    // cycle: ascending -> descending -> none
    setSortDir(d => d === "ascending" ? "descending"
                  : d === "descending" ? "none" : "ascending");
  }, [sortKey]);

  const allSelected = selected.size === rows.length && rows.length > 0;
  const someSelected = selected.size > 0 && !allSelected;

  const toggleAll = () => {
    const next = allSelected ? new Set<string>() : new Set(rows.map(r => r.id));
    setSelected(next); onSelectionChange?.([...next]);
  };
  const toggleRow = (id: string) => {
    const next = new Set(selected);
    next.has(id) ? next.delete(id) : next.add(id);
    setSelected(next); onSelectionChange?.([...next]);
  };

  return (
    <div className="table-scroll" role="region" aria-label={caption} tabIndex={0}>
      <table>
        <caption>{caption}</caption>
        <thead>
          <tr>
            {selectable && (
              <th scope="col" className="select-col">
                <SelectAll checked={allSelected} indeterminate={someSelected}
                           onChange={toggleAll} label="Select all rows" />
              </th>
            )}
            {columns.map(col => {
              const active = sortKey === col.key;
              const ariaSort: SortDir = active ? sortDir : "none";
              return (
                <th key={col.key} scope="col"
                    aria-sort={col.sortable ? ariaSort : undefined}
                    className={col.numeric ? "num" : undefined}>
                  {col.sortable ? (
                    <button type="button" className="sort-btn"
                            onClick={() => toggleSort(col.key)}>
                      {col.header}
                      <SortIcon dir={active ? sortDir : "none"} />
                    </button>
                  ) : col.header}
                </th>
              );
            })}
          </tr>
        </thead>
        <tbody>
          {sorted.map(row => {
            const isSel = selected.has(row.id);
            // human-readable row identity = the first (primary) column's value
            const rowLabel = String(row[columns[0].key]);
            return (
              <tr key={row.id} aria-selected={selectable ? isSel : undefined}>
                {selectable && (
                  <td className="select-col">
                    <input type="checkbox" checked={isSel}
                           onChange={() => toggleRow(row.id)}
                           aria-label={`Select row ${rowLabel}`} />
                  </td>
                )}
                {columns.map((col, i) => {
                  const content = col.render ? col.render(row) : String(row[col.key]);
                  // The first data column is ALWAYS the row header — gated on
                  // position, not selection. The checkbox <td> sits before it,
                  // so a selectable row is <td checkbox> + <th scope="row"> + <td>…
                  return i === 0
                    ? <th key={col.key} scope="row"
                          className={col.numeric ? "num" : undefined}>{content}</th>
                    : <td key={col.key}
                          className={col.numeric ? "num" : undefined}>{content}</td>;
                })}
              </tr>
            );
          })}
        </tbody>
      </table>
    </div>
  );
}

// Select-all checkbox: indeterminate is a DOM property, not an attribute
function SelectAll({ checked, indeterminate, onChange, label }: {
  checked: boolean; indeterminate: boolean; onChange: () => void; label: string;
}) {
  const ref = useRef<HTMLInputElement>(null);
  useEffect(() => { if (ref.current) ref.current.indeterminate = indeterminate; },
            [indeterminate]);
  return <input ref={ref} type="checkbox" checked={checked}
                onChange={onChange} aria-label={label}
                aria-checked={indeterminate ? "mixed" : checked} />;
}

function SortIcon({ dir }: { dir: SortDir }) {
  return <span aria-hidden="true">
    {dir === "ascending" ? " ▲" : dir === "descending" ? " ▼" : " ⇅"}
  </span>;
}
```

Why this is the senior version:
*   **`aria-sort`** **lives on the** **`<th>`**, and only on the _active_ column, with the value cycling `ascending → descending → none`. Screen readers announce "sorted ascending" when the user lands on that header. This is the single most-forgotten sort accessibility detail.
*   **The sort control is a real** **`<button>`** inside the `<th>`\*\* — not an `onClick` on a `<div>`. Keyboard-operable and announced as a button for free.
*   **The first data column is a** **`<th scope="row">`** so each row has a header, and rows are announced with their identity. The row-header is gated on _column position_ (`i === 0`), not on `selectable` — so turning selection on adds a leading checkbox `<td>` without demoting the row header to a plain cell. The per-row checkbox `aria-label` uses that same primary-column value ("Select row Acme Co"), never the opaque `row.id`.
*   **`indeterminate`** **is set imperatively** (`ref.current.indeterminate`) because there is no HTML attribute for it, and paired with `aria-checked="mixed"`.
*   **Generic** **`<T extends { id: string }>`** gives type-safe columns (`key` must be a real field) and a stable React key.
*   **`useMemo`** **on the sort** so re-renders don't re-sort unnecessarily; sorting a _copy_ (`[...rows]`) so we never mutate props.

### 9.4 The Scroll-Region wrapper & responsive CSS
The horizontal-scroll strategy done accessibly, plus the stacked-card collapse.

**Focusable, labelled scroll region** (so keyboard users can reach overflow):

```css
.table-scroll {
  overflow-x: auto;
  -webkit-overflow-scrolling: touch;
  scrollbar-gutter: stable;
}
.table-scroll:focus-visible {
  outline: 2px solid #DCA424;
  outline-offset: 2px;

```

The `role="region"` + `aria-label` + `tabIndex={0}` in §9.3 is what makes this real: a keyboard user can Tab to the container and scroll it with arrow keys, and a screen reader announces it as a named region. A bare `overflow-x:auto` div is a keyboard trap-in-reverse — the overflow is unreachable without a mouse.

**Stacked-card collapse** (below a breakpoint each row becomes a labelled block):

```css

  table, thead, tbody, th, td, tr { display: block; }
  thead { position: absolute; left: -9999px; }   /* hide real header row */
  tr { margin-bottom: 12px; border: 1px solid #2a2333; border-radius: 8px; }
  td {
    display: flex; justify-content: space-between; gap: 16px;
    border: none; border-bottom: 1px solid #2a2333;
  }

    font-weight: 600; color: #DCA424;

```

```plain
<td data-label="August">$42,800</td>   <!-- data-label feeds the ::before -->
```

**Caveat:** the fragment above is a single _value_ cell shown only to illustrate `data-label` → `::before`. It is not a full row. In a real row the first (row-identifying) cell is still `<th scope="row">` — e.g. `<th scope="row" data-label="Region">North America</th>` — and it gets a `data-label` too so its column name shows in the stacked-card layout. Don't read this one-line snippet as license to make every cell a `<td>`.

**The honest caveat:** `display: block` on table elements _strips the table semantics_ — the browser stops exposing it as a table to assistive tech. For a browse-one-record-at-a-time table that's an acceptable trade; for data where comparison matters, prefer horizontal scroll. If you need block layout _and_ semantics, re-assert roles (`role="table"`, `role="row"`, `role="cell"`) — but that's fragile, and a sign you might want the scroll strategy instead. Container queries (`@container`) are the modern upgrade so the table adapts to _its_ width, not the viewport's.

### 9.5 TanStack Table (the headless logic layer)
For anything beyond a static table, don't hand-roll sorting/filtering/pagination/selection — use **TanStack Table** (v8, framework-agnostic, headless). It owns the _logic and state_; you own the markup and styles (so all the semantics above stay yours).

```typescript
import {
  useReactTable, getCoreRowModel, getSortedRowModel,
  getPaginationRowModel, flexRender, type ColumnDef, type SortingState,

import { useState } from "react";

  { accessorKey: "status", header: "Status" },

export function InvoiceTable({ data }: { data: Invoice[] }) {

    getPaginationRowModel: getPaginationRowModel(),
  });

  return (
    <table>
      <caption>Invoices</caption>
      <thead>
        {table.getHeaderGroups().map(hg => (
          <tr key={hg.id}>
            {hg.headers.map(h => {
              const sorted = h.column.getIsSorted(); // 'asc' | 'desc' | false
              return (
                <th key={h.id} scope="col"
                    aria-sort={sorted === "asc" ? "ascending"
                             : sorted === "desc" ? "descending" : "none"}

            })}
          </tr>
        ))}

          <tr key={row.id}>

              // header (<th scope="row">), every other cell is a <td>.

That's why it's the shadcn default: **you keep the semantic** **`<table>`** **and the a11y, it keeps the state machine.** When your needs outgrow it (huge datasets, complex editing, frozen panes out of the box), that's the Data Grid conversation — AG Grid, Glide Data Grid — and the Data Grid doc.

### 9.6 Column resizing (the basics)
Resizable columns = a draggable handle on the right edge of each header that adjusts that column's width. The mechanics:
*   Put a grabber element in each `<th>`; on `pointerdown` record the start X and start width; on `pointermove` set the column width to `startWidth + (currentX - startX)`; on `pointerup` release.
*   Apply width via a `<col>` in `<colgroup>` or a CSS variable per column — cheaper than restyling every cell.
*   `table-layout: fixed` makes resizing predictable (column widths honored exactly instead of content-driven auto sizing).
*   Enforce a `min-width` so a column can't collapse to nothing.
*   Persist widths to `localStorage`/user prefs — resized columns are user state.

```typescript
function useColumnResize(startWidth: number, onResize: (w: number) => void) {
  return (e: React.PointerEvent) => {
    const startX = e.clientX;
    const move = (m: PointerEvent) =>
      onResize(Math.max(64, startWidth + (m.clientX - startX)));  // 64px min
    const up = () => {
      document.removeEventListener("pointermove", move);
      document.removeEventListener("pointerup", up);
    };
    document.addEventListener("pointermove", move);
    document.addEventListener("pointerup", up);
    (e.target as Element).setPointerCapture?.(e.pointerId);
  };
}
```

TanStack Table has column resizing built in (`enableColumnResizing`, `columnSizing` state) — reach for it rather than hand-rolling once you're past a couple of columns. Full drag-reorder + resize + virtualization at once is, again, the Data Grid tier.

### 9.7 Pagination vs. infinite scroll (hooking up large data)
A table over 50-ish rows needs a strategy for _not_ rendering everything. Three, and they're not interchangeable:

*   **Pagination:** fixed page size, page controls below the table. **Best for tables** — it gives a stable, addressable position ("page 3"), works with the browser back button, is keyboard-simple, and is easy to make accessible. Server-side pagination (the server returns only the page) is mandatory once data is large. Announce page changes to `aria-live`.
*   **Infinite scroll:** load more rows as the user nears the bottom (IntersectionObserver on a sentinel). Good for _feeds_, risky for _tables_ — you lose "where am I," footers become unreachable, and screen-reader users get a moving target. If you must, pair it with a "Load more" button as the accessible fallback and keep total-count context.
*   **Virtualization:** render only the visible rows (windowing) while keeping the scrollbar sized for the full set. This is a _rendering_ optimization orthogonal to the two above — you can paginate _and_ virtualize. Virtualized rows complicate a11y (rows enter/leave the DOM), which is one reason heavy virtualization pushes you toward Data Grid territory.

```typescript
// Pagination controls with an aria-live announcement
<nav aria-label="Table pagination">
  <button onClick={prev} disabled={page === 1}>Previous</button>
  <span aria-live="polite">Page {page} of {totalPages}</span>
  <button onClick={next} disabled={page === totalPages}>Next</button>
</nav>
```

```typescript
// Infinite-scroll sentinel (IntersectionObserver) — feeds, not comparison tables
const sentinel = useRef<HTMLTableRowElement>(null);
useEffect(() => {
  const io = new IntersectionObserver(([e]) => e.isIntersecting && loadMore(), {
    rootMargin: "200px",

  if (sentinel.current) io.observe(sentinel.current);
  return () => io.disconnect();
}, [loadMore]);

### 9.8 The Backend (the endpoint behind a server-driven table)
Any real table over meaningful data is **server-driven**: the server does the sorting, filtering, and paging and returns one page. The frontend sends its table state; the endpoint answers with rows + a total count.

```typescript
// GET /api/invoices?sort=amount&dir=desc&page=2&pageSize=25&status=overdue
import { z } from "zod";

const Query = z.object({
  sort: z.enum(["client", "amount", "status"]).default("client"),
  dir:  z.enum(["asc", "desc"]).default("asc"),
  page: z.coerce.number().int().positive().default(1),
  pageSize: z.coerce.number().int().min(1).max(100).default(25), // cap the page size
  status: z.string().optional(),
});

app.get("/api/invoices", requireAuth, async (req, res) => {
  const q = Query.safeParse(req.query);
  if (!q.success) return res.status(422).json(q.error.issues);
  const { sort, dir, page, pageSize, status } = q.data;

  // allow-list the sort column — NEVER interpolate req.query into SQL
  const orderBy = { [sort]: dir };            // sort is a validated enum, safe
  const where = { orgId: req.user.orgId, ...(status ? { status } : {}) };

  const [rows, total] = await Promise.all([
    db.invoice.findMany({ where, orderBy,
      skip: (page - 1) * pageSize, take: pageSize }),
    db.invoice.count({ where }),
  ]);

  res.json({ rows, total, page, pageSize });   // total powers the pager
});
```

Backend rules a table silently depends on:
*   **Allow-list the sort column and direction.** A sort param that flows into `ORDER BY` is a SQL-injection and info-disclosure vector if you interpolate it. Validate against an enum of real columns — exactly as above.
*   **Always scope by tenant/user** (`orgId`). A table endpoint that forgets the `WHERE orgId = …` leaks other customers' rows — a classic broken-access-control bug (OWASP A01). The UI showing only your rows is _not_ a boundary.
*   **Cap** **`pageSize`****\*\*\*\*\*\*\*\*.** Uncapped, `?pageSize=1000000` is a cheap denial-of-service and a data-exfiltration lever.
*   **Return the total count** so the client can render "Page 2 of 40" and disable Next correctly. For huge tables use keyset/cursor pagination (`WHERE id > lastId`) instead of `OFFSET`, which degrades on deep pages.
*   **Sorting must be stable** — add a tiebreaker (usually `id`) so equal values don't reshuffle between pages.

### 9.9 Vanilla JS (sort + select, no framework)
The building block frameworks abstract. Delegate one listener for sorting, one for selection.

```javascript
const table = document.querySelector("#data");

// Sorting via delegation on the header
table.querySelector("thead").addEventListener("click", (e) => {
  const btn = e.target.closest("button[data-sort]");
  if (!btn) return;
  const th = btn.closest("th");
  const key = btn.dataset.sort;
  const current = th.getAttribute("aria-sort") || "none";
  const next = current === "ascending" ? "descending" : "ascending";

  // reset all headers, then set this one — only one active sort
  table.querySelectorAll("th[aria-sort]").forEach(h => h.setAttribute("aria-sort", "none"));
  th.setAttribute("aria-sort", next);

  const tbody = table.tBodies[0];
  const rows = [...tbody.rows];
  const dir = next === "ascending" ? 1 : -1;
  rows.sort((a, b) => {
    const av = a.querySelector(`[data-col="${key}"]`).textContent.trim();
    const bv = b.querySelector(`[data-col="${key}"]`).textContent.trim();
    const na = parseFloat(av.replace(/[^0-9.-]/g, ""));
    const nb = parseFloat(bv.replace(/[^0-9.-]/g, ""));
    const cmp = !isNaN(na) && !isNaN(nb) ? na - nb : av.localeCompare(bv);
    return cmp * dir;
  });
  rows.forEach(r => tbody.appendChild(r));   // re-append in sorted order
});

// Select-all with indeterminate
const selectAll = table.querySelector("#select-all");
selectAll.addEventListener("change", () => {
  // Toggling select-all is a definitive all-on/all-off action, so clear the
  // control's OWN indeterminate flag and re-assert aria-checked to a boolean —
  // otherwise a checkbox left "mixed" keeps that state after the user resolves it.
  selectAll.indeterminate = false;
  selectAll.setAttribute("aria-checked", String(selectAll.checked));
  table.querySelectorAll("tbody input[type=checkbox]")
       .forEach(cb => { cb.checked = selectAll.checked; syncRow(cb); });
});
table.tBodies[0].addEventListener("change", (e) => {
  if (e.target.matches("input[type=checkbox]")) {
    const boxes = [...table.querySelectorAll("tbody input[type=checkbox]")];
    const checked = boxes.filter(b => b.checked).length;
    const partial = checked > 0 && checked < boxes.length;
    selectAll.checked = checked === boxes.length;
    selectAll.indeterminate = partial;
    // aria-checked must mirror the tri-state: "mixed" for partial, else boolean.
    selectAll.setAttribute("aria-checked", partial ? "mixed" : String(selectAll.checked));
  }
});
```

### 9.13 Python (backend + a server-rendered table)
**Backend** (FastAPI) — the paged, sorted, validated endpoint:

```python
from fastapi import FastAPI, Depends, HTTPException, Query
from enum import Enum

app = FastAPI()

class SortCol(str, Enum):     # allow-list, mirrors the TS enum
    client = "client"; amount = "amount"; status = "status"

@app.get("/api/invoices")
def list_invoices(
    sort: SortCol = SortCol.client,
    dir: str = Query("asc", pattern="^(asc|desc)$"),
    page: int = Query(1, ge=1),
    page_size: int = Query(25, ge=1, le=100),   # capped
    user=Depends(require_auth),
):
    order = f"{sort.value} {'DESC' if dir == 'desc' else 'ASC'}, id ASC"  # stable tiebreak
    rows = db.query(
        "SELECT * FROM invoices WHERE org_id = %s "
        f"ORDER BY {order} LIMIT %s OFFSET %s",
        (user.org_id, page_size, (page - 1) * page_size),   # org scope enforced
    )
    total = db.scalar("SELECT count(*) FROM invoices WHERE org_id = %s", (user.org_id,))
    return {"rows": rows, "total": total, "page": page, "page_size": page_size}
```

Note `sort` is an `Enum` so it can _only_ be a real column — the `f"ORDER BY {order}"` is safe because `order` is built from validated enum values, never raw input. The parameterized `%s` protects the data values.

@Component({

### 9.16 Web Component (framework-agnostic)
Wrapping a table in a custom element that light-DOM-projects real `<tr>`/`<td>` so semantics survive. **Do not** put table rows behind a shadow boundary that breaks the `<table>` parse — project them.

```typescript
class SortableTable extends HTMLElement {
  connectedCallback() {
    // enhance the light-DOM <table> the author wrote — don't replace it
    const table = this.querySelector("table");
    if (!table) return;
    table.querySelectorAll("th[data-sortable]").forEach((th) => {
      const btn = document.createElement("button");
      btn.type = "button";
      btn.textContent = th.textContent!;
      btn.addEventListener("click", () => this.sort(th as HTMLTableCellElement));
      th.textContent = "";
      th.append(btn);
      th.setAttribute("aria-sort", "none");
    });
  }
  sort(th: HTMLTableCellElement) {
    const dir = th.getAttribute("aria-sort") === "ascending" ? "descending" : "ascending";
    this.querySelectorAll("th[aria-sort]").forEach(h => h.setAttribute("aria-sort", "none"));
    th.setAttribute("aria-sort", dir);
    /* reorder rows in the light-DOM tbody */
  }
}
customElements.define("sortable-table", SortableTable);
// <sortable-table><table>…real semantic markup…</table></sortable-table>
```

The lesson: for tables, the _progressive-enhancement_ web-component pattern (wrap and enhance real markup) beats the _shadow-DOM-render_ pattern, because a `<table>` split across a shadow boundary loses its semantics. Enhance, don't replace.

### 9.18 Testing (behavior + a11y, incl. axe on table semantics)
Test the _relationships and behavior_, not the class names. A table's correctness is: right headers, right scope, sort state exposed, selection works, and it passes an automated semantics scan.

**Unit / component (Vitest + Testing Library):**

```typescript
import { render, screen, within } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { axe } from "jest-axe";
import { DataTable } from "./DataTable";

const cols = [
  { key: "client", header: "Client" },
  { key: "amount", header: "Amount", numeric: true, sortable: true },
];
const rows = [{ id: "1", client: "Acme", amount: 300 },
              { id: "2", client: "Beta", amount: 100 }];

describe("DataTable", () => {
  it("exposes a table with an accessible name (caption)", () => {
    render(<DataTable caption="Invoices" columns={cols} rows={rows} />);
    expect(screen.getByRole("table", { name: /invoices/i })).toBeInTheDocument();
  });

  it("marks column headers with the right role and count", () => {
    render(<DataTable caption="Invoices" columns={cols} rows={rows} />);
    expect(screen.getAllByRole("columnheader")).toHaveLength(2);
  });

  it("sorts when a header button is activated and exposes aria-sort", async () => {
    render(<DataTable caption="Invoices" columns={cols} rows={rows} />);
    const amountHeader = screen.getByRole("columnheader", { name: /amount/i });
    await userEvent.click(within(amountHeader).getByRole("button"));
    expect(amountHeader).toHaveAttribute("aria-sort", "ascending");
    // first body row is now the smallest amount
    const firstRow = screen.getAllByRole("row")[1];
    expect(within(firstRow).getByText("100")).toBeInTheDocument();
  });

  it("has no axe-detectable table a11y violations", async () => {
    const { container } = render(
      <DataTable caption="Invoices" columns={cols} rows={rows} />);
    expect(await axe(container)).toHaveNoViolations();
  });
});
```

**What axe checks on a table** (and why you run it): every `<td>` is associated with a header, `<th>` cells have `scope` or are otherwise resolvable, the table isn't used for layout without `role="presentation"`, and no empty header cells orphan a column. It catches the exact relationship bugs that are invisible on screen but fatal to a screen-reader user.

**E2E (Playwright):**

```typescript
import { test, expect } from "@playwright/test";
import AxeBuilder from "@axe-core/playwright";

test("sortable table sorts and stays accessible", async ({ page }) => {
  await page.goto("/invoices");
  const table = page.getByRole("table", { name: "Invoices" });
  await table.getByRole("button", { name: "Amount" }).click();
  await expect(page.getByRole("columnheader", { name: "Amount" }))
    .toHaveAttribute("aria-sort", "ascending");
  const results = await new AxeBuilder({ page }).include("table").analyze();
  expect(results.violations).toEqual([]);
});
```

**What to assert / skip:** _Do_ test — table has an accessible name, correct header roles/counts, sort toggles `aria-sort` _and_ reorders rows, selection updates state and the select-all goes indeterminate, empty state renders. _Don't_ test — exact padding, hex colors, class strings. Those break tests without catching real bugs. **Always** run `axe` scoped to the table — it's the cheapest catch for the semantics that matter.

## 10\. Accessibility (non-negotiable)
A table is one of the highest-leverage accessibility surfaces on the web: get the semantics right and a blind user navigates it as fluently as a sighted one; get them wrong and the data is a fog.
*   **Use a real** **`<table>`** **with real** **`<th>`****/****`<td>`****\*\*\*\*\*\*\*\*.** Native semantics give screen-reader users a "table navigation mode" — move cell to cell, and the software announces the relevant column and row headers automatically. No ARIA reconstruction matches it.
*   **`<caption>`** **as the accessible name.** Announced on entry with dimensions ("Invoices, table, 3 columns, 25 rows"). If a visible heading already names it, keep the caption but `sr-only` it.
*   **`scope`** **on every header.** `scope="col"` for column headers, `scope="row"` for the row-identifying cell. This is _the_ attribute that wires values to their labels. For multi-level headers, use `id` + `headers`.
*   **Sort exposed with** **`aria-sort`** on the active `<th>` (`ascending` / `descending` / `none`), and the trigger is a real `<button>` inside the header so it's keyboard-operable and announced. Only one column carries a non-`none` value at a time.
*   **Selection announced by the checkbox, not the row.** The per-row checkbox carries the selection state a screen reader actually reports — give it a per-row `aria-label` ("Select row Acme Co") and let its checked/unchecked state be the announcement. `aria-selected="true"` on a `<tr>` inside a _static_ `role="table"` is **not reliably announced** (unlike a `role="grid"`, where it is part of the spec) — treat it as a styling/state hook (`tr[aria-selected="true"]{…}`), not as the thing that tells a non-visual user a row is selected. The select-all reflects the partial state via `aria-checked="mixed"` + the `indeterminate` DOM property.
*   **The scroll region is reachable:** the horizontal-scroll wrapper gets `role="region"`, an `aria-label`, and `tabindex="0"` so keyboard users can focus and arrow-scroll to the overflow columns. An unfocusable `overflow:auto` div hides data from keyboard users.
*   **Async states announced:** wrap "Loading…", "No results", and page-change messages in an `aria-live="polite"` region (and set `aria-busy="true"` on the table during refetch) so non-visual users hear what changed.
*   **Contrast & not-color-alone:** text vs background ≥ 4.5:1; zebra stripes and status colors must clear contrast, and status must never be conveyed by color alone — pair it with text or an icon (a red dot _and_ the word "Overdue").
*   **Touch/row target ≥ 44px** for any interactive row or in-cell control; don't cram two tap targets into a 28px row.
*   **Don't over-ARIA.** A native `<table>` needs almost no ARIA — just `aria-sort` and selection state. Bolting `role="table"`/`role="row"` onto real table elements is redundant and can _break_ the built-in semantics. Reach for roles only when you've abandoned real elements (a div-grid), and then you're likely building a Data Grid, not a Table.

## 11\. Innovative & Emerging Ideas
The table looks solved but keeps moving:
*   **Container-query responsiveness:** a table that picks scroll vs. stack vs. priority-columns based on _its own_ width (`@container`), so one component is correct in a sidebar and a full-width pane.
*   **CSS** **`subgrid`** **alignment:** nested cell content (a two-line cell, an expand panel) aligns to the parent table's column tracks without magic-number widths.
*   **AI summary & query rows:** a natural-language filter bar over the table, an AI-generated "insights" row, per-column trend explanations, streaming cell population with skeletons.
*   **`:has()`****\*\*\*\*\*\*\*\*-driven state:** row hover/selection styling and "any-cell-invalid → flag the row" done in pure CSS with `tr:has(td[aria-invalid])`, no JS.
*   **View Transitions on sort/paginate:** rows smoothly animate to their new positions when the sort changes, making the reorder legible instead of a jarring jump — with `prefers-reduced-motion` honored.
*   **Sticky Liquid-Glass headers:** the 2026 sticky `<thead>` as refractive translucent material floating over the data.
*   **Server Components + streaming:** the table shell and headers render instantly; rows stream in as the DB responds, with skeleton rows as the placeholder.

## 12\. UX & Comprehension Killers (the silent ones)
None of these throw an error. They just quietly make a table slower to read and less trustworthy — and on a pricing or dashboard page, that's real money.
*   **Left-aligned numbers.** The cardinal sin. Magnitudes don't line up, so users can't compare at a glance. Right-align + `tabular-nums`, every time.
*   **No visual row rhythm on wide tables.** A 12-column table with no zebra or hover highlight makes users lose their row mid-scan and misread values across the wrong row. Add a hover highlight at minimum.
*   **A spinner that collapses the layout.** Replacing the whole table with a centered spinner on every sort/page-change makes the page jump and feels broken. Use skeleton rows on first load, dim-in-place on refetch.
*   **Bare headers over a void (no empty state).** Column headers floating over nothing tells the user nothing. Show a real empty state with a reason and an action — and distinguish "no data yet" from "no results for this filter."
*   **Stacked cards for comparison data.** Collapsing a comparison/financial table to one-record-per-card _destroys its purpose_ — you can no longer compare columns. Use horizontal scroll when comparison is the point.
*   **Missing** **`<caption>`** **and** **`scope`****\*\*\*\*\*\*\*\*.** Invisible on screen, fatal to screen-reader users — every value announced without its column/row header is noise.
*   **Truncating without recourse.** Ellipsis-clipping a cell with no tooltip, expand, or wrap hides data the user came for. Give them a way to see the full value.
*   **Client-side everything on big data.** Loading 10,000 rows to the browser to sort/filter/paginate locally janks the page and leaks the whole dataset. Push it to the server past a few hundred rows.
*   **Unstable sort / reshuffling rows.** Rows that jump around between pages because the sort has no tiebreaker make users distrust the data. Add a stable `id` tiebreak.
*   **Sort that isn't keyboard-reachable.** A sort handler on a `<div>` or the whole `<th>` with no `<button>` locks out keyboard users and screen readers. Sort triggers are buttons.

**The through-line:** these all fail _quietly_ — no crash, just a table people trust a little less and read a little slower. Audit the alignment and the states before you blame the data.

## 13\. Advanced Patterns
Senior-move versions of the patterns above.

### Multi-column & grouped sort
Real data tables often sort by a primary column then a secondary (status, then date). Hold an _array_ of sort descriptors and let Shift-click add a secondary sort; expose only the primary in `aria-sort` (the spec allows one). TanStack's `sorting` state is already an array — lean on it.

### Column visibility, order, and persistence as user state
Which columns show, in what order, at what width, and the chosen density are **user preferences**, not app state. Persist them (localStorage or server profile) keyed per table. A power user who hides six columns expects them hidden next login. This is what turns a table into a _tool_.

### Row virtualization without breaking a11y
When you must render thousands of rows, window them (`@tanstack/react-virtual`): render only visible rows, pad the scroll height with spacer rows so the scrollbar is honest, and keep `aria-rowcount`/`aria-rowindex` set to the _full_ count so assistive tech knows "row 40 of 8,000" even though only 20 are in the DOM. This is the boundary where a Table starts turning into a Data Grid.

### TS-enforced column/row-header correctness
Type the column config so a numeric column _must_ declare its alignment, and so the row-header column is explicit — the type system enforces the a11y rule instead of a human remembering it:

```typescript
type Column<T> =
  | { key: keyof T & string; header: string; rowHeader: true;  numeric?: false }
  | { key: keyof T & string; header: string; rowHeader?: false; numeric?: boolean };
// exactly one column should be rowHeader: true — lint/assert it at build
```

### Editable cells — and when to stop
A little inline edit (click a cell, it becomes an input, blur to save with optimistic UI + rollback) is fine on a Table. But once you need cell-range selection, copy-paste, keyboard grid navigation, and frozen panes, **stop** — you're rebuilding a spreadsheet, and that's the Data Grid. Knowing where the Table ends is a senior judgment call.

### Design tokens for the table system
Drive the whole table off tokens so density, theming, and dark mode are one-line swaps — not a per-cell rewrite:

```css
:root {
  --tbl-row-h: 44px;
  --tbl-cell-px: 16px;
  --tbl-border: #2a2333;
  --tbl-header-bg: #1a1523;
  --tbl-row-hover: rgba(220,164,36,0.08);
  --tbl-row-selected: rgba(95,44,130,0.18);
  --tbl-accent: #DCA424;
}
:root[data-density="compact"]  { --tbl-row-h: 32px; --tbl-cell-px: 12px; }
:root[data-density="comfy"]    { --tbl-row-h: 56px; --tbl-cell-px: 20px; }
```

Change one token, every table restyles; swap the block for dark mode. This is the layer that connects a generic table to the UJG brand system.

## 14\. Performance & Bundle Cost
A table feels free until it has 5,000 rows.
*   **Virtualize past a few hundred rows.** The DOM node count is the killer: 5,000 rows × 8 cells = 40,000 nodes chokes layout and memory. Window it so only ~30 rows exist at once. Biggest single table perf win by far.
*   **Server-side sort/filter/paginate on large data.** Don't ship 10,000 rows to sort in the browser — it's slow _and_ a data leak. The client holds one page; the server does the work (§9.8).
*   **Delegate events, don't per-cell bind.** One listener on `<tbody>` for row clicks/selection beats a handler per row (§9.9). For 1,000 rows that's 1 closure vs. 1,000.
*   **Memoize rows in React.** Wrap row components in `memo` and stabilize handlers with `useCallback` so re-sorting or selecting one row doesn't re-render all of them. Reach for it when the table is large and updates often.
*   **`content-visibility: auto`** on off-screen row groups lets the browser skip rendering work for rows not in the viewport — a cheap, CSS-only partial-virtualization win for medium tables.
*   **Don't animate layout properties.** Animating row height/width on expand thrashes reflow every frame. Animate `transform`/`opacity`; use `grid-template-rows` transitions for expand where you can.
*   **`table-layout: fixed`** for big tables: the browser sizes columns from the first row instead of measuring every cell, a real layout-speed win (and it makes truncation/resize predictable).

## 15\. Security (a table endpoint is an exfiltration surface)
Tables are the front door to your data, which makes their endpoints a favorite target. Mostly invisible in the UI.
*   **Broken access control (OWASP A01) is the #1 table bug.** A table endpoint that forgets `WHERE org_id = :me` returns _everyone's_ rows. The UI showing only your data is not a boundary — the server must scope every query to the authenticated tenant/user, and re-check row-level permission for row actions. Never trust a row `id` the client sent as proof of ownership.
*   **Sort/filter params are injection vectors.** A `sort` or `filter` value interpolated into `ORDER BY`/`WHERE` is SQL injection. Allow-list sort columns to an enum; parameterize all values (§9.8, §9.13).
*   **Cap page size and rate-limit.** Uncapped `pageSize` or unthrottled paging turns your table endpoint into a bulk-export tool for a scraper. Cap the page, rate-limit per user + IP.
*   **Don't over-return columns.** `SELECT *` into a JSON response leaks fields the table never shows (password hashes, internal flags, other users' PII). Select only the columns the table renders; shape the response server-side.
*   **CSV/export is its own attack surface.** "Export to CSV" must re-authorize (same scope as the table), and guard against CSV-injection — a cell starting with `=`, `+`, `-`, or `@` can execute as a formula when opened in Excel. Prefix such cells with a `'`.
*   **Row actions re-check server-side.** Selecting rows and hitting "Delete 12" must verify the user may delete _each_ of those specific rows — bulk actions are where authorization gets skipped. Audit-log who deleted what.

## 16\. Senior-Level Checklist (ship-ready)
Before a table is "done":
- [ ] Real `<table>` with `<thead>`/`<tbody>`/(`<tfoot>` if totals) — never a layout table, never a div-pile.
- [ ] `<caption>` present as the accessible name (`sr-only` if a visible heading exists).
- [ ] Column headers `scope="col"`; each row's identifying cell is `<th scope="row">`.
- [ ] Numbers right-aligned with `tabular-nums`; headers align to their data; text left-aligned.
- [ ] Sort exposed via `aria-sort` on the active header; the trigger is a real `<button>`; sort is stable (tiebreak).
- [ ] Selection: per-row checkbox with a human `aria-label` ("Select row Acme Co") carrying the announced state, `aria-selected` on rows as a style hook only, select-all with `indeterminate` + `aria-checked="mixed"`.
- [ ] All async states: skeleton on first load, dim-in-place + `aria-busy` on refetch, distinct empty vs no-results, error with retry.
- [ ] Responsive strategy chosen deliberately (scroll / stacked / priority) and matched to the user's task.
- [ ] Horizontal-scroll wrapper is a focusable, `aria-label`led `role="region"`.
- [ ] Large data: server-side sort/filter/paginate; virtualization past a few hundred rows.
- [ ] Endpoint scopes every query to the tenant, allow-lists sort columns, caps page size, returns a total count.
- [ ] Status/validation shown with text or icon, not color alone; contrast ≥ 4.5:1; interactive rows ≥ 44px.
- [ ] `axe` run scoped to the table passes; keyboard can reach sort, selection, and the scroll region.
- [ ] Density/column-visibility/width persisted as user state where it matters.

## 17\. Visual Styles (the same table, eleven skins)
Style is skin; the `<th scope>`/`aria-sort`/`<caption>` skeleton, keyboard behavior, focus rings, and 44px row target are **identical** across all eleven. Guard glass/liquid-glass/neu for contrast (data tables are contrast-critical — never let a translucent header eat text legibility); guard aurora/liquid-glass for `prefers-reduced-motion`.

*   **Flat:** solid header bar, hairline row borders, one-color zebra, no shadow. The scan-fastest, most data-honest skin — the default for dense Data Alchemy dashboards.
*   **Material:** 56px header, elevation on the sticky `<thead>` as it separates from scrolling rows, ripple on row press, sort arrows that fade in on header hover.
*   **Glassmorphism:** translucent `backdrop-filter: blur()` header over a vivid page. Looks premium; watch header-text contrast hard — data legibility beats the effect.
*   **Liquid Glass (2026):** the sticky `<thead>` as Apple's refractive material — translucent, specular rim, a sheen that shifts as rows scroll under it. Stunning over deep Eminence with dense data. Web = honest approximation (`backdrop-filter` + layered highlights); SwiftUI's `Table` in a `.glassEffect()` container is native. Reduced-motion kills the sheen.
*   **Neumorphism:** rows as soft-extruded panels on a same-color surface. Pretty, contrast-poor — accent/marketing tables only, never financial data.
*   **Skeuomorphism:** the "real ledger" look — ruled lines, faint paper texture, inset cells. Nostalgic; reserve for themed/finance-flavored surfaces.
*   **Neo-Brutalism:** thick borders, hard offset shadow on the table block, zero radius, mono headers, clashing zebra. High personality for a bold dashboard; keep numeric alignment disciplined so it stays readable.
*   **Claymorphism:** big radius on the table block, soft inner light, puffy row hover. Friendly, low-density — comparison tables on a marketing page, not admin grids.
*   **Aurora / Gradient:** animated multi-hue gradient header bar on dark; rows stay flat for legibility. Premium campaign moment; honor `prefers-reduced-motion`.
*   **Minimal / Swiss:** no borders, generous whitespace, typographic hierarchy and alignment do all the work, hairline under the header only. The most elegant read for a considered data table.
*   **UJG Brand:** Goldenrod sort indicators and left-accent selection bar on a deep Eminence/Night header, Platinum text, Sienna/Spanish-Orange status badges, confident radius, a warm glow on the sticky header. Numbers in tabular Urbanist, right-aligned. The house default: dark, saturated, disciplined — the Liquid-Glass header accent sings on the Eminence backdrop.

**Rule that never changes:** the style is skin. Semantics, keyboard navigation, focus ring, sort exposure, and the 44px row target stay identical across all eleven. Full guidance on the [Design Styles (visual languages)](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200551) reference.

**Bottom line:** a table is deceptively humble — it's just rows and columns until you realize it's the surface where people make decisions about real data, and the one component whose _semantics_ (not its looks) determine whether half your users can use it at all. Master the `<caption>`/`<th scope>` skeleton, the alignment discipline, the full async-state set, the responsive tradeoffs, and the server contract that keeps it fast and safe — and know exactly where the Table ends and the [Data Grid](https://app.clickup.com/8495850/docs/838qa-81211/838qa-216791) begins.
