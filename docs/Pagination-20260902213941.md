## 1\. What Pagination Actually Is
Pagination is the pattern for splitting a large result set into discrete, navigable chunks — pages — and giving the user controls to move between them. That's the surface. Underneath, it's two very different problems that people constantly conflate:

*   **The UI control** — the row of numbered links, prev/next arrows, ellipses, and "showing 1–20 of 4,312" status. This is what designers mean by "pagination."
*   **The data-access strategy** — how the backend actually fetches "page 7." This is `LIMIT/OFFSET` vs. cursor/keyset, and it's where the real engineering lives. A pretty pager on top of a naive `OFFSET 200000` query is slow no matter how it looks.

The word also hides three sibling patterns people treat as interchangeable and shouldn't:

*   **Classic pagination:** discrete pages, explicit controls, the URL changes (`?page=3`). You always know where you are and how much is left.
*   **"Load more":** a single button appends the next chunk to the current view. One long growing list, no page boundaries, usually no URL state.
*   **Infinite scroll:** the next chunk loads automatically as you approach the bottom. No button, no boundaries, and — done carelessly — no way back to the footer.

The single most common mistake: reaching for infinite scroll because it feels "modern," on content where users need to _find_, _return to_, and _share_ specific items. Rule of thumb: **if the user needs to locate a specific result, jump around, bookmark a position, or reach the footer, paginate. If they're grazing an endless feed for serendipity, infinite scroll earns its keep.**
* * *

## 2\. Why It Matters
Pagination is where scale meets the user. Everything you do to a dataset larger than one screen passes through it, which gives it outsized leverage on four things at once:

*   **Findability and task completion.** Search results, product grids, admin tables, transaction histories — the user's whole job is locating a row. Good pagination (jump-to-page, clear totals, stable ordering) makes a 4,000-row set feel like a filing cabinet. Bad pagination makes it feel like a haystack.
*   **SEO and crawlability.** This is the quiet one. Paginated pages have real, distinct, shareable URLs (`?page=2`), so search engines can crawl and index deep content. Infinite scroll hides everything past the first viewport behind JavaScript — crawlers often never see it, and that content effectively doesn't exist to Google. For any content-driven site, pagination isn't a UX preference, it's an indexation strategy.
*   **Performance and cost.** Page size caps how many rows you fetch, serialize, and render per request. It's the difference between a 20-row query and a "SELECT everything and pray" that melts the database. And the _kind_ of pagination (offset vs. cursor) decides whether page 10,000 is as fast as page 1 or times out (see §9).
*   **Trust and orientation.** "Showing 41–60 of 4,312" tells the user the system knows how much data exists and where they are in it. A feed that just… keeps going, with no total and no position, feels bottomless and slightly untrustworthy — users can't tell if they've seen everything or the app is broken.

## 3\. Anatomy of a Pager
Every well-built pagination control is composed of predictable parts:

*   **Container:** a `<nav>` landmark with `aria-label="Pagination"` so assistive tech can find and skip it. Not a bare `<div>`.
*   **Page list:** an ordered/unordered list (`<ul>`) of page items. Semantically a list because it _is_ one.
*   **Page links:** the numbered controls. Real `<a href>` when the page has a URL; `<button>` only when it's a pure in-app state change with no shareable URL.
*   **Current-page marker:** the active page, styled _and_ flagged with `aria-current="page"`. Style alone is not enough.
*   **Previous / Next controls:** directional movement. At the ends they become non-actionable — and how you express "non-actionable" is an accessibility decision, not a CSS one (see §5, §10).
*   **First / Last controls (optional):** jump to the boundaries. Valuable when totals are large.
*   **Ellipsis / overflow:** the `…` that stands in for the runs of pages you're not showing. Presentational, not a control.
*   **Status / result summary:** "Showing 41–60 of 4,312 results." The single most under-used, most orienting part.
*   **Page-size selector:** "Rows per page: 20 ▾." Lets the user trade density for fewer clicks.
*   **Jump-to-page (optional):** a small input for "go to page \_\_\_," essential past a few dozen pages.

## 4\. Sizes, Density & Page-Size Choices
Two different "size" questions live here: how big the control is, and how many items go on a page.

**Control density** — the pager chrome scales like any button row:

| Size | Item height | Item min-width | Font | Use |
| ---| ---| ---| ---| --- |
| SM | 32px | 32px | 13px | Dense admin tables, sidebars |
| MD | 40px | 40px | 14px | Default for most UI |
| LG | 48px | 48px | 16px | Mobile-first, touch-primary |

Every page item stays a **≥44×44px tap target** even at SM — expand the hit area with padding, don't shrink the touchable region to match a tiny glyph.

**Page size** — how many rows per page — is a product decision with performance teeth:

| Page size | Good for | Watch out for |
| ---| ---| --- |
| 10 | Scannable lists, mobile | More pagination clicks, more requests |
| 20–25 | The default sweet spot for most tables | — |
| 50 | Power users, data-dense admin | Heavier render, taller scroll |
| 100 | Bulk operations, export prep | Real render + payload cost; virtualize the rows |

Rules that matter:

*   **Offer a page-size selector** (10 / 20 / 50 / 100) for any data table. Different users have different jobs on the same screen.
*   **Persist the choice** in the URL (`?size=50`) and ideally per-user, so it survives navigation and refresh.
*   **Cap it server-side.** A client asking for `?size=100000` must be clamped to a max (say 100). Never let the client dictate an unbounded fetch — that's a denial-of-service vector (see §9, §15).
*   **Changing page size resets to page 1** in almost every case — page 7 of size 20 has no stable meaning at size 50.

## 5\. States (the part juniors forget)
A production pager has far more states than "page 1 vs page 2." Missing states are the #1 tell of an amateur build.

1. **Default (rest)** — the baseline row of links.
2. **Hover** — pointer over a page item. Subtle background shift. (Absent on touch — never rely on it alone.)
3. **Focus** — reachable by keyboard, with a visible `:focus-visible` ring. Every item and arrow is a Tab stop (or part of a managed group).
4. **Active (pressed)** — the moment of click. Slight darken/scale, sells the tap.
5. **Current page** — the page you're on. Visually distinct _and_ `aria-current="page"`. It is typically **not a link** — you can't navigate to where you already are.
6. **Disabled-at-ends** — Prev on page 1, Next on the last page. Non-actionable. Done right, this is **not a dead button**: either render it as non-interactive text with `aria-disabled="true"` (kept discoverable, click is a no-op) or omit the `href` and mark it. A `<button disabled>` that silently does nothing and drops out of the tab order confuses screen-reader users who were told it exists.
7. **Loading** — the next page is fetching. Disable controls, show a spinner or skeleton rows, keep the pager's height stable to avoid layout shift.
8. **Error** — the page fetch failed. Surface a retry, don't just freeze on the old page silently.
9. **Empty / zero results** — no data at all. Hide the pager or show "0 results" — never render a lone "Page 1 of 0."
10. **Single page** — the entire set fits on one page. Convention: hide the numbered controls entirely (a one-page pager is noise), but you may still show the "Showing 1–8 of 8" status.

Component-specific truth: the ellipsis (`…`) is **presentational, never a state and never focusable**. It's a gap marker, not a control.

## 6\. Types & Variants
Same job, different shapes. Pick per data size, device, and content type.

*   **Numbered pagination:** the classic `‹ 1 2 3 … 20 ›`. Best when totals are known and jumping matters (search, catalogs, admin).
*   **Prev/Next only:** just `‹ Previous | Next ›`. Best when the total is unknown or expensive to count, or on mobile. Pairs naturally with cursor pagination (§9), which often can't cheaply know the total page count.
*   **Load more button:** one button appends the next chunk. Good for feeds where users mostly want "more" but you still want a footer reachable and a deliberate user action.
*   **Infinite scroll:** auto-loads on scroll. Good for media/social feeds; costly for findability, SEO, and the back-button. If you use it, add a "back to top," keep the URL updated with the scroll position, and provide a real footer escape.
*   **Cursor / "keyset" pager:** UI is usually prev/next, but the engine underneath uses a cursor token, not a page number. The correct choice for large, live, deep datasets (see §9).
*   **Compact / mobile pager:** collapses to `‹ Prev · 3 / 20 · Next ›` or a page-size-aware `1 … 20`. Sheds middle numbers on narrow screens.
*   **With page-size selector + status:** the full "data table" variant — numbers, size dropdown, and "Showing X–Y of Z." The standard for admin/BI surfaces (this is UJG's Data Alchemy default).

**The tradeoff table you should have memorized:**

| Concern | Classic pagination | Load more | Infinite scroll |
| ---| ---| ---| --- |
| Findability / jump to a spot | Best | Poor | Poor |
| SEO / crawlable deep content | Best | OK (if links exist) | Poor |
| Back-button returns you correctly | Best | Weak | Worst |
| Reaching the footer | Always | Usually | Often impossible |
| Shareable position (URL) | Yes | Rarely | Rarely |
| "Endless graze" feel | No | Some | Best |
| Sense of total / progress | Best | Weak | None |

The pattern is stark: **SEO, findability, back-button, and footer access all favor pagination.** Infinite scroll wins exactly one column — the endless graze — and only for content where that's the actual goal.

## 7\. When to Use It (and When Not To)
Use classic pagination when the user needs to **locate, return to, share, or bound** a result. Concretely:

*   **Search results and catalogs** — people jump, compare across pages, and bookmark. Google itself paginates.
*   **Data tables and admin** — findability and a sense of total are the whole point.
*   **Any content you want indexed** — blog archives, product listings, documentation indexes.
*   **Anywhere the footer matters** — infinite scroll's fatal flaw is a footer the user can never reach because content keeps loading above it.

Reach for **load more** when users mostly want "a bit more" and you want a deliberate action plus a reachable footer — comment threads, activity logs.

Reach for **infinite scroll** only when the content is a graze-forever feed (social, media discovery) _and_ you accept the SEO/back-button/footer costs and mitigate them.

Don't paginate when:

*   The whole set comfortably fits on one screen (just show it — a pager on 6 items is clutter).
*   The data is small enough to load once and filter/sort client-side (a client-side table beats a round-trip per page under ~a few hundred rows).

Placement heuristics:

*   **Bottom of the content, always.** Often **top-and-bottom** for long tables so users don't scroll back up to move on.
*   **Right-align or center** the control; keep the "Showing X–Y of Z" status left-aligned near it.
*   **Keep prev/next reachable in thumb range** on mobile; consider a sticky bottom bar for long lists.

## 8\. Pagination Across Design Systems
Same component, different house rules. Knowing these makes you fluent in any codebase.

*   **Material Design (Google):** table pagination is "rows per page" + range label + prev/next arrows (`MatPaginator`) rather than a long numbered strip. Compact, table-oriented, `firstPage`/`lastPage` optional.
*   **Apple HIG (iOS/macOS):** no numbered web-style pager. The native analog is the **page control** — the row of dots under a paged scroll view — plus large-title lists that lean on scrolling. Explicit numbered pagination is a web/desktop-data convention, not an iOS one.
*   **Fluent (Microsoft):** data-grid oriented; pagination appears in `DetailsList`/DataGrid footers with page size and range, tuned for dense enterprise tables.
*   **Ant Design / enterprise:** the richest pager out there — numbered pages, ellipsis with `…` that expands ±5 on click, `showSizeChanger`, `showQuickJumper` (type a page), `showTotal` render function. Built for data-heavy admin.
*   **Bootstrap:** ships a ready-made `.pagination` component — a `<ul class="pagination">` of `.page-item`/`.page-link`, with `.active` and `.disabled` helpers. Semantic list out of the box (see §9.12).
*   **Tailwind / utility-first:** no prescribed pager; you compose one from utilities, then extract it into a component. Freedom plus consistency risk.
*   **shadcn/Radix (2024+ web standard):** ships a `Pagination` set of accessible primitives (`PaginationContent`, `PaginationItem`, `PaginationLink`, `PaginationEllipsis`) — semantic `<nav>`, `aria-current` baked in, appearance fully yours (see §9.7).

## 8b. Visual Styles (the same pager, eleven aesthetics)
Design systems are _whose_ rules; visual styles are _which look_. The same semantic pager can wear any of these skins. Pick per project, client, and era. See them all in the [Design Styles gallery](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200551); every style skins every variant from one shared token set.

*   **Flat:** solid fill on the current page, crisp edges, no shadow. Reads instantly.
*   **Material:** subtle elevation on hover, ripple on the active page, compact "rows per page" framing.
*   **Glassmorphism:** translucent pager bar with `backdrop-filter: blur()` over a vivid background. Watch contrast on the numbers.
*   **Liquid Glass (the 2026 trend):** Apple's iOS 26 / macOS Tahoe language, glassmorphism's successor. The pager pill _refracts_ what's behind it with a specular rim and a moving sheen — the current page reads as a bead of light sliding along the track. Web = honest approximation with layered highlights; SwiftUI emits native `.glassEffect()`. See the 2026 note below.
*   **Neumorphism:** page items as soft extruded pills on a same-color surface; the current page pressed _in_. Pretty, contrast-poor — accent only.
*   **Skeuomorphism:** beveled number keys, inner highlights, the current page "lit." The tactile look.
*   **Neo-Brutalism:** hard offset shadow, thick border, zero radius, the active page in a clashing block. High personality.
*   **Claymorphism:** big radius, puffy soft-glow page pills, the current one inset. Friendly.
*   **Aurora / Gradient:** animated multi-hue gradient behind the active page on a dark bar. Premium — honor `prefers-reduced-motion`.
*   **Minimal / Swiss:** type and spacing do the work — thin numbers, a single underline or weight change for current, near-zero decoration.
*   **UJG Brand:** Goldenrod current-page bead on deep Eminence, confident radius, a warm glow on hover. The house default.

**Rule that never changes:** the style is skin. The pager's `<nav>` semantics, `aria-current`, keyboard order, focus ring, and 44px targets stay identical across all eleven.

### What's trending in 2026
The dominant force this year is **Liquid Glass**: Apple shipped it across iOS 26, iPadOS, and macOS Tahoe in late 2025, and the web is approximating it with `backdrop-filter`, layered highlights, and the emerging refraction proposals. For a pager it shows up as a glass track with the current-page indicator behaving like a moving bead of light.

Around it, the 2026 currents that touch pagination specifically:

*   **Cursor-first data loading** as datasets and live feeds grow — keyset pagination becomes the default backend even when the UI still shows numbers.
*   **URL-as-state everywhere:** frameworks push page/size/sort into `searchParams` so every view is shareable and server-renderable (Next.js App Router, Remix, TanStack Router).
*   **Hybrid "load more + deep-linkable pages":** an infinite/append feed that still writes `?page=` to the URL so the back-button and SEO survive.
*   **Motion-forward but restrained:** the current-page bead animates between positions; killed under `prefers-reduced-motion`.

**For UJG:** lean the house pager toward a Liquid Glass track over deep Eminence with a Goldenrod current bead for campaign/marketing surfaces; keep Flat/Swiss for Data Alchemy tables where density and legibility beat spectacle. Contrast and reduced-motion are non-negotiable no matter how on-trend the skin.

The biggest section. Everything from the semantic markup to the query that makes deep pages fast.

### 9.1 HTML (the semantic foundation everyone should master first)
The correct pager is a **`<nav>`** **landmark wrapping a list of links** — not a pile of divs, not a row of bare buttons.

```html
<nav aria-label="Pagination">
  <ul class="pagination">
    <!-- Previous: at the start it's non-actionable, not a dead button -->
    <li>
      <span class="page-link is-disabled" aria-disabled="true">
        <span aria-hidden="true">&lsaquo;</span> Previous
      </span>
    </li>

    <li><a class="page-link" href="?page=1">1</a></li>

    <!-- Ellipsis: presentational, NOT focusable, NOT a control -->
    <li><span class="ellipsis" aria-hidden="true">&hellip;</span></li>

    <li><a class="page-link" href="?page=4">4</a></li>

    <!-- Current page: aria-current is the load-bearing part -->
    <li>
      <a class="page-link is-current" href="?page=5" aria-current="page">5</a>
    </li>

    <li><a class="page-link" href="?page=6">6</a></li>

    <li><span class="ellipsis" aria-hidden="true">&hellip;</span></li>

    <li><a class="page-link" href="?page=20">20</a></li>

    <!-- Next: a real link because there IS a next page -->
    <li>
      <a class="page-link" href="?page=6" rel="next">
        Next <span aria-hidden="true">&rsaquo;</span>
      </a>
    </li>
  </ul>
</nav>

<!-- Status: announce the range, live for screen readers -->
<p class="pagination-status" aria-live="polite">
  Showing <strong>81&ndash;100</strong> of <strong>4,312</strong> results
</p>
```

Key HTML rules:

*   **`<nav aria-label="Pagination">`** turns the pager into a labeled landmark that screen-reader users can jump to and skip. The label distinguishes it from other navs on the page.
*   **Links, not buttons, when there's a URL.** `<a href="?page=3">` is shareable, middle-clickable into a new tab, crawlable, and back-button-correct. Use `<button>` only for pure in-app state with no URL.
*   **`aria-current="page"`** on the active item is how assistive tech announces "you are here." Visual highlight alone is invisible to a screen reader.
*   **Disabled-at-ends is** **`aria-disabled`****\*\*\*\*, not a dead** **`<button disabled>`****\*\*\*\*.** Render prev/next at the boundary as a non-link `<span>` (or a link without `href`) marked `aria-disabled="true"` so it's still discoverable and announced, but inert.
*   **The ellipsis is** **`aria-hidden="true"`** and never focusable — it carries no action.
*   **`rel="prev"`****/****`rel="next"`** hint the sequence to browsers and some crawlers.

### 9.3 React + TypeScript (a proper reusable component with the ellipsis algorithm)
The heart of this doc. The hard part of a pager isn't the markup — it's **deciding which page numbers to show** so a 200-page set fits in one row as `1 … 4 5 6 … 200`. Here's the algorithm, isolated and tested-in-isolation-able, then the component.

```typescript
// usePagination.ts — the ellipsis/truncation algorithm, framework-agnostic logic
export const DOTS = "dots" as const;

interface Args {
  currentPage: number;   // 1-based
  totalPages: number;
  siblingCount?: number; // pages to show on each side of current (default 1)
  boundaryCount?: number;// pages pinned at each end (default 1)
}

/** Returns the items to render: page numbers interleaved with DOTS markers. */
export function paginationRange({
  currentPage,
  totalPages,
  siblingCount = 1,
  boundaryCount = 1,
}: Args): (number | typeof DOTS)[] {
  const range = (start: number, end: number) =>
    Array.from({ length: end - start + 1 }, (_, i) => start + i);

  // How many slots we need if we show everything without dots:
  // boundaries (both ends) + current + siblings (both sides) + 2 dots
  const totalSlots = boundaryCount * 2 + siblingCount * 2 + 3;

  // Few enough pages? Show them all, no ellipsis.
  if (totalPages <= totalSlots) return range(1, totalPages);

  const leftSiblingStart = Math.max(currentPage - siblingCount, boundaryCount + 2);
  const rightSiblingEnd = Math.min(
    currentPage + siblingCount,
    totalPages - boundaryCount - 1,
  );

  // Show a left dot when there's a gap between the start boundary and the left sibling.
  const showLeftDots = leftSiblingStart > boundaryCount + 2;
  const showRightDots = rightSiblingEnd < totalPages - boundaryCount - 1;

  const startPages = range(1, boundaryCount);
  const endPages = range(totalPages - boundaryCount + 1, totalPages);

  if (!showLeftDots && showRightDots) {
    // Near the start: 1 2 3 4 5 … 20
    const leftItemCount = boundaryCount + siblingCount * 2 + 2;
    return [...range(1, leftItemCount), DOTS, ...endPages];
  }
  if (showLeftDots && !showRightDots) {
    // Near the end: 1 … 16 17 18 19 20
    const rightItemCount = boundaryCount + siblingCount * 2 + 2;
    return [...startPages, DOTS, ...range(totalPages - rightItemCount + 1, totalPages)];
  }
  // In the middle: 1 … 4 5 6 … 20
  return [
    ...startPages,
    DOTS,
    ...range(leftSiblingStart, rightSiblingEnd),
    DOTS,
    ...endPages,
  ];
}
```

```tsx
// Pagination.tsx — the component
import { paginationRange, DOTS } from "./usePagination";

interface PaginationProps {
  currentPage: number;
  totalItems: number;
  pageSize: number;
  onPageChange: (page: number) => void;
  siblingCount?: number;
}

export function Pagination({
  currentPage,
  totalItems,
  pageSize,
  onPageChange,
  siblingCount = 1,
}: PaginationProps) {
  const totalPages = Math.ceil(totalItems / pageSize);
  if (totalPages <= 1) return null;                 // one page = no pager

  const pages = paginationRange({ currentPage, totalPages, siblingCount });
  const onFirst = currentPage === 1;
  const onLast = currentPage === totalPages;

  const from = (currentPage - 1) * pageSize + 1;
  const to = Math.min(currentPage * pageSize, totalItems);

  return (
    <nav aria-label="Pagination">
      <ul className="pagination">
        <li>
          <button
            type="button"
            className="page-link"
            onClick={() => { if (!onFirst) onPageChange(currentPage - 1); }}
            aria-disabled={onFirst}         // non-actionable at the boundary, still discoverable + in tab order (NOT a dead `disabled` button)
            rel="prev"
          >
            <span aria-hidden="true">&lsaquo;</span> Previous
          </button>
        </li>

        {pages.map((p, i) =>
          p === DOTS ? (
            <li key={`dots-${i}`}>
              <span className="ellipsis" aria-hidden="true">&hellip;</span>
            </li>
          ) : (
            <li key={p}>
              <button
                type="button"
                className={`page-link ${p === currentPage ? "is-current" : ""}`}
                onClick={() => onPageChange(p)}
                aria-current={p === currentPage ? "page" : undefined}
                aria-label={
                  p === currentPage ? `Page ${p}, current page` : `Go to page ${p}`
                }
              >
                {p}
              </button>
            </li>
          ),
        )}

        <li>
          <button
            type="button"
            className="page-link"
            onClick={() => { if (!onLast) onPageChange(currentPage + 1); }}
            aria-disabled={onLast}          // non-actionable at the boundary, still discoverable + in tab order
            rel="next"
          >
            Next <span aria-hidden="true">&rsaquo;</span>
          </button>
        </li>
      </ul>

      <p className="pagination-status" aria-live="polite">
        Showing {from}&ndash;{to} of {totalItems} results
      </p>
    </nav>
  );
}
```

Why this is the senior version, not the junior one:

*   **The range logic is extracted and pure** (`paginationRange`) — you unit-test the ellipsis math with zero rendering (see §9.11). Juniors inline it in JSX and can't test it.
*   **`siblingCount`** **and** **`boundaryCount`** **are parameters,** so the same component does `1 … 4 5 6 … 20` or a wider `1 2 … 9 10 11 … 99 100` without a rewrite.
*   **`aria-current="page"`** **and per-item** **`aria-label`** ("Go to page 6" / "Page 5, current page") so screen readers get meaning, not just a naked digit.
*   **Returns** **`null`** **for a single page** — no clutter on small sets.
*   **Computes and announces the range** in a `polite` live region so page changes are _spoken_, not just repainted.

> **Links vs. buttons here:** this version uses `<button>` + `onClick` for a client-state SPA table. If the page has a real URL, swap each `<button>` for `<a href={`?page=${p}`}>` (or a Next.js `<Link>`) so the pager is shareable, crawlable, and back-button-correct. Same component shape, different element. See §9.8.

### 9.4 The Backend Side — Offset vs. Cursor (the real distinction)
This is where pagination is won or lost, and where most "why is page 5,000 so slow" tickets come from. The UI showing page numbers does **not** dictate how the server fetches them.

**Offset pagination (****`LIMIT / OFFSET`****).** The obvious approach: skip `(page-1) * size` rows, take `size`.

```sql
SELECT id, title, created_at
FROM articles
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 100000;          -- page 5,001 at size 20
```

Why it's slow at depth: `OFFSET 100000` doesn't magically jump — the database **scans and discards 100,000 rows** before returning 20. Cost grows linearly with page depth. Page 1 is instant; page 5,000 crawls. Worse, on a live dataset it's **not stable**: if 3 rows are inserted while the user pages, everything shifts down and they see duplicates or skip rows across page boundaries.

When offset is fine: small/bounded datasets, admin tables where nobody goes past page ~50, and cases where you genuinely need "jump to arbitrary page N" and a total count.

**Cursor / keyset pagination (the fast one).** Instead of "skip N rows," remember the last row you saw and ask for "rows _after_ this one." The cursor is a value (or tuple) from the ordering columns, not a page number.

```sql
-- First page: no cursor
SELECT id, title, created_at
FROM articles
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- Next page: "after" the last row of the previous page.
-- created_at + id is the tuple; id breaks ties so ordering is TOTAL and stable.
SELECT id, title, created_at
FROM articles
WHERE (created_at, id) < ($lastCreatedAt, $lastId)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

Why it's fast: with an index on `(created_at DESC, id DESC)`, the database **seeks directly** to the cursor position and reads 20 rows — O(1) with respect to depth. Page 5,000 is as fast as page 1. And it's **stable under inserts**: you're anchored to a real row, not an offset that shifts.

The two rules that make cursor pagination correct:

1. **Stable, total ordering.** You must order by something unique, or append a unique tie-breaker (`id`). Ordering by `created_at` alone breaks when two rows share a timestamp — the cursor can't tell them apart and you drop or repeat rows. `(created_at, id)` is total.
2. **The cursor encodes the ordering tuple**, usually base64'd so it's opaque to the client: `encode("2026-07-22T10:00:00Z|8412")`. The client passes it back verbatim; it never constructs one.

The tradeoff you accept: cursor pagination gives you **prev/next**, not "jump to page 137." There's no cheap page number and often no cheap total count. That's why cursor-paginated UIs almost always show `‹ Prev · Next ›` (and sometimes "load more"), not a numbered strip. Match the UI to the engine.

**Rule of thumb:** deep, large, live, or infinite-feed data → **cursor**. Small, bounded, admin data where users jump to arbitrary pages and want a total → **offset**. Never bolt a "jump to page 9,999" control onto a dataset you can only serve fast with a cursor.

### 9.5 Node.js (a cursor-paginated endpoint)
The full handler. Express-style, but the shape is universal.

```typescript
import express from "express";
import { z } from "zod";

const router = express.Router();

// Validate + CLAMP the page size. Never let the client dictate an unbounded fetch.
const Query = z.object({
  cursor: z.string().optional(),               // opaque token from us
  limit: z.coerce.number().int().min(1).max(100).default(20),
});

// cursor <-> "createdAt|id", base64 so the client can't read/forge structure cheaply
const encodeCursor = (createdAt: string, id: string) =>
  Buffer.from(`${createdAt}|${id}`).toString("base64url");
const decodeCursor = (c: string) => {
  const [createdAt, id] = Buffer.from(c, "base64url").toString().split("|");
  if (!createdAt || !id) throw new Error("bad cursor");
  return { createdAt, id };
};

router.get("/api/articles", async (req, res) => {
  const parsed = Query.safeParse(req.query);
  if (!parsed.success) return res.status(422).json(parsed.error.issues);
  const { cursor, limit } = parsed.data;

  const after = cursor ? decodeCursor(cursor) : null;

  // Fetch limit + 1 to know if there's a next page WITHOUT a second COUNT query.
  const rows = await db.query(
    `SELECT id, title, created_at
       FROM articles
      ${after ? "WHERE (created_at, id) < ($1, $2)" : ""}
      ORDER BY created_at DESC, id DESC
      LIMIT $${after ? 3 : 1}`,
    after ? [after.createdAt, after.id, limit + 1] : [limit + 1],
  );

  const hasNext = rows.length > limit;
  const page = hasNext ? rows.slice(0, limit) : rows;
  const last = page[page.length - 1];

  res.json({
    data: page,
    pageInfo: {
      hasNextPage: hasNext,
      endCursor: last ? encodeCursor(last.created_at, last.id) : null,
    },
  });
});

export default router;
```

Note the `limit + 1` trick: fetch one extra row; if it comes back, there's a next page. That gives you `hasNextPage` for free without a second `COUNT(*)` — which on a big table is itself expensive. Offset pagers that show a total page count pay for that `COUNT`; cursor pagers usually skip it.

### 9.6 Python (offset endpoint + a rendered pager)
**Backend** (FastAPI) doing classic offset pagination with a total, the admin-table case:

```python
from fastapi import FastAPI, Query, Depends
from math import ceil

app = FastAPI()

@app.get("/api/orders")
def list_orders(
    page: int = Query(1, ge=1),
    size: int = Query(20, ge=1, le=100),        # clamp: never unbounded
    user=Depends(require_auth),

    total = db.count_orders(user_id=user.id)

    return {
        "data": rows,
        "page": page,
        "size": size,
        "total": total,
        "total_pages": total_pages,
        "from": offset + 1 if total else 0,
        "to": min(offset + size, total),

```

### 9.8 Next.js (App Router: URL as state, server-rendered)
This is the pattern that makes pagination shareable, crawlable, and back-button-correct: **the page number lives in** **`searchParams`****\*\*\*\*, and the page is a Server Component that reads it.** No client state, no `useState` for the current page.

```tsx
// app/articles/page.tsx  — a Server Component
import { Pagination } from "@/components/Pagination";

export default async function ArticlesPage({
  searchParams,
}: {
  searchParams: Promise<{ page?: string; size?: string }>;
}) {
  const { page: pageParam, size: sizeParam } = await searchParams;
  const page = Math.max(1, Number(pageParam) || 1);
  const size = Math.min(100, Math.max(1, Number(sizeParam) || 20)); // clamp

  const { data, total } = await getArticles({ page, size }); // runs on the server

  return (
    <>
      <ArticleList items={data} />
      {/* Links point at ?page=N, so each page is a real, shareable, indexable URL */}
      <Pagination currentPage={page} totalItems={total} pageSize={size} basePath="/articles" />
    </>
  );
}
```

```tsx
// The links become <Link href> so navigation is client-fast but URL-backed.
import Link from "next/link";
// inside Pagination, each item:
<Link
  href={`${basePath}?page=${p}&size=${size}`}
  aria-current={p === currentPage ? "page" : undefined}
  scroll={true}          // jump to top on page change; set false to preserve scroll
  className={`page-link ${p === currentPage ? "is-current" : ""}`}
>
  {p}
</Link>
```

Why URL-as-state is the senior choice:

*   **Shareable:** a user pastes `/articles?page=7` into Slack and the recipient lands on page 7.
*   **Back-button-correct:** browser history has one entry per page, so Back returns to the previous page exactly. (This is precisely what infinite scroll breaks.)
*   **Server-renderable and crawlable:** the server reads `searchParams`, fetches the right slice, and returns real HTML that Google can index. No JS required to see page 7.
*   **Refresh-safe:** reload keeps you on page 7. Client-only `useState` pagination loses your place on refresh.

For client-side updates without a full navigation, use `useRouter().push()` / `useSearchParams()` to write `?page=` — you keep the URL benefits while updating in place.

### 9.9 Vanilla JavaScript (no framework)
The building block everything else abstracts — worth knowing cold. Note the URL sync and the delegated listener.

```javascript
const pager = document.querySelector("nav[aria-label='Pagination']");

pager.addEventListener("click", async (e) => {
  const link = e.target.closest("a.page-link, button.page-link");
  if (!link || link.getAttribute("aria-disabled") === "true") return;
  if (link.classList.contains("is-current")) return;   // no-op on current
  e.preventDefault();

  const page = Number(new URL(link.href, location.origin).searchParams.get("page"));

  // Keep the URL in sync so back/forward and refresh work.
  const url = new URL(location.href);
  url.searchParams.set("page", page);
  history.pushState({ page }, "", url);

  await loadPage(page);
});

// Make the browser Back/Forward buttons actually re-load the right page.
window.addEventListener("popstate", (e) => {
  loadPage(e.state?.page ?? 1);
});

async function loadPage(page) {
  const status = document.querySelector(".pagination-status");
  status.textContent = "Loading…";
  const res = await fetch(`/api/articles?page=${page}`);
  const { data, from, to, total } = await res.json();
  renderRows(data);
  status.textContent = `Showing ${from}–${to} of ${total} results`; // announced via aria-live
}
```

The `popstate` handler is the part juniors skip — without it, the pager updates the URL but the Back button does nothing, which is the exact bug that makes SPAs feel broken.

```typescript
      b.addEventListener("click", () =>
        this.dispatchEvent(new CustomEvent("pagechange", { detail: Number(b.dataset.page), bubbles: true }))));
  }
}
customElements.define("ui-pagination", UIPagination);
// <ui-pagination current-page="5" total-pages="20"></ui-pagination>
```

## 10\. Accessibility (non-negotiable)
Pagination is a navigation control, and screen-reader users depend on it to understand _where they are_ and _how much is left_. The details:

*   **Landmark + label:** wrap in `<nav aria-label="Pagination">`. The label is required — a page can have several navs, and "Pagination" is how AT users tell them apart and skip the pager.
*   **A list of links:** the items belong in a `<ul>`/`<li>`. It _is_ a list; mark it as one. Use `<a href>` when there's a URL (shareable, back-button-correct), `<button>` only for pure in-app state.
*   **Current page:** exactly one item carries `aria-current="page"`. This is the single most important a11y attribute here — it's how the screen reader announces "current page." Never rely on color/weight alone.
*   **Meaningful link names:** each numbered link should read as "Go to page 6," not a bare "6" floating out of context. The current one reads "Page 5, current page." Prev/Next read "Previous page" / "Next page," not just "‹" / "›".
*   **Disabled ends done right — not a dead button.** Prev on page 1 must be _announced as unavailable_, not silently missing or an inert `<button disabled>` that vanished from the tab order. Two correct patterns: (a) a `<span aria-disabled="true">` that's still in the reading order but does nothing, or (b) a link without `href` marked `aria-disabled="true"`. The failure mode is a button a screen reader announces as present-and-clickable that does nothing when activated.
*   **The ellipsis is** **`aria-hidden="true"`** and never focusable — it's decoration, not a control. A screen reader hearing "dot dot dot, button" is noise.
*   **Announce page changes.** When the page updates in place (SPA), sighted users see new rows but AT users get silence. Pair the pager with an `aria-live="polite"` status region ("Showing 81–100 of 4,312 results" / "Page 5 loaded") so the change is spoken. Move focus deliberately — often to the results heading or the top of the new list — so keyboard users aren't dumped back at the top of the document.
*   **Keyboard:** every control is Tab-reachable (or the group uses roving tabindex — see the Button reference §9.20), Enter/Space activates, and the focus ring is always visible (`:focus-visible`). Never `outline: none` without a replacement.
*   **Contrast & target size:** page numbers vs. background ≥ 4.5:1 (WCAG AA); the current-page fill must still pass. Every item ≥ 44×44px tap target even when the glyph is small.

## 11\. Innovative & Emerging Ideas
Pagination looks solved but keeps evolving:

*   **Cursor-first by default.** As datasets and live feeds grow, keyset pagination is becoming the standard backend even behind a numbered-looking UI, with the page number mapped to a cached cursor.
*   **Hybrid append + deep-links.** "Load more" or infinite scroll that _still_ writes `?page=`/scroll position to the URL, so you get the graze feel without sacrificing the back-button and SEO — the best-of-both pattern gaining traction.
*   **Prefetch on hover/intent.** Prefetch page N+1 when the user hovers "Next" or nears the bottom, so the next page is instant. Frameworks (Next.js `<Link>` prefetch, TanStack Query prefetching) make this cheap.
*   **`useOptimistic`** **/ instant page swaps.** Render the next page's skeleton immediately and reconcile when data lands, so pagination feels zero-latency.
*   **Virtualized "infinite table."** Windowed rendering (TanStack Virtual) shows a scrollbar over 100k rows while only rendering the visible slice — cursor fetches feed it. Pairs with the Table doc.
*   **View Transitions API.** Native browser cross-fade/slide between pages triggered by the pager, no heavy JS.
*   **Keyset with total estimates.** Postgres `reltuples` or sampled counts give an _approximate_ total ("~4,300 results") so a cursor UI can still show scale without an expensive exact `COUNT`.

## 12\. Conversion & UX Killers (mistakes that bleed money or trust silently)
None of these throw an error. They quietly drop findability, SEO, and trust — which makes them dangerous.

*   **Infinite scroll on findable content.** The classic. Users can't return to a spot, can't reach the footer, can't share a position, and Google can't index past the fold. Reserve it for graze-feeds; paginate anything users need to _find_.
*   **State only in the client, not the URL.** No `?page=`, so refresh loses your place, Back does nothing, and links aren't shareable. The URL _is_ the pagination state — put it there.
*   **Dead disabled buttons at the ends.** A `<button disabled>` prev on page 1 that dropped from the tab order confuses AT users; a button that's announced but silently no-ops is worse. Use `aria-disabled` on a non-actionable element.
*   **No total, no range.** A bare `‹ 1 2 3 ›` with no "of 4,312" leaves users blind to scale and progress. The status line is cheap orientation — ship it.
*   **`OFFSET`** **at depth.** Page 5,000 times out because the query scans and discards 100k rows. Users bail; you blame "traffic." Switch to cursor for deep data.
*   **Unstable ordering.** Ordering by a non-unique column means rows shift, repeat, or vanish across pages as data changes. Add a unique tie-breaker (`id`) to make ordering total.
*   **Missing** **`aria-current`****\*\*\*\*.** The current page is styled but not announced, so screen-reader users have no idea which page they're on.
*   **Unclamped page size.** `?size=100000` lets a client (or attacker) demand a giant fetch. Clamp server-side, always.
*   **Resetting scroll wrong.** Jumping to the very top of the document on page change (losing the table header context) or _not_ scrolling at all (new rows load below the fold, user thinks nothing happened). Scroll to the results region.
*   **Pager on one page of results.** Rendering `1` alone, or "Page 1 of 1," is clutter. Hide the control when there's a single page.

**The through-line:** these fail _quietly_ — no crash, just lower engagement, worse indexation, and users who can't find what they came for. Audit your pager before you audit your bounce rate.

## 13\. Advanced Patterns
The senior-move versions of the patterns above.

**Design tokens for the pager.** Drive it from tokens so a rebrand or dark mode is a variable swap, not a rewrite:

```css
:root {
  --pg-item-size: 40px;
  --pg-radius: 8px;
  --pg-gap: 4px;
  --pg-current-bg: #5F2C82;      /* Eminence */
  --pg-current-fg: #fff;
  --pg-focus: #DCA424;           /* Goldenrod */
}
.page-link { min-width: var(--pg-item-size); min-height: 44px; border-radius: var(--pg-radius); }
.page-link.is-current { background: var(--pg-current-bg); color: var(--pg-current-fg); }
.page-link:focus-visible { outline: 2px solid var(--pg-focus); outline-offset: 2px; }
@media (prefers-color-scheme: dark) { :root { --pg-current-bg: oklch(62% 0.14 305); } }
```

**TypeScript: make illegal pagers unrepresentable.** A discriminated union forces the right props per mode — an offset pager _requires_ a total; a cursor pager _forbids_ one and requires cursors:

```typescript
type OffsetPager = {
  mode: "offset";
  currentPage: number;
  totalItems: number;    // required — offset can count
  pageSize: number;
};
type CursorPager = {
  mode: "cursor";
  hasNextPage: boolean;
  hasPrevPage: boolean;
  startCursor: string | null;
  endCursor: string | null;
  // no totalItems — cursor pagers don't cheaply know it
};
type PagerProps = OffsetPager | CursorPager;
// Now `mode: "cursor"` with `totalItems` won't compile. The type encodes the backend reality.
```

**Encapsulate the URL sync in a hook.** So every table shares one source of truth for page/size:

```typescript
function usePageParams() {
  const params = useSearchParams();
  const router = useRouter();
  const page = Math.max(1, Number(params.get("page")) || 1);
  const size = Math.min(100, Math.max(1, Number(params.get("size")) || 20));
  const setPage = (p: number) => {
    const next = new URLSearchParams(params);
    next.set("page", String(p));
    router.push(`?${next}`, { scroll: false });
  };
  return { page, size, setPage };
}
```

**Prefetch the next page.** Warm the cache on intent so "Next" is instant:

```typescript
onMouseEnter={() => queryClient.prefetchQuery(["articles", page + 1], () => fetchPage(page + 1))}
```

**`aria-live`** **for the systems view.** Treat the pager, the results region, and the status line as one system: page change → fetch → update rows → move focus to the results heading → announce the new range in the live region. A pager that only repaints numbers is a visual fragment; a pager that orients every input mode is an _architecture_.

## 14\. Performance & Bundle Cost
A pager feels free. At scale, the cost is in the query and the render, not the row of numbers.

*   **The query is the cost, not the control.** `OFFSET 100000` scans 100k rows per request; cursor/keyset seeks directly and reads only the page. This is the single biggest performance lever in pagination — see §9.4. On a hot table, that's the difference between a 2ms and a 2,000ms page load.
*   **Skip the** **`COUNT(*)`** **when you can.** Showing an exact total on every page means a `COUNT` over the (filtered) set each request — expensive on big tables. Cursor pagers avoid it with the `limit + 1` trick (§9.5); offset pagers that need a total should cache the count or show an estimate (§11).
*   **Virtualize large page sizes.** A 100-row page still renders 100 DOM subtrees. For dense tables, windowed rendering (TanStack Virtual, `react-window`) renders only the visible rows. Pairs with the Table doc.
*   **Keep the pager height stable during load.** Show skeleton rows at the fixed page height so the pager doesn't jump — animating only `opacity`/`transform`, never `height`, avoids reflow (compositor-only).
*   **The truncation math is O(1).** `paginationRange` builds a fixed-size array regardless of total pages — a 10,000-page set produces the same ~9-item render as a 20-page set. That's the whole point of the ellipsis: bounded UI over unbounded data.
*   **Prefetch, don't preload everything.** Prefetch _the next_ page on hover/idle; don't eagerly fetch all pages. Prefetching one page is a win; fetching fifty is the problem you paginated to avoid.
* * *

## 15\. Security (the pager reaches the server)
Pagination params are user-controlled input hitting your database. Treat them as hostile.

*   **Clamp page size, always.** `?size=100000` (or `?limit=-1`) is a denial-of-service and memory-exhaustion vector. Validate and clamp to a hard max (e.g. 100) server-side. The client's dropdown is a hint, not a limit.
*   **Validate** **`page`****/****`cursor`** **types.** `?page=abc`, `?page=-5`, `?page=1e9` must be coerced/rejected, not passed into a query. A negative or absurd offset can error or leak.
*   **Don't trust the cursor's contents.** A base64 cursor is opaque, not secure — a client can decode and tamper with it. Validate the decoded values (types, ranges) and, critically, **re-scope the query by authorization** so a tampered cursor can't page into another tenant's rows. The cursor says _where_, auth says _whose_.
*   **Authorization scopes every page.** Each page request must re-check that this user may see this data and filter to their rows (`WHERE user_id = ...`). Never assume "the UI only showed their pages" — the endpoint is callable directly with `curl?page=...`.
*   **Rate-limit deep paging.** Scripted crawlers hammering `?page=1..N` are a scraping and cost-abuse pattern. Rate-limit per user/IP; cursor pagination also makes bulk scraping marginally harder than predictable offsets.
*   **Avoid leaking totals you shouldn't.** "Showing 1–20 of 4,312" can reveal the size of a private dataset. For sensitive data, consider omitting exact totals.

## 16\. Senior-Level Checklist (ship-ready)
Before a pager is "done":

- [ ] Wrapped in `<nav aria-label="Pagination">` with a list of items.
- [ ] Real `<a href>` links when pages have URLs; `<button>` only for pure in-app state.
- [ ] Exactly one item carries `aria-current="page"`.
- [ ] Prev/Next disabled-at-ends via `aria-disabled` on a non-actionable element — **not** a dead `<button disabled>`.
- [ ] Ellipsis is `aria-hidden` and not focusable.
- [ ] Truncation logic (`1 … 4 5 6 … 20`) extracted to a pure, unit-tested function.
- [ ] "Showing X–Y of Z" status present and in an `aria-live="polite"` region.
- [ ] Page/size live in the URL (`?page=&size=`) — shareable, refresh-safe, back-button-correct.
- [ ] Page-size selector where it's a data table; changing size resets to page 1.
- [ ] Backend uses cursor/keyset for deep or live data; offset only for small/bounded sets.
- [ ] Ordering is total (unique tie-breaker) so pages don't overlap or skip.
- [ ] Page size clamped server-side; `page`/`cursor` validated; queries scoped by authorization.
- [ ] Single-page and zero-result states handled (hide the pager, don't show "Page 1 of 0").
- [ ] Every control ≥ 44px, keyboard-operable, visible focus ring, contrast ≥ 4.5:1.
- [ ] Focus moves to the results region on page change; the change is announced.

## 17\. Visual Styles (the same pager, eleven skins)
The eleven visual languages, skin-only. **Semantics, keyboard order,** **`aria-current`****\*\*\*\*, focus ring, and 44px targets never change** — only the paint does. Full guidance in the [Design Styles gallery](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200551).

*   **Flat:** solid Eminence fill on the current page, no shadow, crisp edges. Reads instantly; the default for dense tables.
*   **Material:** subtle elevation on hover, ripple on activation, compact "rows per page" framing à la `MatPaginator`.
*   **Glassmorphism:** translucent pager bar with `backdrop-filter: blur()` over a vivid backdrop. Guard number contrast.
*   **Liquid Glass (2026):** a refractive glass track; the current page is a bead of light with a specular rim that slides between positions. Web = layered-highlight approximation; SwiftUI = native `.glassEffect()`. Guard contrast and `prefers-reduced-motion`.
*   **Neumorphism:** soft extruded page pills on a same-color surface; current page pressed _in_. Low contrast — accent use only, guard legibility.
*   **Skeuomorphism:** beveled number "keys," inner highlights, the current page lit like a physical button.
*   **Neo-Brutalism:** thick borders, hard offset shadows, zero radius, the active page a clashing block. Loud and confident.
*   **Claymorphism:** big radius, puffy soft-glow pills, current page inset. Friendly, approachable.
*   **Aurora / Gradient:** animated multi-hue gradient behind the active page on a dark bar. Premium — honor `prefers-reduced-motion` (kill the animation).
*   **Minimal / Swiss:** thin numerals, generous spacing, a single weight change or underline for current. Type does the work.
*   **UJG Brand:** Goldenrod current-page bead on deep Eminence/Night, confident radius, a warm glow on hover. The house default; lean Liquid-Glass for campaign surfaces, Flat/Swiss for Data Alchemy tables.

**Rule that never changes:** style is skin, behavior is the skeleton. Guard glass/liquid-glass/neu for contrast; guard aurora/liquid-glass for `prefers-reduced-motion`.

**Bottom line:** pagination is a two-headed component — a deceptively simple row of numbers sitting on top of the single most important query-performance decision in your app. Get the UI right (semantic `<nav>`, `aria-current`, honest disabled ends, URL-as-state, a real "of Z" status) and get the engine right (cursor for depth, stable total ordering, clamped and authorized params), and you've turned a bottomless dataset into something a user can actually navigate, share, and trust. Match the control to the engine — numbered pages over offset, prev/next over cursor — and never reach for infinite scroll on content people need to find.
