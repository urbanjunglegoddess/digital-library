## 1\. What an Info Label Actually Is
An info label is a **form/section label paired with an info affordance** — the small "ⓘ" or "?" sitting next to the label text that, when activated, surfaces supplementary help. It's the Fluent UI `InfoLabel` pattern: a `<label>` plus an info **button** that opens a popover or toggletip carrying the explanation.

The word "info label" hides four things people constantly conflate:

*   **Info Label (label + on-demand help):** a label with an attached button that _reveals_ secondary help when asked. The help is hidden until the user wants it. This doc.
*   **Field label (plain):** just the `<label>` naming the control. No affordance, no help. Every input needs one of these; not every one needs the info button.
*   **Tooltip (alone):** a small text bubble that appears on hover/focus of _any_ element. Passive, non-interactive, transient. A tooltip attached to an icon is _one possible reveal mechanism_ for an info label — but a tooltip is not itself an info label, and (see §7) it's usually the wrong mechanism.
*   **Inline help text:** persistent explanatory text rendered _below the field_, always visible. This is `aria-describedby` help that never hides.

The distinction that trips people: **an info label is a composition, not a control.** It's a label + a button + a reveal surface. The single most common mistake is building the affordance as a bare icon (`<span>ⓘ</span>` or an `<svg>` with a hover title) instead of a real, focusable `<button>` with an accessible name. That icon-as-decoration version is invisible to keyboards and screen readers — the entire help content simply doesn't exist for a chunk of your users.

Rule of thumb: **if the help is essential to filling the field correctly, it's inline help text (always visible). If it's optional or secondary, it's an info label (revealed on demand). If it's a passing hint on any element, it's a tooltip.** Pick deliberately.
* * *

## 2\. Why It Matters
The info label looks like a nicety. It's actually load-bearing for three things:

*   **Form completion and conversion.** Every field that confuses a user is a field they abandon. The info label lets you keep the form _visually clean_ (short labels, no walls of text) while still answering "wait, what does 'routing number' mean?" the instant they ask. Progressive disclosure done right lifts completion without cluttering the layout.
*   **Trust and comprehension.** "Why do you need my date of birth?" "What counts as a strong password here?" "What's a MSA?" A well-placed ⓘ answers the objection at the exact moment it forms, inside the flow, without a support ticket. That's the difference between a form that feels considerate and one that feels extractive.
*   **Accessibility, which is where this component lives or dies.** The info affordance is the single most commonly botched accessibility pattern in forms. A hover-only tooltip on a non-focusable icon fails keyboard users, screen-reader users, touch users, and anyone who can't hover — which is a lot of people. Get the info label right and you've internalized the hardest 20% of accessible-widget engineering: accessible names, focus management, `Esc` to dismiss, and associating help with the thing it describes.
* * *

## 3\. Anatomy of an Info Label
Every correctly-built info label is composed of predictable parts:

*   **Label text:** the `<label for="…">` naming the field. Verb-or-noun clear ("Routing number," not "RN"). This is the primary, always-visible content.
*   **Info trigger:** a real `<button type="button">` — not a span, not a bare SVG. It carries the icon and an **accessible name** ("More info about routing number"). It's a genuine tab stop.
*   **Icon:** the glyph inside the trigger — ⓘ (info) or ? (help). Decorative to assistive tech (`aria-hidden="true"`) because the button's accessible name already carries the meaning.
*   **Reveal surface:** the thing that opens — a **toggletip** or **popover** (usually) or a tooltip (rarely). Holds the supplementary help. Can be plain text or rich/interactive content (links, formatting).
*   **The field it describes:** the actual `<input>`/`<select>`/control. When the help is short and essential, it's wired to the field via `aria-describedby`.
*   **Dismiss affordance:** `Esc` closes the reveal; clicking outside closes it; focus returns to the trigger. For popovers, an explicit close button when content is long.

The mental model: **label + button + surface.** Three parts, one composition. Drop any and you've got a different (usually broken) thing.
* * *

## 4\. Reveal Surface: Sizing & Density
The trigger is a button, so it inherits button sizing — but it's usually an _icon button_ at the small end, sitting next to label text. Real values:

| Token | Trigger size | Icon glyph | Reveal max-width | Use |
| ---| ---| ---| ---| --- |
| Compact | 20×20px (44px hit area) | 14px | 240px | Dense forms, table headers |
| Default | 24×24px (44px hit area) | 16px | 320px | Most forms |
| Comfortable | 28×28px | 18px | 360px | Marketing forms, onboarding |

Rules that matter:

*   **The visible trigger can be 20px, but the hit target stays ≥44px.** Expand it with padding or a pseudo-element. This is the exact same rule as any icon button — small glyph, generous tappable area. A 16px icon you have to pixel-hunt for on mobile is a rage-tap.
*   **The reveal surface gets a max-width (~40–60ch)** so long help wraps into readable lines instead of a single 900px sentence.
*   **Vertical rhythm:** the trigger's optical center should align with the label's cap height, not its baseline. Use `align-items: center` on the label row and the ⓘ sits right.
*   **Never let the trigger inflate the label's line-height** and push the field down. Constrain the button's box.
* * *

## 5\. States (the part juniors forget)
The info label has states on _two_ objects: the trigger and the reveal. Missing states are the tell of an amateur build.

**The trigger (button) states:**

1. **Default (rest)** — muted icon color, no background. It should read as "optional, here if you need it," not compete with the label.
2. **Hover** — subtle bg or color shift. (Touch has no hover, so never make hover the _only_ way content appears.)
3. **Focus** — reachable by keyboard, visible ring via `:focus-visible`. Non-negotiable.
4. **Active (pressed)** — the moment of click. Slight darken.
5. **Expanded / open** — the reveal is showing. Reflect it with `aria-expanded="true"` (for popover/toggletip triggers) so screen readers announce the state.
6. **Disabled** — rare for info triggers (if the field is disabled, the help usually still helps). If you do disable it, say why.

**The reveal surface states:**

1. **Closed** — default; not in the DOM's accessibility tree, or hidden.
2. **Open** — visible, positioned, focus handled. For a popover, focus may move into it; for a toggletip, focus stays on the trigger and content is announced via a live region.
3. **Positioned / flipped** — when there's no room below, it flips above or shifts to stay in the viewport (collision handling — see §13).
4. **Dismissing** — `Esc`, outside-click, or scroll closes it; focus returns to the trigger.

The through-line juniors miss: **`aria-expanded`** **on the trigger and focus-return on dismiss.** If activating the ⓘ doesn't announce "expanded" and dismissing doesn't put focus back where it was, the widget is broken for keyboard and screen-reader users even if it looks perfect.
* * *

## 6\. Types & Variants
Info labels vary along two axes: the **icon** and the **reveal mechanism**.

**By icon:**

*   **Info (ⓘ):** neutral "here's more context." The default. Reads as supplementary detail, definitions, "why we ask."
*   **Help (?):** "you might be confused; here's clarification." Slightly more remedial in tone. Common in settings and technical forms.
*   **Rule:** never use a raw icon with no accessible name. The glyph is decorative; the button's name ("More info about X") is what carries meaning. See §10.

**By reveal mechanism** (the real decision — see §7):

*   **Tooltip-style:** hover/focus reveals a short text bubble. Simplest, but the most fragile for accessibility. Only honest for _very short, non-interactive, non-essential_ text.
*   **Toggletip:** click a button to toggle a small bubble; content announced via an `aria-live` region. Correct when the help is short but you need it to be reliably reachable by touch and screen readers.
*   **Popover:** click a button to open a positioned surface that can hold rich, long, or interactive content (links, formatting, a "learn more"). The default for anything beyond a sentence. Focus can move inside; `Esc` closes.

**By content weight:**

*   **Definition:** one-liner explaining a term ("Routing number: the 9-digit number identifying your bank").
*   **Rationale:** "why we ask" ("We use this to verify your identity; we never share it").
*   **Rich help:** multiple sentences, a link to docs, an example image. Popover territory.
* * *

## 7\. When to Use One (and When Not To) — plus the reveal-mechanism decision
Use an info label when help is **optional or secondary** — useful to some users, some of the time, but not required to complete the field. Reach for something else when:

*   **The info is essential to every user.** Then it's not on-demand help — it's **inline help text** rendered below the field and wired with `aria-describedby`, always visible. Hiding essential instructions behind a click is user-hostile. ("Password must be 12+ characters" is inline help, not an ⓘ.)
*   **It's a passing hint on a non-form element.** A truncated table cell, an icon-only toolbar button — that's a plain **Tooltip** on the element itself, not a label+button composition.
*   **The "help" is really an error.** Validation feedback goes in an inline error region with `aria-live`, not behind an info icon.
*   **You'd need one on every field.** If every field has a ⓘ, your labels are too terse. Fix the labels first; reserve the info affordance for genuine edge cases.

### The reveal-mechanism decision (the crux of this component)
This is the choice that separates a correct info label from a broken one. Three options, one usually right:

**Tooltip — usually wrong here.** A tooltip appears on hover/focus and vanishes on blur. The problems: (1) **hover doesn't exist on touch**, so mobile users can't trigger it reliably; (2) a tooltip **can't hold interactive content** — you can't put a link in it, because moving toward the link dismisses it; (3) screen-reader support for `title`\-style and even ARIA tooltips is **inconsistent** — the content is frequently not announced, or announced at the wrong time. A tooltip is only honest for a _short, static, non-essential_ hint, and even then a toggletip is safer.

**Toggletip — right when help is short but must be reachable.** A toggletip is a **button you click** (not hover) that toggles a small bubble; the bubble's text is placed inside an `aria-live` region so it's _announced_ when it appears. Because it's click-driven, it works on touch. Because it uses a live region, screen readers reliably read it. Use it for short definitions and "why we ask" one-liners.

**Popover — right when content is long or interactive.** A popover is a positioned surface opened by a button, that can hold **rich content**: multiple sentences, formatting, links, a "learn more," even an image. Focus can move inside it; `Esc` closes it; focus returns to the trigger. This is the default for anything beyond a single short sentence, and it's what Fluent's `InfoLabel` uses.

**The heuristic:** _short + static + non-essential_ → toggletip. _Long or interactive_ → popover. _Only reach for a bare tooltip when the content is trivial and you accept its accessibility limits._ The reason a toggletip/popover beats a tooltip almost every time: **tooltips can't be reliably read and can't hold anything you'd want to interact with**, and info-label help is often exactly the kind of content (a link to docs, a formatted definition) that a tooltip can't carry. Cross-link the Tooltip and Popover docs for the full mechanics of each surface.

## 8\. Info Labels Across Design Systems
Same idea, different names and defaults. Knowing these makes you fluent anywhere.

*   **Fluent (Microsoft):** ships an actual **`InfoLabel`** component — a `Label` plus an `InfoButton` that opens a **popover** with the help content. This is the canonical named pattern and the reference for this doc. The info button is a real button with an accessible name; the surface is a popover, not a tooltip.
*   **Material Design (Google):** no single "info label" primitive. You compose a `FormField` label with an `IconButton` (info icon) that opens a **rich tooltip** (Material 3's rich tooltip _is_ interactive and dismissible — closer to a popover than a classic tooltip) or a small dialog. Supporting text below the field covers the "always visible" case.
*   **Apple HIG (iOS/macOS):** the info button is a first-class control — the "ⓘ" **`.infoButton`** / info-style button — typically opening a popover on macOS or a detail sheet on iOS. Apple is explicit that info reveals _more detail_, not essential instructions.
*   **Ant Design / enterprise:** `Form.Item` label supports a `tooltip` prop that renders a `QuestionCircleOutlined` icon with a **popover-backed** hint. Extremely common in dense admin UIs; Ant wires the icon as a focusable trigger for you.
*   **Carbon (IBM):** `Toggletip` and `Tooltip` are separate, documented components, and Carbon is explicit about the distinction — Toggletip for interactive/clickable help, Tooltip for short passive hints. Their guidance mirrors §7 exactly.
*   **Tailwind / utility-first:** no prescribed component. You compose a label, an icon button, and a positioned surface (often with Radix or Floating UI for behavior). Freedom + the risk of shipping the broken hover-span version if you're not careful.
*   **shadcn/Radix:** `Popover` (or `HoverCard`/`Tooltip`) primitives from Radix give you the behavior and accessibility; you compose the info label from `Label` + a `Button` + `Popover`. Radix handles focus, `Esc`, and outside-click for free — which is the whole point.

## 8b. Visual Styles (the same info label, eleven skins)
The info label's _skin_ can change; its skeleton cannot. The trigger stays a focusable button, `Esc` still closes, the accessible name still exists, the 44px target holds — across all eleven. See the [Design Styles gallery](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200551) for the full treatment.

*   **Flat:** muted circular ⓘ, no shadow; the reveal is a plain card with a hairline border.
*   **Material:** icon button with a ripple on press; the reveal is a rich tooltip with elevation shadow.
*   **Glassmorphism:** the popover is translucent with `backdrop-filter: blur()` over a vivid background. Watch contrast on the help text.
*   **Liquid Glass (the 2026 trend):** Apple's iOS 26 / macOS Tahoe material — the popover is a refractive translucent surface with a specular rim and a moving sheen, not a static blur. Pill-ish, reactive. Guard for contrast and reduced-motion.
*   **Neumorphism:** the ⓘ is a soft extruded circle on a same-color surface. Pretty, contrast-poor — accent only, and don't hide essential help behind a barely-visible glyph.
*   **Skeuomorphism:** a beveled, glossy "?" that looks like a physical help button; the reveal reads like a paper note.
*   **Neo-Brutalism:** hard black ring around the ⓘ, thick border on the popover, offset shadow, zero radius. High personality.
*   **Claymorphism:** puffy rounded ⓘ with inner light and soft glow; the popover is a big-radius soft card.
*   **Aurora / Gradient:** the icon or popover border carries an animated multi-hue gradient. Honor `prefers-reduced-motion`.
*   **Minimal / Swiss:** a thin "?" set in the type scale, the reveal a tight card with generous whitespace and no decoration.
*   **UJG Brand:** Goldenrod ⓘ on deep Eminence/Night; the popover is a warm-glow card, Goldenrod focus ring, Platinum help text on the dark field. Confident radius, warm and legible.

**Rule that never changes:** style is skin, behavior is the skeleton. Guard glass / liquid-glass / neumorphism for contrast (help text must clear 4.5:1); guard aurora / liquid-glass for `prefers-reduced-motion`.

## 9\. The Code
### 9.1 HTML (the foundation everyone should master first)
The composition, done honestly. Note: the affordance is a **button**, and it has an **accessible name**.

```plain
<!-- Info label: label text + a real button that reveals help -->
<div class="field">
  <span class="field__labelrow">
    <label for="routing" class="field__label">Routing number</label>

    <!-- The affordance is a BUTTON, not a bare icon/span -->
    <button
      type="button"
      class="info-trigger"
      aria-label="More info about routing number"
      aria-expanded="false"
      aria-controls="routing-help"
    >
      <svg aria-hidden="true" focusable="false" width="16" height="16"><!-- ⓘ --></svg>
    </button>
  </span>

  <input id="routing" name="routing" inputmode="numeric" />

  <!-- The revealed help (popover-style surface) -->
  <div id="routing-help" role="dialog" aria-label="Routing number help" hidden>
    The 9-digit number identifying your bank, on the bottom-left of a check.
    <a href="/help/routing">Learn more</a>
  </div>
</div>

<!-- Contrast: ESSENTIAL help is inline text, always visible, wired to the field -->
<label for="pw">Password</label>
<input id="pw" type="password" aria-describedby="pw-help" />
<p id="pw-help" class="help-text">Must be at least 12 characters.</p>
```

Key HTML rules:

*   **The trigger is a** **`<button type="button">`****\*\*\*\*\*\*\*\*.** Not a `<span>`, not a bare `<svg>`, not a `<div onClick>`. Only a real button is focusable, keyboard-operable, and exposed with role `button` for free. `type="button"` so it never submits the form.
*   **The button has an accessible name** via `aria-label` ("More info about X"). The icon inside is `aria-hidden="true"` and `focusable="false"` so it's decorative — the button name carries all the meaning.
*   **`aria-expanded`** **reflects open/closed** for popover/toggletip triggers; **`aria-controls`** points at the reveal.
*   **Essential help is a separate, always-visible** **`<p>`** wired with `aria-describedby` on the input — _not_ hidden behind the button.

### 9.3 React + TypeScript (a proper reusable InfoLabel)
The Fluent-style API: a label plus an info button that opens a popover, with focus management, `Esc` to close, and outside-click dismissal. This is the longest block on purpose — it's the component.

```typescript
import {
  forwardRef, useId, useRef, useState, useEffect, useCallback,
  type ReactNode, type LabelHTMLAttributes,
} from "react";

type Reveal = "popover" | "toggletip";

interface InfoLabelProps extends Omit<LabelHTMLAttributes<HTMLLabelElement>, "children"> {
  /** The visible label text. */
  label: ReactNode;
  /** id of the form control this labels (the <label for>). */
  htmlFor: string;
  /** The help content revealed by the info button. */
  info: ReactNode;
  /** popover (rich/long, focusable) or toggletip (short, announced). */
  reveal?: Reveal;
  /** ? vs ⓘ */
  icon?: "info" | "help";
  /** Accessible name for the trigger; defaults from the label. */
  infoButtonLabel?: string;
}

export const InfoLabel = forwardRef<HTMLLabelElement, InfoLabelProps>(
  ({ label, htmlFor, info, reveal = "popover", icon = "info",
     infoButtonLabel, ...labelRest }, ref) => {
    const [open, setOpen] = useState(false);
    const surfaceId = useId();
    const triggerRef = useRef<HTMLButtonElement>(null);
    const surfaceRef = useRef<HTMLDivElement>(null);

    const name =
      infoButtonLabel ??
      (typeof label === "string" ? `More info about ${label}` : "More info");

    const close = useCallback(() => {
      setOpen(false);
      triggerRef.current?.focus();     // focus returns to the trigger
    }, []);

    // Esc closes; outside-click closes
    useEffect(() => {
      if (!open) return;
      const onKey = (e: KeyboardEvent) => { if (e.key === "Escape") close(); };
      const onDown = (e: PointerEvent) => {
        const t = e.target as Node;
        if (!surfaceRef.current?.contains(t) && !triggerRef.current?.contains(t)) {
          setOpen(false);
        }
      };
      document.addEventListener("keydown", onKey);
      document.addEventListener("pointerdown", onDown);
      return () => {
        document.removeEventListener("keydown", onKey);
        document.removeEventListener("pointerdown", onDown);
      };
    }, [open, close]);

    // Popover: move focus into the surface. Toggletip: keep focus on trigger.
    useEffect(() => {
      if (open && reveal === "popover") surfaceRef.current?.focus();
    }, [open, reveal]);

    return (
      <span className="field__labelrow">
        <label ref={ref} htmlFor={htmlFor} className="field__label" {...labelRest}>
          {label}
        </label>

        <button
          ref={triggerRef}
          type="button"
          className="info-trigger"
          aria-label={name}
          aria-expanded={open}
          aria-controls={surfaceId}
          onClick={() => setOpen((o) => !o)}
        >
          <InfoIcon kind={icon} />
        </button>

        {/* Popover: a focusable dialog. Toggletip: a live region. */}
        {reveal === "popover" ? (
          <div
            id={surfaceId}
            ref={surfaceRef}
            role="dialog"
            aria-label={typeof label === "string" ? `${label} help` : "Help"}
            className="info-popover"
            tabIndex={-1}
            hidden={!open}
          >
            {info}
          </div>
        ) : (
          <span
            id={surfaceId}
            role="status"
            aria-live="polite"
            className="info-toggletip"
            hidden={!open}
          >
            {open ? info : null}
          </span>
        )}
      </span>
    );
  }
);
InfoLabel.displayName = "InfoLabel";

function InfoIcon({ kind }: { kind: "info" | "help" }) {
  return (
    <svg aria-hidden="true" focusable="false" width="16" height="16" viewBox="0 0 16 16">
      <circle cx="8" cy="8" r="7" fill="none" stroke="currentColor" strokeWidth="1.5" />
      <text x="8" y="12" textAnchor="middle" fontSize="10" fill="currentColor">
        {kind === "help" ? "?" : "i"}
      </text>
    </svg>
  );
}
```

Why this is the senior version, not the junior one:

*   **The trigger is a real button** with an accessible name derived from the label ("More info about Routing number"). No bare icon, ever.
*   **`reveal`** **switches the surface's semantics**, not just its look: a popover is a focusable `role="dialog"`; a toggletip is a `role="status"` live region that _announces_ its text when it appears. This is the §7 decision encoded in the API.
*   **Focus is managed:** popover moves focus in; both return focus to the trigger on close. `Esc` and outside-click close.
*   **`aria-expanded`** **tracks state** so assistive tech announces open/closed.
*   **Extends native** **`label`** **attributes** so `className`, `id`, etc. pass through.

Usage:

```typescript
<InfoLabel
  htmlFor="routing"
  label="Routing number"
  reveal="popover"
  info={<>The 9-digit number on the bottom-left of a check. <a href="/help">Learn more</a></>}
/>
<input id="routing" inputMode="numeric" />
```

### 9.5 shadcn/ui + Radix (the 2024+ standard)
Radix `Popover` gives you focus management, `Esc`, and outside-click for free. You compose the info label from `Label` + `Button` + `Popover` — which is the whole reason to reach for it.

```typescript
import * as Popover from "@radix-ui/react-popover";
import { Label } from "@/components/ui/label";
import { Info } from "lucide-react";   // named import — tree-shakeable

export function InfoLabel({
  htmlFor, label, info,
}: { htmlFor: string; label: string; info: React.ReactNode }) {
  return (
    <span className="inline-flex items-center gap-1.5">
      <Label htmlFor={htmlFor}>{label}</Label>
      <Popover.Root>
        <Popover.Trigger asChild>
          <button
            type="button"
            aria-label={`More info about ${label}`}
            className="grid h-6 w-6 place-items-center rounded-full text-muted-foreground
                       hover:text-foreground focus-visible:outline-none
                       focus-visible:ring-2 focus-visible:ring-ring">
            <Info aria-hidden className="h-4 w-4" />
          </button>
        </Popover.Trigger>
        <Popover.Portal>
          <Popover.Content
            sideOffset={6}
            className="max-w-xs rounded-md border bg-popover p-3 text-sm shadow-md
                       data-[state=open]:animate-in"
          >
            {info}
            <Popover.Arrow className="fill-popover" />
          </Popover.Content>
        </Popover.Portal>
      </Popover.Root>
    </span>
  );
}
```

Radix wires `aria-expanded`, `aria-controls`, focus trapping-and-return, and `Esc` on the trigger/content pair. `asChild` merges Popover behavior onto _your_ button so you keep `type="button"` and your own accessible name. This is the least-code correct version.

### 9.8 Web Component (framework-agnostic)
Works in any framework or none. Shadow DOM scopes the styles.

```typescript
class InfoLabel extends HTMLElement {
  static observedAttributes = ["label", "for", "info"];
  private open = false;
  connectedCallback() {
    this.attachShadow({ mode: "open" });
    this.render();
    this.addEventListener("keydown", (e) => {
      if ((e as KeyboardEvent).key === "Escape") this.setOpen(false);
    });
  }
  attributeChangedCallback() { if (this.shadowRoot) this.render(); }
  setOpen(v: boolean) { this.open = v; this.render(); }
  render() {
    const label = this.getAttribute("label") ?? "";
    const info = this.getAttribute("info") ?? "";
    const forId = this.getAttribute("for") ?? "";
    // Build the STATIC skeleton only — never interpolate user data into the HTML string.
    this.shadowRoot!.innerHTML = `
      <style>/* scoped: trigger + popover styles */</style>
      <span part="row">
        <label part="label"></label>
        <button type="button" part="trigger"
                aria-expanded="${this.open}" aria-controls="info-surface">ⓘ</button>
        <div id="info-surface" role="dialog" part="popover"
             ${this.open ? "" : "hidden"}></div>
      </span>`;
    // Assign dynamic values as TEXT / attributes — never via innerHTML.
    // (escapes XSS, matching §15; run rich help through DOMPurify if HTML is required)
    const labelEl = this.shadowRoot!.querySelector("label")!;
    const btn = this.shadowRoot!.querySelector("button")!;
    const surface = this.shadowRoot!.getElementById("info-surface")!;
    labelEl.setAttribute("for", forId);
    labelEl.textContent = label;
    btn.setAttribute("aria-label", `More info about ${label}`);
    surface.setAttribute("aria-label", `${label} help`);
    surface.textContent = info;
    btn.addEventListener("click", () => this.setOpen(!this.open));
  }
}
customElements.define("info-label", InfoLabel);
// Usage: <info-label for="routing" label="Routing number" info="The 9-digit…"></info-label>
```

### 9.10 Testing (unit + a11y)
An info label is behavior — you test behavior, not markup. The four assertions that matter: the trigger has an accessible name, activating it reveals the help, `Esc` closes it and returns focus, and axe is clean.

```typescript
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { axe } from "jest-axe";
import { describe, it, expect } from "vitest";
import { InfoLabel } from "./InfoLabel";

const setup = () =>
  render(<InfoLabel htmlFor="x" label="Routing number" info="The 9-digit number." />);

describe("InfoLabel", () => {
  it("exposes a named info button (not a bare icon)", () => {
    setup();
    expect(
      screen.getByRole("button", { name: /more info about routing number/i })
    ).toBeInTheDocument();
  });

  it("reveals help on activation and marks expanded", async () => {
    setup();
    const trigger = screen.getByRole("button", { name: /more info/i });
    expect(trigger).toHaveAttribute("aria-expanded", "false");
    await userEvent.click(trigger);
    expect(trigger).toHaveAttribute("aria-expanded", "true");
    expect(screen.getByText(/9-digit number/i)).toBeVisible();
  });

  it("closes on Escape and returns focus to the trigger", async () => {
    setup();
    const trigger = screen.getByRole("button", { name: /more info/i });
    await userEvent.click(trigger);
    await userEvent.keyboard("{Escape}");
    expect(screen.queryByText(/9-digit number/i)).not.toBeVisible();
    expect(trigger).toHaveFocus();          // focus came back
  });

  it("is keyboard operable", async () => {
    setup();
    await userEvent.tab();                   // reach the label's field or trigger
    await userEvent.tab();
    await userEvent.keyboard("{Enter}");     // activate whatever trigger is focused
  });

  it("has no axe violations", async () => {
    const { container } = setup();
    expect(await axe(container)).toHaveNoViolations();
  });
});
```

What to assert (and skip):

*   **Do test:** the button is found `byRole` with its name (proves the icon isn't bare), activation toggles `aria-expanded` and reveals the text, `Esc` closes and returns focus, axe passes.
*   **Don't test:** exact class names, the SVG's path data, popover pixel coordinates. Implementation details that break tests without catching real bugs.

## 10\. Accessibility (non-negotiable — this is the whole game)
The info label is _the_ component where accessibility is the point. Get these right:

*   **Real** **`<button>`** **for the trigger.** It comes with role, keyboard operability (Enter/Space), and focus for free. A `<span>`, bare `<svg>`, or `<div onClick>` is invisible to keyboards and screen readers — the help ceases to exist for those users. This is the single most-failed rule.
*   **Accessible name on the trigger.** `aria-label="More info about routing number"` — specific, not "info" or "?". The visible glyph is `aria-hidden="true"` and `focusable="false"` (the latter stops IE/legacy from tab-stopping the SVG). Never rely on the icon alone to convey meaning.
*   **The info button is a real tab stop.** It's in the natural tab order. Don't `tabindex="-1"` it.
*   **Keyboard:** Enter/Space activates (native button behavior). **`Esc`** **closes** the reveal. When it closes, **focus returns to the trigger** — never dumped to `<body>`.
*   **Reveal semantics match the mechanism:** a **popover** is `role="dialog"` and focus can move into it; a **toggletip** puts its text in an `aria-live="polite"` / `role="status"` region so it's _announced_ when it appears. A bare **tooltip** relies on `aria-describedby` pointing at the bubble — but see §7 for why tooltips are unreliable here.
*   **`aria-expanded`** on the trigger reflects open/closed for popover/toggletip patterns; **`aria-controls`** points at the surface.
*   **Associate essential help with the field via** **`aria-describedby`****\*\*\*\*\*\*\*\*.** When the help is short and needed to fill the field, wire the input to it: `<input aria-describedby="help-id">`. Then the help is read as part of the field's description — no click required. Reserve the click-to-reveal button for _optional_ detail.
*   **Contrast:** the icon and the help text both clear **4.5:1** against their background. A muted-gray ⓘ that's decorative-faint can fail — mute the color, not the contrast.
*   **Touch target ≥ 44px** even when the glyph is 16–20px. Expand with padding/pseudo-element.
*   **Don't hide essential instructions behind the affordance.** If a user _must_ read it to succeed, it's inline help text, always visible. The info button is for the optional layer.

## 11\. Innovative & Emerging Ideas
The info label looks solved but keeps moving:

*   **Native HTML Popover API:** `popovertarget` wires a button to a `popover` element with light-dismiss (`Esc` + outside-click) and top-layer rendering **with zero JavaScript**. `<button popovertarget="help">ⓘ</button><div id="help" popover>…</div>`. This is quickly becoming the correct default for the reveal surface — the browser handles focus and dismissal.
*   **CSS Anchor Positioning:** `anchor()` positions the popover relative to the trigger natively, with automatic collision flipping (`position-try`), retiring most of the Floating UI / Popper JS math.
*   **AI-generated contextual help:** the info content assembled on the fly from a docs source or model, so the ⓘ answers "what does this field mean _for me_" rather than a static string. Streaming into the popover replaces the old static bubble.
*   **`aria-description`** **(emerging):** a more direct way to attach a description than `aria-describedby` juggling, once support solidifies.
*   **Progressive disclosure analytics:** instrumenting which ⓘ's get opened tells you which labels are unclear — the info label doubles as a UX research signal (see §12).
* * *

## 12\. Conversion / UX Killers (the silent ones)
None of these throw an error. They just quietly cost you completed forms and trust.

*   **Bare-icon affordance.** A `<span>ⓘ</span>` with a `title` or a hover-only tooltip: invisible to keyboard, touch, and screen readers. The help exists for mouse users only. This is the #1 tell of an amateur build — and it's an accessibility lawsuit waiting to happen.
*   **Tooltip carrying a link.** You put "Learn more" in a hover tooltip; the user moves toward it, the tooltip vanishes, the link is unreachable. If the help is interactive, it's a popover — period (§7).
*   **Hiding essential info behind the ⓘ.** "Password must be 12+ chars" behind a click means users fail validation, get frustrated, and bounce. Essential = inline and visible.
*   **A ⓘ on every field.** If everything has one, your labels are too terse and users tune the icons out entirely. Fix the labels; reserve the affordance.
*   **Mystery-meat icon with a vague name.** A "?" whose button is named "help" or nothing. The screen-reader user hears "button" and has no idea what it explains. Name it "More info about X."
*   **No dismiss / focus trap escape.** The popover opens and there's no `Esc`, no outside-click close, or focus never returns to the trigger. Keyboard users get stranded.
*   **Content that shifts layout.** The reveal pushes the form fields down when it opens, so the user loses their place and mis-taps. Render it in the top layer (Popover API / portal), overlapping, not inline-pushing.
*   **Faint icon that fails contrast.** A pale-gray ⓘ that reads as "disabled" or is invisible on the background. Muted ≠ sub-4.5:1.

**The through-line:** these all fail _quietly_ — no crash, just a slightly lower completion rate and a slice of users who literally can't reach your help. Audit your info affordances before you blame the form length.

## 13\. Advanced Patterns
Techniques that lean on the platform and the type system instead of hand-rolled JS.

### Native Popover API + Anchor Positioning (near-zero JS)
The 2026 correct default. The button, the light-dismiss, and the positioning are all declarative:

```plain
<button type="button" class="info-trigger"
        popovertarget="routing-help"
        aria-label="More info about routing number"
        style="anchor-name: --routing-info">ⓘ</button>

<div id="routing-help" popover="auto" class="info-popover"
     style="position-anchor: --routing-info; position-area: block-end;">
  The 9-digit number identifying your bank. <a href="/help">Learn more</a>
</div>
```

`popover="auto"` gives you `Esc` + outside-click dismissal and top-layer rendering free; `position-area` + `position-try` flip it into view near the trigger with no JS positioning library. Progressive enhancement: falls back to a static block where unsupported.

### TypeScript: force the accessible name at compile time
Make it impossible to ship an unnamed info button. A discriminated union requires either a string `label` (from which the name derives) or an explicit `infoButtonLabel`:

```typescript
type WithDerivableName = { label: string; infoButtonLabel?: string };
type WithExplicitName  = { label: React.ReactNode; infoButtonLabel: string };
type InfoLabelName = WithDerivableName | WithExplicitName;
// A non-string label now REQUIRES infoButtonLabel — the compiler enforces the a11y rule.
```

### Choosing the surface from content, in the API
Bake the §7 decision into a prop the type system understands, so a long/interactive `info` can't ship as a fragile tooltip:

```typescript
type RevealFor<T> =
  T extends string ? "tooltip" | "toggletip" | "popover"  // short: any
  : "popover";                                            // rich node: popover only
```

### aria-describedby vs. click-to-reveal — the association pattern
The nuance most people miss: **short essential help should be** **_both_** **visible and associated**, while optional help is _revealed_. Wire the two layers explicitly:

```plain
<label for="pw">Password</label>
<input id="pw" type="password"
       aria-describedby="pw-req">
<p id="pw-req">Must be at least 12 characters.</p>          <!-- always visible, essential -->
<button popovertarget="pw-optional-pop" aria-label="More info about password strength">ⓘ</button>
<div id="pw-optional-pop" popover>Mix cases and symbols for a stronger score.</div>
```

The essential requirement is inline and in `aria-describedby`; the optional nicety is behind the ⓘ. That's the whole design philosophy of the component in five lines.

## 14\. Performance & Bundle Cost
The info label feels free. At scale it isn't quite.

*   **The icon-import trap.** The most common perf mistake: `import * as Icons from "lucide-react"` to get one ⓘ pulls the whole library. Use the named import — `import { Info } from "lucide-react"` — so the bundler tree-shakes the rest. On a form with a dozen info labels this is the difference between 2KB and 300KB.
*   **Don't mount every popover eagerly.** A form with 20 info labels shouldn't render 20 hidden dialogs into the DOM on load. Render the reveal surface **lazily on first open** (conditional render, not `display:none` on a pre-built tree) so the initial DOM stays lean.
*   **Prefer the native Popover API over a JS positioning library** where support allows. Floating UI / Popper is ~10–15KB and runs layout math every frame while open; `position-anchor` + `position-try` is free and native.
*   **Delegate, don't multiply listeners.** 50 info triggers with 50 individual `keydown`/outside-click listeners is wasteful. One delegated document listener that reads which trigger is open scales better (the native Popover API does this for you).
*   **Animate only** **`transform`****/****`opacity`** on the reveal, never `width`/`height`/`top` — those force reflow every frame. Respect `prefers-reduced-motion`.
* * *

## 15\. Security
An info label is almost pure presentation, so its attack surface is genuinely small — but three real edges are worth naming. First, if the help content is user- or CMS-authored, escape or sanitize it before it lands in the reveal surface: a toggletip or popover that assigns it via `innerHTML` (or `v-html`, `dangerouslySetInnerHTML`, `[innerHTML]`) is a stored-XSS hole — render help as text, or run it through a sanitizer like DOMPurify. Second, info popovers frequently carry links, so any external `<a>` needs `rel="noopener noreferrer"` so the opened page can't reach back through `window.opener` and can't leak a full referrer. Third, don't treat help text as a hiding place: it ships to every client in the initial payload or CMS response and is trivially readable in DevTools, so keep secrets, internal IDs, and authorization-sensitive detail out of it — "hidden until hover" is not access control. Beyond those, the component introduces essentially no new surface; it's a button and a bubble, and the security work is the same escaping-and-linking discipline you already owe every other component.

## 16\. Senior-Level Checklist (ship-ready)
Before an info label is "done":

- [ ] The trigger is a real `<button type="button">` — never a span, bare `<svg>`, or `<div onClick>`.
- [ ] The button has a specific accessible name ("More info about X"), not "info" or "?".
- [ ] The icon inside is `aria-hidden="true"` and `focusable="false"`.
- [ ] Reveal mechanism chosen deliberately: toggletip (short) or popover (long/interactive); tooltip only for trivial static hints.
- [ ] `aria-expanded` reflects open/closed; `aria-controls` points at the surface.
- [ ] `Esc` closes the reveal; outside-click closes it; **focus returns to the trigger**.
- [ ] Popover content is reachable (focus moves in) or announced (toggletip live region).
- [ ] Essential help is inline + `aria-describedby`, not hidden behind the button.
- [ ] Icon and help text both clear 4.5:1 contrast; touch target ≥ 44px.
- [ ] Reveal renders in the top layer / portal — doesn't shift the form layout.
- [ ] Icons imported by name (tree-shakeable); surfaces mounted lazily.
