## 1\. What a Combo Box Actually Is
A combo box is a **text input fused to a popup listbox that the text filters.** You type; the list narrows; you pick. That fusion — a free-typing field _plus_ a constrained set of options — is the entire identity of the component. Everything else is a variation on it.

The word gets slapped on three different things that are _not_ the same, and picking the wrong one is the most common architecture mistake in this whole area:

*   **Combo box (input + filtered listbox):** a text field with `role="combobox"` that expands a listbox of options the text filters. May allow free text or force a choice. Autocomplete, typeahead, "search this dropdown," command palette — all combo boxes. This doc.
*   **Select / native dropdown (****`<select>`****):** you pick from a _fixed_ list. **No typing to filter** (beyond the browser's crude first-letter jump). No free text. It's a picker, not a search. If the user can't type to narrow, it's a select — not a combo box. See the sibling **Select** reference for that component.
*   **Search bar (input → results elsewhere):** a text field whose results render in a _separate region_ (a page, a results panel), not in an attached popup listbox you navigate with arrow keys. A search bar submits a query; a combo box selects an option. A search bar with a live suggestions dropdown is _becoming_ a combo box for the duration of that dropdown.

The defining trait, said once so it sticks: **a combo box is a TEXT INPUT that filters an associated popup listbox.** No text input → it's a select or a menu. No attached listbox you navigate → it's a search bar. Both present → combo box.

Two more distinctions people trip on:

*   **Combo box vs. menu (****`role="menu"`****).** A menu is a list of _commands_ (actions you invoke). A listbox is a list of _values_ (things you select). A combo box pops a **listbox**, never a menu. Command palettes blur this — a command palette is a combo box whose "options" happen to run actions on Enter — which is exactly why shadcn's `Command` is built on the combobox/listbox primitive, not the menu primitive.
*   **Autocomplete vs. combo box.** "Autocomplete" is a _behavior_ (predicting/completing input), not a component. It's implemented _with_ the combo box pattern. So "autocomplete," "typeahead," and "combo box" are the same component wearing different job titles.

## 2\. Why It Matters
The combo box is where **large choice sets meet human patience.** A native `<select>` with 12 countries is fine; a `<select>` with 195 is a scroll-and-squint disaster. The combo box exists because at scale, _typing to filter beats scrolling to find_ — and that scaling problem is everywhere: country, state, city, currency, timezone, user, product, tag, repo, emoji, GIF, Slack channel, Notion page.

*   **It's a conversion surface.** Address autocomplete lifts checkout completion measurably — every field you can auto-fill from one typed line is a field the user doesn't abandon over. Search-as-you-type on a product catalog is the difference between "found it in two keystrokes" and "left for a competitor." The combo box is quietly one of the highest-leverage inputs in commerce.
*   **It's an accessibility minefield.** More than almost any other widget, a combo box is where teams _think_ they built something accessible and shipped a keyboard trap. The core trick — keeping real DOM focus in the input while a _virtual_ cursor (`aria-activedescendant`) walks the options — is subtle, and getting it wrong means screen-reader users hear nothing as they arrow through the list. Get it right and you've solved one of the genuinely hard a11y problems.
*   **It sets the "this app is fast" tone.** A combo box that lags a keystroke, flashes an empty list before results land, or dumps a raw "no results" with no styling makes the whole product feel broken. Debounce, loading, and empty states aren't polish here — they're the perceived-performance core of the interaction.
*   **It's a security surface.** The text the user types often becomes a query against your database or a third-party API. That means injection, over-fetching, enumeration, and rate-abuse all live behind the innocent-looking input. See §9.10 and §15.

## 3\. Anatomy of a Combo Box
Every well-built combo box is these parts, and each maps to a specific ARIA attribute:

*   **The input** — the text field itself. Carries `role="combobox"`, `aria-expanded`, `aria-controls` (pointing at the listbox), `aria-activedescendant` (pointing at the highlighted option), and `aria-autocomplete`. This is the element that keeps real focus the entire time.
*   **The trigger / disclosure button** — the caret or search icon. Optional but expected; toggles the listbox open/closed. Must have an `aria-label` and be excluded from the tab sequence (`tabindex="-1"`) so it doesn't add a second stop — the input is the interactive stop.
*   **The popup / listbox** — the container with `role="listbox"`, referenced by the input's `aria-controls`. Appears on type/focus/click, positioned against the input with a floating-positioning engine (collision-aware, flips above when there's no room below).
*   **Options** — each with `role="option"`, a unique `id`, and `aria-selected`. The highlighted one is pointed at by the input's `aria-activedescendant`.
*   **The highlight (active option)** — the visually emphasized row the virtual cursor sits on. **Not** the same as selection, and **not** real DOM focus. This distinction is the soul of the component.
*   **Selection** — for multi-select, the committed values render as **tokens/chips** before or inside the input. For single-select, the chosen label fills the input.
*   **Status region** — a visually-hidden `aria-live` node that announces "12 results available," "no results," "loading," so non-visual users get the same feedback sighted users get from the list changing.
*   **The clear button** — an `×` to reset the field. `aria-label="Clear"`, `tabindex="-1"`.
*   **Empty / loading / error slots** — the listbox's alternate contents when there are no matches, results are in flight, or the fetch failed.

## 4\. Sizes & Density
A combo box inherits input sizing, but the _popup_ has its own density budget. Real values:

| Size | Input height | Input padding (H) | Font | Option height | Use |
| ---| ---| ---| ---| ---| --- |
| SM | 32px | 10px | 13px | 32px | Dense toolbars, table filters, command palettes |
| MD | 40px | 12px | 14px | 40px | Default for forms |
| LG | 48px | 16px | 16px | 44px | Mobile-first, primary search |

Popup rules that matter:

*   **Option height ≥ 36px** for comfortable pointing; **≥ 44px** on touch. The visible input can be 32px in a dense UI, but the _tap target_ on each option should still clear 44px on touch devices.
*   **Cap the visible popup height** (e.g. `max-height: 320px`) and scroll inside it. Never let the listbox run off-screen; a floating engine should size it to the available viewport and flip up when needed.
*   **Match popup width to the input** by default (so it reads as attached), but allow it to grow for long option labels rather than truncating meaning away.
*   **Chips wrap, they don't clip.** In a multi-select, tokens should wrap to a second line and grow the control's height, not overflow-hidden the earlier selections out of sight.

## 5\. States (where combo boxes are won or lost)
A combo box has every input state _plus_ a whole popup-and-async layer. Missing states here is the #1 tell of a build that "worked on my machine with three hardcoded options."

**Input-level states**
1. **Default (rest)** — collapsed, placeholder or selected value showing.
2. **Hover** — subtle border/bg shift on the field.
3. **Focus** — visible `:focus-visible` ring on the input. Focus **stays here** the entire interaction.
4. **Disabled** — `disabled` on the input, popup can't open.
5. **Readonly (select-only variant)** — `aria-readonly`, the user can open and pick but not free-type.
6. **Invalid** — `aria-invalid="true"` + error message, e.g. free text that isn't an allowed option.

**Popup / listbox states**
7\. **Closed** — `aria-expanded="false"`, listbox not rendered (or `hidden`).
8\. **Open / expanded** — `aria-expanded="true"`, listbox visible.
9\. **Filtering** — user is typing; the option set is narrowing live.
10\. **Active-option (highlighted)** — one option is the virtual-cursor target via `aria-activedescendant`; visually emphasized.
11\. **Selected** — `aria-selected="true"` on committed option(s). Distinct from highlighted.

**Async / data states (the ones tutorials skip)**
12\. **Loading** — remote fetch in flight. Spinner in the field or a skeleton in the popup; `aria-busy`. Don't blank the previous results until new ones arrive.
13\. **No results** — query returned nothing. A styled empty state with a next step ("No cities match 'zzz' — check spelling"), not a bare closed popup.
14\. **Error** — the fetch failed. An in-popup error row with a retry affordance, announced politely. _Never_ a silent empty list that looks identical to "no results."
15\. **Min-query** — below the threshold to search (e.g. "type at least 2 characters"). An explicit hint, not an empty void.
16\. **Creatable / add-new** — the typed value isn't in the list but can be created; the popup shows a "Create 'foo'" affordance as a real option.

The four async states — **loading, no-results, error, min-query** — must be _visually distinct from each other_. Collapsing them into one blank popup is the single most common combo-box bug in production, and it reads to the user as "this is broken."

## 6\. Types & Variants
Combo boxes fan out along a few independent axes. A real component library exposes them as props, not separate components.

**By editability**
*   **Editable (autocomplete) combo box:** free text allowed; typing filters _and_ can become the value. The classic search/typeahead. `aria-autocomplete="list"` (or `"both"` for inline).
*   **Select-only combo box:** the input filters but the value _must_ be one of the options — free text that doesn't match is rejected/reverted on blur. This is a `<select>` with type-to-filter superpowers. Radix/shadcn `Combobox` and the Command pattern default here.

**By autocomplete behavior (****`aria-autocomplete`****)**
*   **`none`****\*\*\*\*:** typing doesn't filter; the list is static (rare, basically a select).
*   **`list`****\*\*\*\*:** typing filters the listbox. The common case.
*   **`both`****\*\*\*\*:** filters the list _and_ inline-completes the input — the predicted rest of the match appears as selected text after the caret (the "inline autocomplete" trick, §9.16).

**By selection count**
*   **Single-select:** one value; picking closes the popup and fills the input.
*   **Multi-select (tokenizing / tag input):** many values; each becomes a chip/token; the popup usually stays open for the next pick. Backspace on an empty input removes the last chip.

**By data source**
*   **Sync / local:** options are in memory; filtering is a client-side `.filter()`. Instant.
*   **Async / remote:** options come from an endpoint per keystroke. Needs debounce, request cancellation, loading/error/no-results. The hard mode (§9.9, §9.10).

**By capability**
*   **Creatable ("add new"):** the typed value can become a brand-new option (tags, labels, invitee emails).
*   **Grouped:** options bucketed under `role="group"` headings (Recent / All, or by category).
*   **Virtualized:** thousands of options windowed so the DOM holds ~20 rows, not 10,000 (§9.17).
*   **Command palette:** a combo box whose options are actions; Enter runs the highlighted command (⌘K). shadcn `Command`, Linear, VS Code, Raycast.

## 7\. When to Use One (and When Not To)
Use a combo box when the user is choosing from a **known set that's too big to eyeball** and typing is faster than scrolling.

*   **≤ ~7 options, always visible is fine →** radio group or segmented control. No popup needed.
*   **~7–15 options, no search needed →** native `<select>`. It's accessible for free, works on every device, and you don't own the a11y bugs.
*   **15+ options, or the user knows what they want →** combo box. Typing to filter earns its complexity here.
*   **Thousands of options, server-side →** async combo box with debounce + virtualization.
*   **Multiple values from a big set (tags, recipients) →** multi-select combo box with tokens.
*   **The set is open-ended (user invents values) →** creatable combo box.
*   **Results belong on their own page/panel, not a small popup →** that's a search bar, not a combo box.

**When** **_not_** **to:** don't reach for a combo box for a yes/no, for 3 mutually-exclusive options, or when the value is genuinely free text with no useful suggestions (that's just an `<input>`). And don't build a custom combo box when a native `<select>` would do — you're taking on the single hardest a11y contract in the widget catalog for no reason.

Placement heuristics: anchor the popup to the input, open **downward by default** and flip up on collision, keep it within the viewport, and never let it cover the input you're typing into. On mobile, consider a full-screen or bottom-sheet variant — a tiny floating popup over the keyboard is a mis-tap generator.

## 8\. Combo Boxes Across Design Systems
Same pattern, very different philosophies and names. Knowing them makes you fluent in any codebase.

*   **Material Design (Google):** "Autocomplete" / "Exposed dropdown menu." Text field + menu, filled/outlined field styling, floating label, ripple. Angular Material `<mat-autocomplete>` is a canonical implementation.
*   **Apple HIG (iOS/macOS):** `UISearchController` with a results updater on iOS; the macOS `NSComboBox` is the literal namesake — an editable text field with an attached list. SwiftUI leans on `.searchable()` with search suggestions.
*   **Fluent (Microsoft):** ships a first-class `ComboBox` (editable and dropdown modes) and a separate `SearchBox` with suggestions. Compact, acrylic surfaces, explicit `allowFreeform` prop.
*   **Ant Design / enterprise:** `<AutoComplete>` and a very powerful `<Select showSearch>` with tags mode, remote fetch, virtual scroll, and grouping built in. The enterprise reference for "combo box with everything."
*   **Carbon (IBM):** distinct `ComboBox` (editable/filterable) vs `Dropdown` vs `MultiSelect` vs `FilterableMultiSelect` — a clean illustration of how the axes in §6 become separate exports.
*   **Tailwind / utility-first:** no built-in behavior; you compose the markup and bring a headless behavior library (Headless UI's `Combobox`, Downshift, or Radix).
*   **Radix / shadcn (2024+ web standard):** shadcn's `Combobox` is `Popover` + `Command`; the `Command` primitive (built on `cmdk`) is the listbox-filtering engine. Headless behavior, your styling, accessibility handled. The de facto modern web answer.
*   **Downshift (Kent C. Dodds):** the venerable headless hook (`useCombobox`, `useMultipleSelection`) that made the `aria-activedescendant` pattern accessible to mortals. Still a great reference implementation.

## 8b. Visual Styles & 2026 Trends
Design systems are _whose_ rules; visual styles are _which look_. The same semantic combo box — input, listbox, options, chips — can wear any of eleven skins (rendered in full in §17). **The skin never touches behavior:** the keyboard map, `aria-activedescendant` virtual cursor, focus ring, and 44px targets are identical across all of them. Full per-style guidance lives on the [Design Styles (visual languages)](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200551).

### What's trending in 2026
**Liquid Glass** leads: Apple shipped it across iOS 26, iPadOS, and macOS Tahoe in late 2025, and web combo-box popups are approximating it with layered `backdrop-filter`, highlight rims, and the emerging refraction proposals — the floating listbox is the perfect surface for it. Around it:

*   **Command-palette everything (⌘K):** the combo box eating navigation. Every serious app now has a global typeahead that searches _and_ acts. `cmdk`/shadcn `Command` made it a two-hour feature.
*   **AI-native suggestions:** the popup as a generative surface — semantic/vector search instead of prefix match, streaming suggestions, "did you mean," and inline AI completions rendered as ghost text in the field.
*   **Spatial & depth-aware popups** carried over from visionOS: soft 3D layering, parallax, content-aware translucency.
*   **Motion-forward but restrained:** the list items stagger-in, the highlight springs — all gated behind `prefers-reduced-motion`.

**For UJG:** a Liquid-Glass popover over deep Eminence with a Goldenrod highlight is the signature move; keep Flat/Swiss for dense data filters and command palettes where speed and legibility beat spectacle. Contrast and reduced-motion stay non-negotiable no matter how on-trend the skin.

## 9\. The Code
This is the big one. A combo box is mostly _behavior_, so the code sections carry the weight of the whole doc.

### 9.1 HTML (the ARIA skeleton everyone should master first)
There is no native combo box element that gives you type-to-filter — `<datalist>` is the closest, and it's the honest starting point before you hand-roll ARIA.

```plain
<!-- The one native-ish option: <input> + <datalist>.
     Real filtering, zero JS — but almost no styling/keyboard control. -->
<label for="fruit">Fruit</label>
<input id="fruit" name="fruit" list="fruits" />
<datalist id="fruits">
  <option value="Apple"></option>
  <option value="Banana"></option>
  <option value="Cherry"></option>
</datalist>
```

`<datalist>` is genuinely accessible and free, but you can't style the popup, control the keyboard, group options, show loading, or do multi-select. The moment you need any of that, you build the ARIA combobox by hand:

```plain
<!-- The WAI-ARIA combobox pattern, editable + list autocomplete -->
<label id="cb-label" for="cb-input">Choose a country</label>

<div class="combo">
  <input
    id="cb-input"
    role="combobox"
    type="text"
    aria-labelledby="cb-label"
    aria-expanded="false"           <!-- truthful: reflects listbox visibility -->
    aria-controls="cb-listbox"       <!-- points at the listbox it owns -->
    aria-autocomplete="list"         <!-- typing filters the list -->
    aria-activedescendant=""         <!-- id of the highlighted option, or empty -->
    autocomplete="off"               <!-- kill the browser's own autofill popup -->
  />
  <button type="button" tabindex="-1" aria-label="Show suggestions"
          aria-controls="cb-listbox" class="combo__toggle">▾</button>

  <ul id="cb-listbox" role="listbox" aria-label="Countries" hidden>
    <li id="opt-1" role="option" aria-selected="false">Canada</li>
    <li id="opt-2" role="option" aria-selected="false">Chile</li>
    <li id="opt-3" role="option" aria-selected="false">China</li>
  </ul>

  <!-- visually hidden, announces result counts / loading / errors -->
  <div class="sr-only" role="status" aria-live="polite"></div>
</div>
```

The non-negotiable HTML rules:

*   **`role="combobox"`** **goes on the** **`<input>`****\*\*\*\*, not a wrapping div.** The modern (ARIA 1.2) pattern puts the role on the text field itself. The old 1.0 pattern wrapped a div — don't; it broke in many screen readers.
*   **`aria-expanded`** **must be truthful** — flip it to `"true"` exactly when the listbox is visible and `"false"` when it isn't. A hardcoded value is a lie assistive tech will repeat.
*   **`aria-controls`** **points at the listbox** **`id`****\*\*\*\*.** `aria-activedescendant` points at the _highlighted option's_ `id` (or is empty). These are different pointers doing different jobs.
*   **`autocomplete="off"`** on the input, or the browser's native autofill dropdown fights your custom popup.
*   **Decorative toggle is** **`tabindex="-1"`** so the whole widget is _one_ tab stop (the input).

The load-bearing CSS idea: **the highlight is a data attribute (****`data-active`****), not** **`:hover`****\*\*\*\*.** Keyboard users move the highlight with arrow keys and never touch the mouse; if your highlight only exists on `:hover`, the keyboard highlight is invisible. Hover is a _secondary_ visual, not the source of truth.

### 9.3 Vanilla JavaScript (the full behavior, no framework)
This is the reference implementation — every framework below is sugar over exactly this logic. The core is: **focus never leaves the input; a** **`activeIndex`** **variable drives** **`aria-activedescendant`****\*\*\*\*.**

```javascript
function createCombobox(root, allOptions) {
  const input   = root.querySelector('[role="combobox"]');
  const listbox = root.querySelector('[role="listbox"]');
  const status  = root.querySelector('[role="status"]');
  let options = [];            // current filtered option elements
  let activeIndex = -1;        // the virtual cursor
  let open = false;

  const setOpen = (next) => {
    open = next;
    listbox.hidden = !open;
    input.setAttribute("aria-expanded", String(open));
    if (!open) { activeIndex = -1; input.removeAttribute("aria-activedescendant"); }
  };

  const setActive = (i) => {
    options.forEach(o => o.dataset.active = "false");
    activeIndex = i;
    if (i >= 0 && options[i]) {
      options[i].dataset.active = "true";
      input.setAttribute("aria-activedescendant", options[i].id);
      options[i].scrollIntoView({ block: "nearest" });   // keep highlight visible
    } else {
      input.removeAttribute("aria-activedescendant");
    }
  };

  const filter = (query) => {
    const q = query.trim().toLowerCase();
    const matches = allOptions.filter(o => o.toLowerCase().includes(q));
    listbox.innerHTML = "";
    options = matches.map((label, i) => {
      const li = document.createElement("li");
      li.id = `opt-${i}`;
      li.role = "option";
      li.className = "combo__option";
      li.textContent = label;
      li.setAttribute("aria-selected", "false");
      li.addEventListener("mousedown", (e) => e.preventDefault()); // keep focus in input
      li.addEventListener("click", () => commit(label));
      listbox.appendChild(li);
      return li;
    });
    status.textContent = matches.length
      ? `${matches.length} result${matches.length === 1 ? "" : "s"} available`
      : "No results";
    setOpen(matches.length > 0 || q.length > 0);
    setActive(matches.length ? 0 : -1);
  };

  const commit = (label) => {
    input.value = label;
    setOpen(false);
    input.focus();
  };

  const ac = new AbortController();               // one signal tears down every listener
  const { signal } = ac;

  input.addEventListener("input", (e) => filter(e.target.value), { signal });
  input.addEventListener("focus", () => { if (input.value) filter(input.value); }, { signal });

  input.addEventListener("keydown", (e) => {
    switch (e.key) {
      case "ArrowDown":
        e.preventDefault();
        if (!open) return filter(input.value);
        setActive((activeIndex + 1) % options.length);
        break;
      case "ArrowUp":
        e.preventDefault();
        if (!open) return;
        setActive((activeIndex - 1 + options.length) % options.length);
        break;
      case "Enter":
        if (open && activeIndex >= 0) { e.preventDefault(); commit(options[activeIndex].textContent); }
        break;
      case "Escape":
        e.preventDefault();
        if (open) setOpen(false); else input.value = "";
        break;
      case "Home": if (open) { e.preventDefault(); setActive(0); } break;
      case "End":  if (open) { e.preventDefault(); setActive(options.length - 1); } break;
      case "Tab":  setOpen(false); break;      // Tab commits focus away, closes list
    }
  }, { signal });

  document.addEventListener("click", (e) => {
    if (!root.contains(e.target)) setOpen(false);
  }, { signal });

  return { destroy: () => ac.abort() };     // removes the document (and input) listeners
}
```

The three subtleties juniors miss, all handled above:

*   **`mousedown`** **→** **`preventDefault()`** **on each option.** Without it, clicking an option blurs the input first (stealing focus and closing the list) before the `click` ever fires. Preventing the default mousedown keeps focus in the input so the click can commit cleanly.
*   **Focus stays in the input;** **`setActive`** **moves a** **_variable_****\*\*\*\*, not** **`.focus()`****\*\*\*\*.** The highlighted option is never DOM-focused. Its `id` is announced via `aria-activedescendant`. That is the entire accessibility contract of the pattern.
*   **Teardown.** The document-level `click` listener is bound to the whole page, so it outlives the widget unless you remove it. Wiring every listener to one `AbortController` and returning `destroy()` lets the caller unbind them all on unmount — no leaked global handler.

### 9.4 React + TypeScript (a proper headless combo box)
The production shape: a reusable, generic, controlled component that manages the virtual cursor, filtering, and full ARIA wiring — and is styling-agnostic. This is usually the longest block in the doc, and here it earns it.

```typescript
import {
  useId, useMemo, useRef, useState, useCallback,
  type KeyboardEvent, type ReactNode,
} from "react";

type ComboboxProps<T> = {
  items: T[];
  value: T | null;
  onChange: (item: T | null) => void;
  itemToString: (item: T) => string;
  renderItem?: (item: T, state: { active: boolean; selected: boolean }) => ReactNode;
  label: string;
  placeholder?: string;
  /** Return a filtered subset; default = case-insensitive substring on itemToString */
  filter?: (items: T[], query: string) => T[];
  disabled?: boolean;
};

export function Combobox<T>({
  items, value, onChange, itemToString, renderItem,
  label, placeholder, filter, disabled,
}: ComboboxProps<T>) {
  const baseId = useId();
  const listboxId = `${baseId}-listbox`;
  const labelId = `${baseId}-label`;
  const inputRef = useRef<HTMLInputElement>(null);

  const [query, setQuery] = useState("");
  const [open, setOpen] = useState(false);
  const [activeIndex, setActiveIndex] = useState(-1);

  const results = useMemo(() => {
    const q = query.trim().toLowerCase();
    if (!q) return items;
    return (filter ?? defaultFilter(itemToString))(items, q);
  }, [items, query, filter, itemToString]);

  const activeId = activeIndex >= 0 ? `${baseId}-opt-${activeIndex}` : undefined;

  const open_ = useCallback(() => { if (!disabled) setOpen(true); }, [disabled]);
  const close = useCallback(() => { setOpen(false); setActiveIndex(-1); }, []);

  const commit = useCallback((item: T) => {
    onChange(item);
    setQuery(itemToString(item));
    close();
    inputRef.current?.focus();
  }, [onChange, itemToString, close]);

  const move = (delta: number) => {
    if (!open) { open_(); return; }
    setActiveIndex((i) => {
      const n = results.length;
      if (n === 0) return -1;
      return (i + delta + n) % n;
    });
  };

  const onKeyDown = (e: KeyboardEvent<HTMLInputElement>) => {
    switch (e.key) {
      case "ArrowDown": e.preventDefault(); move(1); break;
      case "ArrowUp":   e.preventDefault(); move(-1); break;
      case "Enter":
        if (open && activeIndex >= 0 && results[activeIndex]) {
          e.preventDefault(); commit(results[activeIndex]);
        }
        break;
      case "Escape":
        e.preventDefault();
        if (open) close();
        else { setQuery(""); onChange(null); }
        break;
      case "Home": if (open) { e.preventDefault(); setActiveIndex(0); } break;
      case "End":  if (open) { e.preventDefault(); setActiveIndex(results.length - 1); } break;
      case "Tab":  close(); break;
    }
  };

  return (
    <div className="combo">
      <label id={labelId} htmlFor={`${baseId}-input`}>{label}</label>
      <input
        id={`${baseId}-input`}
        ref={inputRef}
        role="combobox"
        type="text"
        className="combo__input"
        placeholder={placeholder}
        disabled={disabled}
        autoComplete="off"
        aria-labelledby={labelId}
        aria-expanded={open}
        aria-controls={listboxId}
        aria-autocomplete="list"
        aria-activedescendant={activeId}
        value={query}
        onChange={(e) => { setQuery(e.target.value); open_(); setActiveIndex(0); }}
        onFocus={open_}
        onKeyDown={onKeyDown}
        onBlur={close}
      />
      <ul
        id={listboxId}
        role="listbox"
        aria-label={label}
        className="combo__listbox"
        hidden={!open}
      >
        {results.map((item, i) => {
          const selected = value != null && itemToString(value) === itemToString(item);
          const active = i === activeIndex;
          return (
            <li
              key={itemToString(item)}
              id={`${baseId}-opt-${i}`}
              role="option"
              aria-selected={selected}
              data-active={active}
              className="combo__option"
              onMouseDown={(e) => e.preventDefault()}   // keep focus in the input
              onClick={() => commit(item)}
              onMouseEnter={() => setActiveIndex(i)}
            >
              {renderItem ? renderItem(item, { active, selected }) : itemToString(item)}
            </li>
          );
        })}
        {open && results.length === 0 && (
          <li role="presentation" className="combo__empty">
            No matches for “{query}”
          </li>
        )}
      </ul>
      <div className="sr-only" role="status" aria-live="polite">
        {open ? `${results.length} results available` : ""}
      </div>
    </div>
  );
}

function defaultFilter<T>(toString: (t: T) => string) {
  return (items: T[], q: string) =>
    items.filter((it) => toString(it).toLowerCase().includes(q));
}
```

Why this is the senior version, not the junior one:

*   **Generic over** **`T`****\*\*\*\*.** It's a combo box of _anything_ — strings, users, products — via `itemToString`, not a strings-only toy.
*   **`aria-activedescendant`** **is derived from** **`activeIndex`**, and focus never leaves the input. The `<li>`s are never `.focus()`\-ed. This is the accessibility spine.
*   **`onMouseDown={preventDefault}`** on options — the same focus-preservation trick as vanilla, now in React idiom. Forgetting it is the #1 React combo-box bug.
*   **Controlled** **`value`** **\+ internal** **`query`** are kept as separate state. The committed value and the in-progress text are genuinely different things; conflating them causes the classic "it reverts what I typed" bug.
*   **`useId`** for collision-free option/listbox ids in a component that may render many times on a page (SSR-safe).

### 9.5 Async / remote options (debounce, cancel, the four states)
The moment options come from a server, four things become mandatory: **debounce** (don't fire on every keystroke), **cancellation** (a slow earlier request must not overwrite a fast later one — the race that shows stale results), and honest **loading / no-results / error** rendering.

```typescript
import { useEffect, useRef, useState } from "react";

type Status = "idle" | "loading" | "success" | "error";

export function useRemoteOptions<T>(query: string, fetcher: (q: string, signal: AbortSignal) => Promise<T[]>, minChars = 2, delay = 250) {
  const [options, setOptions] = useState<T[]>([]);
  const [status, setStatus] = useState<Status>("idle");
  const controllerRef = useRef<AbortController | null>(null);

  useEffect(() => {
    const q = query.trim();
    if (q.length < minChars) { setOptions([]); setStatus("idle"); return; }

    const t = setTimeout(async () => {
      controllerRef.current?.abort();               // cancel the in-flight request
      const controller = new AbortController();
      controllerRef.current = controller;
      setStatus("loading");
      try {
        const data = await fetcher(q, controller.signal);
        setOptions(data);
        setStatus("success");
      } catch (err) {
        if ((err as Error).name === "AbortError") return;  // superseded, ignore
        setStatus("error");
      }
    }, delay);                                       // debounce

    return () => {
      clearTimeout(t);                               // reset debounce on next keystroke
      controllerRef.current?.abort();                // abort any in-flight fetch on unmount
    };
  }, [query, fetcher, minChars, delay]);

  return { options, status };
}
```

And the popup that renders each state _distinctly_ — the part that separates a real async combo box from a broken one:

```typescript
function AsyncListbox<T>({ status, options, query, minChars, render, onRetry }: {
  status: Status; options: T[]; query: string; minChars: number;
  render: (o: T) => ReactNode; onRetry: () => void;
}) {
  if (query.trim().length < minChars)
    return <li className="combo__hint">Type at least {minChars} characters…</li>;
  if (status === "loading")
    return <li className="combo__loading" aria-busy="true">Searching…</li>;
  if (status === "error")
    return (
      <li className="combo__error">
        Something went wrong.{" "}
        <button type="button" onMouseDown={(e) => e.preventDefault()} onClick={onRetry}>Retry</button>
      </li>
    );
  if (status === "success" && options.length === 0)
    return <li className="combo__empty">No results for “{query}”.</li>;
  return <>{options.map(render)}</>;
}
```

The rule restated: **min-query, loading, no-results, and error are four different renders.** Never let two of them collapse into the same blank popup. And always `AbortController`\-cancel — without it, typing "react" fast can leave you showing results for "rea" because that request happened to resolve last.

### 9.6 Multi-select with tokens/chips
Multi-select changes three things: the popup stays open after a pick, selected values render as removable chips, and **Backspace on an empty input removes the last chip.**

```typescript
export function MultiCombobox<T>({ items, value, onChange, itemToString, label }: {
  items: T[]; value: T[]; onChange: (next: T[]) => void;
  itemToString: (t: T) => string; label: string;
}) {
  const baseId = useId();
  const inputId = `${baseId}-input`;
  const listboxId = `${baseId}-listbox`;
  const [query, setQuery] = useState("");
  const [open, setOpen] = useState(false);
  const selectedKeys = new Set(value.map(itemToString));
  const available = items.filter((it) => !selectedKeys.has(itemToString(it)));
  const results = available.filter((it) =>
    itemToString(it).toLowerCase().includes(query.trim().toLowerCase()));

  const add = (item: T) => { onChange([...value, item]); setQuery(""); };   // stay open
  const removeLast = () => onChange(value.slice(0, -1));
  const remove = (item: T) =>
    onChange(value.filter((v) => itemToString(v) !== itemToString(item)));

  return (
    <div className="combo combo--multi">
      <label htmlFor={inputId}>{label}</label>
      <div className="combo__control">
        {value.map((v) => (
          <span key={itemToString(v)} className="chip">
            {itemToString(v)}
            <button type="button" aria-label={`Remove ${itemToString(v)}`}
                    tabIndex={-1} onClick={() => remove(v)}>×</button>
          </span>
        ))}
        <input
          id={inputId}
          role="combobox"
          aria-expanded={open}                {/* bound to real open state, not a bare attr */}
          aria-controls={listboxId}
          aria-autocomplete="list"
          value={query}
          onFocus={() => setOpen(true)}
          onChange={(e) => { setQuery(e.target.value); setOpen(true); }}
          onKeyDown={(e) => {
            if (e.key === "Backspace" && query === "" && value.length) removeLast();
          }}
        />
      </div>
      {/* aria-multiselectable belongs on the listbox, never the input */}
      <ul id={listboxId} role="listbox" aria-label={label}
          aria-multiselectable="true" hidden={!open}>
        {/* options omitted — same as §9.4 but calls add() and does not close */}
      </ul>
    </div>
  );
}
```

Multi-select a11y notes: put `aria-multiselectable="true"` on the listbox, keep `aria-selected` accurate on _every_ option (selected ones stay in the list marked, or move to the chip row — pick one model and be consistent), and make chip removal reachable. The chip's `×` is usually `tabindex="-1"` with removal driven from the input's keyboard (Backspace) so the tab order stays clean; power users get an arrow-key chip-navigation layer on top.

### 9.7 Creatable ("add new") combo box
When the typed value isn't in the list but should be creatable (tags, invitee emails), surface a synthetic "Create" option:

```typescript
const trimmed = query.trim();
const exactExists = results.some((r) => itemToString(r).toLowerCase() === trimmed.toLowerCase());
const showCreate = trimmed.length > 0 && !exactExists;

// render at the end of the listbox:
{showCreate && (
  <li role="option" id={`${baseId}-create`} aria-selected={false}
      data-active={activeIndex === results.length}
      onMouseDown={(e) => e.preventDefault()}
      onClick={() => commitNew(trimmed)}>
    Create “{trimmed}”
  </li>
)}
```

The create row lives at index `results.length`, so the §9.4 cursor must count it or arrows/Enter never reach it. Extend the navigable range and special-case Enter on the create index:

```typescript
const optionCount = results.length + (showCreate ? 1 : 0);   // create row is index results.length

const move = (delta: number) => {
  if (!open) { open_(); return; }
  setActiveIndex((i) => {
    if (optionCount === 0) return -1;
    return (i + delta + optionCount) % optionCount;          // wraps THROUGH the create row
  });
};

// in onKeyDown's Enter case:
case "Enter":
  if (open && showCreate && activeIndex === results.length) {
    e.preventDefault(); commitNew(trimmed);                  // the synthetic "Create" row
  } else if (open && activeIndex >= 0 && results[activeIndex]) {
    e.preventDefault(); commit(results[activeIndex]);
  }
  break;
```

Gotchas: validate the created value before committing (an email combo box should reject `notanemail`), de-dupe case-insensitively so "React" and "react" don't both get created, and make the create row a real navigable option — Down-arrow should reach it and Enter should trigger it, exactly like a normal option (the range extension above is what makes that true).

### 9.8 Downshift, Radix & shadcn `Command` (don't hand-roll if you don't have to)
Three battle-tested ways to get the pattern without owning every ARIA edge case.

**Downshift** **`useCombobox`** — the headless hook that popularized the accessible pattern. It hands you the prop-getters and manages `aria-activedescendant`, highlight index, and open state:

### 9.9 Next.js (App Router: server-fetched options, client interactivity)
The combo box _input_ must be a Client Component (it has state and `onKeyDown`), but the **search can run on the server** via a Server Action or a Route Handler — no separate API layer needed, and the query never trusts the client.

```typescript
// app/actions/search-users.ts
"use server";
import { z } from "zod";
import { db } from "@/lib/db";

const Query = z.string().min(2).max(64);

export async function searchUsers(raw: string) {
  const q = Query.parse(raw);                 // validate the typed query server-side
  // parameterized query — never string-concatenate user input (see §15)
  return db.user.findMany({
    where: { name: { contains: q, mode: "insensitive" } },
    select: { id: true, name: true },
    take: 20,                                  // cap the result set
  });
}
```

### 9.10 The search endpoint (Node.js) — the server behind the popup
Every keystroke can hit this. It must be fast, capped, validated, and abuse-resistant.

```typescript
import express from "express";
import { z } from "zod";
const router = express.Router();

const SearchQuery = z.object({
  q: z.string().trim().min(1).max(64),
  limit: z.coerce.number().int().min(1).max(50).default(20),
});

router.get("/api/search/cities", requireAuth, rateLimit({ windowMs: 60_000, max: 120 }), async (req, res) => {
  const parsed = SearchQuery.safeParse(req.query);
  if (!parsed.success) return res.status(422).json({ error: parsed.error.issues });
  const { q, limit } = parsed.data;

  // Parameterized — the driver escapes q; we never build SQL by concatenation.
  const rows = await db.query(
    `SELECT id, name FROM cities WHERE name ILIKE $1 ORDER BY population DESC LIMIT $2`,
    [`${q}%`, limit]          // prefix match hits the index; %q% would table-scan
  );

  res.set("Cache-Control", "private, max-age=30");   // short cache for repeat prefixes
  res.json({ q, results: rows });
});

export default router;
```

Endpoint concerns every async combo box silently depends on:

*   **Cap the result set** (`LIMIT`, `.take()`). A query of `"a"` must never try to return a million rows.
*   **Prefix match (****`name%`****) uses the index; contains (****`%name%`****) table-scans.** For "search anywhere in the string" at scale, reach for a trigram index (Postgres `pg_trgm`), full-text search, or a dedicated engine (Elasticsearch/Meilisearch/Typesense).
*   **Validate and bound the query** — length limits stop someone shipping a 2MB "search term" to melt your DB.
*   **Rate-limit per user + per IP.** A typeahead is a request amplifier; one user typing = dozens of requests. Debounce is the client's politeness; rate limiting is your defense.
*   **Auth + row-level authorization.** A user-search combo box must only return users the caller is allowed to see, or it becomes a data-exfiltration endpoint (§15, enumeration).

### 9.11 Python (FastAPI search endpoint + a rendered combo box)
**Backend** (FastAPI) receiving each keystroke's query:

```python
from pydantic import BaseModel

app = FastAPI()

class City(BaseModel):

    name: str

@app.get("/api/search/cities", response_model=list[City])
def search_cities(
```

### 9.13 Other frameworks (Vue, Svelte, Angular)
Same ARIA skeleton, different syntax. The `role="combobox"` input never changes.

**Vue 3 (****`<script setup>`****):**

```plain
</template>
```

**Svelte** mirrors the Vue block exactly — `bind:value={query}`, a reactive `$: results = …` filter, `on:keydown` running the same Arrow/Enter/Escape switch, and `on:mousedown|preventDefault` on each `<li>` to keep focus in the input. Same skeleton, Svelte syntax.

**Angular** leans on **Angular Material's** **`<mat-autocomplete>`**, the idiomatic answer rather than hand-rolling:

```plain

  <mat-label>Country</mat-label>
  <input matInput [formControl]="ctrl" [matAutocomplete]="auto" />
  <mat-autocomplete #auto="matAutocomplete">
    <mat-option *ngFor="let c of filtered | async" [value]="c">{{ c }}</mat-option>
  </mat-autocomplete>
</mat-form-field>
```

`filtered` is an `Observable` derived from `ctrl.valueChanges` with `debounceTime` and a filter — Angular's reactive-forms idiom fits the debounce-a-stream shape of a combo box beautifully.

**Bootstrap** has _no_ native combo box — there's no honest `btn`\-style class for it. Its `dropdown` is a menu of actions, not a filtered listbox. To get one on Bootstrap you either style the markup from §9.1 with Bootstrap utilities and bring your own JS, or add a third-party plugin (e.g. `bootstrap-select`/Tom Select). Don't reach for `.dropdown` and call it a combo box; the semantics are wrong.

### 9.14 Web Component (framework-agnostic)
A combo box that works in any framework or none:

```typescript
class UiCombobox extends HTMLElement {
  private options: string[] = [];
  private active = -1;
  private input!: HTMLInputElement;
  private list!: HTMLUListElement;
  connectedCallback() {
    this.attachShadow({ mode: "open" });
    this.options = JSON.parse(this.getAttribute("options") ?? "[]");
    // Build the shell ONCE. Never rewrite shadowRoot.innerHTML on keystroke — that
    // replaces the <input>, killing its listeners and its focus/caret after one key.
    this.shadowRoot!.innerHTML = `
      <style>/* scoped, no leakage */</style>
      <input role="combobox" aria-expanded="false" aria-controls="lb" aria-autocomplete="list" autocomplete="off">
      <ul id="lb" role="listbox"></ul>`;
    this.input = this.shadowRoot!.querySelector("input")!;
    this.list  = this.shadowRoot!.querySelector("ul")!;
    this.input.addEventListener("input", () => { this.active = -1; this.renderList(); });
    this.input.addEventListener("keydown", (e) => this.onKey(e as KeyboardEvent));
    this.renderList();
  }
  private onKey(e: KeyboardEvent) {
    const list = this.filtered(this.input.value);
    if (e.key === "ArrowDown") {
      e.preventDefault();
      if (list.length === 0) return;                       // guard modulo-by-zero → no opt-NaN
      this.active = (this.active + 1) % list.length;
      this.renderList();
    }
    if (e.key === "Enter" && this.active >= 0 && list[this.active]) {
      this.input.value = list[this.active]; this.active = -1; this.renderList();
    }
  }
  private filtered(q = "") { return this.options.filter(o => o.toLowerCase().includes(q.toLowerCase())); }
  // Re-render ONLY the list. The <input> (focus, caret, value) is left untouched.
  private renderList() {
    const list = this.filtered(this.input.value);
    this.input.setAttribute("aria-expanded", String(list.length > 0));
    if (this.active >= 0 && list.length)
      this.input.setAttribute("aria-activedescendant", `opt-${this.active}`);
    else
      this.input.removeAttribute("aria-activedescendant");
    // textContent, not innerHTML — option labels are never interpolated as HTML (no XSS).
    this.list.replaceChildren(...list.map((o, i) => {
      const li = document.createElement("li");
      li.id = `opt-${i}`;
      li.setAttribute("role", "option");
      if (i === this.active) li.dataset.active = "true";
      li.textContent = o;
      return li;
    }));
  }
}
customElements.define("ui-combobox", UiCombobox);
// <ui-combobox options='["Canada","Chile","China"]'></ui-combobox>
```

Three bugs the naive version ships, all fixed above: (1) it rebuilt `shadowRoot.innerHTML` on every keystroke, replacing the `<input>` — so the widget went dead and lost its caret after a single key; the shell is now built once and only the `<ul>` re-renders. (2) It interpolated `value="${q}"` and `<li>…${o}…</li>` as raw HTML — an XSS hole; options are now built with `textContent`. (3) `(active + 1) % list.length` on an empty list produced `aria-activedescendant="opt-NaN"`; the empty case now returns early.

### 9.16 The inline-autocomplete (text-selection) trick
`aria-autocomplete="both"` inline-completes: as you type "ca", the field shows "ca**nada**" with "nada" pre-selected (highlighted) after the caret. Type the next real character and it replaces the selection; press Delete and the completion vanishes. The mechanic is `setSelectionRange`:

```javascript
function inlineComplete(input, typed, firstMatch) {
  // firstMatch starts with `typed`, e.g. typed="ca", firstMatch="Canada"
  if (!firstMatch || !firstMatch.toLowerCase().startsWith(typed.toLowerCase())) return;
  input.value = typed + firstMatch.slice(typed.length);   // "ca" + "nada"
  input.setSelectionRange(typed.length, input.value.length); // select "nada"
}

input.addEventListener("input", (e) => {
  // Only complete on forward typing, never on Backspace (or it fights the user)
  if (e.inputType === "deleteContentBackward") return;
  const match = filtered(input.value)[0];
  inlineComplete(input, input.value, match);
});
```

The critical guard: **never inline-complete on Backspace.** If you re-complete while the user is deleting, they can never erase anything — every delete instantly refills. Gate it to forward `insertText` input types only. Set `aria-autocomplete="both"` so screen readers announce that inline completion is happening.

### 9.17 Virtualization (thousands of options)
A combo box over 10,000 options can't put 10,000 `<li>`s in the DOM — that's a multi-hundred-millisecond layout on every keystroke. Windowing renders only the ~15 rows in view plus a buffer, translated inside a tall spacer:

```typescript
import { useVirtualizer } from "@tanstack/react-virtual";

function VirtualListbox({ items }: { items: string[] }) {
  const parentRef = useRef<HTMLUListElement>(null);
  const rows = useVirtualizer({
    count: items.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 40,        // row height
    overscan: 8,
  });
  return (
    <ul ref={parentRef} role="listbox" style={{ height: 320, overflow: "auto" }}>
      <li style={{ height: rows.getTotalSize(), position: "relative" }} aria-hidden="true" />
      {rows.getVirtualItems().map((v) => (
        <li key={v.key} role="option" id={`opt-${v.index}`}
            style={{ position: "absolute", top: 0, transform: `translateY(${v.start}px)`, height: v.size, width: "100%" }}>
          {items[v.index]}
        </li>
      ))}
    </ul>
  );
}
```

The a11y catch with virtualization: `aria-activedescendant` must point at an option that is **currently rendered**. When the user arrows to option #4,000, you must scroll the virtualizer so that row exists in the DOM before setting `aria-activedescendant` to its id — otherwise you're pointing at a node that isn't there and the screen reader announces nothing. Prefer virtualization only past a few hundred options; below that it's complexity you don't need.

## 10\. Accessibility (non-negotiable, and the hardest part)
The combo box is the widget most teams _think_ they made accessible and didn't. The contract:

**Roles & structure**
*   `role="combobox"` on the **text input** (ARIA 1.2 pattern), `role="listbox"` on the popup, `role="option"` on each item, `role="group"` for grouped sections.
*   Every option has a **unique** **`id`** so `aria-activedescendant` can point at it.

**State attributes (must be truthful, updated live)**
*   `aria-expanded` — `true` iff the listbox is visible.
*   `aria-controls` — the listbox `id`.
*   `aria-activedescendant` — the highlighted option's `id`, or absent when nothing is highlighted.
*   `aria-autocomplete` — `none` / `list` / `both` describing the completion behavior.
*   `aria-selected` — on options, reflecting committed selection.
*   `aria-multiselectable="true"` on the listbox for multi-select.
*   `aria-invalid` + an `aria-describedby` error node when free text is rejected.

**The focus rule — the soul of the component**
DOM focus **stays on the input** for the entire interaction. The user _feels_ like they're moving through the list, but the options are never `.focus()`\-ed. The highlight is a **virtual cursor** communicated only through `aria-activedescendant`. Move real focus into the options and you break the pattern — the input loses focus, typing stops working, and screen readers get confused. (The one alternative, the "focus the option" pattern, exists but is far harder to get right; `aria-activedescendant` is the recommended default.)

**Keyboard map (the full contract)**

| Key | Closed | Open |
| ---| ---| --- |
| Type a character | opens + filters | filters |
| `↓` Down | opens, highlights first (or keeps input) | next option (wraps) |
| `↑` Up | opens (highlight unchanged) | previous option (wraps) |
| `Enter` | — (or submit form) | select highlighted, close |
| `Esc` | clear the field (optional) | close, keep the typed text |
| `Home` / `End` | move caret in input | first / last option (or caret — pick one, be consistent) |
| `Tab` | move to next control | select-or-close, then move on |
| `Backspace` (multi-select, empty input) | remove last chip | remove last chip |
| `Alt+↓` / `Alt+↑` | open / close without moving highlight (native-parity) |  |

**Announcements**
*   A visually-hidden `role="status" aria-live="polite"` region announces result counts ("12 results available"), "No results," "Loading," and "Error" — because a sighted user sees the list change and a screen-reader user needs to be _told_.
*   Don't over-announce: `polite`, not `assertive`, and debounce the announcement so rapid typing doesn't machine-gun the screen reader.

**Contrast & targets**
*   Option text ≥ 4.5:1 against the popup background; the active-option highlight must be distinguishable by more than color (weight, a check, a border) for color-blind users.
*   Option tap targets ≥ 44px on touch. The visible input can be denser, but the options can't be.

## 11\. Innovative & Emerging Ideas
The combo box looks solved and keeps evolving:

*   **Semantic / vector search suggestions:** the popup ranked by embedding similarity instead of prefix match — "type the vibe, get the option." AI-native combo boxes fuzzy-match meaning, not spelling.
*   **Streaming AI completions as ghost text:** inline autocomplete (§9.16) but the completion is generated, not looked up — the field predicts the rest of your sentence.
*   **Command palette as the primary nav (⌘K):** the combo box eating the menu bar. `cmdk` made a global search-and-act surface a standard feature; users now _expect_ it.
*   **Multi-modal combo boxes:** voice dictation into the same field that filters the same list, one handler for typed and spoken queries.
*   **Scoped / faceted typeahead:** typing `in:design` inside the field switches the option source (Slack/Linear-style), the combo box reconfiguring its own data source from the query.
*   **View Transitions on option commit:** the selected option morphing into a chip or into the destination, native-browser, no heavy JS.
*   **On-device fuzzy matching (WASM):** libraries like `fuzzysort`/`uFuzzy` compiled to WASM ranking tens of thousands of options per keystroke with zero server round-trip.
* * *

## 12\. Conversion / UX Killers (the silent bleeders)
None of these throw an error. They just quietly drop completion and make the app feel broken.

*   **No debounce on remote search.** Firing a request per keystroke floods the server, races results, and makes the popup flicker between stale and fresh. The user sees jitter and distrusts it.
*   **Blank popup for every async state.** Loading, no-results, error, and min-query all rendering as the same empty box is _the_ classic combo-box failure. The user can't tell "still loading" from "nothing here" from "it broke."
*   **The request-race bug.** No cancellation, so a slow "rea" request resolves after a fast "react" one and the user picks from the wrong list. Feels haunted.
*   **Stealing focus into the options.** Break the `aria-activedescendant` rule and keyboard users lose the ability to keep typing; screen-reader users hear silence while arrowing. Instant accessibility failure.
*   **Filtering that fights the user.** Case-sensitive matching, matching only the _start_ of the string when users expect _contains_, or diacritic-strict matching ("Zurich" not matching "Zürich"). People blame themselves, then leave.
*   **No keyboard support.** Mouse-only combo boxes (click to open, click to pick, no arrow keys, no Enter) are half a component. Power users live on the keyboard here.
*   **Popup that covers the input or runs off-screen.** No collision handling means the thing you're typing into disappears behind its own suggestions on a short viewport.
*   **Reverting the user's text on blur without warning.** Select-only combo boxes that silently erase a near-match on blur feel like the app "ate" the input. Snap to the best match or show why it was rejected.
*   **Over-eager inline autocomplete.** Completing on Backspace so the field can't be cleared (§9.16). Rage-inducing.
*   **No min-query threshold on a huge dataset.** Searching on the first keystroke returns 50,000 rows for "a" and hammers the DB for nothing. Require 2–3 characters first.

The through-line: every one fails _quietly_. No crash, just abandonment and support tickets about "search is broken."
* * *

## 13\. Advanced Patterns
*   **Async state machine.** Model the popup as an explicit machine — `idle → typing → debouncing → loading → (success | empty | error)` — with XState or a reducer. Every "which blank state is this" bug becomes a named, testable node.
*   **Request cancellation as first-class.** `AbortController` on every fetch, plus a monotonic request id so even non-abortable transports (some GraphQL clients) can discard stale responses (§9.5).
*   **Highlight the match.** Bold the matched substring in each option (`<mark>`, built from text nodes — never raw HTML, §15) so the user sees _why_ a result matched.
*   **Grouped + sticky headers.** `role="group"` with `aria-label`, sticky group headings (Recent / All), keyboard nav skipping the non-interactive headers.
*   **TS-enforced a11y.** A discriminated union that _requires_ a `label`/`aria-label`, and requires `onCreate` when `creatable` is true — a misconfigured combo box won't compile.
*   **Design tokens for the popup.** Primitive → semantic → component tokens (`--combo-option-active-bg: var(--color-selection)`) so highlight, surface, and chip colors retheme and dark-mode by a token swap (same three-tier model as Button §9.23).
*   **Controlled/uncontrolled split.** Expose controlled `value`/`onChange` and uncontrolled `defaultValue`, and keep the in-progress `query` separate from the committed `value` (the reverting-text bug lives here).
* * *

## 14\. Performance & Bundle Cost
*   **Debounce is a perf feature, not just UX.** Every un-debounced keystroke is a filter pass (local) or a request (remote); 250ms of debounce can cut request volume 5–10× on fast typists.
*   **Filter cost at scale.** A naive `.filter(includes)` over 50k strings per keystroke is fine; over 500k with fuzzy scoring it's not — memoize results, precompute a lowercased index, or move filtering to a WASM matcher (§11) or the server.
*   **Virtualize past a few hundred options** (§9.17) — the difference between a 4ms and a 250ms keystroke. Below that, don't: the windowing math costs more than it saves.
*   **The icon-import trap** (same as Button): `import { Check } from "lucide-react"`, never `import * as Icons` — a namespace import adds hundreds of KB for one checkmark per option row.
*   **Don't thrash layout on filter.** Keep the popup height stable (scroll inside), animate only `opacity`/`transform`, and key options stably so the framework reuses nodes instead of tearing them down each keystroke.
*   **Bundle:** Downshift (~5KB) and `cmdk` are cheap; a full `react-select` (multi-select, async, virtualized, theming) is heavier — don't ship the kitchen sink for a 12-item picker.
* * *

## 15\. Security (the input is a query into your system)
The text the user types often becomes a database query or a third-party API call. That makes the combo box a real attack surface.

*   **Injection.** The typed query hits your data layer. **Always parameterize** (`ILIKE $1`, bound params) — never string-concatenate user input into SQL, NoSQL, or a search-engine query. A combo box that builds `WHERE name LIKE '${q}'` is an SQL-injection hole with autocomplete.
*   **Enumeration / data exfiltration.** A user-search or email combo box that returns anyone in the system lets an attacker harvest your user list one prefix at a time. Scope results to what the caller is authorized to see, and consider not autocompleting sensitive identifiers (emails, account numbers) at all.
*   **Over-fetching.** Always cap the result set server-side (`LIMIT`). A query of `"a"` must never attempt to serialize your whole table.
*   **Rate abuse.** A typeahead is a request amplifier — one user = dozens of requests/minute. Rate-limit per user _and_ per IP; debounce is client-side courtesy, not a defense. Login/coupon/username-availability combo boxes are brute-force targets.
*   **ReDoS.** If you filter with a user-influenced regex, a crafted pattern can hang the thread. Prefer plain `includes`/tokenized matching; if you must regex, use a safe, bounded matcher.
*   **XSS in options.** Options fetched from a server and rendered as HTML (highlighting the match with `dangerouslySetInnerHTML`) can inject script. Escape option text; if you highlight matches, build the `<mark>` from text nodes, not by interpolating raw HTML.
*   **The client filter is not authorization.** Filtering options in the browser is UX. If some options are privileged, the _server_ must never send them to an unauthorized client in the first place — "we filtered them out client-side" means they were still in the payload.

## 17\. Visual Styles (the same combo box, eleven skins)
Skin only — the input filters the listbox, focus stays on the input, `aria-activedescendant` drives the highlight, and the 44px option targets hold in every single one. Only the paint changes.

*   **Flat:** solid field, 1px border, flat popup with a hairline shadow; active option a solid fill. Reads instantly.
*   **Material:** filled/outlined field, floating label animating up on focus, elevation-shadowed menu, ripple on the option press, active option tinted with the primary container color.
*   **Glassmorphism:** translucent popup, `backdrop-filter: blur()` over a vivid backdrop; re-check option text contrast (frosted glass eats legibility).
*   **Liquid Glass (2026):** refractive translucent popover, specular rim, sheen that shifts with motion; pill field. Honest web approximation via layered `backdrop-filter`; SwiftUI emits `.glassEffect()`. Guard reduced-motion.
*   **Neumorphism:** soft-extruded field and popup, dual shadows on one background color; active option an _inset_ press. Contrast-poor — verify the highlight is actually visible.
*   **Skeuomorphism:** beveled "search well" field, gradient-filled options, inner highlights; the tactile real-search-box look.
*   **Neo-Brutalism:** thick black border, hard offset popup shadow, zero radius, a loud clashing highlight on the active option. Maximum personality.
*   **Claymorphism:** big radius, puffy field, soft inner-light options, gentle glow on the highlight. Friendly.
*   **Aurora / Gradient:** animated multi-hue gradient on the field border or the active-option highlight over a dark popup. Premium; honor `prefers-reduced-motion`.
*   **Minimal / Swiss:** underline-only field, borderless popup, type and whitespace carry it; active option marked by weight or a rule, not a fill.
*   **UJG Brand:** Goldenrod highlight on the active option, Eminence-on-Night popup, warm glow, confident radius, ≥44px option targets, visible Goldenrod focus ring on the input. The house default — dark saturated surface makes a Liquid-Glass popover sing.

**Rule that never changes:** style is skin, behavior is the skeleton. Guard glass / liquid-glass / neu for option contrast; guard aurora / liquid-glass for `prefers-reduced-motion`. Full guidance on the [Design Styles (visual languages)](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200551).

**Bottom line:** a combo box is a text input, a listbox, and a virtual cursor pretending to be one control. The visual is trivial; the contract is not — real focus stays on the input while `aria-activedescendant` walks the options, four async states must stay visually distinct, the typed query has to be debounced, cancelled, and treated as an untrusted database query, and the whole thing has to work from the keyboard for people who never touch the mouse. Nail those and you've mastered the component teams most often ship broken — and one of the highest-leverage inputs in any product that helps humans find one thing inside thousands.
