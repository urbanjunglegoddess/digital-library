# Password Input

# The Password Input: A Senior Engineer's Complete Breakdown
The field where security, usability, and accessibility collide harder than anywhere else in a form. A masked input looks trivial and hides an enormous amount of correctness. Here it is from first principles to production code.
* * *

## 1\. What It Actually Is
A password input is a text field whose characters are obscured (rendered as dots or bullets) by default, so the secret being typed isn't visible on screen. At its core it's `<input type="password">` — the browser handles the masking, keeps the value out of most autofill previews, and signals to password managers that this is a credential field. In practice a real password input is a small system: the masked field, a show/hide toggle, a strength meter, a caps-lock warning, and — critically — a paired (often visually hidden) username field so password managers can offer to save and fill the credential.

The three things people confuse it with, named and distinguished:
*   **Plain text input with masking CSS.** Some teams fake masking with `-webkit-text-security` or a custom font on a `type="text"` field. This looks masked but is NOT a password field: browsers won't offer to save it, password managers won't fill it, and `autocomplete` semantics break. Use the real `type="password"`.
*   **PIN / OTP input.** A 4–6 digit one-time code or numeric PIN belongs in a segmented OTP/Pin component with `inputmode="numeric"` and `autocomplete="one-time-code"`, not a masked password field. OTP codes are short-lived and numeric; passwords are long-lived secrets.
*   **Sensitive-but-not-secret text.** API keys shown once, credit-card numbers (`autocomplete="cc-number"`, not password), or SSNs are sensitive but have their own autocomplete tokens and validation. Masking alone doesn't make something a "password."
*   **Search/username field that happens to be secret-ish.** A username or email is not masked and uses `autocomplete="username"`. It matters because it must be present alongside the password for managers to work.

**Rule of thumb:** if the value is a reusable account secret the user chose or must remember, it's a password input (`type="password"` + a matching `autocomplete` token + a username field in the same form). If it's a short numeric one-time code, it's an OTP input. If it's structured PII with its own autocomplete token, use that token — masking is a display choice, not a component type.
* * *

## 2\. Why It Matters
The password input carries more weight per pixel than almost any component, because failures here are simultaneously security incidents, conversion leaks, and accessibility violations.

*   **Conversion and abandonment.** Sign-in and sign-up are the narrowest funnels in most products. A password field with no show/hide toggle, an aggressive "must contain a symbol" validator that rejects a good passphrase, or a paste block that fights password managers produces measurable drop-off. Masked-only fields (no reveal) increase failed logins and reset requests — and every reset email is a support cost and a re-auth risk.
*   **Security posture.** This is the entry point to the account. Getting `autocomplete` wrong trains browsers to autofill the wrong value; leaving the value reflected in the DOM, logs, or analytics leaks credentials; blocking paste pushes users toward shorter, weaker, human-memorable passwords — the opposite of the goal. NIST SP 800-63B explicitly says: allow paste, allow long passwords, don't force arbitrary composition rules, and check against breached-password lists. The component is where those policies are enforced or violated.
*   **Accessibility and trust.** Screen-reader users need the toggle's state announced, the strength meter announced via a live region (not silently repainted), and caps-lock warned about — a caps-lock-induced failed login is invisible and infuriating to someone who can't see the indicator light. A field that silently rejects input or gives no feedback reads as broken, and "feels broken" at the login screen is the worst possible first impression.
*   **Legal / compliance.** Credentials in logs or crash reports can be a reportable data breach under GDPR/CCPA and will fail SOC 2 / PCI review. The masking and the "never log the value" discipline aren't polish — they're audit line items.
* * *

## 3\. Anatomy
Every well-built password input is composed of predictable parts. Preserving the original's list and going deeper:

*   **Field container** — the bordered box holding the input and the trailing toggle. Owns padding, border, radius, focus ring, and the error/valid border color. Uses `display: flex` so the toggle sits inside the same visual box as the text.
*   **Masked input** — the real `<input type="password">`. The browser renders each character as a bullet (•) or asterisk. Carries `autocomplete` (`current-password` or `new-password`), `name`, an `id` for the label, and `aria-describedby` pointing at hints/errors/strength.
*   **Paired username field** — a `type="text"`/`type="email"` input with `autocomplete="username"` in the SAME `<form>`. Required for password managers to associate and save the credential. On change-password screens it may be visually hidden but must exist in the DOM.
*   **Label** — a real `<label for="password">`. Never placeholder-as-label; the label must persist while typing.
*   **Show/hide toggle** — a `<button type="button">` (not a div, not inside the tab trap incorrectly) with an icon (eye / eye-off), `aria-pressed` reflecting revealed state, and an `aria-label` that changes between "Show password" and "Hide password". Toggling flips the input's `type` between `password` and `text`.
*   **Caps-lock warning** — a small inline message ("Caps Lock is on") driven by `KeyboardEvent.getModifierState("CapsLock")`, exposed via `aria-live="polite"` or `role="status"`.
*   **Strength meter** — a segmented bar or single meter (`<meter>` or ARIA `progressbar`/`meter`) reflecting an entropy/zxcvbn score, updated as the user types, announced through an `aria-live="polite"` region — and it must NEVER block submission or paste.
*   **Strength label** — the text tier ("Weak / Fair / Good / Strong"), the accessible name for the meter; color alone is never the only signal.
*   **Requirements checklist** — optional live list (min length, etc.) with each item's met/unmet state exposed to assistive tech, linked to the input via `aria-describedby`.
*   **Hint / error region** — the `aria-describedby` target that carries help text in rest state and the validation error in error state, with `aria-invalid` toggled on the input.
* * *

## 4\. Sizes / Scale / Density
Password inputs follow the same height scale as text inputs, but the trailing toggle constrains the minimum touch target and inline padding. The toggle button must stay ≥44×44px even when the field is visually 32px, achieved by expanding its hit area with padding, not by shrinking the icon below a tappable size.

| Size | Token | Field height | Inline padding | Font | Toggle hit area | Use case |
| ---| ---| ---| ---| ---| ---| --- |
| SM | `--pw-h-sm` | 32px | 10px | 13px | 44×44 (overflows field) | Dense admin, settings rows, compact re-auth |
| MD | `--pw-h-md` | 40px | 12px | 14px | 44×44 | Default for most login/signup forms |
| LG | `--pw-h-lg` | 48px | 16px | 16px | 48×48 | Mobile-first, primary auth screens |

Rules that matter:
*   **16px minimum font on mobile.** iOS Safari zooms the viewport when a focused input's font is below 16px. A login field that yanks the layout on focus is a conversion killer; set `font-size: 16px` (or the `--pw-font-md` token) at mobile breakpoints regardless of tier.
*   **Reserve trailing space for the toggle.** The input needs `padding-inline-end` large enough that masked bullets never slide under the eye icon. Token it (`--pw-toggle-gutter: 44px`) so the icon and text never collide.
*   **Touch target is non-negotiable.** The toggle's visible icon can be 20px, but its clickable box is ≥44px via padding. On the SM tier the button legitimately overflows the field's vertical bounds — that's correct, not a bug.
*   **Strength meter height** is a spacing token (`--pw-meter-h: 4px` default, 6px on LG) with its own top gap; it should never change the field's own height or cause layout shift when it appears.
* * *

## 5\. States
A production password input has more states than a plain button because it layers input validity, reveal state, and credential-specific conditions on top of the generic set. Every state described, not just named.

1. **Default / hidden (rest)** — masked bullets, neutral border, toggle showing the "eye" icon with `aria-pressed="false"`. The baseline.
2. **Hover** — subtle border/background shift on the field and a distinct hover on the toggle button. Never the only affordance (absent on touch).
3. **Focus** — visible focus ring via `:focus-visible` on the field (and separately on the toggle, since it's a distinct focus stop). The ring must meet 3:1 non-text contrast.
4. **Revealed / visible** — input `type` flipped to `text`, plaintext shown, toggle icon becomes "eye-off", `aria-pressed="true"`, `aria-label` becomes "Hide password". This state is inherently riskier (shoulder-surfing, screen recording, screenshots) — see §15.
5. **Caps Lock on** — an inline warning appears while the field is focused and Caps Lock is active; clears when Caps Lock turns off or focus leaves. Announced politely.
6. **Typing / strength-updating** — as characters change, the strength meter and any requirements list update live; the `aria-live` region debounces announcements so it doesn't spam every keystroke.
7. **Error** — validation failed (too short, doesn't match confirm, server rejected). Border/error color, `aria-invalid="true"`, error text in the `aria-describedby` region. Color is never the sole signal — an icon or text accompanies it.
8. **Valid / success** — optional confirmation (checkmark, "Passwords match" on a confirm field). Transient, announced politely.
9. **Loading / submitting** — during async submit the field is often set `readonly` (not `disabled`, which would drop its value from the form and blur focus jarringly) and the submit button disabled; prevents edits mid-request without losing the value.
10. **Disabled** — reduced opacity, `cursor: not-allowed`, `disabled` attribute or `aria-disabled` with inert handling; the toggle disables too.
11. **Autofilled** — the browser/password-manager filled the value; browsers apply their own `:autofill` background. Don't fight it into invisibility; ensure text contrast still passes.
* * *

## 6\. Types / Variants
Every functional variant named and described. Minimum bar exceeded:

*   **Minimal (toggle only)** — masked field plus show/hide, no strength UI. Correct for **login** (`autocomplete="current-password"`), where scoring an existing password is pointless and noisy.
*   **With strength meter** — adds a live entropy/zxcvbn-scored bar. For **sign-up / change password** (`autocomplete="new-password"`). Guidance, never a gate.
*   **With requirements checklist** — live-updating rules (min length, etc.) that tick off as satisfied. Pairs with or replaces the meter. Prefer a single meaningful rule (length) over four arbitrary composition rules per NIST.
*   **Strength + requirements combined** — meter for overall quality, checklist for the one or two hard requirements. The fullest sign-up variant.
*   **Confirm-password (paired field)** — a second `type="password"` with `autocomplete="new-password"`, validated to match the first; shows a match/mismatch state. Reduces typo lockouts on accounts with no reveal.
*   **Current + new + confirm (change-password triad)** — three fields: current (`current-password`) to re-authenticate, new and confirm (`new-password`). The username field should still be present (often hidden) so managers update the saved entry.
*   **Reveal-while-held** — the value shows only while the toggle (or a key) is pressed, re-masking on release. Lower shoulder-surf exposure than a sticky toggle; common on high-security/native.
*   **Passphrase-oriented** — wide field, generous max length, monospace optional, encourages long human passphrases; no composition nagging.
* * *

## 7\. When to Use (and When Not To)
Use a password input when the user enters a **reusable secret credential**: login, registration, change-password, re-authentication before a sensitive action, or entering an existing secret/token that must be typed and remembered.

Use when:
*   Signing in to an account (single password field, `current-password`).
*   Creating an account or setting a new password (`new-password`, plus strength guidance).
*   Changing or resetting a password (current + new + confirm).
*   Confirming identity before a high-stakes action (re-auth modal).

Don't use / use something else when:
*   You need a **one-time code or numeric PIN** → use an **OTP / Pin Input** with `autocomplete="one-time-code"` and `inputmode="numeric"`. Masking a 6-digit SMS code as a password breaks autofill of the code.
*   The value is **structured PII** (card number, SSN, phone) → use the field type with the correct `autocomplete` token and format validation, not a generic masked password.
*   You want to **hide non-secret text** for privacy on shared screens → that's a visibility toggle on a normal `text` field, not credential semantics.
*   You're building **API-key display** (shown once, copied) → a read-only masked-reveal display field, not a credential input with `new-password`.

Placement heuristics:
*   **Password follows username, both in one** **`<form>`****.** Managers key off the pair; splitting them across steps (username page → password page) needs the hidden username field on the password step or autofill degrades.
*   **Toggle inside the field, at the trailing edge**, vertically centered, never overlapping the caret's text.
*   **Strength meter and errors go below the field**, in the reserved describedby region, so appearing/disappearing doesn't shove the submit button.

## 8\. Across Design Systems
Same masked field, different opinions about the toggle, the meter, and the semantics.

*   **Material Design (Google) / MUI** — `TextField` with `type="password"` and an `InputAdornment` holding an `IconButton` (visibility / visibility\_off from Material Symbols). Floating label animates up; error text and helper text live in `FormHelperText` wired via `aria-describedby`. No built-in strength meter — teams add one.
*   **Apple HIG (iOS/macOS)** — `SecureField` in SwiftUI. The system integrates iCloud Keychain, AutoFill, and Passwords app; it offers "Automatic Strong Password" and the Passwords sheet. A reveal control and the strong-password suggestion are system-provided. HIG discourages custom composition rules and favors passkeys where possible.
*   **Fluent (Microsoft)** — WinUI `PasswordBox` with a built-in reveal button (`PasswordRevealMode`: Peek / Hidden / Visible). Peek mode reveals only while the reveal glyph is pressed — the "reveal-while-held" pattern baked in. On web, Fluent UI React exposes a password `Input` with a `contentAfter` slot for the toggle.
*   **Ant Design** — `Input.Password` ships the toggle out of the box (`iconRender`, `visibilityToggle`), controllable visibility, and a separate `Progress`/custom meter for strength. Enterprise-dense; the reveal is a first-class prop.
*   **Tailwind CSS** — no component; you compose a `relative` wrapper with an absolutely-positioned toggle button and utilities for states (`focus-within:ring-2`, `aria-invalid:border-red-500`). Freedom plus the responsibility to wire ARIA and autocomplete yourself.
*   **shadcn/ui + Radix** — `Input` (styled) with no native password variant; teams wrap it with a toggle button and a `useState` for visibility. Radix provides `Label`, `Form` (validation + `aria-describedby` wiring); the strength meter is custom, often over `zxcvbn`.
*   **Bootstrap 5** — `.form-control` with `type="password"` inside an `.input-group`, the toggle as an `.input-group-text`/`.btn` at the end. No JS toggle by default — you add the click handler. Validation classes (`.is-invalid`, `.invalid-feedback`) supply error semantics.
*   **Carbon (IBM)** — a dedicated `PasswordInput` with a built-in show/hide button and proper labeling; a solid reference for accessible defaults.

### 8b. What's trending in 2026
*   **Passkeys are eating the password.** WebAuthn/passkeys (FIDO2) let the password input become a fallback, not the front door. New auth screens increasingly lead with "Sign in with a passkey" and keep the password field as progressive fallback via `autocomplete="username webauthn"` on the username field and conditional UI.
*   **Password managers as the assumed default.** Both platform (iCloud Keychain, Google Password Manager) and third-party managers are ubiquitous; the field is now designed to _cooperate_ with them (correct autocomplete, real form, no paste block) rather than to be typed into by hand.
*   **Breach-aware fields.** Inline "this password appeared in a data breach" warnings using k-anonymity range queries (HIBP Pwned Passwords) at sign-up, done client-side against a hashed prefix so the full password never leaves the device.
*   **NIST-aligned simplification.** The trend is _fewer_ rules: length over composition, no forced periodic rotation, no arbitrary symbol requirements, paste always allowed — the modern field nudges with a meter instead of blocking with regex.
*   **Liquid Glass / frosted auth cards.** Apple's iOS 26 / macOS Tahoe language pushes translucent auth surfaces; the password field sits on a refractive card with a specular rim — pretty, but reveal-state and contrast caveats get _more_ important on glass.

### 9.1 HTML (semantic foundation with ARIA)

```html
<!-- SIGN-IN: existing password. Username present for password managers. -->
<form action="/login" method="post" autocomplete="on">
  <label for="username">Email</label>
  <input id="username" name="username" type="email"
         autocomplete="username" autocapitalize="none" spellcheck="false" />

  <label for="current-pw">Password</label>
  <div class="pw-field">
    <input id="current-pw" name="password" type="password"
           autocomplete="current-password"
           autocapitalize="none" spellcheck="false"
           aria-describedby="pw-caps" />
    <button type="button" class="pw-toggle"
            aria-pressed="false" aria-controls="current-pw"
            aria-label="Show password">
      <svg class="i-eye" aria-hidden="true" focusable="false"><!-- eye --></svg>
    </button>
  </div>
  <p id="pw-caps" role="status" aria-live="polite" hidden>Caps Lock is on</p>

  <button type="submit">Sign in</button>
</form>

<!-- SIGN-UP: new password with strength meter (guidance, not a gate). -->
<form action="/signup" method="post">
  <label for="su-user">Email</label>
  <input id="su-user" name="username" type="email" autocomplete="username" />

  <label for="new-pw">Create password</label>
  <div class="pw-field">
    <input id="new-pw" name="password" type="password"
           autocomplete="new-password" minlength="8"
           aria-describedby="pw-strength pw-hint" />
    <button type="button" class="pw-toggle" aria-pressed="false"
            aria-controls="new-pw" aria-label="Show password">
      <svg class="i-eye" aria-hidden="true" focusable="false"></svg>
    </button>
  </div>
  <p id="pw-hint">Use 8+ characters. A long passphrase beats a short complex one.</p>
  <div class="pw-strength">
    <meter id="pw-meter" min="0" max="4" low="2" high="3" optimum="4"
           value="0" aria-hidden="true"></meter>
    <span id="pw-strength" role="status" aria-live="polite">Strength: empty</span>
  </div>

  <button type="submit">Create account</button>
</form>
```

Key HTML rules:
*   **Real** **`type="password"`**, never CSS-faked masking — browsers and managers depend on the real type.
*   **`autocomplete`** **is load-bearing:** `current-password` for login, `new-password` for signup/change (which also tells managers to _offer a generated password_ and NOT to autofill the old one).
*   **The username field must exist in the same form**, even hidden on multi-step flows, or "save password" won't fire.
*   The toggle is a real `<button type="button">` (so Enter/Space work and it never submits the form), with `aria-pressed` + a changing `aria-label`.
*   **Never** add `onpaste="return false"` — paste must work (NIST).

### 9.3 React + TypeScript (full reusable component)

```tsx
import { forwardRef, useId, useRef, useState, InputHTMLAttributes } from "react";

type PasswordFieldProps = Omit<
  InputHTMLAttributes<HTMLInputElement>,
  "type" | "autoComplete"
> & {
  label: string;
  /** login -> current-password, signup/change -> new-password */
  purpose: "current-password" | "new-password";
  error?: string;
  hint?: string;
};

export const PasswordField = forwardRef<HTMLInputElement, PasswordFieldProps>(
  function PasswordField(
    { label, purpose, error, hint, id, ...rest },
    forwardedRef
  ) {
    const reactId = useId();
    const inputId = id ?? `pw-${reactId}`;
    const capsId = `${inputId}-caps`;
    const hintId = `${inputId}-hint`;
    const errId = `${inputId}-err`;

    const [revealed, setRevealed] = useState(false);
    const [capsOn, setCapsOn] = useState(false);
    const localRef = useRef<HTMLInputElement>(null);

    const describedBy =
      [hint ? hintId : null, error ? errId : null, capsOn ? capsId : null]
        .filter(Boolean)
        .join(" ") || undefined;

    function checkCaps(e: React.KeyboardEvent<HTMLInputElement>) {
      // getModifierState is the reliable, layout-independent check.
      setCapsOn(e.getModifierState?.("CapsLock") ?? false);
    }

    return (
      <div className="pw-block">
        <label htmlFor={inputId}>{label}</label>
        <div className="pw-field" data-invalid={Boolean(error)}>
          <input
            id={inputId}
            ref={mergeRefs(forwardedRef, localRef)}
            type={revealed ? "text" : "password"}
            autoComplete={purpose}
            autoCapitalize="none"
            spellCheck={false}
            aria-invalid={Boolean(error) || undefined}
            aria-describedby={describedBy}
            onKeyUp={checkCaps}
            onKeyDown={checkCaps}
            onBlur={() => setCapsOn(false)}
            {...rest}
          />
          <button
            type="button"
            className="pw-toggle"
            aria-pressed={revealed}
            aria-controls={inputId}
            aria-label={revealed ? "Hide password" : "Show password"}
            onClick={() => {
              setRevealed((v) => !v);
              // keep focus & caret in the field after toggling
              const el = localRef.current;
              if (el) {
                const pos = el.value.length;
                requestAnimationFrame(() => {
                  el.focus();
                  el.setSelectionRange?.(pos, pos);
                });
              }
            }}
          >
            {revealed ? <EyeOffIcon /> : <EyeIcon />}
          </button>
        </div>
        {hint && !error && <p id={hintId}>{hint}</p>}
        {error && (
          <p id={errId} role="alert" className="pw-error">
            {error}
          </p>
        )}
        <p id={capsId} role="status" aria-live="polite" hidden={!capsOn}>
          Caps Lock is on
        </p>
      </div>
    );
  }
);

function mergeRefs<T>(...refs: (React.Ref<T> | undefined)[]) {
  return (node: T) => {
    for (const ref of refs) {
      if (typeof ref === "function") ref(node);
      else if (ref && "current" in ref)
        (ref as React.MutableRefObject<T>).current = node;
    }
  };
}

const EyeIcon = () => (
  <svg width="20" height="20" viewBox="0 0 24 24" aria-hidden="true" focusable="false">
    <path fill="currentColor" d="M12 5c-5 0-9 4.5-10 7 1 2.5 5 7 10 7s9-4.5 10-7c-1-2.5-5-7-10-7Zm0 11a4 4 0 1 1 0-8 4 4 0 0 1 0 8Z" />
  </svg>
);
const EyeOffIcon = () => (
  <svg width="20" height="20" viewBox="0 0 24 24" aria-hidden="true" focusable="false">
    <path fill="currentColor" d="M2 4.3 3.3 3l17.7 17.7-1.3 1.3-3-3A11.7 11.7 0 0 1 12 20C6 20 2 14 2 12a13 13 0 0 1 3.6-4.4L2 4.3ZM12 8a4 4 0 0 1 4 4l-4-4Z" />
  </svg>
);
```

### 9.4 Vanilla JavaScript (no framework, full keyboard)

```html
<div class="pw-field" data-pw>
  <input type="password" autocomplete="current-password"
         aria-describedby="caps-msg" />
  <button type="button" class="pw-toggle"
          aria-pressed="false" aria-label="Show password"></button>
</div>
<p id="caps-msg" role="status" aria-live="polite" hidden>Caps Lock is on</p>

<script>
document.querySelectorAll("[data-pw]").forEach((field) => {
  const input = field.querySelector("input");
  const toggle = field.querySelector(".pw-toggle");
  const caps = document.getElementById("caps-msg");

  toggle.addEventListener("click", () => {
    const show = input.type === "password";
    input.type = show ? "text" : "password";
    toggle.setAttribute("aria-pressed", String(show));
    toggle.setAttribute("aria-label", show ? "Hide password" : "Show password");
    // restore focus + caret so typing continues seamlessly
    const end = input.value.length;
    input.focus();
    try { input.setSelectionRange(end, end); } catch {}
  });

  function caps_(e) {
    const on = e.getModifierState && e.getModifierState("CapsLock");
    caps.hidden = !on;
  }
  input.addEventListener("keydown", caps_);
  input.addEventListener("keyup", caps_);
  input.addEventListener("blur", () => (caps.hidden = true));
  // NOTE: no paste blocking, ever.
});
</script>
```

```ts
// app/(auth)/signup/actions.ts
"use server";
import { z } from "zod";
import { createHash } from "node:crypto";
import argon2 from "argon2";
import { db } from "@/lib/db";

const Schema = z.object({
  username: z.string().email(),
  password: z.string().min(8).max(256), // allow long; cap only to bound cost
});

/** HIBP k-anonymity: only the SHA-1 prefix (5 chars) ever leaves the server. */
async function isBreached(password: string): Promise<boolean> {
  const sha1 = createHash("sha1").update(password).digest("hex").toUpperCase();
  const prefix = sha1.slice(0, 5);
  const suffix = sha1.slice(5);
  const res = await fetch(`https://api.pwnedpasswords.com/range/${prefix}`, {
    headers: { "Add-Padding": "true" },
  });
  if (!res.ok) return false; // fail open: never block signup on a 3rd-party outage
  const body = await res.text();
  return body.split("\n").some((line) => line.split(":")[0].trim() === suffix);
}

export async function signUp(_prev: unknown, formData: FormData) {
  const parsed = Schema.safeParse(Object.fromEntries(formData));
  if (!parsed.success) return { error: "Enter a valid email and an 8+ char password." };

  const { username, password } = parsed.data;
  if (await isBreached(password))
    return { error: "That password has appeared in a breach. Choose another." };

  // Hash SERVER-SIDE with argon2id (or bcrypt). Never hash on the client.
  const hash = await argon2.hash(password, { type: argon2.argon2id });
  await db.user.create({ data: { email: username, passwordHash: hash } });
  // password + hash go out of scope here; never log either.
  return { error: null };
}
```

```python
import hashlib
import httpx
from fastapi import FastAPI, Form, HTTPException
from pydantic import BaseModel, EmailStr, constr
from argon2 import PasswordHasher

app = FastAPI()
ph = PasswordHasher()  # argon2id defaults

class SignUp(BaseModel):
    username: EmailStr
    password: constr(min_length=8, max_length=256)

async def is_breached(password: str) -> bool:
    sha1 = hashlib.sha1(password.encode()).hexdigest().upper()
    prefix, suffix = sha1[:5], sha1[5:]
    async with httpx.AsyncClient(timeout=3.0) as client:
        try:
            r = await client.get(
                f"https://api.pwnedpasswords.com/range/{prefix}",
                headers={"Add-Padding": "true"},
            )
        except httpx.HTTPError:
            return False  # fail open on third-party outage
    return any(line.split(":")[0].strip() == suffix for line in r.text.splitlines())

@app.post("/signup")
async def signup(username: str = Form(...), password: str = Form(...)):
    data = SignUp(username=username, password=password)  # server-side validation
    if await is_breached(data.password):
        raise HTTPException(422, "That password has appeared in a breach.")
    pw_hash = ph.hash(data.password)   # hashing is SERVER-side only
    # persist pw_hash; the raw password is never logged, echoed, or stored
    return {"ok": True}
```

## 10\. Accessibility
STANDALONE. Never folded into §9. The password input has three distinct accessibility jobs: the field, the toggle, and the live feedback (caps-lock + strength).

**Roles and attributes**
*   The field is a native `<input type="password">` — it exposes the correct role and, importantly, screen readers announce it as a _protected/secure_ field and do NOT read the characters aloud. Preserve that: don't move the value into a `type="text"` field permanently.
*   The label is a real `<label for>`; never placeholder-only (placeholder vanishes on input and has poor contrast).
*   The toggle is `<button type="button">` with `aria-pressed` (true when revealed) and an `aria-label` that changes ("Show password" ⇄ "Hide password"). Optionally `aria-controls` the input's id.
*   Errors: set `aria-invalid="true"` on the input and point `aria-describedby` at the error node; use `role="alert"` on the error so it's announced immediately.
*   Strength meter: use `<meter>` or `role="meter"`/`progressbar` with an accessible name, and mirror the tier text in an `aria-live="polite"` region so it's announced without stealing focus. Never rely on bar color alone.
*   Caps-lock message: `role="status"` + `aria-live="polite"`, toggled `hidden`.

**Keyboard map (interactive)**

| Key | Focus on field | Focus on toggle |
| ---| ---| --- |
| Tab | Move to the toggle (next stop) | Move to next control (submit) |
| Shift+Tab | Move to previous control (username) | Move back to the field |
| Enter | Submit the form (implicit submit) | Activate toggle (does NOT submit — `type="button"`) |
| Space | Insert a space into the password | Activate toggle |
| Printable keys | Type into the masked value | — |
| Esc | (browser: may clear autofill suggestion) | — |

**Focus management**
*   After toggling reveal/hide, **return focus to the input** and restore the caret to its previous position (or end), so a keyboard user isn't dumped out of the field mid-entry.
*   Never move focus automatically on strength change — the meter updates silently via the live region.
*   On async submit, prefer `readonly` over `disabled` so the field doesn't lose focus and drop out of the tab order abruptly.

**Contrast & target size**
*   Masked text and typed plaintext ≥ 4.5:1 against the field background (WCAG AA). The bullet glyphs count as text.
*   Field border, focus ring, and the strength meter segments are non-text UI: ≥ 3:1 against adjacent colors.
*   The toggle button's hit target ≥ 44×44px even when the icon is 20px and the field is 32px tall.

**Reduced motion & forced colors**
*   Under `prefers-reduced-motion`, drop the toggle's transition and any strength-bar fill animation; snap between states.
*   Under `forced-colors`/Windows High Contrast, keep a real border and let system colors show the focus ring; don't rely on a custom shadow that disappears.

**Common failures specific to this component**
*   Icon-only toggle with no `aria-label` (screen reader reads "button" — useless).
*   `aria-pressed` never updated, so the revealed state isn't announced.
*   Strength meter repainted with no live region — sighted-only feedback.
*   Caps-lock indicated by color only, or not at all — invisible to blind users who then fail login silently.
*   Placeholder used as the label; disappears when typing.
*   Toggle implemented as a `<div>`/`<span>` with a click handler — not keyboard-operable, no role.
*   Blocking paste — hostile to password managers and to screen-reader/switch users who can't hand-type a 20-char secret.

## 11\. Innovative / Emerging Ideas
*   **Passkeys / WebAuthn conditional UI.** The password field becomes the fallback while the username field carries `autocomplete="username webauthn"`, letting the browser surface a passkey in the same autofill dropdown. The 2026 direction is "password optional."
*   **On-device breach and reuse warnings.** Browsers (Chrome, Safari) already flag compromised/reused passwords at sign-in; apps mirror this with client-side k-anonymity checks so the field can warn "seen in a breach" before submit, with the full secret never leaving the device.
*   **`EditContext`** **and better IME/secure input.** The 2026-era `EditContext` API gives custom editable surfaces first-class input handling; combined with form-associated custom elements and `ElementInternals`, a fully custom password component can finally participate in autofill and validation like a native input.
*   **Automatic strong-password generation inline.** Platform managers offer a generated password directly in the field (iOS/macOS "Automatic Strong Passwords," Chrome suggestion). Designing the `new-password` field to _invite_ the suggestion (correct autocomplete, visible affordance) beats nagging users to invent one.
*   **Passphrase-first UX.** Fields that measure and reward length (entropy) rather than composition, with a real-time zxcvbn estimate and "time to crack" framing instead of "add a symbol."
*   **Hold-to-reveal with auto re-mask.** Reveal only while pressed, auto re-hide after a few seconds or on blur, reducing the shoulder-surf/screenshot window that a sticky toggle leaves open.
* * *

## 12\. Conversion / UX Killers
Each is a specific, silent failure that costs logins, resets, or trust — with the fix implied.

*   **No show/hide toggle.** Users can't verify what they typed, mistype, get locked out, and flood password-reset (a support cost and a re-auth risk). Fix: ship the toggle on every password field, defaulting to masked.
*   **Blocking paste (****`onpaste`** **prevented).** Password-manager users can't fill; everyone else picks shorter, weaker, typeable passwords. It actively lowers security and enrages users. Fix: never block paste — it's a NIST requirement.
*   **Wrong or missing** **`autocomplete`** **/ no username field.** Managers don't offer to save or fill, the browser autofills the wrong value, and users abandon. Fix: `current-password` vs `new-password` correctly, always a `username` field in the same form.
*   **Over-strict composition rules.** "Must contain an uppercase, a number, and a symbol" rejects strong passphrases and pushes users to "Password1!" patterns. Fix: enforce length, guide with a meter, drop arbitrary character mandates (NIST).
*   **Silent caps-lock failures.** User's Caps Lock is on, login fails with a generic "wrong password," they can't tell why, and try again → lockout. Fix: detect and warn inline while focused.
*   **Strength meter that blocks submit.** Gating the button until "Strong" frustrates users with a fine password and tanks completion. Fix: the meter guides; only a minimal length is a hard rule.
*   **16px-below font causing mobile zoom.** The layout lurches on focus, the toggle jumps, thumbs miss. Fix: `font-size: 16px` on the field at mobile widths.
*   **Reveal state with no auto-remask on a shared/recorded screen.** Users reveal, walk away, and the plaintext lingers in screenshots/recordings. Fix: consider hold-to-reveal or auto re-mask on blur for sensitive contexts.
*   **Disabling the field (not readonly) during submit.** A `disabled` field is dropped from the submitted form data and loses focus jarringly. Fix: use `readonly` while submitting.

## 13\. Advanced Patterns
*   **TypeScript-enforced a11y via discriminated union.** Make the intent un-skippable: a login field can't accidentally ship as `new-password`, and an icon-only toggle can't ship without a label.

```ts
type Purpose =
  | { mode: "login"; autoComplete: "current-password" }
  | { mode: "signup" | "change"; autoComplete: "new-password"; showStrength?: boolean };

type PasswordFieldProps = {
  label: string;          // visible label REQUIRED — no placeholder-only fields
} & Purpose;

// <PasswordField mode="login" autoComplete="new-password" />  // ❌ compile error
// <PasswordField mode="login" autoComplete="current-password" label="Password" /> // ✅
```

*   **Design-token tiers for the whole field.** Primitive → semantic → component, so a rebrand or dark mode is a token swap, never a rewrite. The strength scale is tokenized so "weak/fair/strong" colors stay consistent and contrast-checked.

```css
:root {
  /* primitive */
  --gold-500:#DCA424; --orange-500:#E86100; --green-900:#042D1D; --eminence:#5F2C82;
  /* semantic */
  --color-focus: var(--gold-500);
  --color-danger: var(--orange-500);
  /* component */
  --pw-focus: var(--color-focus);
  --pw-invalid-border: var(--color-danger);
  --pw-strength-1: var(--orange-500);
  --pw-strength-2: var(--gold-500);
  --pw-strength-3: var(--green-900);
  --pw-toggle-size: 44px;
}
.pw-field:focus-within { outline: 2px solid var(--pw-focus); }
.pw-field[data-invalid="true"] { border-color: var(--pw-invalid-border); }
```

*   **Debounced, off-main-thread strength scoring.** `zxcvbn` is heavy (~400KB). Lazy-load it, run it in a Web Worker, and debounce so scoring never blocks keystrokes:

```ts
const worker = new Worker(new URL("./zxcvbn.worker.ts", import.meta.url), { type: "module" });
let t: number;
input.addEventListener("input", () => {
  clearTimeout(t);
  t = window.setTimeout(() => worker.postMessage(input.value), 200);
});
worker.onmessage = (e) => announceStrength(e.data.score); // updates aria-live region
```

*   **Form-associated custom element** using `ElementInternals` (`static formAssociated = true`, `this.attachInternals().setFormValue(...)`) so a fully custom password component still submits, validates, and participates in autofill like a native `<input>`.

## 14\. Performance & Bundle Cost
*   **Lazy-load the strength library.** `zxcvbn` and its dictionaries are hundreds of KB — never in the initial login bundle. Dynamic-import it only on the sign-up route, and only after first keystroke. Login (the hot path) ships the field with zero scoring code.
*   **Tree-shake icons.** Import `{ Eye, EyeOff }` by name, never `import * as Icons`. A namespace import of an icon set can add hundreds of KB for two glyphs.
*   **Compositor-only animations.** Animate the toggle hover and strength-bar fill with `transform`/`opacity`, not `width`/`height`/`box-shadow`, so the meter update doesn't trigger layout reflow every keystroke. Keep the field's own width fixed when the meter/error appears (reserve the space) to avoid layout shift.
*   **Debounce scoring and breach checks.** Score/breach-check on a 200–300ms debounce, not per keystroke, and run scoring in a Web Worker so typing never janks. The HIBP range call happens once on blur/submit, not on every character.
*   **Don't re-render the whole form on keystroke.** In React, keep the password value local (or memoize siblings) so typing doesn't re-render the strength library, the username field, and the submit button on every character.

## 15\. Security
STANDALONE. Never folded into §9. The password input is the single highest-value attack surface in most apps: it handles the plaintext credential in the browser for a few milliseconds, and every link in the chain after it must be engineered as if it's under attack — because it is.

**Never log, reflect, or echo the value.** The plaintext password must never appear in application logs, request logs, access logs, error messages, crash reports, breadcrumbs, or analytics events. This is the most common real-world leak: a global request logger that dumps `req.body`, a Sentry breadcrumb capturing the form, a `console.log(formData)` left in. Scrub `password` (and confirm/current) from every logging and telemetry pipeline explicitly. Credentials in logs is a reportable breach under GDPR/CCPA and an automatic SOC 2 / PCI failure.

**Keep the value out of the DOM, URL, and analytics.** Don't reflect it into another element, a hidden field, a `data-*` attribute, or `localStorage`. Never submit a password via GET (it lands in the URL, browser history, referrer headers, and server logs) — always POST. Don't send it to session-replay tools (FullStory/LogRocket/Hotjar); password fields are masked by those tools by default, but a custom `type="text"` reveal or a mirrored value defeats that masking — one more reason not to permanently swap the field to `text`.

**HTTPS only — no exceptions.** A password field on an `http://` page is transmitted in cleartext and is trivially sniffable; browsers now actively warn. Serve auth pages over TLS, set `Strict-Transport-Security` (HSTS), and mark auth cookies `Secure`, `HttpOnly`, and `SameSite=Lax`/`Strict`. Mixed content (an HTTP form action from an HTTPS page) is equally fatal.

**`autocomplete`** **correctness is a security control, not just UX.** `current-password` vs `new-password` tells the browser/manager whether to fill the existing secret or generate/save a new one. Getting it wrong can cause the browser to autofill the old password into a "new password" field (silently keeping a compromised secret) or fail to save the new one. `autocomplete="off"` on password fields is an anti-pattern that browsers largely ignore and that pushes users away from managers toward weak, reused passwords.

**Hashing is server-side, with a slow adaptive KDF — never client-side.** Hash with **argon2id** (preferred) or **bcrypt** on the server, with a per-user salt (built into both). Never hash in the browser: client-side hashing means the hash _becomes_ the password (an attacker who steals it authenticates directly), it can't use server-only secrets/pepper, and it can't be upgraded server-side. The raw password enters the server, is validated and hashed, and both plaintext and hash immediately go out of scope — never stored in plaintext, never logged.

**Server-side validation and breached-password checks.** The client's `minlength`/strength meter is a hint; the server re-validates length and any real policy. Check new passwords against a breach corpus using **k-anonymity**: SHA-1 the password, send only the first **5 hex characters** of the hash to the HIBP Pwned Passwords range API, and compare the returned suffixes locally — the full password and full hash never leave your server, and HIBP never sees enough to identify it. Fail _open_ (don't block signup) if the third-party API is down.

**Rate-limit and monitor the endpoints.** Login, signup, password-reset, and re-auth are brute-force and credential-stuffing targets. Rate-limit per account AND per IP (and consider per-ASN), add exponential backoff and lockout-with-recovery, require CAPTCHA/proof-of-work after N failures, and alert on stuffing patterns. The password field's client-side niceties do nothing here — the defense is entirely server-side.

**Reveal-state is its own risk.** Toggling to plaintext exposes the secret to shoulder-surfing, over-the-shoulder cameras, screen sharing, and screenshots/screen recording. Default to masked, consider hold-to-reveal or auto re-mask on blur in sensitive/shared contexts, and never leave a field permanently in `text` mode "for convenience."

**Paste MUST be allowed.** Blocking paste is a security _anti-pattern_: it prevents password managers from working, which forces shorter, memorable, reused passwords — strictly weaker. NIST SP 800-63B explicitly requires that verifiers permit paste. There is no legitimate security reason to block it.

**Other surface:** protect auth forms against clickjacking (`Content-Security-Policy: frame-ancestors 'none'`), enforce CSRF tokens on the login/change POST, and don't reveal whether the _username_ or the _password_ was wrong (generic "invalid credentials").

## 16\. Senior-Level Checklist
Ship-ready gate. Every item non-negotiable.

- [ ] Real `<input type="password">` (not CSS-masked `text`), with a real `<label for>` (no placeholder-as-label).
- [ ] Correct `autocomplete`: `current-password` for login, `new-password` for signup/change — and a `username`/email field present in the SAME form.
- [ ] Show/hide toggle is a `<button type="button">` with `aria-pressed` and a changing `aria-label`; focus and caret return to the field after toggling.
- [ ] Keyboard-operable throughout; visible `:focus-visible` ring on both field and toggle; toggle hit target ≥ 44×44px.
- [ ] Caps-lock detected via `getModifierState` and announced through a `role="status"`/`aria-live` region.
- [ ] Strength meter (signup) is guidance only — never blocks submit or paste — and is announced via `aria-live`, not color alone.
- [ ] **Paste is allowed.** No `onpaste` blocking anywhere.
- [ ] Text/bullet contrast ≥ 4.5:1; border/focus/meter non-text contrast ≥ 3:1; `prefers-reduced-motion` and `forced-colors` handled.
- [ ] `font-size: 16px` on mobile to prevent iOS zoom; trailing gutter reserved so bullets never slide under the toggle.
- [ ] Value never logged, reflected into the DOM/URL, or sent to analytics/session-replay; auth pages HTTPS-only with HSTS.
- [ ] Server-side: validate length, argon2id/bcrypt hashing (never client-side), breach check via k-anonymity, rate-limiting + generic error messages on the endpoint.
- [ ] Async submit uses `readonly` (not `disabled`) so the value isn't dropped and focus isn't lost.

## 17\. Visual Styles
The same masked field + toggle across the 11 core visual languages. The skin changes; the semantics, keyboard behavior, focus ring, 44px toggle target, and "never block paste" rule do not.

*   **Flat** — solid 1px border, crisp corners, a flat eye glyph; the strength bar is a plain 4-segment row of solid fills. Reads instantly, scales fast, contrast is easy to guarantee.
*   **Material** — the field as an outlined/filled `TextField` with a label that floats up on focus, a ripple on the toggle icon button, and an underline/outline that animates to the accent color; the strength meter as a determinate `LinearProgressIndicator`.
*   **Glassmorphism** — a translucent field with `backdrop-filter: blur()` over a vivid auth background, the eye icon frosted; watch bullet-text contrast against the blurred content behind — often needs a semi-opaque scrim so the masked dots stay ≥4.5:1.
*   **Liquid Glass (2026 — Apple iOS 26 / macOS Tahoe)** — the field sits on a refractive pill card with a specular rim and a sheen that shifts with motion; the toggle is a floating glass capsule, and the reveal transition subtly refracts. Gorgeous, but reveal-state contrast and reduced-motion caveats get stricter here.
*   **Neumorphism** — the field as a soft _inset_ groove (dual light/dark inner shadows) on a same-color surface, the toggle as a small extruded pill; pretty but contrast-poor — accent use only, and the focus ring must still be a real high-contrast outline, not just a shadow.
*   **Skeuomorphism** — an inset "engraved" text well with a beveled edge and inner highlight, the eye toggle rendered as a tactile glossy button; the bullets look pressed into the surface. The literal "real object" login look.
*   **Neo-Brutalism** — thick black border, zero radius, a hard offset drop shadow on the field, the toggle a chunky bordered button in a clashing accent; the strength bar is a blocky segmented row. Loud, high-personality auth.
*   **Claymorphism** — big radius, puffy field with a soft inner top-light and bottom-shadow, a rounded pillowy toggle; the strength segments are rounded candy-like pills. Friendly, approachable signup.
*   **Aurora / Gradient** — an animated multi-hue gradient border or focus glow on a dark field, the strength meter filling with a gradient from danger to success; honor `prefers-reduced-motion` and keep the masked text on a solid backing for contrast.
*   **Minimal / Swiss** — no box, just a bottom rule and generous type; the toggle is a quiet text link ("Show"), the strength shown as a single restrained word. Typography and spacing do all the work.
*   **UJG Brand** — Goldenrod (`#DCA424`) focus ring and eye glyph on a deep Eminence (`#5F2C82`) / Night (`#0A0A0A`) field, Platinum bullet text, a warm glow on focus; the strength bar runs Spanish Orange → Goldenrod → Dark Green. The house default.

**The rule that never changes:** the style is skin, the behavior is the skeleton. Across all eleven skins the field stays a real `<input type="password">`, the toggle stays a labeled `<button>` with `aria-pressed`, focus stays visible, the target stays ≥44px, caps-lock is still warned, and paste is never blocked. Change the paint, never the wiring.
