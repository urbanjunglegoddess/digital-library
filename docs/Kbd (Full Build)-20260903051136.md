## 1\. What a Kbd Actually Is
A **kbd** (keyboard key indicator) is a small inline element styled to look like a physical keyboard key. It displays keyboard shortcuts in menus, tooltips, command palettes, and documentation.

The HTML `<kbd>` element is the semantic base. It represents "a span of inline text denoting textual user input from a keyboard, voice input, or other text entry device" (MDN).

**Kbd (this doc):** visual key cap representation.
**Tooltip:** a container that might hold a Kbd. Different component.
**Button:** an interactive control. Kbd is display-only, non-interactive.
**Badge:** a status indicator. Different purpose.
**Shortcut text:** just plain text like "Ctrl+S". A Kbd makes it look like actual keys.
* * *

## 2\. Why It Matters
**Discoverability.** Keyboard shortcuts are invisible until documented. Kbd elements in menus, tooltips, and command palettes teach users the shortcuts exist.
**Scannability.** The key-cap visual stands out from surrounding text, making shortcuts easy to spot when scanning documentation or UI.
**Platform correctness.** Cmd on macOS, Ctrl on Windows/Linux. Showing the wrong modifier frustrates users and erodes trust in the documentation.
**Professional polish.** A plain-text "Ctrl+S" looks amateur next to a properly styled key indicator that resembles an actual keyboard key. It's a small detail that signals craft.
* * *

## 3\. Anatomy
**Container:** the key-cap shaped box. Slightly raised appearance (border, shadow, or gradient) mimicking a physical key.
**Label:** the key name inside. Can be a symbol (⌘, ⇧, ⌥, ↵) or text (Cmd, Shift, Alt, Enter, Esc).
**Separator (for combinations):** a `+` or space between keys in a shortcut (Cmd + K).
**Platform symbols:**
*   Mac: ⌘ (Cmd), ⌥ (Option/Alt), ⇧ (Shift), ⌃ (Ctrl), ↵ (Return)
*   Windows/Linux: Ctrl, Alt, Shift, Enter, Win
* * *

## 4\. Sizes / Scale

| Token | Height | Padding | Font | Use |
| ---| ---| ---| ---| --- |
| S | 18-20px | 2px 5px | 11px | Dense menus, compact UI |
| M | 22-26px | 3px 6px | 12px | Default (menus, tooltips) |
| L | 28-32px | 4px 8px | 13px | Documentation, tutorials |

The kbd is always inline, flowing with surrounding text. It should not break the line's vertical rhythm significantly. `vertical-align: baseline` or `middle` depending on context.

Minimum width: enough for the widest common key ("Backspace" or "Shift"). Single keys like "K" get compact padding.
* * *

## 5\. States
Kbd is **non-interactive** and **display-only**. It has no hover, focus, active, or disabled states. It's a typographic element, not a control.

Variants by context:
*   **Light mode:** dark key on light background (most common in docs).
*   **Dark mode:** light key on dark background.
*   **In a menu item:** aligned right within the menu row, muted color to not compete with the action label.
*   **In prose:** inline with body text, slightly more prominent.
*   **In a tooltip:** matches the tooltip's color scheme.
* * *

## 6\. Types / Variants
**Single key:** just one key (K, Enter, Esc, Space).
**Modifier:** a modifier key (Cmd/Ctrl, Shift, Alt/Option).
**Combination:** two or more keys pressed together (Cmd+K, Ctrl+Shift+P).
**Sequence:** keys pressed in order, not simultaneously (g then i). Separated by "then" or a space rather than "+".
**Platform-aware:** automatically shows the correct modifier for the user's OS (Cmd on macOS, Ctrl on Windows/Linux).
**Symbol vs. Text:** ⌘ vs. "Cmd", ⇧ vs. "Shift". Symbols are denser; text is more universally understood.
* * *

## 7\. When to Use (and When Not To)
**Use Kbd when:**
*   Displaying keyboard shortcuts in menus, tooltips, or command palettes
*   Documenting keyboard interactions in help text or tutorials
*   Showing key bindings in settings/preferences

**Don't use when:**
*   The key is interactive (it does something on click) → use a Button
*   You're showing a generic label → use a Badge
*   The shortcut is in running prose and a simple inline code span suffices
*   For output (what the computer types back) → that's `<samp>` or `<code>`, not `<kbd>`
*   The shortcut doesn't exist yet (don't show a Kbd for unimplemented features)
* * *

## 8\. Across Design Systems
**GitHub:** uses `<kbd>` extensively in documentation with a subtle box-shadow style.
**Linear:** shows shortcuts in command palette items and menus with muted kbd styling.
**VS Code:** keyboard shortcuts in the command palette and keybinding settings.
**Apple HIG:** uses SF Symbols for key caps (⌘⇧K) in menu items natively.
**shadcn:** no dedicated `<Kbd>` component but the styling pattern is common in menu items.
**Radix:** no built-in Kbd; it's a styling-only component.
**Chakra:** `<Kbd>` component with styled key-cap appearance.

### 9.1 HTML (semantic)

```html
<!-- Single key -->
<kbd>K</kbd>

<!-- Combination (nested kbd) -->
<kbd><kbd>Cmd</kbd>+<kbd>K</kbd></kbd>

<!-- In a menu item -->
<div class="menu-item">
  <span>Open command palette</span>
  <kbd class="kbd"><kbd class="kbd">⌘</kbd><kbd class="kbd">K</kbd></kbd>
</div>

<!-- Platform-aware -->
<kbd class="kbd kbd--combo">
  <kbd class="kbd">
    <span class="kbd--mac">⌘</span>
    <span class="kbd--win">Ctrl</span>
  </kbd>
  +
  <kbd class="kbd">K</kbd>
</kbd>

<!-- Sequence (keys pressed one after another, not together) -->
<span class="kbd-sequence">
  <kbd class="kbd">g</kbd>
  <span class="kbd-then">then</span>
  <kbd class="kbd">i</kbd>
</span>
```

The nested `<kbd>` pattern: `<kbd><kbd>Cmd</kbd>+<kbd>K</kbd></kbd>` is the semantically correct way to mark up a key combination. The outer `<kbd>` represents the combined input; inner `<kbd>` elements represent individual keys.

### 9.4 React + TypeScript

```typescript
import { ReactNode } from 'react';

interface KbdProps {
  children: ReactNode;
  size?: 'sm' | 'md' | 'lg';
  variant?: 'default' | 'muted' | 'light';
}

export function Kbd({ children, size = 'md', variant = 'default' }: KbdProps) {
  return <kbd className={`kbd kbd--${size} kbd--${variant}`}>{children}</kbd>;
}

// Combination helper
export function KbdCombo({ keys }: { keys: string[] }) {
  return (
    <kbd className="kbd kbd--combo">
      {keys.map((key, i) => (
        <span key={i}>
          {i > 0 && <span className="kbd-separator">+</span>}
          <Kbd size="sm">{key}</Kbd>
        </span>
      ))}
    </kbd>
  );
}

// Platform-aware modifier
export function KbdMod({ children }: { children: ReactNode }) {
  const isMac = typeof navigator !== 'undefined' && navigator.platform.includes('Mac');
  return <Kbd>{isMac ? '⌘' : 'Ctrl'}</Kbd>;
}

// Usage in a menu item:
<div className="menu-item">
  <span>Command palette</span>
  <KbdCombo keys={[isMac ? '⌘' : 'Ctrl', 'K']} />
</div>
```

## 10\. Accessibility
**`<kbd>`** **is natively semantic.** Screen readers recognize it and read the text content. No special ARIA needed for the basic case.

**Nested** **`<kbd>`** **for combinations:** `<kbd><kbd>Cmd</kbd>+<kbd>K</kbd></kbd>` reads naturally as "Cmd plus K."

**Symbol accessibility:** if using symbols (⌘, ⇧), some screen readers may not announce them correctly. Options:
*   Use `aria-label` on the outer `<kbd>`: `<kbd aria-label="Command plus K">⌘K</kbd>`
*   Use visually-hidden text alongside: `<kbd><span class="sr-only">Command</span>⌘</kbd>`
*   Prefer text labels ("Cmd") in accessible contexts; symbols in dense menus where sighted-user scanning speed matters.

**In menus:** the Kbd is supplemental info to the menu item label. AT reads the menu item label first ("Open command palette"), then may read the Kbd. It shouldn't interfere with the primary label. Using `aria-keyshortcuts` on the menu item is an alternative that separates the shortcut semantically.

**`aria-keyshortcuts`** **attribute (on the element the shortcut activates):**

```html
<button aria-keyshortcuts="Control+k">Open command palette</button>
```

This is the proper way to associate a shortcut with its target element for AT. The visual Kbd is the user-facing representation.

## 11\. Innovative / Emerging Ideas
*   **Dynamic Kbd based on user's actual bindings:** if the app supports custom keybindings, the Kbd display updates to show the user's configured shortcut.
*   **Kbd with recording:** in a keybinding settings UI, an input that captures the next keystroke and displays it as a Kbd.
*   **Animated key press:** subtle depression animation when the actual shortcut is pressed (teaching mode).
*   **Global shortcut palette:** a floating reference card showing all available shortcuts, each rendered as Kbd elements.
*   **Platform auto-detection at build time:** SSR detects the User-Agent and serves the correct platform symbols, avoiding a client-side flash of the wrong symbols.
*   **Shortcut registration system:** each component registers its shortcuts; the Kbd pulls from a central registry so displayed shortcuts stay in sync with actual keybindings.
* * *

## 12\. Conversion / UX Killers
*   **Wrong platform modifier:** showing ⌘ on Windows. Confuses users who don't have that key.
*   **Symbols without text fallback:** ⌘⇧K is elegant but unreadable for users unfamiliar with Mac symbols.
*   **Kbd that looks clickable:** styled too much like a button. Users try to click it expecting action.
*   **Inconsistent styling:** some shortcuts shown as plain text, others as styled keys. Pick one and commit.
*   **Too prominent in menus:** the Kbd styling competes with the action label for visual attention. Keep it muted.
* * *

## 13\. Advanced Patterns
### Platform-aware rendering hook

```typescript
function usePlatform() {
  const [platform, setPlatform] = useState<'mac' | 'win' | 'linux'>('mac');
  useEffect(() => {
    const ua = navigator.userAgent.toLowerCase();
    if (ua.includes('mac')) setPlatform('mac');
    else if (ua.includes('win')) setPlatform('win');
    else setPlatform('linux');
  }, []);
  return platform;
}

function PlatformKbd({ mac, win }: { mac: string; win: string }) {
  const platform = usePlatform();
  return <Kbd>{platform === 'mac' ? mac : win}</Kbd>;
}

// Usage:
<PlatformKbd mac="⌘K" win="Ctrl+K" />
```

## 16\. Senior-Level Checklist
- [ ] Semantic `<kbd>` element used (not `<span>` or `<div>`)
- [ ] Combinations use nested `<kbd>`: `<kbd><kbd>Cmd</kbd>+<kbd>K</kbd></kbd>`
- [ ] Platform-aware: Cmd on macOS, Ctrl on Windows/Linux
- [ ] Symbols have text alternatives for AT (sr-only or aria-label)
- [ ] Consistent styling across the app (one Kbd style, not mixed)
- [ ] Muted in menus (doesn't compete with action labels)
- [ ] Doesn't look clickable (clearly a label, not a button)
- [ ] Monospace or system font for consistent key sizing
- [ ] Border-bottom-width > border-top for depth illusion
- [ ] Works in both light and dark themes
- [ ] `user-select: none` (selecting a Kbd text is rarely useful)

## 17\. Visual Styles
**Flat:** solid background, 1px border, slight bottom-border for depth. The GitHub style.
**Material:** slightly elevated with subtle shadow. Rounded corners per M3.
**Glassmorphism:** translucent key face with blur behind. Subtle.
**Liquid Glass (2026):** refractive key cap with specular rim. Mimics a real glass keycap. The macOS Sequoia keyboard hint look.
**Neumorphism:** raised key from soft surface. The most natural fit for Kbd since physical keys ARE neumorphic in real life.
**Skeuomorphism:** literally looks like a physical keyboard key. Bevel, inner shadow, gradient face. The most "realistic" style.
**Neo-Brutalism:** thick border, hard offset shadow, bold text. Oversized and unapologetic.
**Claymorphism:** puffy rounded key. Soft inner glow. Playful.
**Aurora/Gradient:** key face has a subtle gradient fill.
**Minimal/Swiss:** just a border, no fill, no shadow. Maximum restraint. The Vercel/Linear style.
**UJG Brand:** Eminence border, Night fill, Platinum text. Goldenrod bottom-shadow for depth.
