# Link

# The Link: A Senior Engineer's Complete Breakdown
The most-used navigation primitive on the web, and the single element people misuse most. Here's everything from first principles to production code.

**Try it live:** the companion playground will let you tune every link variant, state, and destination type — internal, external, download, `mailto:`/`tel:`, and button-styled — and watch it output live code across HTML, CSS, React+TS, Next.js, React Router, Vue, Svelte, and more. It's built in a later pass, so treat the URLs below as the map, not the territory yet.

**Audit a link:** the companion audit will paste-in any anchor markup and run live checks — is it a real `<a href>`? Does the accessible name make sense out of context? Does `target="_blank"` carry `rel="noopener noreferrer"`? Does it rely on color alone? — then export a client-ready report.

This doc is a sibling to the [Button reference](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200231) and the [Cards reference](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200471). If you read one thing across both Link and Button, read this: **a link navigates to a resource; a button performs an action.** That one distinction is the spine of everything below.
* * *

## 1\. What a Link Actually Is
A link is a control that **navigates** — it takes the user to a resource identified by a URL. That resource is usually another page, but it can be a spot on the current page (`#section`), a file to download, an email client (`mailto:`), or a phone dialer (`tel:`). The element is the HTML anchor: `<a href="...">`.

The word "link" hides a distinction people collapse constantly, and it's the mirror image of the one in the [Button doc](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200231):

*   **Link (navigation):** goes _somewhere_. Changes the URL, adds a browser-history entry, is bookmarkable, opens in a new tab on middle-click. Semantically an `<a href>`.
*   **Button (action):** does something _now_ on the current page. Submit, open a modal, add to cart, toggle a setting. Semantically a `<button>`.

Here is the rule, stated once and load-bearing for the whole doc: **if it goes to a URL, it's a link; if it performs an action, it's a button. Never fake either with a** **`<div onclick>`****\*\*\*\*\*\*\*\*.**

**The two failure modes, both common, both wrong:**

*   **A "link" that is really a** **`<div>`** **or** **`<span>`** **with a click handler.** It has no `href`, so it isn't in the tab order, doesn't respond to Enter, isn't announced as a link, can't be opened in a new tab, and can't be right-click-copied. It _looks_ clickable and is broken for everyone not using a mouse. This is the #1 accessibility mistake on the web.
*   **An** **`<a>`** **with no** **`href`** **(or** **`href="#"`** **/** **`href="javascript:void(0)"`****\*\*\*\*\*\*\*\*) used to fire an action.** An anchor without a valid `href` is **not a link** — the browser doesn't expose it as one, and it drops out of keyboard navigation. If it performs an action, it should have been a `<button>`.

Corollary that trips up even mid-level engineers: **an** **`<a>`** **without** **`href`** **is not a link.** The `href` is what _makes_ it a link. Strip it and you have inert markup with anchor styling.
* * *

## 2\. Why It Matters
Links are how the web coheres. Every journey — search result to landing page, nav to product, footer to policy — is a link being followed. That gives them outsized weight across three axes:

*   **SEO and discoverability live here.** Crawlers follow `<a href>` links to find and rank pages. A "link" built from a `<div onclick>` router push is invisible to a crawler — the destination effectively doesn't exist to Google. Real anchors with real `href`s are the difference between a page that ranks and one that's a ghost.
*   **It's the accessibility frontier, again.** Screen-reader users pull up a list of every link on a page and navigate by it. If your links say "click here," "read more," "learn more" — stripped of surrounding context — that list is a wall of identical, meaningless entries. Meaningful link text isn't polish; it's whether the page is usable at all for those users.
*   **It sets the trust tone.** A link that silently opens a new tab, kicks off a 40 MB download, or hands the user to a sketchy external domain with no warning feels like a trap. Telling the user _where a link goes and what it will do_ before they click is a core trust signal — and, for `target="_blank"`, a genuine security requirement.
* * *

## 3\. Anatomy of a Link
Every well-built link is composed of predictable parts:

*   **Anchor element (****`<a>`****):** the container. Inline by default; can be styled to any shape including a button.
*   **`href`****\*\*\*\*\*\*\*\*:** the destination URL. The single required attribute — no `href`, no link.
*   **Accessible name (the link text):** what a screen reader announces and what the user reads. Must be meaningful _out of context_.
*   **Affordance:** the visual signal that this text is a link — classically an underline plus a distinct color. This is what tells sighted users "this is clickable."
*   **State affordances:** `:link` (unvisited), `:visited`, `:hover`, `:focus-visible`, `:active`. Each communicates something real.
*   **Destination hints (optional but recommended):** an external-link icon, a "(opens in new tab)" note, a file-type/size badge for downloads. These set expectations before the click.
*   **`rel`** **/** **`target`** **attributes:** relationship and window-target metadata. Load-bearing for security (`rel="noopener noreferrer"`) and SEO (`rel="nofollow"`, `rel="sponsored"`).
* * *

## 4\. Scale & Density
Links don't have a size scale the way buttons do — they inherit the text they live in. What you _do_ control is target size, spacing, and the density of links in a block of text.

| Context | Guidance | Why |
| ---| ---| --- |
| Inline text link | Inherit font size; underline on | Sits in a sentence; underline is the only reliable "I'm a link" signal |
| Standalone nav link | ≥44px tap target via padding | Touch reach; the visible text may be small |
| List of links (nav, footer) | ≥44px row height, generous line spacing | Prevents fat-finger mis-taps between adjacent links |
| Button-styled link (CTA) | Follow button sizing (40–56px height) | It looks like a button, so it must have a button's hit area |
| Dense link clusters (tag clouds, breadcrumbs) | Min gap so targets don't merge | Adjacent links under 44px + no gap = guaranteed mis-taps |

Rules that matter:

*   **A visually small inline link still needs a real target.** WCAG 2.5.8 sets a 24px minimum for targets; the practical mobile floor is 44px. Expand with padding, not by making the text huge.
*   **Never crowd links.** Two links touching with no space between them is a mis-tap generator, and screen-magnifier users can't tell where one ends.
*   **Line-height matters for wrapped links.** A long link that wraps to two lines should keep its underline legible on both.
* * *

## 5\. States (all five, and why removing one hurts)
A link has five interactive states, and — unlike a button — one of them is _persistent across page loads_: `:visited`. Dropping states is the tell of a rushed build.

1. **Default /** **`:link`** — an unvisited link. Distinct color **and** (for inline links) an underline. Never color alone.
2. **`:visited`** — the user has been here before. Historically a slightly muted/different color. This is real usability: it tells people what they've already explored, especially in search results, docs, and long link lists. Browsers restrict what you can style on `:visited` (privacy — see §10) but color is allowed.
3. **`:hover`** — pointer is over it. Underline appears/thickens, color shifts. Doesn't exist on touch, so never the _only_ affordance.
4. **`:focus-visible`** — reachable by keyboard. **Must** have a visible ring. Use `:focus-visible` so mouse clicks don't flash it but Tab does. This is non-negotiable; a link nobody can see focus on is unusable by keyboard.
5. **`:active`** — the instant of click/tap. Brief color or emphasis shift; sells the press.

**The cardinal sin:** **`a { text-decoration: none }`** **on body links.** Stripping the underline from inline links and relying on color alone fails WCAG 1.4.1 (Use of Color) — colorblind users and low-contrast environments can't tell link from text. Underlines on inline links are not decoration; they're the affordance. Remove them in nav bars and card links (where position/layout signals clickability), keep them in running prose. If you must drop the underline elsewhere, guarantee a **3:1 contrast between link color and surrounding text** _and_ add an underline on hover/focus.
* * *

## 6\. Types & Variants (by destination and by treatment)
Links vary along two axes: _where they go_ (which changes required attributes) and _how they look_ (which is skin only).

**By destination — this changes the markup:**

*   **Internal link:** same site, relative or absolute path. Standard `<a href="/pricing">`.
*   **Anchor / in-page link:** jumps to an `id` on the current page. `<a href="#section-2">`. Also powers "skip to content."
*   **External link:** off your domain. Signal it (icon + "(opens external site)"), and if it opens a new tab, secure it with `rel="noopener noreferrer"`. Often add `rel="nofollow"`/`rel="ugc"`/`rel="sponsored"` for SEO on untrusted or paid links.
*   **Download link:** points at a file. Add the `download` attribute and warn the user with file type + size ("PDF, 2.4 MB"). Downloads are unexpected — say so before the click.
*   **`mailto:`** **link:** opens the user's email client. `<a href="mailto:hello@urbanjunglegoddess.com">`. Can prefill subject/body via query params.
*   **`tel:`** **/** **`sms:`** **link:** opens the dialer / messaging. `<a href="tel:+15035551234">`. Huge on mobile; make the whole phone number a link.

**By treatment — this is skin only (semantics never change):**

*   **Inline text link:** underlined, in-flow. The default and most common.
*   **Standalone / nav link:** in a nav bar or menu, underline often dropped, layout signals clickability.
*   **Button-styled link:** looks exactly like a button — fill, radius, padding — but **navigates**, so it's still an `<a href>`. This is the most misused variant; see §7.
*   **Card / block link:** an entire card is one link. Wrap the card in `<a>` (or use a "stretched link" overlay), keeping one accessible name.
*   **Icon link:** icon-only (e.g. a social icon). _Must_ have an accessible name via `aria-label` or visually-hidden text.
* * *

## 7\. The Link-vs-Button Trap (the spine of this doc)
This is where careers-worth of bugs live. Two symmetrical mistakes:

**Mistake 1 — a button that navigates.** Someone needs a "See pricing" call-to-action styled as a big filled button, so they write `<button onclick="location.href='/pricing'">`. Now: middle-click doesn't open a new tab, Cmd/Ctrl-click doesn't either, right-click has no "Open in new tab / Copy link," the crawler can't follow it, and it breaks entirely with JS disabled. **It navigates, so it must be an** **`<a href="/pricing">`** — styled to _look_ like a button.

**Mistake 2 — a link that acts.** Someone needs an "Add to cart" or "Delete" control and reaches for `<a href="#" onclick="addToCart()">`. Now the `href="#"` scrolls to top, the URL is meaningless, and screen readers announce a "link" that goes nowhere. **It performs an action, so it must be a** **`<button>`****\*\*\*\*\*\*\*\*.**

The look is fully decoupled from the semantics:

*   A **link can look like a button** — fill, radius, glow — and still be an `<a>` because it _navigates_. (In shadcn, this is exactly what `asChild` + `Slot` exists for: button styling merged onto a real `<a>`/`<Link>`.)
*   A **button can look like a link** — underlined text, no chrome — and still be a `<button>` because it _acts_. (`.btn-link` in Bootstrap; a text-button variant everywhere else.)

**The test:** ask "after I activate this, has the URL changed / could I have bookmarked the result?" If yes → link. If it did something to the current state → button. Style second, semantics first.
* * *

## 8\. Links Across Design Systems
Same anchor, different house rules.

*   **Material Design (Google):** Links use the primary/tint color, underline optional in dense UI but recommended in body text. Distinguishes "text button" (action) from "link" (navigation) explicitly. Standalone links pair with a trailing external/open-in-new icon.
*   **Apple HIG (iOS/macOS):** Links are tinted text, typically no underline, relying on the system tint color for affordance — acceptable because Apple guarantees the tint contrasts. In web contexts, underline body links anyway.
*   **Fluent (Microsoft):** `Link` is a distinct component from `Button`, with explicit inline vs. standalone modes and built-in external-link iconography.
*   **Ant Design / enterprise:** `Typography.Link` and a `<a>`\-based `Link`, with `disabled` and `nofollow`\-aware props; dense admin UIs lean on color + hover underline.
*   **Tailwind / utility-first:** No prescribed look; you compose `text-*`, `underline`, `hover:`, `focus-visible:` utilities. Usually wrapped in a `Link` component to enforce consistency and the `rel` rules.
*   **shadcn/Radix (2024+ web standard):** No standalone Link primitive — you style a native `<a>` (or framework `Link`) and use `buttonVariants({ variant: "link" })` when you want link-styled text or a button-styled link. Behavior stays native anchor.
*   **Bootstrap:** `.link-primary`, `.link-*` utilities, `.stretched-link` for card-wide links, `.btn.btn-link` for a button that looks like a link.

**Rule that never changes:** the skin is the design system's; the semantics are the platform's. A link is an `<a href>` in every one of them.

## 9\. The Code
### 9.1 HTML (the foundation everyone should master first)

```plain
<!-- Internal navigation: the default link -->
<a href="/pricing">See pricing</a>

<!-- In-page anchor -->
<a href="#faq">Jump to FAQ</a>

<!-- External link opening a new tab: SECURITY-REQUIRED rel -->
<a href="https://partner.example.com"
   target="_blank"
   rel="noopener noreferrer">
  Partner portal
  <span class="visually-hidden"> (opens in a new tab)</span>
</a>

<!-- Download link: warn with type + size -->
<a href="/files/ujg-brand-guide.pdf" download>
  Download the brand guide
  <span class="visually-hidden"> (PDF, 2.4 MB)</span>
</a>

<!-- Email + phone -->
<a href="mailto:hello@urbanjunglegoddess.com?subject=Project%20inquiry">
  Email us
</a>
<a href="tel:+15035551234">(503) 555-1234</a>

<!-- Icon-only link: accessible name is mandatory -->
<a href="https://instagram.com/urbanjunglegoddess" aria-label="UJG on Instagram">
  <svg aria-hidden="true">…</svg>
</a>

<!-- Meaningful text, NOT "click here" -->
<a href="/reports/q3">Read the Q3 revenue report</a>
```

Key HTML rules:

*   **No** **`href`****\*\*\*\*\*\*\*\*, no link.** `<a>` without `href` is not focusable and not announced as a link. If it fires an action, it should be a `<button>`.
*   **`target="_blank"`** **demands** **`rel="noopener noreferrer"`****\*\*\*\*\*\*\*\*.** Without `noopener`, the newly-opened page can reach back through `window.opener` and redirect your tab to a phishing clone (tabnabbing). Modern browsers imply `noopener` for `target="_blank"`, but set it explicitly — older browsers, embedded webviews, and email clients don't. `noreferrer` additionally strips the `Referer` header.
*   **Warn about new tabs and downloads.** A visually-hidden "(opens in a new tab)" or "(PDF, 2.4 MB)" tells screen-reader users what's about to happen. Sighted users get an icon.
*   **Decorative icons get** **`aria-hidden="true"`****\*\*\*\*\*\*\*\*;** the link needs its own text or `aria-label`.

### 9.2 CSS (states done right)

```css
a {
  color: #5F2C82;                 /* Eminence — distinct from body text */
  text-decoration: underline;      /* the affordance; keep it on inline links */
  text-underline-offset: 0.15em;
  border-radius: 2px;
}
a:visited { color: #7E3209; }      /* Sienna — "you've been here" */
a:hover   { color: #4c2368; text-decoration-thickness: 2px; }
a:active  { color: #E86100; }      /* Spanish Orange — the press */

/* Keyboard focus only, not mouse clicks */
a:focus-visible {
  outline: 2px solid #DCA424;      /* Goldenrod ring */
  outline-offset: 2px;
}

/* If you MUST drop the underline (nav/cards), buy it back on interaction
   AND guarantee 3:1 contrast vs surrounding text via color. */
.nav a { text-decoration: none; }
.nav a:hover,
.nav a:focus-visible { text-decoration: underline; }

/* External-link affordance via generated content */
a[target="_blank"]::after {
  content: " ↗";
  font-size: 0.8em;
}
```

The `:visited` restriction is real: browsers only let you change a short allowlist of properties on `:visited` (color, background-color, border-color, outline-color) and always render them as if fully opaque — a privacy defense so a page can't sniff your history via `getComputedStyle`. Color is the reliable `:visited` lever.

### 9.3 React + TypeScript (a proper reusable component)
A senior Link component that **detects external/download destinations, applies the security** **`rel`** **automatically, and warns about new tabs** — the things juniors forget every time.

```typescript
import { forwardRef, AnchorHTMLAttributes } from "react";

interface LinkProps extends AnchorHTMLAttributes<HTMLAnchorElement> {
  href: string;                    // required: no href, no link
  newTab?: boolean;                // explicit override
  download?: boolean | string;
}

/** A link is external if it has a protocol/host that isn't ours. */
function isExternal(href: string): boolean {
  return /^https?:\/\//i.test(href) &&
    !href.startsWith(window.location.origin);
}

export const Link = forwardRef<HTMLAnchorElement, LinkProps>(
  // Pull rel/target OUT of rest so a caller can't spread over and strip the
  // derived security attributes — that's how the tabnabbing guard leaks.
  ({ href, newTab, download, children, rel: relProp, target: targetProp, ...rest }, ref) => {
    const external = isExternal(href);
    // A caller can force a new tab via newTab OR by passing target="_blank".
    const opensNewTab = newTab ?? (targetProp === "_blank" || external);
    const isDownload = download != null && download !== false;

    // security: a new-tab link ALWAYS carries noopener noreferrer, MERGED with
    // (never overridden by) any SEO rel the caller passes (nofollow/ugc/sponsored).
    const relTokens = new Set(relProp ? relProp.split(/\s+/).filter(Boolean) : []);
    if (opensNewTab) { relTokens.add("noopener"); relTokens.add("noreferrer"); }
    const rel = relTokens.size ? [...relTokens].join(" ") : undefined;

    return (
      <a
        {...rest}
        ref={ref}
        href={href}
        // security: derived target/rel come AFTER {...rest} so nothing can strip them
        target={opensNewTab ? "_blank" : targetProp}
        rel={rel}
        download={download}
      >
        {children}
        {external && <span aria-hidden="true"> ↗</span>}
        {opensNewTab && (
          <span className="visually-hidden"> (opens in a new tab)</span>
        )}
        {isDownload && (
          <span className="visually-hidden"> (downloads a file)</span>
        )}
      </a>
    );
  }
);
Link.displayName = "Link";
```

Why this is the senior version:

*   **`href`** **is a required prop.** The type system won't let you build a link without a destination — the exact bug that produces fake `<div>` links.
*   **`rel`** **is derived, never forgotten.** Any link that opens a new tab gets `noopener noreferrer` automatically — and it's _merged_ with (not clobbered by) any SEO `rel` the caller passes, because `rel`/`target` are pulled out of `...rest` instead of being spread over. You can't ship the tabnabbing vulnerability, even when an author adds `rel="nofollow"`/`"sponsored"`/`"ugc"`.
*   **External + download are detected,** and the user is warned in both the visual layer (icon) and the a11y layer (visually-hidden text).
*   **Extends native** **`AnchorHTMLAttributes`** so `onClick`, `aria-*`, `data-*`, `className` all pass through for free.

### 9.4 Next.js (App Router: the framework Link)
Next's `<Link>` gives client-side navigation (no full reload) **but still renders a real** **`<a href>`** — so middle-click, Cmd-click, "copy link," SEO crawling, and no-JS all keep working. That last point is why you never hand-roll SPA navigation with `router.push` on a `<div>`.

```typescript
// app/components/Nav.tsx
import Link from "next/link";

export function Nav() {
  return (
    <nav>
      {/* Renders <a href="/pricing"> — prefetched, client-nav, crawlable */}
      <Link href="/pricing">Pricing</Link>

      {/* External still uses a plain <a> with the security rel */}
      <a href="https://status.example.com"
         target="_blank" rel="noopener noreferrer">
        Status ↗
      </a>
    </nav>
  );
}
```

The rule for every SPA framework: **the framework** **`Link`** **must emit an** **`<a href>`****\*\*\*\*\*\*\*\*.** Client-side routing is a progressive enhancement layered _on top of_ a working anchor — intercept the click, but the anchor is the ground truth.

### 9.5 React Router (client-side nav, same principle)

```typescript
import { Link, NavLink } from "react-router-dom";

// <Link> renders <a href="/dashboard"> and intercepts the click for SPA nav
<Link to="/dashboard">Dashboard</Link>

// <NavLink> adds active-state styling based on the current route
<NavLink
  to="/reports"
  className={({ isActive }) => isActive ? "link link--active" : "link"}
>
  Reports
</NavLink>
```

Both render honest anchors. `NavLink` is the tool for nav menus where the current page's link should be marked — pair the active class with `aria-current="page"` (see §10) so screen readers know which item is current, not just sighted users.

### 9.6 Vanilla JS (progressive enhancement, done right)
The wrong instinct is to attach a `click` handler that calls `preventDefault()` and does `location.href` — that throws away middle-click and modifier-click. The right pattern intercepts only plain left-clicks and lets the browser handle everything else:

```javascript
document.addEventListener("click", (e) => {
  const link = e.target.closest("a[data-spa]");
  if (!link) return;

  // Respect the user's intent to open a new tab / window / download
  if (
    e.defaultPrevented ||
    e.button !== 0 ||                       // not a left-click
    e.metaKey || e.ctrlKey ||               // Cmd/Ctrl-click = new tab
    e.shiftKey || e.altKey ||               // Shift/Alt = new window/download
    link.target === "_blank"
  ) return;                                  // let the browser do its thing

  e.preventDefault();
  history.pushState(null, "", link.href);    // client-side nav
  renderRoute(link.href);
});
```

The whole point: the `<a href>` still works without JavaScript, and every native gesture (new tab, new window, copy link) survives. You _enhance_ the anchor; you don't replace it.

### 9.8 shadcn/ui (button-styled link the correct way)
shadcn has no `Link` primitive; it gives you `buttonVariants` so a real anchor can wear button styling. This is the sanctioned answer to the §7 trap.

```typescript
import Link from "next/link";
import { buttonVariants } from "@/components/ui/button";
import { cn } from "@/lib/utils";

// A LINK that LOOKS like a primary button — still an <a href>, so it
// navigates correctly: middle-click, SEO, no-JS all work.
<Link href="/signup" className={cn(buttonVariants({ variant: "default", size: "lg" }))}>
  Start free trial
</Link>

// A BUTTON that LOOKS like a link — still a <button>, because it acts.
<Button variant="link" onClick={openDialog}>Learn more</Button>
```

`variant: "link"` renders `text-primary underline-offset-4 hover:underline`. The clever part is the decoupling: the styling is a class, the semantics are the element you put it on. Choose the element by _what it does_, then apply whichever variant looks right.

### 9.9 Other Frameworks (Vue, Svelte, Angular)
Same anchor, different syntax — and each has a framework Link that still emits `<a href>`.

**Vue 3 + Vue Router:**

```plain
<script setup lang="ts">
defineProps<{ href: string; external?: boolean }>();
</script>

<template>
  <!-- Internal: RouterLink renders <a href> with client-side nav -->
  <RouterLink v-if="!external" :to="href"><slot /></RouterLink>
  <!-- External: plain anchor with the security rel -->
  <a v-else :href="href" target="_blank" rel="noopener noreferrer">
    <slot /> <span aria-hidden="true">↗</span>
  </a>
</template>
```

**Svelte (SvelteKit):**

```plain
<!-- SvelteKit needs NO special component: a plain <a href> gets
     client-side routing for free when it points inside the app. -->
<a href="/dashboard">Dashboard</a>
<a href="https://example.com" target="_blank" rel="noopener noreferrer">
  External ↗
</a>
```

**Angular (RouterLink):**

```typescript
// Internal navigation — routerLink renders an <a href> and intercepts clicks
// <a routerLink="/reports" routerLinkActive="active"
//    ariaCurrentWhenActive="page">Reports</a>
//
// External — a plain href with rel
// <a href="https://example.com" target="_blank" rel="noopener noreferrer">

// </a>
```

SvelteKit is the tell: the "framework Link" is literally just `<a href>` because that's what a link _is_. Every other framework's Link component is machinery to preserve that truth while adding client-side nav.

### 9.10 Web Component (framework-agnostic smart link)
The href comes from an attribute an author (or, in a CMS, untrusted input) sets — so this is exactly the §15 case: **allowlist the scheme and never string-interpolate the href into** **`innerHTML`****\*\*\*\*\*\*\*\*.** Build the anchor with the DOM API so a value like `javascript:…` or a `">`\-breakout can't execute in your origin.

```typescript
class SmartLink extends HTMLElement {
  // §15: allowlist known-safe schemes; reject everything else (no blocklist).
  static SAFE_SCHEMES = ["http:", "https:", "mailto:", "tel:"];

  static sanitizeHref(raw: string): string {
    const value = raw.trim();
    // Relative / same-page URLs carry no scheme and are safe to keep as-is.
    if (value === "" || /^(\/|#|\?|\.\/|\.\.\/)/.test(value)) return value || "#";
    try {
      const url = new URL(value, location.origin);
      return SmartLink.SAFE_SCHEMES.includes(url.protocol) ? value : "#";
    } catch {
      return "#";
    }
  }

  connectedCallback() {
    const href = SmartLink.sanitizeHref(this.getAttribute("href") ?? "");
    const external = /^https?:\/\//i.test(href) &&
      !href.startsWith(location.origin);
    const newTab = this.hasAttribute("new-tab") || external;

    const root = this.attachShadow({ mode: "open" });

    // DOM construction, not innerHTML: the href never reaches an HTML string,
    // so it can't break out of the attribute or inject markup (XSS).
    const a = document.createElement("a");
    a.setAttribute("href", href);              // already scheme-allowlisted
    if (newTab) {
      a.setAttribute("target", "_blank");
      a.setAttribute("rel", "noopener noreferrer");   // reverse-tabnabbing guard
    }
    a.appendChild(document.createElement("slot"));
    if (external) a.append(" ↗");
    if (newTab) {
      const sr = document.createElement("span");
      sr.style.cssText =
        "position:absolute;width:1px;height:1px;overflow:hidden;clip:rect(0 0 0 0)";
      sr.textContent = " (opens in a new tab)";
      a.appendChild(sr);
    }
    root.appendChild(a);
  }
}
customElements.define("smart-link", SmartLink);
// <smart-link href="https://example.com">Docs</smart-link>
```

### 9.11 Native Mobile (SwiftUI, Jetpack Compose, Flutter)
Off the web, "link" splits into two ideas: navigation _within_ the app (a router destination) and _opening a URL_ (hands off to the browser/dialer/mail). The navigation kind is closer to routing; the open-URL kind is the direct analog of a web link.

**SwiftUI (iOS):**

```plain
// Opens a URL in Safari / the relevant app
Link("Partner portal", destination: URL(string: "https://example.com")!)

// Email / phone via the same URL scheme mechanism as mailto:/tel:
Link("Email us", destination: URL(string: "mailto:hello@ujg.com")!)

// In-app navigation is NavigationLink, the routing analog — not a "link"
// NavigationLink("Pricing", value: Route.pricing)
```

**Jetpack Compose (Android / Kotlin):**

```kotlin
val ctx = LocalContext.current
Text(
  "Partner portal",
  modifier = Modifier.clickable {
    ctx.startActivity(Intent(Intent.ACTION_VIEW, Uri.parse("https://example.com")))
  }
)
// Compose 1.7+ also has LinkAnnotation for inline links inside AnnotatedString.
```

**Flutter (Dart):**

```plain
// url_launcher for external URLs / mailto / tel
InkWell(
  onTap: () => launchUrl(Uri.parse('https://example.com')),
  child: const Text('Partner portal'),
)
// Named routes (Navigator.pushNamed) cover in-app navigation.
```

The through-line: on the web one element (`<a href>`) covers both in-app navigation and opening a resource, because URLs cover both. Native platforms split them — routing vs. `openURL` — so pick the API by _which kind of navigation_ you mean.

### 9.12 Testing the Link
You test a link by its **role, its accessible name, its destination, and its security attributes** — never its classes or color.

**Unit / component (Vitest + React Testing Library + jest-axe):**

```typescript
import { render, screen } from "@testing-library/react";
import { axe } from "jest-axe";
import { describe, it, expect } from "vitest";
import { Link } from "./Link";

describe("Link", () => {
  it("is exposed as a link with an accessible name", () => {
    render(<Link href="/pricing">See pricing</Link>);
    const link = screen.getByRole("link", { name: /see pricing/i });
    expect(link).toHaveAttribute("href", "/pricing");
  });

  it("adds security rel + new-tab warning for external links", () => {
    render(<Link href="https://example.com">Docs</Link>);
    const link = screen.getByRole("link", { name: /docs/i });
    expect(link).toHaveAttribute("target", "_blank");
    expect(link).toHaveAttribute("rel", "noopener noreferrer");
    // the warning is announced, not just shown
    expect(screen.getByText(/opens in a new tab/i)).toBeInTheDocument();
  });

  it("keeps noopener noreferrer even when the caller passes their own rel", () => {
    // an author adds a paid-link rel; the security rel must MERGE, not vanish
    render(<Link href="https://ad.example.com" rel="nofollow sponsored">Sponsor</Link>);
    const relValue = screen.getByRole("link", { name: /sponsor/i }).getAttribute("rel") ?? "";
    const tokens = relValue.split(/\s+/);
    expect(tokens).toEqual(expect.arrayContaining(["noopener", "noreferrer", "nofollow", "sponsored"]));
  });

  it("rejects meaningless link text (author-side lint / review gate)", () => {
    render(<Link href="/x">click here</Link>);
    // A real audit flags this — 'click here' is not meaningful out of context.
    expect(screen.getByRole("link").textContent).not.toMatch(/^click here$/i);
  });

  it("has no automatically-detectable a11y violations", async () => {
    const { container } = render(<Link href="/pricing">See pricing</Link>);
    expect(await axe(container)).toHaveNoViolations();
  });
});
```

**End-to-end (Playwright):**

```typescript
import { test, expect } from "@playwright/test";

test("nav link navigates and marks current page", async ({ page }) => {
  await page.goto("/");
  await page.getByRole("link", { name: "Pricing" }).click();
  await expect(page).toHaveURL(/\/pricing/);
  await expect(page.getByRole("link", { name: "Pricing" }))
    .toHaveAttribute("aria-current", "page");
});
```

What to actually assert (and what to skip):

*   **Do test:** it's found `byRole("link")` (proves it's a real anchor, not a `<div>`), the accessible name is meaningful, the `href` is correct, external links carry `rel="noopener noreferrer"`, and the current nav item has `aria-current="page"`.
*   **Don't test:** exact colors, underline style, class names. Those break tests without catching real bugs.
*   **Bonus:** run `axe` — it catches the `<div onclick>` fake-link, missing accessible name, and color-contrast failures automatically.

## 10\. Accessibility (non-negotiable)
Links are where screen-reader and keyboard users live. Get these right and most of navigation accessibility comes free.

*   **Use a real** **`<a href>`****\*\*\*\*\*\*\*\*.** It's focusable, Enter-activatable, announced as "link," and open-in-new-tab-able for free. A `<div onclick>` gives you _none_ of that and must be rebuilt.
*   **Keyboard:** Enter activates a link (Space does _not_ — that's the button difference; Space scrolls the page). Native anchors handle this; fake links don't.
*   **Meaningful accessible name.** Screen-reader users list every link out of context. "Click here," "read more," "learn more" alone are useless in that list. Fix it three ways:
    *   Rewrite the visible text: "Read the Q3 report" instead of "read more."
    *   Add visually-hidden context: `Read more<span class="visually-hidden"> about Q3 revenue</span>`.
    *   Or `aria-label="Read more about Q3 revenue"` (overrides the visible text for AT).
*   **Icon-only links need an accessible name** via `aria-label` or visually-hidden text.
*   **Don't rely on color alone** (WCAG 1.4.1). Inline links need an underline or another non-color signal; if you drop the underline, link-vs-text color must hit **3:1 contrast** and interaction must add a signal.
*   **Focus visible** (WCAG 2.4.7): never `outline: none` without a replacement. `:focus-visible` ring.
*   **`aria-current="page"`** on the link to the current page in a nav — announces "current page," not just a highlight color.
*   **Warn about context change:** `target="_blank"`, downloads, and `mailto:`/`tel:` all change context or leave the page. Add visually-hidden "(opens in a new tab)" / "(downloads a file)" so it isn't a surprise (WCAG 3.2.5).
*   **Skip link:** the first focusable element on the page should be a "Skip to main content" link that jumps past the nav — critical for keyboard and screen-reader users who'd otherwise Tab through the whole menu on every page.
*   **`:visited`** **is a privacy boundary,** not just a style: browsers deliberately limit it so pages can't detect your history. Style within the allowlist (color) and don't try to defeat it.
*   **Target size ≥24px (WCAG 2.5.8), 44px practical floor** on touch. Don't crowd adjacent links.

**The skip-link pattern:**

```plain
<a href="#main" class="skip-link">Skip to main content</a>
…
<main id="main" tabindex="-1">…</main>
```

```css
.skip-link {
  position: absolute;
  left: -9999px;
}
.skip-link:focus {          /* becomes visible only when Tabbed to */
  left: 1rem; top: 1rem;
  z-index: 1000;
  padding: .5rem 1rem;
  background: #DCA424; color: #0A0A0A;
}
```

## 11\. Innovative & Emerging Ideas
The anchor looks solved but keeps gaining power at the platform level:

*   **View Transitions API + cross-document transitions:** native, animated page-to-page morphs triggered by ordinary `<a>` navigation — SPA-smoothness with zero routing JavaScript. Opt in with `@view-transition { navigation: auto; }`.
*   **Speculation Rules API:** `<script type="speculationrules">` tells the browser to prefetch/prerender likely next pages, so following a link feels instant — the standards-based successor to framework prefetch.
*   **Link previews / hover cards:** rich popovers on hover/focus (Wikipedia-style), now buildable declaratively with the Popover API anchored to the link.
*   **`text-fragment`** **deep links (****`#:~:text=`****):** link straight to a highlighted phrase on a page, no author-added anchor needed.
*   **`prefers-reduced-data`****\*\*\*\*\*\*\*\*:** skip prefetch and heavy preview media for users on metered/limited connections.
*   **AI-native "smart links":** links whose destination is resolved or summarized by an agent on hover, with a streaming preview — bolt this onto a real `<a>`, never instead of one.

## 12\. Conversion & UX Killers (silent bleeders)
None throw an error. They just quietly cost you trust, SEO, and clicks.

*   **`<div onclick>`** **fake links.** Invisible to crawlers, broken for keyboard/AT, no new-tab/copy-link. The destination page effectively doesn't exist to Google. The most expensive "it looks fine" bug on the web.
*   **"Click here" / "read more" / "learn more" alone.** Screen-reader users get a list of identical, meaningless links; sighted users get no scent of what's on the other side. Every link should name its destination.
*   **Underlines stripped from body links.** Colorblind and low-contrast users can't tell link from text. Fails WCAG. Keep underlines in prose.
*   **`target="_blank"`** **without** **`rel="noopener noreferrer"`****\*\*\*\*\*\*\*\*.** Tabnabbing hole _and_ (for many users) a jarring surprise tab. If you open new tabs, secure them and warn.
*   **Silent downloads.** A link that fires a 40 MB PDF with no warning reads as an attack. Label type + size.
*   **Removed** **`:visited`** **styling.** In long link lists, search results, and docs, losing "you've already seen this" makes users re-read and re-click. Cheap to keep, costly to drop.
*   **Buttons that navigate / links that act.** Breaks middle-click, SEO, and keyboard expectations in both directions. See §7.
*   **No focus ring.** Keyboard users lose their place entirely. `outline: none` with no replacement is a silent lockout.
*   **Crowded link clusters on mobile.** Adjacent sub-44px links with no gap = mis-taps = users landing on the wrong page and bouncing.

**The through-line:** these fail quietly — no crash, just a lower conversion number and a worse crawl. Audit your links before you audit your ad spend.
* * *

## 13\. Advanced Patterns
*   **`rel`** **for SEO and trust:** `nofollow` (don't pass ranking signal), `sponsored` (paid), `ugc` (user-generated), `me` (identity verification, e.g. Mastodon/IndieAuth). Untrusted or paid outbound links should carry the right `rel` or you leak ranking equity and invite spam penalties.
*   **Stretched / card links (one accessible name):** make an entire card clickable without nesting interactive elements. Bootstrap's `.stretched-link` on a single anchor overlays the whole card; keep exactly _one_ link per card so the accessible name stays singular.

```css
.card { position: relative; }
.card a.stretched::after {
  content: ""; position: absolute; inset: 0;   /* the whole card is the target */
}
```

*   **Prefetch on intent:** prefetch a link's destination on `mouseenter`/`focus` (or via Speculation Rules) so the navigation feels instant — but gate it on `prefers-reduced-data`.
*   **TypeScript-enforced safe links:** a discriminated union can _require_ `rel="noopener noreferrer"` whenever `target="_blank"` is set, catching tabnabbing at compile time.

```typescript
type SafeLink =
  | { href: string; target?: never; rel?: string }
  | { href: string; target: "_blank"; rel: "noopener noreferrer" };
// <Link target="_blank"> won't compile without the security rel.
```

*   **Typed internal routes:** generate a union of valid app paths (`type Route = "/" | "/pricing" | ...`) and type `href` against it so a link to a dead internal route fails the build — the SPA analog of a broken-link check.
* * *

## 14\. Performance & Bundle Cost
*   **Links are nearly free** — they're anchors, not JS widgets. The cost shows up in _navigation_, not the element.
*   **Prefetch is a double-edged sword.** Framework `Link` components prefetch destinations (Next prefetches on viewport-enter by default). Great for speed, wasteful on data-limited devices and huge link lists. Cap it, or use `prefetch={false}` for low-value links, and honor `prefers-reduced-data`.
*   **Event delegation for big link lists.** If you enhance links with client-side routing, bind one delegated listener on the container (see §9.6), not one per link. A 500-link archive with 500 listeners is 500 closures; one delegated handler is one.
*   **Don't ship an icon library for one arrow.** The external-link "↗" is a text glyph or a single inline SVG — never `import * as Icons`.
*   **Cross-document View Transitions** are compositor-driven and cheap; prefer them to JS-animated page transitions.
* * *

## 15\. Security
A link is a navigation primitive, but it's also an attack surface the moment any part of its `href` is attacker-influenced — so treat every destination as untrusted input. The `target="_blank"` rule is a real security control, not etiquette: without `rel="noopener noreferrer"` the page you opened can reach back through `window.opener` and silently rewrite your tab to a phishing clone (reverse tabnabbing), while `noreferrer` also stops that destination from reading your source URL out of the `Referer` header. A user-supplied `href` is a live XSS vector — a value like `javascript:stealSession()` or a hostile `data:` URL executes in your own origin the instant it's clicked, so never render an arbitrary href: allowlist known-safe schemes (`http`, `https`, `mailto`, `tel`) and reject everything else rather than trying to blocklist the bad ones. Guard against open redirects in the same spirit: any link that bounces through your own domain with a `?url=` or `?next=` parameter must validate that destination against an allowlist, or your trusted domain becomes a laundering service for someone else's phishing. Links pointing at user-generated content should carry `rel="nofollow ugc"` so you neither hand ranking equity to spammers nor invite link-injection abuse. And download links to user-uploaded files inherit content-type and `Content-Disposition` concerns — serve them with a correct MIME type and `Content-Disposition: attachment`, ideally from an isolated origin, so a malicious upload can't render as active HTML inside your domain. The through-line: an anchor is only as trustworthy as the URL you put in it — validate the scheme, secure the new tab, and never let unchecked user input reach `href`.

## 16\. Senior-Level Checklist (ship-ready)
Before a link is "done":
- [ ] It's a real `<a href>` — never a `<div>`/`<span>` with a click handler.
- [ ] It navigates. If it performs an action, it's a `<button>` instead (§7).
- [ ] `href` is a valid destination — not `#`, not `javascript:void(0)`.
- [ ] Link text is meaningful out of context — no bare "click here"/"read more."
- [ ] Icon-only links have an accessible name (`aria-label` / visually-hidden).
- [ ] Inline links have an underline (or ≥3:1 color contrast vs text + an interaction signal).
- [ ] All states styled: `:visited`, `:hover`, `:focus-visible`, `:active`.
- [ ] `target="_blank"` carries `rel="noopener noreferrer"` and warns about the new tab.
- [ ] Downloads warn with file type + size; `mailto:`/`tel:` are labeled.
- [ ] External / paid / UGC links carry the right `rel` (`nofollow`/`sponsored`/`ugc`).
- [ ] Current nav item has `aria-current="page"`.
- [ ] A "Skip to main content" link is the first focusable element on the page.
- [ ] SPA `Link` components render a real `<a href>` (middle-click, SEO, no-JS survive).
- [ ] Target ≥44px on touch; adjacent links aren't crowded.

## 17\. Visual Styles (the same link, eleven aesthetics)
Design systems are _whose_ rules; visual styles are _which look_. The same semantic link — real `<a href>`, meaningful name, focus ring, security `rel` — can wear any of these skins. **Style is skin; behavior is the skeleton.** None of these change the semantics, keyboard behavior, focus ring, or target size.

*   **Flat:** solid link color, crisp underline, no shadow. Reads instantly; the safe default for body text.
*   **Material:** primary-tint color, underline in body, ripple + trailing "open in new" icon on standalone links.
*   **Glassmorphism:** for button-styled links over vivid backdrops — translucent + `backdrop-filter: blur()`. Guard contrast hard; underlines can vanish on glass.
*   **Liquid Glass (the 2026 trend):** Apple's iOS 26 / macOS Tahoe language — a button-styled link as a refractive translucent pill with a specular rim and moving sheen. Web is an honest approximation; SwiftUI's `Link` inherits native `.glassEffect()`. Guard for contrast _and_ `prefers-reduced-motion`.
*   **Neumorphism:** button-styled link as a soft extruded surface on a same-color field. Pretty, contrast-poor — accent use only, and inline links still need an underline.
*   **Skeuomorphism:** the classic "blue underlined" web link is itself skeuomorphic; button-styled links get bevels and gradient fills.
*   **Neo-Brutalism:** hard offset shadow, thick border, zero radius on button-styled links; inline links get a chunky, high-contrast underline. Loud on purpose.
*   **Claymorphism:** big radius, soft inner light, puffy button-styled links. Friendly, approachable CTAs.
*   **Aurora / Gradient:** animated multi-hue gradient text or CTA on dark. Premium — honor `prefers-reduced-motion` or the sheen becomes a hazard.
*   **Minimal / Swiss:** typography and a hairline underline do all the work; near-zero decoration, sharp corners.
*   **UJG Brand (the house default):** Goldenrod (`#DCA424`) links on deep Eminence (`#5F2C82`) / Night (`#0A0A0A`) surfaces, with a warm-glow underline that thickens on hover and a Goldenrod focus ring. Visited links shift to Sienna (`#7E3209`). Button-styled CTAs lean Liquid Glass over the dark, saturated backdrop where the refraction sings. Keep Flat/Swiss for dense data views; reserve Aurora/Brutalism for campaign moments. Full guidance lives in the [Design Styles (visual languages)](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200551) reference.

**Rule that never changes:** whichever skin you pick, the link stays an `<a href>` with a meaningful name, a visible focus ring, a 44px target, and `rel="noopener noreferrer"` on every new-tab link.
* * *

**Bottom line:** a link is one element with one job — navigate to a resource — and almost every link bug traces back to forgetting that. Use a real `<a href>` for navigation and a `<button>` for actions; write link text that means something out of context; secure and announce every new tab and download; keep the underline and the focus ring. Master those and you've mastered the connective tissue of the entire web. For the other half of this pair — controls that _act_ instead of _navigate_ — see the [Button reference](https://app.clickup.com/8495850/docs/838qa-81211/838qa-200231), and for link-heavy navigation patterns, the Navigation and Breadcrumb docs alongside it.
