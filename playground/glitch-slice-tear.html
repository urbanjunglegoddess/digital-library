What this playground proves

    

      
Crank the step count. Set steps to 6 or 12 and watch the flash meter climb. This is the one glitch variant that can build a genuine seizure hazard, and the step rate is the lever that does it. For more drama, raise amplitude instead — distance is free, frequency is not.

      
The meter is a screen, not a verdict. WCAG 2.3.1 is a luminance and area test over rendered pixels — it depends on the background behind the text and how much of the visual field the headline fills, so no DOM measurement can decide it. What this counts is discrete visual state changes, which is what the step control actually drives. At or below 3/s you are safe whatever the pixels do; above it, keep steps at 2 and get a real assessment if the headline is full-bleed.

      
One copy of the text. There is no aria-hidden duplicate and no content: attr(data-text) pseudo-element — generated content is exposed to assistive tech on several engines, so the classic three-layer glitch gets announced twice.

      
Nothing touches layout. The properties meter reads the running animation's keyframes directly. Only clip-path, transform and text-shadow appear, so the box never moves and CLS is zero.

      
Replay actually restarts. The state swaps between two identically-defined keyframe names. Re-applying the same animation-name does nothing at all — the most common slice-tear bug.

      
Zero JavaScript in production. The JS here drives the controls and the meters. In production this variant is a stylesheet plus animation-timeline: view() — no hook, no observer, no runtime.

      
Reduced motion declares nothing. Tick the switch: no animation is assigned at all, and the scanline leaves the DOM.
